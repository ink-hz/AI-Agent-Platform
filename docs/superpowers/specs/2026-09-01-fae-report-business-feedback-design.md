# FAE 成果报告与业务反哺极简设计

日期：2026-09-01  
状态：产品设计已确认，等待实施计划  
涉及系统：AI-FAE-Agent、AI-Agent-Platform

## 1. 目标

FAE 成果报告必须用最短路径回答四个问题：

1. FAE Agent 被使用了多少；
2. 它形成了什么业务价值；
3. 回答效果如何；
4. 客户问题反哺了哪些业务改进。

现有页面虽然已经按四个一级维度组织，但又在每个维度下增加 `depth`、`complexity`、`products`、`capabilities`、`quality`、`reliability` 等可见分组，造成重复标题、重复说明和指标卡堆叠。本次设计删除这些子维度。

最终页面只有四段内容和一条连续叙事，不再表现为 BI 看板或技术治理目录。

## 2. 已确认的产品原则

### 2.1 只有四个维度

- 使用情况；
- 业务价值；
- 回答效果；
- 业务反哺。

产品、质量、SDK、资料、方案、销售和客户机会只是业务信号的标签或筛选条件，不是页面章节。

### 2.2 每个维度只有三层信息

每段固定包含：

1. 一句结论；
2. 一张主要图表或一组关键数字；
3. 一段证据与解释。

不再为不同指标种类建立子章节，不再给每个指标重复展示一套说明卡。

### 2.3 报告与执行分离

分析报告保存发布时的冻结成果，业务反哺工作台保存最新推进状态。二者通过稳定的 `business_signal_id` 关联。

报告发布后不可原地修改。后续责任部门、行动和结果发生变化时，历史报告仍显示当时快照，并提供“查看最新状态”入口。

### 2.4 不新增复杂脱敏系统

本次不建设新的字段级脱敏引擎、规则中心或多套公开版本。

报告只使用聚合指标和业务已批准展示的内容，不包含原始客户身份、原始会话全文、附件原件或可公开识别的内部 Session ID。具体 Session 和证据继续复用 Platform 现有服务端权限检查。现有小样本门禁继续有效，但页面不把“脱敏”本身设计成产品功能。

## 3. 非目标

- 不增加第五个一级维度；
- 不把报告做成可编辑任务看板；
- 不把现有“反馈与修复”改造成通用业务流程系统；
- 不复制完整生产会话到报告包；
- 不建设组织级工单、审批、通知或 SLA 平台；
- 不引入复杂标签树、评分模型或自动责任人分派；
- 不使用 Mock 数据补齐缺失内容；
- 不修改已经发布的 v1 报告。

## 4. 用户与阅读边界

### 4.1 管理层

读取成果报告、聚合业务信号和发布时状态，不进入原始 Session。

### 4.2 FAE 团队

读取成果报告、业务信号详情、行动和结果摘要，以及已有权限范围内的运营数据。

### 4.3 Platform Owner

读取全部内容，发布报告，归并业务信号，更新责任部门、行动、状态和结果证据，并按现有权限进入原始 Session 与复审证据。

首版不新增临时人员名单。责任部门成员的写权限等统一授权模型具备后再开放。

## 5. 页面设计

### 5.1 成果总览

第一屏只显示：

- 报告标题、周期、数据截止时间和版本；
- 一句核心结论；
- 服务规模、业务信号、推进行动、验证改善四个数字；
- 本期最重要的三条结论。

第一屏不出现同步状态、数据库状态、失败层、Agent ID 或内部枚举。

### 5.2 使用情况

只显示：

- 一句使用结论；
- 一张周度趋势图；
- Session、Turn、多轮会话三个关键数字；
- 一句话说明主要产品和需求方向。

附件、非工作时段、高频产品和需求仍可进入统计口径或图表数据，但不各自占用一个分组。

### 5.3 业务价值

只显示：

- 一句价值结论；
- 已确认价值与潜在机会的对比；
- 一至三个经过业务批准的案例，沿用现有内容与证据访问边界。

潜在机会必须明确标注为未实现价值，不得与已经实现的成果合计。

### 5.4 回答效果

只显示：

- 一句质量结论；
- 独立复审覆盖、完全解决率、首轮解决率、负反馈影响四个数字；
- 一句话说明主要改进空间。

延迟、兜底和多轮收敛作为补充统计口径展示，不建立“质量”或“可靠性”子章节。

### 5.5 业务反哺

只显示：

- 一句业务反哺结论；
- `发现 → 接受 → 行动中 → 已交付 → 已验证改善` 的单条进度图；
- 最重要的五至八个业务信号；
- “查看全部业务信号”入口。

每个重点信号只显示：标题、简短客户信号、业务判断、责任部门、当前状态、当前行动或结果。详细证据进入治理详情页。

### 5.6 业务反哺工作台

FAE 工作台增加一个“业务反哺”入口，与“反馈与修复”并列：

```text
概览 / Sessions / 业务反哺 / 反馈与修复 / 分析报告
```

页面只包含：

- 四个概览数字；
- 搜索和少量筛选；
- 业务信号列表；
- 业务信号详情。

业务类别、责任部门、状态、产品和周期只作为筛选条件，不形成多级导航。

## 6. 报告合同 v2

### 6.1 兼容策略

现有 `fae.analysis-report` v1 保持可读、不可修改。新增 v2 合同，不在 v1 字段上做兼容性补丁。Platform API 能同时读取 v1 与 v2，页面对 v1 使用旧数据适配器，对 v2 使用新极简展示。

报告仓库继续保存完整、规范化的 JSON payload 和 SHA-256，不复制一套报告存储。

### 6.2 最小新增结构

v2 保留报告元数据、来源、四维指标、摘要和批准案例，新增 `business_signals`。每条信号包含：

- `business_signal_id`：跨报告稳定 UUID；
- `category`：单值业务标签；
- `title`；
- `customer_need`；
- `business_judgment`；
- `impact_scope`；
- `confidence`；
- `occurrence_count` 与统计口径；
- `affected_products`；
- `affected_scenarios`；
- `evidence_refs`；
- `owner_department_snapshot`；
- `status_snapshot`；
- `action_summary_snapshot`；
- `result_snapshot`；
- `success_metric_ids`。

不新增可见的子维度字段。指标仍直接属于四个一级维度。

### 6.3 稳定信号 ID

分析流程先生成候选信号。发布前，Owner 将候选信号匹配到已有业务信号，或创建新 UUID。最终发布包只能包含已解析的稳定 `business_signal_id`，不得使用标题哈希或每期随机 ID。

同一业务信号可以出现在多个报告版本中，从而形成跨周期趋势。

## 7. 最小业务治理模型

治理模型只保留完成闭环必需的三类记录：

1. `business_signals`：稳定身份、当前标题、类别、责任部门和状态；
2. `business_signal_actions`：一个信号下的行动、负责人角色、状态和成功指标；
3. `business_signal_events`：状态、责任、行动和结果变化的追加式审计事件。

证据继续引用既有 Session、Turn、反馈、Issue、报告和发布制品，不复制原始内容，不新增第四套证据库。

业务信号状态：

```text
待研判 → 持续观察 → 已接受 → 已采取行动 → 已验证改善
                  └→ 暂缓
                  └→ 不采纳
```

行动状态：

```text
建议行动 → 已认领 → 计划中 → 进行中 → 待验证 → 已完成
                               └→ 受阻
                               └→ 已取消
```

“行动已完成”不自动等于“业务已改善”。进入“已验证改善”必须存在结果证据和成功指标对比。

## 8. 数据流

```text
FAE 生产数据
    ↓
分析与独立复审
    ↓
候选业务信号
    ↓ Owner 归并稳定 ID
业务治理记录 ──────────────┐
    ↓ 当前状态              │
冻结报告 v2 ← 发布时快照 ───┘
    ↓
管理层成果页
```

持续看板仍由每日生产同步驱动；冻结报告仍由经过复审的分析包驱动。两者不得混用时间口径。

## 9. 服务端接口

现有报告读取接口保持不变，只扩展为可返回 v1 或 v2 合同。

业务反哺首版提供最小接口：

- 列出业务信号；
- 读取业务信号详情；
- Owner 创建或归并信号；
- Owner 更新责任部门与状态；
- Owner 新增或更新行动；
- Owner 追加结果证据。

写接口必须使用现有认证、CSRF、审计和乐观锁约束。不得用一个通用 JSON Patch 端点绕过状态机。

## 10. 失败与空数据

- v2 报告合同校验失败时，整份报告拒绝发布；
- 某条业务信号没有稳定 ID 时，整份报告拒绝发布；
- 没有业务信号时显示“本期未发布业务反哺信号”，不生成示例；
- 没有行动或结果时显示真实状态，不自动补写进展；
- 最新治理状态不可用时，报告仍显示冻结快照并明确截止时间；
- v1 报告继续正常读取，不强制迁移为 v2。

## 11. 实施阶段

### 阶段 1：极简化现有页面

删除可见子维度、重复说明和指标卡堆叠。保持 v1 数据可读，用现有真实报告验证四段式页面。

### 阶段 2：报告 v2 与真实数据包

新增 v2 合同和解析，扩充现有 198 项分析结果中真正需要展示的指标，生成第一份含业务信号的真实报告。不得硬编码 692、1492 等当前数字。

### 阶段 3：业务反哺工作台

增加最小治理表、服务端权限、列表和详情页，将报告信号链接到最新治理状态。

### 阶段 4：真实发布与验收

导入新报告版本，验证现有角色与证据访问边界、历史版本不可变、数据截止提示、业务信号关联、移动端和回滚。

## 12. 验收标准

- 页面只有四个一级维度，没有可见子维度；
- 每个维度最多一个主图和四个关键数字；
- 第一屏能直接说明规模、价值、业务信号和已验证改善；
- 已实现价值与潜在价值清楚区分；
- 业务信号能从报告快照进入最新治理详情；
- 历史报告不会因治理状态更新而改变；
- v1 报告仍可读取；
- 不出现 Mock、硬编码生产数字或原始客户身份；
- API 服务端执行权限控制；
- 真实报告导入、页面、移动端、权限和回滚验收全部通过。
