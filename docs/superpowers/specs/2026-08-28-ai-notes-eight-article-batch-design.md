## 已确认的发布方式

- 使用一个隔离分支完成整个批次。
- 内部严格一次只处理一篇，按固定顺序完成精读、重写、图示、测试和独立提交。
- 八篇写作期间均为 `draft: true`，不提前进入生产目录。
- 单篇完成表示内容已达到发布质量，不表示可以单独上线。
- 最后一个发布提交统一把八篇改为 `draft: false`，使用相同的实际首次上线日期。
- 任一文章未通过机器门禁时，整批继续保持草稿；不删除难写文章来缩小用户确认的八篇范围。
- 八篇一起合并、推送和部署，生产文章总数从 6 增加到 14。
- 用户明确由自己负责上线后的浏览器视觉验收。本批次不把代理侧桌面/手机浏览器检查作为部署阻塞项，但仍保留 Mermaid 真实渲染、SVG 清洗、白底、尺寸相关组件测试和生产资产核验。

## 八篇内容边界

### 1. Agent 身份与最小权限

回答 Agent 代表谁、权限从哪里来、一次行动如何被允许，以及事后如何证明。正文覆盖用户委托、工作负载身份、Token Exchange、能力与资源授权、动态风险、审批绑定、凭证隔离和审计证据。

不展开传统登录页面、SSO 产品对比、云厂商 IAM 功能清单，也不重复企业级 Agent 全景架构。候选图包括身份与委托链、行动授权决策和高风险审批闭环。

### 2. LLM 推理服务工程

回答模型请求如何在有限 GPU 上获得可预测的吞吐、延迟和成本。正文覆盖 Prefill/Decode、连续批处理、KV Cache、量化、投机解码、模型路由、容量规划、排队和成本权衡。

不重复请求入口、RAG、工具和输出验证，不把某个推理框架的当前参数写成普遍原理。候选图包括推理数据路径、批处理与 KV 生命周期、路由和容量决策。

### 3. AI × 云原生运行时

回答 AI 工作负载与普通 Web 服务在资源、制品、弹性和恢复方面有什么不同。正文覆盖 CPU/GPU 资源特征、调度与排队、节点和模型缓存、镜像与模型制品、灰度发布、隔离、弹性、检查点和故障恢复。

不迁移通用 Kubernetes 百科，不展开模型推理算法和应用层编排。候选图包括 AI 运行时分层、模型发布链和故障恢复流程。

### 4. LLM / Agent 可观测性

回答如何从一次结果追溯到请求、上下文、模型、检索、工具、验证和反馈。正文覆盖模型与 Prompt 版本、Trace、Token、延迟、成本、工具调用、RAG 证据、答案质量、评估集、人工反馈和改进闭环。

日志、指标和 Trace 基础知识只保留服务于 AI 质量链的部分，不重复 RAG 算法或 Agent 状态机。候选图包括端到端证据链、分层信号模型和反馈到评估的闭环。

### 5. Hermes 与 OpenClaw 开源 Agent 运行时

回答两个开源项目怎样组织 Agent 循环、上下文、Skills、工具、记忆、沙箱和恢复，并区分可验证的公开事实与合理的工程推断。文章以共同问题为主线，不做功能数量竞赛。

不复述框架选型结论，不把仓库结构猜测成内部运行事实。候选图包括通用运行时循环、能力边界和两个项目的责任映射。

### 6. MetaBot 远程控制总线

回答 IM、Web 或其他渠道如何可靠地控制远端 Agent。正文覆盖多渠道适配、消息归一化、会话与身份绑定、持久执行器、Agent 总线、命令生命周期、断线恢复、幂等、审计和远程控制风险。

旧稿中的代码规模、旧组织部署和无法复核的实现细节全部删除。候选图包括渠道到 Agent 的控制平面、持久命令状态和断线恢复流程。

### 7. 主流 Agent 框架选型

回答团队应当选择开发者工具、编排库、Agent 运行时还是端到端平台。评价维度包括控制流、状态持久化、工具和权限、可恢复性、评估、部署边界、可观测性和团队所有权。

文章引用前面具体运行时作为样本，不再逐篇复制其架构；不承诺永久有效的排行榜。候选图包括产品形态分类、生产能力矩阵和选型决策树。

### 8. 意图驱动的 AI 业务平台

回答业务平台如何从固定页面旅程演进为“表达意图、受控规划、能力执行、验证反馈”。正文覆盖意图入口、能力目录、确定性编排与 Agent 的边界、信任分级、人在环、完成证据和渐进式演进。

删除“消灭 UI”、完全自治和自我进化等无法负责的绝对化表达，不重复企业级 Agent 全景。候选图包括平台分层、意图执行链、信任等级和渐进演进路线。

## 写作与事实核验流程

每篇依次执行：

1. 计算主要源稿 SHA-256 和行数，从第一行读到最后一行。
2. 在研究台账记录章节级保留、删除、改写和去重决定。
3. 为会变化或影响工程决策的主张查找迁移当天的一手资料；技术检索只使用官方文档、规范、论文和官方仓库。
4. 先写文章问题、边界和目录，再从空白正文重新组织，不在旧稿上做全局替换。
5. 使用 `author: 苍渊`、固定座右铭和 `draft: true` 写入目标目录；正文从 H2 开始。
6. 只在图能显著压缩三项以上关系时添加 Mermaid。每张图提供唯一 `accTitle`、`accDescr`、语义 `classDef` 和白色大分组。
7. 图前说明要观察什么，图后解释关键路径、权衡和失败分支。
8. 与既有六篇和本批次已完成草稿逐节复读，删除重复段落和互相矛盾的结论。
9. 增加文章内容合同和真实 Mermaid 渲染测试，完成机器审查后提交该篇草稿。
10. 开始下一篇，直到八篇草稿全部完成。

产品能力、版本、标准状态和项目架构若无法从当前一手资料确认，就删除、降级为有边界的工程推断，或明确标注为作者建议。禁止沿用旧稿中的未来预测、市场规模、代码规模、生产效果和无法复核经历。

## 草稿和测试架构

### 单篇草稿合同

- 文件名、slug、标题、分类、作者、座右铭、标签和草稿状态；

- Mermaid 数量不固定，但存在的图必须具有唯一元数据、语义样式和白色大分组；

测试不会把半成品草稿暴露给运行时，也不会放宽 `draft: false` 的正式门禁。

## 统一发布与失败处理

八篇草稿完成并通过定向门禁后，在一个发布提交中同时执行：

1. 把八篇 `draft` 从 `true` 改为 `false`；
2. 设置共同的实际 `publishedAt` 和 `updatedAt`；
3. 移除只为草稿期存在的显式 Mermaid 文件清单；
4. 由正式文章自动发现测试覆盖全部新图；
5. 运行内容校验、后端全量、前端全量和生产构建；
6. 扫描旧品牌、旧组织、危险协议、H1、原生 HTML 和灰色大分组；

若任一机器门禁失败，恢复或保持八篇草稿状态，修复后重新运行整批门禁。部署失败时保留已经推送的精确提交，按部署脚本的锁、回滚和健康状态排查，不绕过受控发布流程。
