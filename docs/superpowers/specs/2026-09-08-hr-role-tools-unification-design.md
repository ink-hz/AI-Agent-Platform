## 1. 产品应该怎样工作

**用户始终在 Hannah 的主对话中开展招聘工作。岗位是当前工作上下文；任务是用户要达成的目标；方法和工具由 Hannah 根据目标选择。**

用户不必先进入岗位页，不必选择内部任务类型，不必管理 JD/JR 模块、草稿编号或上下文版本。

典型过程：

1. 用户在输入框旁搜索选择一个岗位，或直接说岗位名称、J 编号、招聘需求。
2. Hannah 确认当前岗位身份，查询官网事实及已经共同确认的招聘标准。
3. 用户说“这个岗位要偏嵌入式，帮我看看哪些背景更合适”，可同时上传材料。
4. Hannah 使用已有招聘方法，按需查资料，给出证据、判断和可执行结果。
5. 用户继续说“先看第二类背景，给我搜寻方向和面试重点”，就在当前对话继续。
6. 用户明确表示已经与用人经理共同确认后，Hannah 保存明确确认的岗位级标准，后续自动复用。

### 主界面只保留这些元素

| 元素 | 用途 |
|---|---|
| 左侧对话记录 | 返回历史工作，搜索已有讨论 |
| 主对话区 | 用户要求、Hannah 回答、必要的工具进度与结果 |
| 输入框 | 本次真实要求及附件，统一发送 |
| 当前岗位标记 | 显示岗位、查询/切换入口；允许通用讨论 |
| 可展开的“本次参考” | 查看采用的岗位事实、已确认标准和材料来源 |
| 按需出现的结果卡片 | 展示具体分析、文件或已确认标准，允许继续修改 |

“岗位资料”作为可展开的信息面板保留，不再是开始工作的前置页面。候选人和成果的检索入口可以放在面板中，不能强迫用户先录入完整档案才能分析材料。

原来的五个岗位任务按钮及后来的“招聘协作”预填菜单均已删除。“查看 JD / JR”直接打开已有资料。后续岗位或候选人成果旁的“继续分析 / 准备面试”应把确切对象、结果引用和可编辑要求带回主对话，由用户明确发送后执行；不能只预填一句通用短语冒充任务功能。后台采用最终发送正文，不另有隐藏任务正文。撤回先前讨论中“输入齐全就直接启动”的建议，不恢复已删除菜单。

## 2. 一个主对话与多个岗位的确切含义

目标支持同一聊天记录按轮选择岗位。这是新增设计：现有 Web 会话绑定和 CLI `role-calibration` 都有单会话单岗位约束，不能声称现成可用。

### 每一轮记录独立的工作范围

```text
Conversation：持续的对话记录
  Turn 1：通用招聘讨论
  Turn 2：岗位 A + 本次材料 + 真实要求
  Turn 3：岗位 A + 用户修正
  Turn 4：岗位 B + 本次材料 + 新的要求
```

复用现有 `platform_hr.position_task_records` 作为有岗位轮次的上下文载体。它已经有 `owner_internal_user_id / position_id / conversation_id / turn_id`，并约束同一 owner、conversation、turn 只有一行，不再新建一套“HR 任务主表”。扩展其角色包、方法目录版本和工具读取日志引用，保留已有唯一性和归属外键。

新轮次统一验证“用户有权访问会话、岗位及本轮材料，且请求与该 Turn/Attempt 对应”。不能只替换最外层 `verified_hr_position`。以下逐处标注改判定、删除或保留；位置基于当前代码，行号仅供定位。

一般对话没有岗位时不伪造一个岗位 ID，继续使用既有 Turn/Attempt 及其输入、事件记录。有岗位时关联扩展后的 `position_task_records`。动态读取记录追加到现有执行事件/审计能力，并引用本轮上下文，不回写已冻结的 `prompt_context/canonical_sha256` 来伪装没有变化。

切换岗位只影响后续轮次，不修改已经发出的轮次，也不重写历史归属。

选择发生在发送前；已经运行的轮次仍显示其原岗位。界面可以准备下一轮的岗位，执行中范围不能随选择器变化。

### 不把所有历史自动喂给新岗位

同一聊天记录不意味着所有岗位、所有候选人的内容都能交叉使用。

- 当前岗位的相关历史可作为上下文。
- 通用招聘偏好只有在适用且允许的情况下复用。
- 其他岗位的事实、未确认建议和候选人材料不自动进入本轮。
- 用户明确要求跨岗位比较时，建立本轮显式多岗位只读范围；写入结论时必须分别指定岗位。

第一版多岗位能力以明确切换为主。跨岗位比较的专门交互不作为主对话收敛的前置条件，不能为了赶进度直接传整段混合历史。

旧会话原有岗位绑定保留用于历史解释。新轮次使用版本化的每轮范围记录；不能通过覆盖旧 `position_conversations` 行来模拟切换。

## 3. 专业能力从哪里来

### 唯一角色来源

以 `Orbbec-Agent-Team/bots/hr/CLAUDE.md` 中 Hannah 的角色、方法、证据纪律和自然语言协作原则为共同来源。Web 与 CLI/飞书使用同一套专业定义，渠道层只处理身份、附件和交付形式。

方法内容的目录与身份服从方法库设计的 [§2.1 一处维护、两处部署](2026-09-08-hr-scenario-methodology-library-design.md#21-一处维护两处部署)及 [§2.2 统一资源身份](2026-09-08-hr-scenario-methodology-library-design.md#22-统一资源身份)。当前七份正文直接位于 Team 的 `bots/hr/knowledge/recruiting/`，不再按 `scenarios/`、`methodologies/`、`models/` 拆目录。平台消费同一提交的发布内容，不维护第二份可编辑正文。方法库旧文档的“尚未部署”描述由下述运行核查覆盖。

2026-09-09 只读核查：运行中的 `metabot-hr` 为 `82ecbb93b46fed4ca1ec0c0890786fe090fc0b88`，`METABOT_HR_ROLE_PACKAGE_ROOT` 指向 `/Users/agentops/AgentRuntime/instances/hr-bot/hr-web-v6/roles`，commit 为 `36b932b01f11e893dcca16ac8162b392b84fbb8c`。该提交目录的 `role-package.json` 声明 cwd 为 `bots/hr`，51 个文件清单包含七份招聘资源；七份实际文件的 SHA-256 均与清单一致。MetaBot `src/runtime/hr-tool-bridge.ts:verifyHrRolePackage` 校验包后返回该目录作为执行 cwd。因此旧工作目录仅有 `.gitkeep` 不能推导 Web Agent 无法读取知识，也不应据此重复部署。开发机 `.superpowers/` 两棵试验发布树不是当前 Web 运行来源；此结论不扩展为独立飞书 Bot 已使用同一目录。文件就绪不等于某次模型已读取或业务质量已通过。

五类专业职责已经在 `CLAUDE.md` 的场景小节中：岗位分析（JD 与人才画像、岗位搜索与校准）、搜寻（专业社区人才搜寻、人才吸引与沟通建议）、候选人评估（简历与公开证据分析）、面试设计（候选人专属面试方案）、复盘（批次反馈诊断与面试官一致性分析）。保持原文组织，只补成果类型与交付声明；“职责、方法、工具”的内容分类不意味着建立三套加载机制。

清单生成链路已经实现：Team `scripts/build_hr_role_package.mjs:buildRolePackage` 使用 `git ls-tree / cat-file` 读取指定 commit 的 Git 对象，将允许根目录内的文件及符号链接依赖物化为只读文件，对每份实际字节计算 SHA-256，生成 `<output>/<commit>/role-package.json`，并返回清单原始字节的 `manifestSha256`。它是发布准备阶段生成的产物，不要求源 worktree 自带清单，也不读取工作区未提交的修改。Platform `backend/app/hr/role_package.py:HrRolePackages.select` 校验文件并冻结清单 hash；MetaBot `src/runtime/hr-tool-bridge.ts:verifyHrRolePackage` 比较命令中的清单 hash、逐文件 hash 与角色身份，随后使用包内 cwd。复核应比较配置所指包中的实际文件与清单，再比较清单 hash 与命令／发布记录；同包自洽不单独证明来源可信。当前发布记录中的清单 hash 为 `92786276c247fe4ee4c1224cfb3232455a0c126cf51b9e54138775c4a46462f7`，本轮只核对生成代码，不重新构包或部署。

场景未匹配时继续用 Hannah 基础角色处理情报、公司研究或通用咨询，不要求用户先归类。完整 `CLAUDE.md` 仍在角色包内；“不套用某场景流程”不意味着运行时能卸载该文件的小节。

已有 skill 继续承载能力边界，方法正文通过引用复用；原生 Read/Glob/Grep 按需读取固定版本文件。方法读取不需要单独造远程工具；平台给浏览器展示内容的只读 API 与模型的原生文件读取不是同一能力。

每个 Attempt 钉住 Team 的不可变 checkout commit 和完整角色包清单：`bots/hr/CLAUDE.md`、递归引用的 shared 规则、相关 skill、目录索引及方法文件哈希。MetaBot 以该版本的 `bots/hr` 作为 cwd，执行前核对清单，禁止使用随部署原地变化的目录。复用部署脚本现有 shared 文件 shasum 校验方式，并扩展到整个角色包。

同一轮恢复/重试引用同一清单；运行中的 Attempt 持有该 checkout，不能被普通发布清理。变更方法后产生新发布包，新轮次才采用。方法使用记录区分已选择、实际读取和结果体现，文件可见或进入清单不等于模型已经使用。

### 任务目标和方法的关系

| 用户目标 | 应使用的能力 |
|---|---|
| 查看或解释当前岗位 | 查询并核验官网事实，解释职责与要求 |
| 调整招聘方向 | 岗位校准方法，分析业务结果、必须/加分/可培养能力 |
| 寻找人才 | 人才画像、对标公司与公开专业渠道搜寻方法 |

方法选择服务用户要求，不能让用户背出内部 `task_kind`。任务可以包含多个步骤，由 Hannah 在同一工作范围内组织工具调用；不为每个建议按钮另建一套执行状态机。

## 4. 上下文按需读取，事实来源保持唯一

### 官网岗位事实

官网 JD 已经包含职责和任职要求。默认动作应是“查看、解释、校准或提出改写建议”，不把已有岗位当作缺少 JD 的空白对象。

`hr-jd-sync` 的 registry 是官网岗位事实的唯一权威维护者；Platform 的官网视图是它的下游投影。现有 importer 读取 registry 状态中的版本和内容哈希，不是读取 Agent 使用的 CLI 公开输出。

当前 `verify-job <query> --json` 没有比较已有快照的入参；其公开白名单也不返回 registry version/contentHash。不能将便宜的快照校验复用写成现有能力。

目标先扩展 `hr-jd-sync` 的公开查询契约：合法响应新增 `registryVersion`、`jobContentHash`、`lastSuccessfulSyncAt` 和校验结果，由同一次可信读取生成；`jobContentHash` 采用 registry 与 importer 已使用的规范化算法，不让 Agent 自己猜测字段后计算哈希。Platform 与 Agent 因而可以比较同一 J 编号的同一内容版本。扩展白名单与 schema 只暴露官网事实凭据，不开放任意状态文件读取。

首版直接执行增强后的 `verify-job` 并比较凭据，不建设另一套“只验证哈希”的快捷服务。该命令仍可能触发全量同步，调用耗时和失败语义需要如实保留，不能包装为廉价本地比对。真正的按凭据快速校验若以后需要，再单独设计。

使用前校验采用现有明确阈值 **24 小时**：超过 24 小时或岗位疑似下线时尝试刷新；校验失败可沿用最后有效版本，但明确降级，不能标记为即时校验成功。36 小时是 registry 健康降级阈值，90 天是岗位来源陈旧提示，均不能替代 24 小时使用前校验。失败回退不因未到 36 小时而假称当前可信。

本轮记录实际采用的版本、哈希和校验状态。`jd-registry` 指令同步认可此统一流程，不重复要求再查一份互不校验的事实。查询失败时用户可继续基于显式提供的材料讨论，但不得冒充已核验官网事实。

只有用户要求改写时，才产出“内部改写建议”，列明基于哪个官网版本、改了什么、为什么改。它不写回或冒充官网事实。没有官网对应项的内部招聘需求可以正常讨论，但明确其来源是用户材料。

### 工具边界

以下是目标能力名称，不表示已经注册或实现了这些工具：

| 能力 | 优先复用方式 | 返回内容或操作边界 |
|---|---|---|
| 查询/核验 JD | 复用 `jd-registry` 的校验服务，通过安全 CLI 或业务桥接访问 | 岗位身份、事实、版本、时效与降级信息 |
| 读取岗位标准 | 统一岗位校准服务 | 当前明确确认的岗位级标准、来源和版本 |
| 读取任务材料 | 已有附件授权与本地已验证文件；云端材料通过授权读取接口 | 仅本轮允许的材料及来源；不直接读取云端数据库 |
| 查询专业证据 | 已有公开信息查询能力 | 来源、证据、时间、失败范围 |
| 提交分析结果 | 明确的结构化结果提交接口 | 本次分析或交付结果，不自动成为长期知识 |
| 保存共同确认 | 统一岗位校准写入接口 | 仅保存用户明确共同确认的岗位级变更 |
| 交付文件 | 复用已有输出授权和文件登记 | 可追溯、可下载的本次交付文件 |

方法文件使用原生文件工具；云端数据与业务写入使用有身份和作用域的接口。给本地进程一个 Read/Bash 工具，不等于它自动获得所有 Platform 用户数据访问权。

工具请求的 owner、conversation、turn、position 与授权来自服务端签发范围，不能只相信模型传来的 UUID。动态读取也必须校验材料归属、保留期和当前授权。

### 明确新增的接口与跨仓协议

现有 relay 面主要是执行生命周期、附件下载与产物上传；没有供 Agent 调用的授权岗位查询或 schema 校验的业务结果提交接口。`write_output` 处理文件字节，不能冒充结构化业务提交。

v5 命令将 `contextMode` 钉为 `frozen_prompt`，回调只接收规定的文本、文件意图和恢复字段，Pydantic/schema 都拒绝未知字段。**不能直接在 v5 增加枚举值、任意 payload 或工具权限字段后继续称为 v5。**

本次选择显式新版本 `core_chat_collaboration_v6`，由 Platform、metabot-dev、Orbbec-Agent-Team 同一次 HR 发布协调切换。冻结初始意图与工具能力描述，按需数据通过新的受授权调用面读取；冻结仍保护输入一致性。严格说，额外查询接口不天然要求修改 contextMode，但本设计同时新增角色包引用、工具能力与结果引用，因此明确升级版本，避免暗改旧契约。

v6 提交面与生命周期面分开：目标新增按 turn/attempt 授权的业务查询、结果提交和确认接口；结果提交先校验 schema/归属/幂等，再返回持久结果引用。终态回调仅引用这些已登记结果，不能靠塞入一段任意 JSON 绕过业务校验。后端拒绝不存在、未提交或不属于本轮的结果引用。

| 仓库 | 必须交付的工作 |
|---|---|
| AI-Agent-Platform | v6 schema/签名/能力授权；新查询与结果提交接口；扩展现有按轮上下文；结果与确认持久化；删除旧 Web 任务与岗位包消费者；主对话统一提交 |
| metabot-dev | v6 接收、原生工具桥接、能力凭据绑定；固定角色 checkout；读取/结果记录关联；终态引用；沿用现有持久执行恢复，不新造执行器 |
| Orbbec-Agent-Team | JD CLI 版本/哈希公开契约；角色与 skill 指令统一；唯一方法发布包；校准 CLI 改用认证业务服务；部署清单与版本一致性 |

这些接口名称与协议版本是目标设计，尚未实现。三仓代码与部署必须作为一个可核对发布组合，不能只上线前端，再把工具未连通留给用户发现。

### 两套已确认标准如何收敛

现有 `role-calibration` 状态与 Platform 的内部岗位理解不能长期双写。

目标是统一的岗位校准业务服务；Web 和 CLI 都调用它，由 Platform 持久业务层承载授权、确认记录及版本。CLI 是新服务的另一种调用形式，不再保持独立本地写入路径。

现有本地校准文件以 J 编号作为键，确认记录只有 `shared_consensus/sourceType`，没有 owner、用户或确认人身份。Platform 的岗位和版本则要求 owner、position、created_by/confirmed_by；同一 J 编号可对应多个 owner 下的岗位。**仅靠 `official_job_id` 无法推导所属用户或补造确认人。**

**平台已确认记录继续作为新服务的数据基础，不以空库开始。** `position_context_versions` 已有 owner、position、created_by，以及由状态约束保证的 confirmed_by/confirmed_at。新校准服务优先原位复用这套持久记录和当前版本指针，替换服务入口即可，不为删除旧按钮搬到另一张空表。

- 当前标准按同一 owner/position 读取 `positions.current_context_version_id` 指向的 confirmed 版本，保留原 ID、模块内容、确认人/时间和来源证据，后续对话可直接复用。旧 JD/JR 内容标为已确认的内部标准，不冒充官网事实。
- 当前 confirmed 版本的 `modules` 包含沿版本链继承的已确认内容；`confirmed_module_names` 只表示该次确认的增量，不能仅迁移这个列表而丢掉此前标准。保留 base/source 版本及原确认链，不重新标记成“本次用户确认”。
- 历史 confirmed/superseded 记录保留可追溯读取，未确认 draft 不进入当前标准；superseded 也可能是已处理的来源草稿，不能把所有 superseded 都提升为当前标准。当前指针与 owner/position/state 不一致时显式报告数据问题，不返回空标准掩盖异常。
- 若实施确需更改存储形状，必须完整映射并核对原记录 ID、内容与确认元数据；新读取验证可见后才切换。仅保留数据库行、在新产品里永远查不到，不算保留。

**CLI 无归属旧卡片才采用“不自动导入”。** 本地文件停止写入并封存，排除自动读取，不把人工归属整理作为上线前置。以后用户明确要保留某条卡片时，核对归属与原文并通过新的真实确认保存；不能把导入者冒充历史确认人。此决定不能扩展为丢弃平台已有确认成果。

CLI/飞书接入新服务必须先解析认证渠道用户到 Platform 身份，不能使用 Bot 服务账号替所有用户建立确认记录。身份缺失时可以分析，但不保存岗位标准；这是需要补建的身份与写入链路，不是复制文件。

官网事实、已确认招聘标准、分析交付物仍是不同对象。统一服务不等于把它们合并成一份会被 AI 随意覆盖的 JD。

## 5. 快照、读取、重试如何同时成立

保留现有持久 Turn/Attempt、命令哈希、租约、幂等和输出授权。它们是执行可靠性基础，不因改成按需工具读取而撤掉。

初始命令记录真实用户要求、工作范围、角色/方法版本，以及允许的工具能力。工具实际读取的事实版本、校准版本、材料摘要和重要证据逐次记录在本轮执行记录中。

规则是：

1. 已受理的命令不原地改写。
2. 读取同一逻辑输入时复用该轮已记录版本，或明确记录新的核验步骤及前后版本关系。
3. 必须重新核验的来源可以查询；结果变化需要成为可见证据，不静默替换本轮已经使用的事实。
4. 同一写操作重试复用幂等键及规范化内容；网络断开不代表应再写一次。
5. 权限撤销、材料过期或删除后，不能以“恢复旧快照”为由重新取得已无权读取的数据。
6. 重试一致性指范围、输入引用及写入效果可追溯，不承诺模型逐字生成相同回答。

新版本继续保护不可变初始命令，并按已记录的工具读取恢复。HR 的 v5 在切换前停止接入，其冻结命令不得改写成 v6；不在新版本内长期运行旧任务恢复适配器。复用 Turn/Attempt 等底座与删除废弃业务协议是两件事。

## 6. 回答、结果与确认只有一套业务约定

### 可读回答

Hannah 正常回答，说明结论、证据和下一步。不得把绝大多数用户任务提示词用于教授 base64 输出格式。

### 结构化结果

有业务结果需要落地时，通过结构化提交工具/接口发送，由服务器按 schema 校验，绑定真实 turn 和岗位。结构化数据与可读回答分离，不从 Markdown 注释正则提取新协议结果。

工具返回具体结果引用。对话卡片直接打开这一结果；“查看结果”不能无差别跳去全部文件列表。分析文本、内部建议、候选人分析与文件可以有不同 schema，但同一结果只有一个负责处理它的业务路径。

一次轮次可以产生多个明确结果，每个结果有独立、幂等的操作 ID；不能把“只留一套契约”误解为每次只能产出一个文件或一段分析。

### 场景与交付成果类型（2026-09-09 修订）

**当前已经有类型和提交校验，缺的是业务成果细分。** Platform `backend/app/execution_relay/contracts_v6.py` 与 `contracts/hr-execution/v6/business-tools.schema.json` 已定义三类结果；`hr/tool_service.py` 校验本轮读取引用、候选人范围和标准版本，登记持久结果。不能把这些能力写成全部待建。

| 已实现类型 | 当前 schema 关键字段 | 归属与限制 | 能否确认成岗位标准 |
|---|---|---|---|
| `hr.analysis.v1` | title、markdown、sourceRefs、methodSteps | owner / conversation / turn；岗位来自本轮，可为空；没有结果自身的候选人归属字段 | 否 |
| `hr.standard-proposal.v1` | title、baseContextVersionId、changes（changeId/module/markdown）、sourceRefs | 必须有本轮岗位；修改模块有白名单 | 只有它可以，经明确条目确认后形成标准 |
| `hr.candidate-analysis.v1` | contextVersionId、positionCandidateIds、逐维 evidence、markdown、来源与方法记录 | 岗位＋已授权候选人；目前必须引用已有真实确认过的岗位标准版本 | 否 |

`hr/calibration_service.py` 已按 `hr.standard-proposal.v1` 筛选来源，并核对真实用户消息、已展示版本、选中条目和并发版本。因此候选人分析结果不能直接通过确认接口变成标准。**这不是正文内容防泄漏证明**：标准变更仍含自由 markdown，当前 schema 不能保证模型不把个人评价装进标准建议正文。

下一步按以下成果结构补齐交付。表中的“新增”均未实现，不能现在提交给生产接口；沿用同一个提交工具、操作幂等键和结果存储，不新增任务执行器。

| 场景／交付成果 | 类型与最小结构 | 归属对象 | 能否成为标准 |
|---|---|---|---|
| JD / JR 修订、人才画像、通用搜索条件、通用面试标准 | 复用 `hr.standard-proposal.v1`；明确基准及按模块分开的变更条目，正文包含改动理由和待验证项 | 岗位 | 用户明确共同确认选中条目后可以；不覆盖官网事实 |
| 人才来源研究、公司地图 | 暂复用 `hr.analysis.v1`；只保存组织／人才池层面的分析，不保存具名候选人卡片或逐人评价 | 岗位；通用咨询可仅归对话 | 报告本身不可以；另提炼无个人信息的岗位建议后确认 |
| 招聘复盘报告 | 暂复用 `hr.analysis.v1`；提交前去标识化，只保留本批共性观察、证据缺口、标准分歧、下一批动作与待统一问题 | 岗位；不含逐人内容 | 报告本身不可以；另提炼岗位建议后确认 |
| 候选人证据分析／需保留逐人证据的复盘 | 现有 `hr.candidate-analysis.v1` 保留历史读取；新提交采用待实现的 `hr.candidate-analysis.v2`，以必填基准引用替代固定 contextVersionId，保留候选人及逐维证据约束 | 岗位＋候选人 | 永不直接确认 |
| 候选人专属面试方案 | 新增 `hr.candidate-interview-plan.v1`：候选人、基准引用、面试目标、能力维度、问题 ID、项目追问、验证目的、有说服力的证据、普通回答、风险信号、技术核验点、记录模板 | 岗位＋单个候选人 | 永不直接确认 |
| 面试记录整理 | 新增 `hr.candidate-interview-record.v1`：候选人、面试方案引用（未使用方案时显式为空）、问题 ID、记录材料引用、回答证据、判断、未知项及后续核验 | 岗位＋单个候选人 | 永不直接确认；缺少记录材料不能生成已发生的面试事实 |
| 候选人沟通草稿 | 新增 `hr.candidate-outreach-draft.v1`：候选人、事实依据、沟通目的、草稿、待核实承诺 | 岗位＋单个候选人 | 永不直接确认；保存不代表已发送 |

新增类型均保留 title、sourceRefs、确切归属和内容哈希；引用文件仍通过现有附件/产物授权。基准引用必须区分“官网版本”“已确认岗位标准版本”“用户提供材料”，只引用实际采用且可授权读取的对象。现有候选人分析强制 `contextVersionId` 的限制需一并修订：没有已确认标准也应允许基于 JD / 用户材料分析，不能伪造确认版本，也不能把候选人结果降为失去归属的通用报告。此变更需要显式版本化 schema，不能暗改原 schema 必填语义。

具体约定：`hr.candidate-analysis.v2` 及候选人面试方案中的 `baselineRefs` 是必填非空数组（至少一项）；每项以 `kind` 判别的严格 `oneOf` 接受以下三种形状，拒绝多分支混合、未知字段、空引用与模型自报的未登记版本：

| kind | 必填身份与版本 | 服务端核验 |
|---|---|---|
| `confirmed_standard` | contextVersionId、readId、contentSha256 | 本轮读取收据；同 owner / 岗位且确实曾确认的版本 |
| `official_position` | positionId、versionRef、readId、contentSha256 | 本轮官网读取收据的确切版本及岗位；保留降级状态，不假称即时核验成功 |
| `user_material` | attachmentId、readId、contentSha256 | 本轮授权材料收据及文件版本；角色说明其为用户提供基准，不冒充官网或确认标准 |

可以组合官网与内部标准，但每项都必须真实存在。`user_material` 首版指已授权附件；只有对话口述而无可登记的基准时，仍可对话分析，不能伪造附件收据或提交为空的结构化候选人成果。将口述需求登记成可引用基准需要另有明确契约，不能悄悄放宽上述 `oneOf`。

岗位级与候选人级是**对象归属**，对话回答／已保存成果／已确认标准是**持久状态**，界面分别表达。已保存成果有 ID、来源、可打开和可引用；仅显示文字不能称为已保存。候选人成果即使用户认可，也仍是候选人成果，不出现“确认成岗位标准”动作。

通用标准中禁止姓名、联系方式、完整简历、候选人卡片、逐人评价、面试官原话及候选人通过/淘汰记录。候选人成果不能整份升级为标准；若用户希望复用经验，另起岗位级建议，提炼不含个人内容的通用条件并单独展示确认。新增 schema 的服务端分类和归属校验是硬门禁；自由文本的业务内容仍需明确审核，不能宣称字段校验足以保证去除全部个人信息。

**标准正文复核控制（新增，尚未实现）：**采用服务端候选人来源标记与真实用户正文复核，不以关键词检测作为唯一放行条件，也不禁止一轮同时交付候选人分析与通用标准建议。服务端从冻结的候选人范围、候选人成果输入引用、已知候选人附件归属及读取收据派生并持久化 `candidateDerived`，模型不能自行清除此标记；未知附件或自由文本不能据此被判定为“不含个人信息”。来源标记为审计事实，不是内容检测结论。

现有勾选条目、填入确认消息和发送流程已绑定真实用户、结果 hash 与选中条目，但它只证明一般确认，不证明已复核个人内容。新确认在同一界面完整展示选中变更正文，并要求用户明确确认“已核对所选正文，仅保留岗位级标准，不含候选人个人信息或逐人评价”；不另设独立审批页面。对所有标准建议执行这项复核，含候选人来源时突出来源提示，避免遗漏未分类附件导致绕过。复核声明绑定 proposalResultId、proposalContentSha256、selectedChangeIds、真实用户消息与时间；缺少声明或条目／正文变化，服务端拒绝确认，须针对新版本重新复核。该声明由认证用户提交，工具请求不能代替用户生成。复核不是允许保存被禁止内容的授权，也不能保证人工绝不漏判；发现个人内容时重写为新建议，不原地修改已有结果。新确认字段与消息语义随协议升级，旧冻结确认消息不能被补造为已完成正文复核。

**复盘的去标识化边界：**岗位复盘不保存姓名、联系方式、候选人编号／可反查映射、可识别的独特经历组合、逐人评价、通过／淘汰记录或面试官原话；改写姓名为“候选人 A”仍不满足要求。只保留不指向个人的模式、证据缺口和标准问题；仍可识别个人则删减该段或保留为具备候选人范围的成果。来源收据仅作受授权追溯，不在岗位报告中展开原始候选人材料。已有 `_read` 会校验候选人读取范围，`_validate_result` 也校验所有结果的来源收据；不能说通用分析完全绕过读取授权，但它确实缺少逐人结果归属字段，不能用来保存候选人明细。CLAUDE.md 的相关禁令针对长期岗位校准，不意味着禁止保存受授权的候选人任务成果。

### 连续工作显式引用成果（新增设计，尚未实现）

当前终态 `resultRefs` 代表本轮输出，不是下一轮的输入。现有 `HrTurnScope` 只有岗位、候选人和附件；读取工具也尚无 `result` 资源类型。不能因为界面能打开成果，就声称模型已具备跨轮读取能力。

从某份面试方案点击“继续记录”时，在主对话“本次参考”显示该方案标题、候选人及不可变版本，用户可打开、移除，再发送自己的要求和面试记录。新轮次冻结所选引用，必须包含 resultId、schemaId、contentSha256；由服务端解析来源 turn、岗位和候选人，不能信任客户端自报归属。切换岗位时移除不适用引用并明确提示，不将上一岗位材料默带给新岗位。

明确采用输入侧顶层字段 `inputResultRefs`（必填数组，无引用时为 `[]`），不复用终态输出侧 `resultRefs`。新版本的上下文规范化哈希键固定为 `prompt / scope / rolePackage / methodSelection / inputResultRefs`，每项包含上述三个必填字段，同一 resultId 不重复；数组顺序亦随命令冻结。面试记录中的非空方案引用必须出现在 `inputResultRefs` 中，并有本轮成功读取收据；显式空值只表示这次确实未使用历史方案，不能用来规避引用校验。

由于当前 v6 的严格字段、结果枚举与哈希约定已经发布，这次新增采用 `core_chat_collaboration_v7`，同步 Platform、MetaBot 与 Team 的工具指令／清单版本；保留 `frozen_intent_with_tools` 的上下文语义。既有 v6 命令及结果继续按原契约解释，不追加字段或重算历史哈希；不把修改顶层字段包装成仅改页面。输入引用本身不授予权限，新 `result` 读取仍须检查当前权限及来源对象的有效性。

实现时协调扩展三仓的严格输入契约与授权读取面：受理校验 owner、当前范围、结果可用性；新轮工具按冻结引用读取并登记本轮 read receipt，后续提交用该收据追溯。旧轮输出不可修改，重试不能静默换最新版本；撤权、删除或版本不匹配显式失败。一般对话可保持语言上的上下文，但不能以聊天历史替代岗位／候选人的授权引用。

实施顺序：先落实上述类型和归属约束 → 版本化提交及结果读取契约 → 有具体对象与“本次参考”的页面入口 → 在现有 Hannah 场景小节补交付声明。只针对新增类型、归属、确认拒绝和跨轮引用补最小真实授权接口用例，页面最后核对引用、编辑与发送。质量评价继续采用[方法库 §10](2026-09-08-hr-scenario-methodology-library-design.md#10-业务效果与故障诊断)，不以 schema 接受或资源可读替代成果质量。

### 共同确认

生成分析不自动形成已确认标准，也不把候选人材料写入长期知识。

用户可用自然语言确认全部、确认部分或纠正。保存操作必须绑定原始认证用户消息、当时展示的建议版本及明确确认的条目；模型不能自己生成“人已确认”的凭据。能明确解析的确认直接处理，含糊或对应版本已变化时，只澄清缺失部分。

内部版本继续用于并发控制与审计，但面向用户展示“已记住哪些标准”“哪些未保存”“与官网变化有什么冲突”。不要求用户管理 UUID、内部模块或版本号。

分析交付记录与长期岗位记忆的保留范围分开。现有草稿能否成为长期标准，由明确确认决定；不能自动批量确认历史草稿来完成迁移。

## 7. 一次性替换与删除范围

按用户最新决定，废弃 Web 岗位任务能力整体替换，不逐入口上线，不建设旧任务兼容消费者，不先修补废弃产品再重新设计。删除旧产品是用户明确的产品决定，不是已由生产数据证实“无人使用”。下面是同一次交付的删除清单，不是分阶段退出表。

| 删除范围 | 同次交付后的行为 |
|---|---|
| 五个固定岗位任务按钮、对应 `_PROMPTS`、专用启动与轮询路径 | 主对话只发送用户可见的最终正文、附件和本轮范围；旧专用请求不能悄悄转成新任务 |
| 自动注入的 `HR_WORKFLOW_CONTRACT_V1` 与通用岗位包生成要求 | Hannah 使用统一角色与方法；业务结果通过明确接口提交 |
| `position_package_projection_loop`、旧岗位包领取及其注册 | 不再扫描回答、创建岗位包账本或自动产生 `position_drafts` |
| 五类岗位模块任务的信封解析、投影和服务装配 | 不再从隐藏 Markdown 注释提取这些业务结果，不保留后台兼容消费者 |
| 独立岗位工作页中重复的启动、确认及状态控制 | 岗位查询与资料从主对话展开，统一结果和确认能力；旧工作页及其专用路由删除 |
| 自动生成内部 JD/JR 副本的默认业务路径 | 官网事实保持权威；只有明确要求时提交带来源的内部建议 |
| `role-calibration` 本地读写路径 | 使用认证校准服务；旧卡片不自动导入或参与新轮次 |
| `position_conversations` 作为新轮次岗位准入门槛 | 使用本轮授权范围；已有绑定只保留历史解释作用 |

删除以调用关系为界：共享的结果 schema、候选人或全景功能仍使用的函数，不能因为与旧任务同处一个文件就整文件删掉。保留这些独立能力不意味着保留旧五按钮、自动岗位包或旧任务适配层。候选人分析进入统一对话时同样使用新提交面；全景生产体系不在本次改造范围。

复用 Turn/Attempt、身份、附件授权、幂等和租约底座；`position_task_records` 扩展后承担每轮范围，不因名字里有 task 就删除。旧数据库函数的定义历史留在已执行迁移中，由新迁移撤销废弃函数和触发器，不能改写旧迁移文件假装从未存在。

### 实现依赖顺序，不拆成多轮产品迁移

1. **定下共同契约。** 三仓落实 v6 命令、能力授权、结构化提交与结果引用；确定按轮记录扩展、JD 凭据和唯一方法目录。接口不存在的部分作为新增工作估算。
2. **接通运行和数据能力。** Platform 建授权读取、结果与确认接口；MetaBot 接工具桥与不可变角色包；Team 补 JD CLI、方法包和校准身份链路。数据库变更扩展已有载体，同步替换所有会话级绑定前置。
3. **统一主对话并删除废弃代码。** 输入、岗位范围、工具进度、精确结果与自然语言确认使用同一链路。删除清单在同次变更中完成，不能只隐藏按钮、保留旧生产者继续写入。
4. **一次协调切换 HR。** 三仓发布清单固定对应提交与协议版本；短暂停止 HR 新轮次受理，确认实际在途状态后切换。若存在在途轮次，通过既有完成或取消流程收尾，不伪造终态、不自动重跑。切换后只启用新 HR 接入与消费者，不保留按入口路由旧协议的开关。

以上顺序用于处理代码依赖，不要求先发布旧契约隔离补丁，不要求先采集历史失败率，也不要求先完成旧卡片归属。协议切换限定 HR；其他 Bot 的现有协议和服务保持原配置，不能为 HR 升级强制迁移全部 Bot。

### `position_drafts` 与旧记录处理

旧 `claim_position_package_projection_v76` 在解析回答前就可能创建 `new_conversation / interactive-v1` 草稿，因此仅修改解析器或删除信封提示仍可能留下新草稿。切换必须撤掉领取、装配和草稿生产路径。

代码退出不以搬运旧数据为前提。历史消息、文件保留既有存储和权限；平台已确认记录按 §4 原位接入新标准查询，保持后续复用，未确认旧任务草稿不自动进入标准。旧本地校准卡封存。既有记录不需要旧后台消费者持续运行才能保留。

历史空草稿的实际数量未知。如实施时清理，只按可证明的来源生成精确清单：旧自动领取创建、内容为空、没有确认或版本、没有业务引用，并在执行时重新校验这些条件。来源不明或存在业务内容的记录不盲删。无需为了删除废弃代码整表清空 `position_drafts`，也不把全库人工归属调查列为上线前置。

### 切换前的已确认数据检查

不为修设计查询生产失败率，也不以使用量决定是否执行用户授权的功能删除。涉及确认服务切换时，实施者必须通过授权只读连接检查平台现存确认记录及当前指针，保留原成果可见性。这是切换的数据保护检查，不是扩大测试范围。本轮未执行生产查询。

最小数量及归属清单可由以下只读 SQL 取得（示例，尚未执行）：

```sql
SELECT owner_internal_user_id, position_id, state, count(*) AS version_count
FROM platform_hr.position_context_versions
WHERE state IN ('confirmed', 'superseded')
GROUP BY owner_internal_user_id, position_id, state;
```

使用既有授权账号，注明其可见范围；受限账号的零行结果不能代表全库。再核对每个当前指针的 owner/position/state 与新服务读取结果，确认当前标准内容和确认元数据未丢失；发现不一致就修复该读取/映射，不能静默跳过或自动重新确认。confirmed 数量为零也只证明没有当前确认版本，不能推导整个产品无人使用。superseded、消息和文件仍可能存在，保留规则不变。

### 发布失败与恢复

三仓版本不匹配时停止 HR 新受理，修复一致的发布组合；不能自动回落到双信封链路。保留必要发布快照、数据备份和既有磁盘门禁。确需恢复旧部署时，HR 接入保持关闭，核对新轮次和持久写入后处理，不把回滚等同于重放用户请求。运行版本清单与数据恢复能力属于发布保护，不构成长期维护两套 HR 产品。

## 8. 验收边界和待核实项

本设计没有执行测试、模型调用、生产数据查询或发布。

后续只围绕具体改动做必要检查，并由用户做真实业务验收；不把全量回归或反复浏览器巡视列为默认步骤。最重要的业务证据是：

- 原样记录并使用了用户本次要求、所选岗位及材料。
- 方法确实来自共同角色/方法版本；实际需要的数据读取能在本轮记录中定位。
- 已有官网 JD 不被无意改写成另一份权威事实。
- 同轮输出只有一个适用的协议与业务处理方，结果能直接打开。
- 同会话切岗位后，历史范围不改变、材料不串用。
- 只有明确共同确认的岗位级结论成为后续标准。
- 新结果提交和重试保持幂等；废弃领取函数、循环及其装配没有继续生产记录。

### 上下文体积的量化口径

当前平台上下文上限为 96 KiB，全景上下文最多占 28 KiB。它们是现有预算，不是已测得的每轮平均值。新首版目标：初始命令中的系统组装业务引导内容不超过 8 KiB，不含真实用户正文、对话历史及原生运行时系统规则；只传范围和数据引用，不再附带完整 JD、全景及方法正文。

对原先实际包含完整 JD/全景的同输入样本，记录新旧平台初始命令的完整 UTF-8 字节数，目标下降至少 50%；这是待验证目标，不是已取得收益。可从留存输入静态比较，不需要为量字节额外调用模型。普通短对话不套用这一降幅目标。

另记工具返回总字节数、读取次数和实际可获得的模型输入消耗/耗时；把初始前推减小与总消耗分开，不能因改成工具读取就宣称整体更省。方法文本预算与方法库设计统一为本轮最多 16 KiB，不截断必需步骤冒充完整使用。

### JD 调用延迟预算

以下为首版目标，尚未实测：有效 registry 的读取/核验目标为 2 秒内；需要全量刷新时，单次工具前台等待预算为 60 秒，2 秒内给出“正在核验官网岗位”的进度。首次调用若遇到过期 registry，可能等待接近 60 秒；无有效 registry 时现有 CLI 会报不可用，不能保证首次调用一定拿到新 JD。

当前官网客户端单请求超时 15 秒并有 2 秒、5 秒重试等待，全量同步可能包含多次请求；这并非已有的 60 秒总上限。Team/工具桥必须新增整次调用 deadline 与取消传播，避免后台残留同步或同轮无穷重试；超时仍使用上一次有效快照并明确校验未完成，没有快照则返回不可用。已有可靠回退与原子 registry 写入应保留，不能杀到半写状态后读损坏文件。

分别记录有效快照读取和刷新路径的耗时、超时及降级状态。减少初始提示词字节不能抵消无限等待，也不意味着首个业务回答或整轮完成时间自动改善。

### 回答质量也是交付证据

效果评价共用 [方法库 §10](2026-09-08-hr-scenario-methodology-library-design.md#10-业务效果与故障诊断)：同输入、材料与模型配置下比较新旧输出，关注岗位相关性、证据充分性、可执行性和未知项处理，同时记录关键证据遗漏、无依据新增结论与用户纠正。

由用户试用的代表性场景提供质量证据，可复用已有基线，保留具体输出和评价，不为这次文档修订调用模型或重跑完整案例集。若仅完成机制与部署，只能报告“链路替换完成，回答质量待用户验收”；没有业务质量证据，不能宣称“不智能已解决”或重新设计的业务目标全部达成。方法库的完整案例计划不是每次改动的默认发布门禁。

### 尚未验证

平台 confirmed/superseded 上下文版本的数量、归属和当前指针一致性，以及旧自动草稿数量、CLI 校准卡归属情况、岗位包 `envelope_invalid` 分布均未查询；不把没有查询写成没有数据或没有影响。

生产历史统计可以帮助确定影响面，但不作为承认代码契约冲突的前置条件。若后续查询，应分别统计任务结果与岗位包处理状态，并按同一 turn 关联；JD/JR 比其他任务失败率高只能构成相关性证据。需要查看受限范围的实际输出类型与错误阶段，才能归因到信封冲突。

若要核实 Hannah 项目记忆是否实际进入 Web 执行，单独保存平台的 frozen prompt 还不够：还应核对原生运行时 cwd、角色/共享规则/方法版本以及对应会话的加载和工具记录。本轮未采集这些数据，不宣称已观察四个指令源的完整模型请求。

本轮设计范围不包括修改模型、发布渠道、全景分析系统或其他 Bot。
