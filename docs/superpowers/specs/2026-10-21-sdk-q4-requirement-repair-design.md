# 2026 Q4 SDK 禅道需求修复设计

## 现状与根因

原 Excel 有独立的“2026年Q4上线版本”工作表，内有 67 条任务、16 个有任务的栏目及 8 个超链接。此前以该表导出的 CSV 导入禅道 #3–#69，任务范围实际上正确，但 CSV 丢失工作表名和超链接，导入正文又把哈希、行号和原始字段表格当作需求描述。禅道记录的创建人是导入服务账号，不等于需求提出人。原表没有提出人和验收标准。

这是来源计划、需求草稿与正式需求之间的职责混淆。再次修复时不能继续为每条任务套统一的“完整需求”模板。

## 目标与边界

- 只使用原 Excel 中名为“2026年Q4上线版本”的工作表，验证 67 条任务与禅道现有记录一一对应。
- 保留禅道 ID、标题、已有负责人、优先级、评审状态和其他用户可能修改的字段；不创建、删除或批准需求。
- 禅道的“来源备注”明确显示工作表、栏目和 Excel 行号。哈希及导入标识留在受保护的修复清单和既有来源数据库，不放进需求正文。
- 正文只保留原任务描述、明确给出的计划版本/日期/风险/进展/备注及原 Excel 的参考链接。缺乏场景、提出人或验收标准的条目明确维持待澄清，不推测这些信息。
- 对已有人为编辑或身份不匹配的记录停止写入并列出冲突，不覆盖。
- 不修改 Nginx 配置、容器部署或其他平台服务；业务上线是禅道数据修复。

## 数据流与安全

修复工具读取 Excel 的指定工作表，解析 A:J 列及单元格超链接；先生成 67 条预览并与禅道现有记录按旧导入标识、标题和优先级校验。默认只读。执行前保存源文件哈希、逐条旧记录、预览结果及禅道数据库转储。正文和验收栏逐条通过禅道原生“变更需求”API 修改，采用最近读取值作为并发前提；写后回读受保护字段。任何差异立即停止，保留已完成条目的回执，以便幂等续跑或回滚。

禅道 OSS 22.6 的普通编辑 API 不接收正文和验收栏，且会清空未传的负责人并改写指派时间，因此不用它批量更新。来源备注通过一笔带 ID、产品、版本、状态和负责人条件的数据库事务写入；任何一条条件不符即整体回滚。禅道 RoadRunner 长驻进程需要重启禅道容器后才能读取这笔数据库修改。不触碰共享 Nginx 或平台容器。先对用户指出的 Android Wrapper 条目做单条受控验证，确认接口行为后再处理其余条目。导入服务账号只保留为技术创建人，提出人继续为空；已有负责人仍为责任人。

## 验收

1. 原 Excel 仅选择 Q4 工作表，解析 67 条、16 个有任务栏目、8 个超链接；Q3 同名任务不会重复进入。
2. Android Wrapper 条目只陈述原计划“根据客户需要更新版本”，明确待确认客户、目标版本、范围和验收标准；不出现哈希、导入标识或假提出人。
3. 67 条逐条回读：身份、负责人、优先级、评审状态与写前一致，来源备注指向 Q4 工作表，正文不含旧导入表格，8 个参考链接保留。
4. 生产数据库备份可读取；禅道入口、SDK 单点登录和行政服务的既有入口保持可用。
