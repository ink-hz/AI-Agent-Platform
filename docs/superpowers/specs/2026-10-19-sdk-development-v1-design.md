# SDK 开发管理平台首版设计

日期：2026-10-19。本文以[平台需求](../../design/2026-10-19-sdk-development-platform-requirements.md)和[开源选型](../../design/2026-10-19-sdk-development-platform-open-source-evaluation.md)为依据。

## 决策与边界

首版在 AI-Agent-Platform 内提供 `/sdk/` 工作台。用户沿用现有企业会话、CSRF 和内部用户 ID，不接触禅道凭据。禅道开源版 22.6 作为需求正文、验收标准与开发任务的唯一权威系统；平台通过固定地址和服务账号调用其 API v2。平台自己的 SDK 数据库保存禅道 ID 的引用、SDK 评审结论、不可变源码候选、构建与测试证据、发布审批和事件日志，不复制可编辑的需求正文和任务状态。SDK 评审结论只在平台生效，界面同时展示禅道原状态，不能把两者混为一谈。

本版由人录入基线、构建、测试和发布信息。没有 GitLab API、Webhook、Issue/MR/流水线同步；链接仅作为文本证据。AI 仅提供后续建议入口，不参与发布判断。禅道原生 UI 不对普通用户开放，避免第二套登录与绕过平台审批。禅道不可用时需求/任务读写明确返回 503；已保存的 SDK 证据可读，但不允许新的发布审批。

## 可用范围

首版业务路径：创建需求 → 评审结论 → 创建关联任务 → 冻结候选基线 → 登记多个构建产物 → 登记逐产物测试结果 → 检查门槛并审批 → 登记实际发布 → 按发布记录反查整条链。创建需求时必填标题、场景、设备/平台、验收标准；禅道 `spec` 和 `verify` 分别承载描述与验收标准。任务使用禅道 `story` 关联。禅道需求 ID 与任务 ID 在平台 URL 和 SDK 证据中保持稳定。

首版基线使用显式、完整的清单：打包仓库提交、主 SDK 版本、构建脚本路径、一级子模块及嵌套子模块的仓库路径与完整 40 位 SHA。冻结后不可修改；修订生成新候选。首版不通过 GitLab 验证 SHA 是否存在，页面明确显示“人工登记，待核对”。

构建运行按候选、操作系统、架构保存命令、退出状态、日志 URI、产物名/大小/SHA-256/URI。测试运行按产物摘要保存测试类别、设备与固件、通过/失败/跳过数、报告 URI、状态和操作者。硬件未到位记录为 `blocked`，不当作通过。首版发布门槛要求：至少一份成功构建和产物；每个将发布的产物都有 `unit` 通过与 `hardware` 通过记录，且二者指向该产物的 SHA-256；无失败或阻塞的最近测试结论。审批由发布负责人执行，实际发布独立登记渠道、时间、批准人、产物摘要、回退 URI。例外放行首版不开放，避免无角色分离时误放行。审批后新增/修改证据会使审批失效，需要重新审批。

## 身份、权限与审计

SDK 专属成员表按现有内部用户 UUID 授予 `viewer`、`contributor`、`reviewer`、`release_manager`。平台所有者通过受审计的 API 管理成员；平台全局管理员不自动获得 SDK 发布权限。`contributor` 创建需求、任务和候选及录入构建；`reviewer` 记录需求评审和测试；`release_manager` 审批、发布；各写角色均可读项目内全部 SDK 记录。未授予 SDK 角色的用户不能读取。发布审批人不得是对应候选的创建人。硬陈旧目录和只读模式禁止写入。

所有写入均要求 `request_id` UUID。平台数据库以 `(actor_id, request_id)` 存操作结果和请求摘要；相同请求重放返回原结果，摘要不同返回 409。禅道创建需求/任务属于跨系统写入：先在平台持久化意图，再调用禅道，成功后写入外部 ID；超时或不确定结果停在 `reconcile_required`，不自动重试创建。管理员需人工核对禅道并完成绑定，防止重复记录。事件追加保存操作者、时间、动作、对象、请求 ID 和关键字段摘要，保留原失败结果。浏览器和日志中均不得出现禅道 token。

## 组件与数据流

1. `sdk_workbench/zentao.py`：固定私网禅道 URL、受限 API 路径、超时和响应大小、令牌缓存及刷新；只接受明确支持的故事和任务操作。服务密码从文件读取。禁用代理环境变量，拒绝跳转。
2. `sdk_workbench/repository.py`：单独 `sdk` schema 的成员、操作意图、候选、构建、测试、审批、发布、事件表；数据库约束确保外键、唯一请求 ID、冻结快照、审批版本。
3. `sdk_workbench/service.py`：权限与状态机、发布门槛、跨系统写入协调；以实际 ZenTao ID 建关联，不接受浏览器伪造的“成功”。
4. `sdk_workbench/routes.py`：同源 `/api/v1/sdk/` 契约；现有中间件完成会话、来源和 CSRF 检查，路由再完成 SDK 角色检查。错误使用固定代码，不透出服务凭据或内部地址。
5. `webui/src/sdk/`：需求列表、需求详情与任务、候选详情、证据录入、发布门槛及追溯；导航出现在“业务工作台”。所有提交显示返回的真实状态和错误，不用前端状态代替服务状态。
6. `deploy/sdk/`：禅道与 MySQL 的私网 Compose 试运行配置、镜像固定版本、持久卷及初始化说明。正式部署需先完成禅道初始化、服务账号最小权限、产品/执行 ID 配置和备份。首版不自动改现有云生产 Compose。

## 接口契约

`GET /api/v1/sdk/me` 返回角色与可操作动作。`GET/POST /requirements`、`GET /requirements/{id}`、`POST /requirements/{id}/reviews`、`POST /requirements/{id}/tasks` 对接禅道与本地评审事件。`GET/POST /candidates`、`GET /candidates/{id}`、`POST /candidates/{id}/builds`、`POST /artifacts/{id}/tests`、`GET /candidates/{id}/gate`、`POST /candidates/{id}/approval`、`POST /candidates/{id}/release` 操作 SDK 证据。所有列表分页，写请求严格校验字段长度和 SHA 格式；每个写接口要求 `request_id`。详情响应包含关联禅道 ID、证据版本、门槛结果和事件时间线。

## 验收

接口测试覆盖真实身份路径、无权限与只读拒绝、CSRF、重复提交、禅道超时不确定写、完整 SHA 清单、两种目标平台、失败/阻塞测试、摘要不匹配、审批人与创建人分离、审批失效和发布反查。ZenTao 适配器先通过隔离 HTTP 试验验证 API 形状，再在试运行容器中用真实 22.6 实例验收。前端构建和组件测试通过后，浏览器连接与页面验收按仓库约定由用户负责。上线结论须同时写明实际禅道版本、平台提交、数据库迁移、真实接口证据与未通过项。

## 落地顺序

先实现可运行的禅道试验环境、适配器、同源需求/任务接口与简洁工作台；再实现 SDK 专属证据库及发布门槛。第一阶段就应能由企业身份创建、查看、评审和拆解真实需求，不能把静态页面当作可用版本。第二阶段完成才可宣称首版业务闭环。每阶段独立测试、审查和提交。
