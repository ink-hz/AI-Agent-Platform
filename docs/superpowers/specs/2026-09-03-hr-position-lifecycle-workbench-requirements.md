# HR Agent 招聘智能增强工作台需求文档

**日期：** 2026-09-03

**状态：** 产品范围已确认，等待接手会话复审

**产品入口：** Agent Platform / HR Agent

**核心业务模型：** Position + Candidate + PositionCandidate

## 1. 产品定义

HR Agent 工作台是覆盖招聘工作全过程的 AI 智能增强层，不是新的招聘管理系统，也不替代
北森。

完整的是 AI 的认知、分析、生成和经验反馈链路，不是招聘申请、审批、排期、Offer、入职等
事务流程。工作台建设 AI 工作所必需的岗位、候选人、简历、证据、面试内容、分析结果和人工
反馈数据，使 HR Agent 能持续理解一个岗位和候选人，而不是每轮只处理一句孤立问题。

最高产品约束：

> Agent Platform 只建设招聘智能增强所必需的上下文、证据、分析和成果能力。任何不直接
> 增强 AI 能力、且已由北森承担的事务流程，一律不进入本产品范围。

本期不接入新的外部业务系统。凡是必须依赖北森、OA、猎聘、BOSS 直聘或其他企业接口才能
成立的能力，全部留空并从本期实现中排除。“留空”不是展示占位页面、灰色按钮或模拟数据，
而是不设计相关数据字段、Adapter、同步任务、API、页面和验收项，待未来单独立项。

## 2. 与现有设计和系统的关系

本需求继承《HR Agent 网页会话工作台设计》中已经建设的持续会话、附件、长任务恢复、结果
文件、引用和反馈能力，不重新实现这些底座。

若两份文档冲突，以本文件为准：

- HR 的业务主线从 Conversation 调整为 Position；
- Candidate 是可复用的独立人才对象；
- PositionCandidate 承载岗位相对的分析、面试和评价；
- Conversation、Attachment 和 Artifact 是上述业务对象下的协作与内容载体；
- 不建设北森式招聘事务流程。

现有能力继续复用：

- `hr-jd-sync`：官网岗位同步、状态判断、版本历史和使用前核验；
- `hr-role-calibration`：岗位级校准结论和版本管理；
- Platform Conversation：持续对话和 Turn；
- Platform Attachment Service：简历、面试材料和生成成果；
- HR MetaBot Runtime：招聘领域分析与生成。

## 3. 真实数据依据

本需求基于 Flywheel 历史只读数据、HR Agent 当前运行库和现有代码核查：

- 识别出 8 个真实历史飞书业务会话、169 条有效用户问题；网页探针和 Canary 已排除；
- 当前运行库有 7 个恢复后的飞书会话、154 条用户消息和 150 条 Assistant 消息；
- 真实会话最长达到 67 轮，同一聊天中出现多个岗位和多类招聘任务；
- 真实业务 Turn 耗时中位数约 117 秒，P90 约 12.5 分钟，P95 约 19 分钟；
- 40 条问题明确引用图片、简历、文件或 PPT，41 条承接上文或要求反复修改；
- 高频任务是 JD/JR 修订、人才画像、人才搜寻、简历与访谈分析、面试题、人才报告、公开研究
  和 Word/PPT 交付；
- 历史附件表、HR 反馈、复审和改进事项未形成完整记录，原链路不能表达真实工作。

由此得到两个核心结论：

1. 一个聊天 Session 不是稳定的招聘项目，不能继续作为岗位和材料的唯一边界；
2. 招聘 Agent 的价值来自长期岗位上下文和候选人上下文，而不是一次性问答。

## 4. 产品目标

1. 同时管理官网同步岗位和通过自然语言新增的内部岗位。
2. 让每个岗位拥有持续、版本化、可复用的岗位智能上下文。
3. 建设独立候选人信息和简历资料，使候选人可以在多个岗位中复用。
4. 在岗位与候选人的关系上完成匹配、证据、面试和评价，而不是复制候选人资料。
5. 用 AI 完成 JD/JR、人才画像、人才挖掘、简历分析、面试设计和面试内容分析。
6. 保存版本化 AI 分析和人工反馈，让后续分析建立在此前事实之上。
7. 从一批候选人的真实分析与面试结果中，反向改善岗位画像、搜索方向和面试标准。
8. 持续关注目标公司、学校、研究机构和专业社区，把公开招聘变化转化为岗位和人才策略。
9. 保持直接、持续的对话体验，不要求用户理解 Run、Trace、Adapter 或内部版本号。

## 5. 明确不做

本期不建设：

- 招聘申请、审批、编制和预算；
- 职位渠道发布及投递管理；
- 候选人招聘阶段流转；
- 面试排期、会议室、日历和通知；
- Offer、背调、入职和电子签；
- 招聘专员任务分配和绩效管理；
- 完整招聘漏斗和运营报表；
- 北森候选人主档的复制品；
- 自动联系、自动淘汰或自动录用；
- 面试实时录音和会议机器人。

以下外部系统相关能力同样全部留空：

- 北森的岗位、候选人、人才库、招聘进度、面试、Offer、入职、组织和绩效数据；
- OA 的招聘需求申请、审批结果和分配信息；
- 猎聘、BOSS 直聘等第三方平台的企业账号搜索、简历获取、沟通、投递和状态同步；
- 薪酬、绩效、组织架构和入转调离系统的数据接入；
- 为未来接入预建的空页面、假数据、桩接口、未使用映射字段和推测性权限模型。

现有官网岗位同步、合法公开网页研究、现有钉钉统一登录和既有飞书 Agent 入口不属于新增外部
业务系统接入，可以继续复用。飞书本期只是 HR Agent 的使用入口，不建设飞书到北森或 OA 的
业务桥接。

## 6. 核心业务对象

### 6.1 Position：岗位

Position 是招聘智能工作的主线，也是用户进入工作台的主要入口。

岗位至少包含：

- 不可变 `position_id`；
- 来源：`official_site / manual`；
- 官网 J 编号和官网岗位记录引用；
- 岗位名称、部门、地点和岗位基础信息；
- 官网当前事实与官网版本；
- 内部需求和用人部门补充信息；
- 当前岗位上下文版本；
- 关联 Conversation、材料、候选人和成果。

岗位名称可以变化或重复，不能作为系统主键。

官网状态与内部工作状态必须分开：

- 官网状态沿用 `active / stale / suspected_inactive / inactive`；
- 内部状态只用于区分 `draft / active / archived`；
- 官网下线不删除工作台岗位，内部归档也不修改官网事实。

### 6.2 PositionContextVersion：岗位智能上下文

岗位上下文是 HR Agent 每次处理该岗位时自动获得的核心信息包，包括：

- 官网原始 JD；
- 用人部门真实诉求；
- 岗位使命和预期成果；
- 当前 JD、JR；
- 必须、加分、可培养能力；
- 优选人才画像；
- 目标公司、学校、实验室和相邻人才来源；
- 搜索关键词和人才地图；
- 筛选和面试评价标准；
- 已被用户确认的岗位级经验；
- 未解决问题和仍需验证的假设。

AI 建议先作为草稿。只有用户明确确认后才形成新的岗位上下文版本。新版本不覆盖历史版本。

### 6.3 Candidate：候选人

Candidate 是独立、稳定、可跨岗位复用的人才对象，不只是某个 Session 的一份附件。

候选人信息至少包括：

- 不可变 `candidate_id`；
- 姓名或用户提供的稳定称谓；
- 当前公司、职位及用户提供的基础职业信息；
- 简历及不同版本；
- 用户补充材料；
- 已核验的公开专业身份和来源；
- 资料来源、更新时间和身份对应置信度。

候选人信息可以由以下方式创建：

- 上传简历后由 AI 提取草稿，用户确认；
- 用户通过对话新增；
- 从合法公开人才研究结果明确加入。

AI 不得因为对话中出现一个人名就自动创建 Candidate。不能确认同名人才身份时不得合并。

### 6.4 CandidateDocument：候选人材料

候选人材料包括：

- 简历及版本；
- 作品集和项目材料；
- 用户补充说明；
- 公开专业证据快照或引用；
- 面试记录、转写文本和评价材料。

原始材料通过 Platform Attachment Service 保存。CandidateDocument 记录业务归属、材料类型、
来源和版本，不复制文件字节。

### 6.5 PositionCandidate：岗位候选关系

Candidate 保存人才事实，PositionCandidate 保存“这个候选人与这个岗位的关系”。同一候选人
可以关联多个岗位，每个岗位拥有独立分析和面试上下文。

PositionCandidate 至少包含：

- `position_id + candidate_id` 唯一关系；
- 加入该岗位的来源和原因；
- 使用的岗位上下文版本；
- 匹配点、证据缺口、冲突和待验证问题；
- 与该岗位有关的面试材料；
- AI 分析版本；
- 人工反馈和人工评价结论。

PositionCandidate 不保存北森式流程阶段、面试排期、Offer 或入职状态。

### 6.6 CandidateAnalysisVersion：AI 分析

AI 分析必须是可追溯、不可原地覆盖的版本化对象。支持的分析类型包括：

- 简历信息提取；
- 岗位匹配分析；
- 公开专业证据分析；
- 候选人挖掘结果分析；
- 面试前分析；
- 面试后分析；
- 多候选人比较；
- 候选人综合总结。

每个分析版本必须记录：

- 目标 PositionCandidate；
- 使用的 PositionContextVersion；
- 使用的简历、证据和面试材料版本；
- 结论、证据、未知项和限制；
- 创建时间和生成它的 Agent/模型版本；
- 它替代的上一分析版本。

岗位画像变化后，旧分析继续保留。系统可以提示重新分析，但不能静默重算或覆盖。

### 6.7 HumanFeedback：人工反馈

人工反馈用于增强 Agent 后续判断，不承担招聘流程状态管理。内容可以包括：

- 对 AI 简历分析的纠正；
- HR 或用人经理确认的匹配点与风险；
- 面试后对具体能力的判断；
- 对某条评分或结论的认可、否定和原因；
- 下一批人才应该调整的方向。

人工反馈与 AI 建议必须分开保存。AI 不得自行生成或改写“人工确认”。

### 6.8 CandidateEvaluation：候选人评价结果

候选人评价结果用于记录“在某个岗位和某版画像下，我们目前如何判断这个候选人”，不是招聘
流程阶段。它至少包含：

- 目标 PositionCandidate；
- 使用的 PositionContextVersion；
- `建议深入 / 有条件匹配 / 证据不足 / 当前不匹配` 等评价结论；
- 维度评价、关键证据、未知项和风险；
- AI 建议与人工结论两个独立字段；
- 人工结论的确认者、确认时间和补充说明；
- 被后续评价替代时的版本关系。

同一候选人在不同岗位下拥有不同评价结果。评价结果不会触发候选人阶段流转、淘汰或录用动作。

### 6.9 TalentSource 与 TalentInsightVersion：人才与组织情报

TalentSource 是可以被多个岗位复用的外部人才来源对象，类型至少包括：

- 公司；
- 学校；
- 实验室或研究机构；
- 专业社区。

公司类 TalentSource 可以关联版本化 PublicJobSnapshot，保存公开招聘岗位、来源、采集时间及与
上一快照的变化。PositionTalentSource 保存某个关注对象为什么与某个岗位相关、优先级、目标
团队或人才方向。

TalentInsightVersion 保存 AI 基于公开事实生成的版本化分析，包括技术方向聚类、招聘资源投入
信号、人才供给判断、JD 对标结果及对当前岗位的影响。公开岗位事实、AI 推断和未知项必须分开。

人才与组织情报服务岗位画像、人才搜寻和面试标准，不建设全网职位聚合器。

## 7. 岗位智能增强能力

### 7.1 官网岗位同步

现有 `hr-jd-sync` 继续承担官网岗位采集、完整性检查、状态判断和版本历史。Platform 负责把
官网岗位投影为 Position，不在用户请求期间临时抓取官网。

用户可以：

- 查看和搜索官网岗位；
- 查看官网状态、版本时间和同步健康；
- 对单个岗位执行使用前核验；
- 从官网岗位进入岗位智能工作台。

官网版本更新只更新“官网事实”，不得覆盖内部岗位上下文、候选人或历史分析。同步失败时保留
最后有效版本并显示更新时间。

### 7.2 对话新增岗位

用户可以直接描述招聘需求。HR Agent 从自然语言中形成岗位草稿，整理岗位名称、使命、预期
成果、必须能力、加分能力、地点和未知项。

只有用户明确确认后，Platform 才创建 Position。内部岗位与官网岗位关联时，必须由用户显式
选择，不按名称自动合并。外部系统岗位关联不在本期范围。

### 7.3 JD、JR 与画像生成

HR Agent 可以基于官网事实、内部需求和用户材料：

- 生成或修订可发布 JD；
- 生成内部 JR；
- 拆解岗位使命、成果和能力层级；
- 生成优选人才画像；
- 形成搜索关键词、目标组织和相邻人才来源；
- 形成筛选和面试评价标准；
- 比较官网版本、内部版本和上一版本差异；
- 检查技术词堆砌、条件过严、表达冗余和招聘平台发布风险。

官网事实、内部原始需求、AI 草稿和用户确认版本必须明确区分。

### 7.4 岗位上下文自动增强

用户在岗位内发起请求时，Platform 自动向 HR Agent 提供当前岗位上下文，不要求用户重复解释
背景。上下文组装至少包括：

```text
当前岗位事实
+ 当前已确认岗位上下文
+ 本轮显式启用材料
+ 与当前问题有关的已确认岗位经验
+ 用户当前请求
```

不得把其他岗位、其他候选人或当前未启用材料自动加入上下文。

## 8. 候选人智能增强能力

### 8.1 简历信息提取和候选人创建

上传简历后，AI 提取候选人基础职业信息、经历、项目、技能和材料中的未知项，形成 Candidate
草稿。用户确认或主动继续岗位分析时，创建 Candidate 和 PositionCandidate。

批量上传时，每份简历独立解析、独立显示状态；一份失败不能使整批失败。系统不得把多个候选人
材料合并为一个上下文。

### 8.2 简历与岗位匹配分析

AI 基于当前岗位上下文分析：

- 岗位相关经历和能力证据；
- 必须、加分、可培养能力的逐项匹配；
- 跨经历能力组合；
- 经历深度、近期程度和可迁移性；
- 简历陈述、公开证据、合理推测和未知项；
- 冲突、风险和面试待验证问题；
- 当前证据支持的下一步建议。

没有材料支持的能力必须标记“未验证”，不能当作“不具备”。

### 8.3 候选人挖掘

HR Agent 根据岗位画像制定人才搜寻策略，并从合法公开专业来源发现人才线索。每条线索至少
包含公开身份、来源、检索时间、岗位相关证据、匹配点、未知项、证据强度和推荐关注理由。

人才线索只有在用户明确加入后才成为 Candidate。AI 不自动联系候选人，也不以低质量线索补足
数量。

### 8.4 面试问题生成

系统支持两类面试内容：

- 岗位通用面试框架；
- 基于 Candidate 和 PositionCandidate 的候选人专属面试方案。

每个候选人专属问题应说明验证目标、针对该候选人的原因、递进追问、有效证据、普通回答、风险
信号和记录位置。生成的面试题成为版本化 Artifact，可以继续对话修改。

### 8.5 面试内容分析

首版支持上传或输入面试记录、语音转写文本、面试官笔记和评价表。AI 结合岗位标准与候选人
材料分析：

- 哪些能力已经获得证据；
- 哪些能力仍未验证；
- 回答的深度、一致性和可迁移性；
- 简历与面试陈述之间的冲突；
- 面试问题是否真正覆盖岗位标准；
- 不同人工反馈的具体一致和冲突点；
- 建议补充的问题和下一步判断重点。

系统分析面试内容，不建设面试排期和面试流程引擎。

### 8.6 候选人比较和评价

多候选人比较必须限定在同一岗位和同一岗位上下文版本下。比较维度来自已确认的人才画像，输出
证据、未知项和适配差异，不只输出一个排序。

如果显示评分，必须同时显示：

- 维度定义；
- 使用的证据；
- 证据覆盖率；
- 未验证项；
- 岗位上下文版本。

评分只是分析表达形式，不自动产生招聘流程动作。人工评价结果用于后续 AI 上下文和岗位复盘，
不冒充北森流程状态。

## 9. 人才与组织情报增强

数据库中的真实请求表明，HR 会反复关注目标公司的招聘信息，并希望从中判断人才和技术方向，
而不只是读取一次职位列表。已出现的需求包括：

- 查看关注公司的全部公开招聘岗位；
- 对比岗位新增、修改和下线；
- 按光学、硬件、结构、软件、算法和制造工艺等方向聚类；
- 判断对方在重点建设哪些技术和团队能力；
- 比较外部 JD 质量、薪酬和人才供给；
- 寻找相关学校、实验室、研究院和专业社区；
- 把外部信号转化为本岗位的人才画像、搜索关键词和面试重点。

### 9.1 关注对象

用户可以在岗位对话中关注公司、学校、研究机构或专业社区，也可以复用已存在的 TalentSource。
新增关注对象必须由用户确认，Agent 不因对话中提到一个组织名称就自动长期跟踪。

关注对象显示公开来源和最近核验时间。无法确认组织身份或存在同名歧义时，必须先让用户选择。

### 9.2 公开招聘快照与变化

对关注公司，系统按批准的公开来源保存 PublicJobSnapshot。每个快照至少包含岗位标题、公开岗位
标识、地点、职责与要求摘要、来源 URL、采集时间和内容哈希。

系统比较相邻快照，输出新增、修改、疑似下线和重新出现的岗位。采集失败时保留最后有效快照，
不得把网络失败解释为公司停止招聘。

本能力只跟踪用户明确关注的对象和当前岗位需要的目标组织，不建设无边界职位抓取平台。

### 9.3 AI 情报分析

HR Agent 可以基于一个或多个快照生成 TalentInsightVersion，回答：

- 该组织近期重点招聘什么；
- 哪些技术方向或地区的投入明显变化；
- 是补充单点专家还是构建完整团队；
- 哪些岗位与当前 Position 相似；
- 哪些 JD 表达和能力要求值得借鉴；
- 该组织可能产生哪些相关人才；
- 当前岗位应如何调整画像、搜索方向和面试重点。

资源投入和团队建设结论属于基于招聘信号的 AI 推断，必须显示依据和置信限制，不能陈述为公司
内部已确认事实。

### 9.4 定期摘要

用户可以为关注对象开启公开招聘变化摘要。摘要只在存在新快照或有意义变化时生成，内容进入
对应岗位的情报上下文；无变化时不制造通知。

摘要能力不包含职位发布、投递、渠道运营或候选人流程动作。

## 10. AI 反馈闭环

工作台需要形成以下智能闭环：

```text
岗位需求
  → JD/JR与优选画像
  → 人才挖掘或简历进入
  → 岗位匹配分析
  → 面试问题
  → 面试内容分析
  → 人工反馈
  → 反向改进画像、搜索方向和面试标准
```

AI 可以从一批 PositionCandidate 的分析和人工反馈中生成岗位级复盘草稿：

- 哪些能力真正具有区分度；
- 哪些硬条件缺乏依据或造成误伤；
- 哪些公司、学校、项目和相邻经历产生了有效人才；
- 哪些面试问题真正获得了证据；
- 下一批搜索关键词和来源应该怎样调整；
- JD、JR 和优选画像是否需要修改。

复盘结果不会自动修改岗位上下文。用户明确确认后，才能形成新的 PositionContextVersion。

## 11. 对话、材料与成果

一个 Position 可以有多个 Conversation；每个 Conversation 创建后只能绑定一个 Position。
候选人专项对话还应绑定 PositionCandidate。

每次向 Agent 发起请求时，Platform 组装：

```text
岗位上下文
+ 当前候选人上下文（如有）
+ 本轮选择的材料
+ 已确认的历史结论
+ 用户当前问题
```

用户上传的简历和面试材料必须明确归属 Candidate 或 PositionCandidate，不能只挂在整个 Session
上。Agent 生成的 JD、画像、人才地图、简历分析、候选人报告和面试方案登记为版本化 Artifact。

长任务不依赖浏览器连接；刷新、断网或关闭页面后继续执行，重新进入时恢复真实状态和成果。

## 12. 页面信息架构

首版只建设两个核心工作区，不增加复杂招聘管理菜单。

```text
HR Agent
├─ 岗位
│  ├─ 官网同步岗位
│  ├─ 对话新增岗位
│  └─ 岗位智能工作台
│     ├─ 持续对话（默认）
│     ├─ 岗位上下文
│     ├─ 人才情报
│     ├─ 候选人
│     └─ 成果
└─ 候选人
   ├─ 候选人信息与简历
   ├─ 关联岗位
   └─ 进入具体 PositionCandidate 分析
```

岗位工作台桌面布局：

```text
┌──────────────┬──────────────────────────────────┬────────────────────┐
│ 岗位列表     │ 当前岗位持续对话或业务内容       │ 岗位材料与成果     │
│ 官网/内部    │ 岗位上下文·候选人·成果           │ 默认可折叠         │
└──────────────┴──────────────────────────────────┴────────────────────┘
```

进入岗位后默认可以直接对话，不先展示复杂仪表盘。用户界面不显示 Mission、Run、Trace、Adapter、
数据库状态或内部状态码。

人才与组织情报在岗位内呈现；跨岗位仅提供一个轻量“关注对象”复用入口，不新增独立情报管理
后台。

## 13. 数据边界与外部系统留空原则

### 13.1 本期事实来源

- 官网岗位事实：`hr-jd-sync`；
- 岗位智能上下文：Platform HR 业务域；
- 候选人基础信息和材料引用：Platform HR 业务域；
- 岗位候选关系和 AI 分析：Platform HR 业务域；
- 候选人评价和人工反馈：Platform HR 业务域；
- 关注对象、公开招聘快照和情报分析：Platform HR 业务域；
- 对话：Platform Conversation；
- 文件：Platform Attachment Service；
- AI 执行：HR MetaBot Runtime。

### 13.2 外部系统能力如何留空

本期所有产品行为必须能够只依赖 Platform、HR MetaBot、`hr-jd-sync` 和用户主动提供的材料
完成。北森、OA、第三方招聘平台及其他企业系统不能成为本期页面可用性、Agent 回答、权限判断
或验收通过的前置条件。

代码和数据模型不为这些系统预建推测性的同步状态、外部主键、流程字段或权限映射。产品页面
也不展示“待接入北森”“即将支持 OA”等入口。未来决定接入某个系统时，应基于当时真实 API、
权限和数据治理要求另写设计文档、迁移与验收计划，不从本期需求中推导实现。

## 14. 现有 HR Agent 规则调整

当前 `bots/hr/CLAUDE.md` 和 `role-calibration` 禁止长期保存候选人卡片、逐人评价和候选人结论。
实施本需求时，边界调整为：

- 继续禁止写入 Agent 知识库、FAQ、官网 JD 注册表、岗位校准文件和共享训练语料；
- 允许通过 Platform 结构化接口写入 Candidate、PositionCandidate、Analysis 和 HumanFeedback；
- 只有用户明确创建、关联、分析或确认时才能写入；
- Agent 不直接读写数据库文件；
- 模型分析可以生成新版本，人工反馈和历史分析不可被模型覆盖；
- 所有读取继续执行岗位和候选人授权。

## 15. AI 行为要求

- 每次分析使用明确的 PositionContextVersion；
- 候选人分析使用明确的 PositionCandidate 和材料版本；
- 事实、用户材料、公开证据、推测和未知项分开表达；
- 不因学校、公司或职位名称直接推断能力；
- 不读取或使用与岗位无关的受保护个人信息；
- 不把未验证能力按零分处理；
- 搜索失败、材料解析不完整和证据不足必须明确显示；
- 人才情报必须区分公开招聘事实、AI 推断和未知项，并显示来源时间；
- 用户确认前，AI 只能保存草稿或建议；
- AI 不执行联系、淘汰、录用、发布职位等招聘事务动作。

## 16. 分阶段范围

### Release 1：岗位智能上下文

- 官网岗位同步投影、状态和版本；
- 对话新增内部岗位；
- Position 和 PositionContextVersion；
- 岗位持续对话；
- JD、JR、人才画像、搜索和面试标准生成；
- TalentSource、PositionTalentSource、PublicJobSnapshot 和 TalentInsightVersion；
- 关注公司公开岗位变化及岗位相关人才情报；
- 现有材料和成果按 Position 归属；
- 历史会话保留未归属状态，支持用户手动关联。

### Release 2：候选人和简历智能

- Candidate、CandidateDocument 和 PositionCandidate；
- CandidateAnalysisVersion 和 CandidateEvaluation；
- 单份和批量简历导入；
- 简历信息提取和用户确认；
- 岗位匹配分析和版本；
- 人才挖掘结果加入 Candidate；
- 同一候选人的多岗位复用。

### Release 3：面试和反馈闭环

- 岗位通用及候选人专属面试方案；
- 面试记录和转写文本分析；
- HumanFeedback；
- 同岗位候选人比较；
- 岗位复盘和优选画像新版本建议。

### 后续阶段

- 面试实时转写；
- 跨岗位人才库运营。

北森、OA、猎聘、BOSS 直聘等系统接入不属于本需求的“后续阶段”，而是未来可能单独立项的
独立项目。

## 17. 验收标准

1. 官网岗位可以同步、搜索和查看版本；失败时保留最后有效版本。
2. 用户可以通过对话形成岗位草稿，明确确认后创建 Position。
3. 用户进入岗位即可持续对话，Agent 自动获得正确岗位上下文。
4. 官网 JD 更新不覆盖内部画像、候选人或历史分析。
5. JD、JR、人才画像和评价标准支持生成、修改、比较和版本确认。
6. 上传简历后形成 Candidate 草稿，未经确认不会自动创建人才记录。
7. Candidate 基础材料可以复用到多个岗位，但岗位相对分析互不混用。
8. 每个 CandidateAnalysisVersion 能反查岗位上下文和材料版本。
9. AI 能生成候选人专属面试问题并分析真实面试记录。
10. AI 建议、候选人评价与人工反馈分开保存，重新分析不覆盖历史记录。
11. 一批候选人完成分析后，可以生成岗位复盘和新版优选画像草稿。
12. 跨岗位或跨候选人材料不得进入错误 Agent 上下文。
13. 刷新、断网和 Worker 重启后，长任务及成果可以恢复。
14. 用户可以关注目标公司并看到有来源、有时间的公开招聘快照和变化。
15. AI 可以把关注公司的招聘变化转化为当前岗位画像、搜索和面试建议，并明确标注推断。
16. 采集失败不会清空最后有效快照，也不会被解释为公司停止招聘。
17. 北森事务流程、自动联系、自动淘汰和自动录用在本期均不可达。

## 18. 成功指标

- 用户重复解释同一岗位背景的次数下降；
- JD/JR、人才画像、简历分析和面试方案的完成率；
- 简历分析中能够关联明确证据的结论比例；
- 候选人专项分析复用正确岗位上下文的比例；
- 面试后“未验证能力”被正确识别的覆盖率；
- 用户纠正能够进入后续同岗位分析的比例；
- 关注对象变化被正确关联到相关岗位并产生可执行建议的比例；
- 生成成果可读取、可下载和可追溯比例；
- 跨岗位或跨候选人错误引用事件数必须为零。

AI 分数和点赞率不作为招聘质量的唯一指标。招聘推进率、周期、招聘经理达成率、入职后岗位
适配性和付薪合理性需要外部系统事实，本期不采集、不估算，也不展示。

## 19. 已冻结的产品决策

1. 产品是招聘 AI 智能增强层，不是招聘系统，不替代北森。
2. 招聘工作流可以完整覆盖，但仅建设直接增强 AI 的能力和数据。
3. Position 是用户招聘工作的主线和主要入口。
4. Candidate 是独立、稳定、可跨岗位复用的人才对象。
5. PositionCandidate 承载岗位相对的匹配、证据、面试和评价。
6. 岗位、候选人、简历和 AI 分析是必须建设的正式业务数据，不埋在聊天文本里。
7. 官网岗位同步和对话新增岗位同时支持。
8. AI 分析版本化，人工反馈与模型建议物理分离。
9. 北森、OA、猎聘、BOSS 直聘等需要企业接口的能力本期全部留空，不建设页面、字段、Adapter、
   模拟数据或占位功能。
10. 不建设候选人流程、排期、Offer、入职等北森事务能力。
11. 人才与组织情报是第三项核心智能能力，与岗位智能和候选人智能共同增强 HR Agent。
12. 关注对象和公开招聘快照是正式数据；情报推断版本化，并且不能冒充组织内部事实。
13. 现有官网岗位同步、公开网页研究、钉钉统一登录和既有飞书入口继续复用，不视为新增外部
    业务系统对接。
14. 任何未来外部系统接入都必须单独立项，不在本需求中预埋推测性设计。
