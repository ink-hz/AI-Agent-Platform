# AI 工程笔记图示增强与第二批生产系统文章设计

## 背景与目标

AI 工程笔记已经上线五篇首批文章，阅读页继续采用左侧分类树和右侧 Markdown 正文。首批内容完成了旧组织痕迹清理、事实核验和主题收敛，但图示处理过度克制：线上五篇共有八张 Mermaid，全部没有显式 `style` 或 `classDef`；多处本应表达层级、职责或阶段关系的内容仍是纯文本箭头。平台的 Mermaid 渲染器能够显示颜色，缺失发生在内容重写阶段，不是渲染能力限制。

本轮工作先建立统一的图示语言并补强首批五篇，再逐篇迁移“生产级 AI 系统”第二批文章。核心目标不是完成固定篇数，而是让每篇文章同时具备准确、易懂、可验证和有技术深度的内容质量。五篇第二批文章是候选范围；任何文章在完整精读后价值不足、重复过多或无法可靠核验，都可以继续保留为草稿或取消发布。

作者继续统一为“苍渊”，座右铭继续为“博观而约取，厚积而薄发。”。新文章的 `publishedAt` 使用在当前平台实际首次上线日期；首批文章补图后只更新 `updatedAt`，不伪造新的首次发布日期。

## 读者与写作层次

文章面向公司全部技术人员，同时保留资深研发需要的工程深度：

1. 导语和主线正文说明问题、系统边界与关键决策，产品、测试、运维和研发均可理解。
2. 进阶章节再展开运行时、性能、算法、协议、安全或评估细节。
3. 每篇明确说明适用条件、不适用条件和主要权衡，不使用绝对化结论。
4. 结尾给出可执行的检查清单，并链接本专题前后文章。
5. 不为统一形式强行套模板；结构服从文章的问题和证据。

## 图示语言

### 图示类型选择

- 系统边界、组件关系、数据流、状态机和多阶段流程优先使用 Mermaid。
- 协议取值、公式、短命令、短状态序列和需要原样复制的内容继续使用文本或代码块。
- 正文可以独立表达核心结论；图用于压缩关系和降低理解成本，不能承担唯一解释责任。
- 超宽、超密或同时表达多个问题的图必须拆成“全景图 + 局部流程图”。不恢复一张图包含六个以上独立主题的旧式大总图。

### 配色规则

图示采用两套互补规则：

1. **分层分区色**用于系统全景图。不同 `subgraph` 使用低饱和浅色背景，帮助读者识别应用、智能、数据、控制和运行等层级。
2. **语义色**用于普通流程图。同一种角色在全部文章中保持一致颜色，让颜色本身传递信息。

语义色基线如下：

| 语义 | 填充色 | 边框色 | 典型对象 |
| --- | --- | --- | --- |
| 输入与用户 | `#DBEAFE` | `#60A5FA` | 用户目标、请求、事件 |
| 模型与推理 | `#EDE9FE` | `#A78BFA` | LLM、规划、判断、生成 |
| 数据与上下文 | `#CCFBF1` | `#5EEAD4` | 文档、状态、向量、上下文 |
| 策略与控制 | `#FEF3C7` | `#F59E0B` | 权限、审批、路由、门禁 |
| 工具与执行 | `#DCFCE7` | `#4ADE80` | 工具、服务、任务执行 |
| 成功与证据 | `#D1FAE5` | `#10B981` | 验证结果、完成证据 |
| 风险与失败 | `#FEE2E2` | `#F87171` | 拒绝、错误、越权、降级 |
| 中性基础设施 | `#F3F4F6` | `#9CA3AF` | 网关、队列、存储、通用组件 |

Mermaid 源码优先使用可复用的 `classDef`，避免为每个节点散落独立颜色。显式文字颜色和边框需要在浅色背景上保持清晰对比。颜色不能替代节点名称、连线标签或图前后的文字说明，确保色觉差异用户仍能理解。

### 阅读与渲染标准

- 每张图只回答一个明确问题；全景图只给边界，细节进入后续图。
- 标签使用短语，不把完整段落塞进节点。
- 桌面宽度和手机宽度都要实际检查；手机上缩小后无法阅读的图必须拆分，而不是依赖无限横向滚动。
- 图前说明“要观察什么”，图后解释关键路径、权衡或异常分支。
- Mermaid 必须使用平台当前真实版本渲染，并经过现有 SVG 清洗链路；不能只做语法扫描。
- 渲染失败时继续保留现有源码回退，但发布门禁不允许已知失败的图进入生产。

## 首批五篇图示补强

### Agent 工程学习地图

- 新增一张分层学习全景图，把最小循环、工具、运行时、知识、治理、评估和多 Agent 表达成有依赖关系的路线。
- 新增一张能力递进图，说明同一个调查任务如何从固定输入演进到可恢复、可审批、可评估的生产任务。
- `tool_call / ask_user / final` 等协议值继续使用文本块，不强行图形化。

### 企业级 Agent 系统架构

- 为现有系统全景图、状态机和 UI/API/工具关系图增加分层或语义色。
- 把运行循环补成独立流程图，突出模型提案、确定性校验、策略决策、工具执行和完成验证。
- 把信任决策补成独立流程图，明确主体、委托、组织策略、资源授权、动态风险、审批绑定和审计证据。

### Claude Code 架构分析

- 为现有受控行动循环和通用 Agent 架构图增加语义色与分层色。
- 新增一张基于当前官方公开事实的能力架构图，覆盖入口、上下文、权限、内置工具、MCP、Hooks、验证和可观测性。
- 旧稿中的生产力时间线、未来预测、内部实现推断和过时界面清单不直接恢复；只有当前官方资料支持的内容才进入新图。

### RAG 检索工程

- 新增一张索引链路图，覆盖解析、分块、Embedding、词法/向量索引、元数据和可选图结构。
- 把查询理解、权限过滤、召回、融合、重排、上下文组装、生成和引用校验补成完整查询链路图。
- 为现有 HNSW 与混合检索图增加语义色；公式、样例证据片段和简短权衡继续保留文本形式。

### AI Native 辅助架构设计

- 为现有材料到评审的协作流程图增加阶段颜色。
- 新增一张人和 AI 的责任边界图：AI 负责提取、对比、推演和检查，人负责目标、约束、取舍、批准和责任承担。
- 不用颜色营造“AI 自动完成架构设计”的错觉，关键决策节点必须明确保留人在环。

上述补图是设计目标，不是机械数量指标。完整复读时如果两张图可以更清楚地合并，或新增图与正文重复，应选择更少但更有效的表达。

## 第二批文章边界

### LLM 应用系统架构

负责从用户请求到可靠回答的应用层全景：入口、模型网关、任务编排、上下文、RAG、工具、输出验证和反馈。只解释推理服务、云原生运行、可观测性和身份治理在全景中的位置，不展开它们的实现细节。

### LLM 推理服务工程

只讨论模型运行与性能：Prefill/Decode、吞吐与延迟、连续批处理、KV Cache、量化、投机解码、模型路由、容量规划和成本权衡。具体产品能力必须按当前官方资料核验，不沿用旧代码样例和版本结论。

### AI × 云原生

只讨论 AI 工作负载的生产基础设施：CPU/GPU 资源特征、调度、弹性、镜像与模型制品、灰度发布、隔离、故障恢复和成本边界。普通 Kubernetes 百科不迁入；每一节必须回答 AI 工作负载与普通 Web 服务有何不同。

### LLM / Agent 可观测性

连接传统信号与 AI 特有质量：日志、指标、Trace、Token、延迟、成本、模型与提示版本、工具调用、检索证据、答案质量、评估集和反馈闭环。Prometheus、OpenTelemetry 等通用知识只保留服务于这条 AI 观测链路的部分。

### Agent 身份与最小权限

聚焦人、Agent、工具和服务之间的身份链：工作负载身份、用户委托、Token Exchange、能力与资源授权、动态风险、审批、凭证隔离和审计。删除云厂商与产品罗列，不把传统 IAM 百科原样迁入。

## 精读、核验与重写流程

每篇文章必须独立完成以下流程：

1. 从头到尾阅读全部源稿，记录章节价值、重复内容、过时事实、旧组织痕迹和可复用图示；不能用关键词规则代替精读。
2. 与已上线文章和本批次其他文章逐节比对，先确定边界，再写正文。
3. 对产品能力、标准、协议、性能机制和安全结论使用迁移当天的官方文档、规范或一手论文核验。
4. 以新的问题结构重写，区分公开事实、工程推断和作者建议；不保留旧日期、旧公司、旧站、项目规模和营销化表达。
5. 先以 `draft: true` 写入，完成正文、图示、引用、交叉复读和真实渲染后才改为 `draft: false`。
6. 每篇独立提交、独立评审。完成一篇可以发布一篇，不等待凑齐五篇。

如果精读结论是源稿不能支持一篇高质量 AI 文章，应停止该篇，而不是靠扩写通用知识凑数。

## 数据流与页面影响

本轮不改变已经确认的左树右文阅读界面、首页入口、文章 API、作者展示或 Markdown 数据流。颜色和结构定义放在文章 Mermaid 源码中，由现有 `ArticleMarkdown` 和 `MermaidDiagram` 渲染。

只有真实渲染检查发现平台组件无法可靠保留 `classDef`、颜色、文字或连线时，才允许对 Mermaid 渲染组件做最小修复；此类修复必须先有失败测试，不能借机重新设计阅读页。

## 发布顺序与失败处理

1. 先定义图示契约和真实 Mermaid 渲染测试。
2. 逐篇补强首批五篇并交叉检查颜色语义，全部通过后作为一次视觉质量更新上线。
3. 第二批从《LLM 应用系统架构》开始，逐篇精读、重写、评审和上线。
4. 后续文章只有在上一篇发布质量稳定后才开始，不设置完成五篇的时间承诺。

单篇失败不会阻止其他已通过文章继续在线。Markdown 解析、Mermaid 渲染、事实核验、外链、移动端阅读或内容评审任一门禁失败时，该篇保持草稿或不更新生产版本。已发布旧文章的补图若失败，则保留线上旧版本，不发布半完成内容。

## 测试与验收

- 内容校验器通过，旧品牌、旧组织、旧时间和一级标题扫描无遗漏。
- 首批五篇的所有既有与新增 Mermaid 均能由项目锁定的 Mermaid 版本真实渲染，并通过 SVG 清洗；页面不进入源码回退状态。
- 图示使用约定的语义类或分层样式，颜色、节点名称和连线标签含义一致。
- 每张图在桌面和手机宽度下实际检查；无文字截断、重叠、不可辨认缩放或无边界横向扩展。
- 每张图有相邻正文解释；移除图片后文章主结论仍然完整。
- 第二批文章逐篇通过主题准入、边界去重、一手来源、外链和内容复读门禁。
- 作者、座右铭、发布日期、更新时间、目录顺序和深链接正确。
- AI 笔记相关后端测试、前端 Markdown/Mermaid 测试、全量前端测试和生产构建通过。
- 每次上线后验证生产 release、运行容器内容、服务健康和认证后的实际文章页面。

## 非目标

- 不新增 CMS、搜索、评论、点赞、作者主页或编辑后台。
- 不重新设计左侧目录树和文章阅读布局。
- 不把所有文本块机械转换成 Mermaid，也不为每篇规定必须达到的图数或字数。
- 不迁移通用云原生、可观测性、IAM 百科；目标内容必须以 AI 系统问题为中心。
- 不恢复缺乏当前证据的预测、产品清单、内部实现推断或旧项目叙事。
