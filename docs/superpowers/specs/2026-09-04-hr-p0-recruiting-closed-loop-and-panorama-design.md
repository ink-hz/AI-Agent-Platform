# HR 智能工作台 P0 招聘闭环与全景分析设计

日期：2026-09-04  
状态：待用户书面复核  
范围：HR 智能工作台 P0

## 1. 背景

HR 智能工作台已经具备对话、附件、岗位、岗位上下文、候选人、任务和成果等部分底座，但当前交付按技术模块拆散，业务用户仍无法稳定完成一条招聘主流程。P0 不再以“页面或数据表是否存在”为完成标准，而以一次真实招聘工作能否从需求走到候选人专属面试题为标准。

P0 同时建设独立的“全景分析”能力。全景分析负责持续收集关注公司的公开招聘事实并生成版本化 AI 分析；岗位 Agent 按需读取这些结果，辅助岗位定义和招聘决策。全景分析不是单个岗位下的附属页面，也不直接覆盖正式岗位数据。

## 2. P0 目标

P0 必须跑通两条相连的主线。

### 2.1 招聘业务闭环

```text
招聘对话
→ 澄清和生成岗位需求
→ 生成、修改 JD 与 JR
→ 用户确认并加入岗位库
→ 在该岗位上传简历
→ 确认候选人
→ 分析候选人与岗位的匹配情况
→ 生成候选人专属面试题
→ 复制或下载正式成果
```

### 2.2 招聘全景分析

```text
关注公司
→ 收集公开招聘数据
→ 保存来源与岗位快照
→ AI 聚类和趋势分析
→ 形成版本化全景分析
→ 岗位 Agent 按需检索并引用
→ 用户确认是否据此修订 JD/JR
```

两条主线通过“按需检索”连接。岗位不复制全景分析，也不要求用户手动挂载整份报告。

## 3. 产品原则

1. 对话是主工作面，不以表单向导代替 Agent 协作。
2. 正式岗位、候选人和成果必须成为业务对象，不能只埋在聊天文本中。
3. AI 可以生成草稿和建议，用户确认后才写入正式岗位或候选人数据。
4. 页面切换、创建岗位、打开资料或执行任务不得卸载当前对话。
5. 公开事实、AI 推断和未知项必须明确区分。
6. 全景分析只提供决策输入，不自动覆盖已确认的 JD、JR 或岗位结论。
7. 失败应局部隔离；全景分析、附件或候选人子能力失败不能使主对话不可用。
8. P0 优先跑通真实使用闭环，不增加 ATS 流程、审批、排期、Offer 或入职能力。

## 4. 页面信息架构

HR 工作台一级导航包含：

- 对话；
- 岗位；
- 全景分析；
- 人，仅在独立候选人页面达到可用标准后显示。P0 中候选人从岗位内进入。

### 4.1 对话与岗位页面

用户可以从普通对话直接描述招聘需求，无须先创建岗位。Agent 在信息不足时自然追问；信息足够后，在消息流中输出“岗位方案”成果卡。

岗位方案至少包含：

- 结构化岗位需求；
- 对外 JD；
- 内部 JR。

岗位需求、JD 和 JR 可分别继续对话修改、复制和下载。用户点击“确认并加入岗位库”后才创建正式岗位。创建成功后，当前 Conversation 原地绑定新 Position，不跳转、不清空消息、不重复执行。

正式岗位页面继续使用宽对话画布。顶部只显示必要的岗位名称、状态和资料入口；“岗位资料”抽屉承载岗位需求、JD/JR、候选人、材料和成果，不能压缩主对话。

附件和图片入口固定在对话输入框下方。用户在岗位对话上传简历后，每份简历形成独立候选人草稿。候选人确认后加入当前岗位，并提供两个主要动作：

- 分析与当前岗位的匹配情况；
- 生成候选人专属面试题。

分析结果和面试题既出现在当前消息流，也登记为当前岗位和候选人的版本化成果。

### 4.2 全景分析页面

全景分析是与“对话”和“岗位”并列的独立功能。

页面采用简单的主从结构：

- 左侧显示关注公司和分析历史；
- 中间显示当前公司或公司组的分析报告；
- 顶部提供添加关注公司、立即更新和选择分析范围；
- 报告内展示研发方向、招聘变化、地域分布、关键能力、重点团队、研发资源投入信号、来源与更新时间；
- 用户可以从每条结论查看支撑它的原始岗位和公开来源。

全景分析不建设复杂采集后台。任务调度、去重和失败详情仅在用户需要时展开。

## 5. 数据与版本

### 5.1 全景分析数据

全景分析保存三层数据。

1. 公开事实：关注公司、岗位标题、原始岗位描述、地点、发布时间、来源链接、采集时间和内容哈希。
2. 分析版本：技术方向聚类、招聘数量变化、重点能力、组织投入信号、趋势判断和未知项。每次重跑产生新版本，不覆盖历史。
3. 岗位引用：岗位 Agent 本轮实际检索到的分析版本、引用片段和来源，随回答及相关成果保存。

同一来源内容哈希未变化时不得重复创建等价快照。内容发生变化时保留新旧版本和观测时间。

### 5.2 岗位与成果数据

对话中的招聘需求先形成 PositionDraft。岗位需求、JD 和 JR 是可独立修改和确认的版本化模块。确认入库时创建 Position，并把已确认模块写入该岗位的首个正式上下文版本。

后续由全景分析或对话产生的修改只能形成新草稿。用户确认后创建新版本，旧版本继续可查。

### 5.3 候选人与分析数据

每份简历独立形成 CandidateDraft。用户确认后创建或关联 Candidate，并通过 PositionCandidate 表达该候选人与当前岗位的关系。

岗位匹配分析必须锁定：

- Position；
- 已确认的岗位上下文版本；
- Candidate；
- 使用的简历版本。

匹配分析至少输出：

- 匹配结论与维度；
- 来自简历的支持证据；
- 能力差距；
- 风险；
- 尚未验证的未知项。

“材料未证明”必须标记为未知或待验证，不能表述为候选人不具备。

## 6. Agent 协作与检索

岗位 Agent 在生成或修订岗位需求、JD/JR、人才画像、搜寻策略，或回答竞品招聘问题时，可按需检索全景分析。

检索流程为：

1. 根据当前岗位名称、技术方向、地点和用户点名的公司形成检索条件；
2. 优先读取最新有效分析版本，并校验采集时间；
3. 返回相关结论、公开事实、AI 推断、未知项、来源和分析版本；
4. 在 Agent 回答和生成成果中保存本轮实际使用的引用；
5. 只生成岗位修改建议，等待用户确认。

岗位 Agent 不应在每次对话中自动联网采集。没有可用分析结果而用户确实需要最新情报时，Agent 提示用户前往全景分析更新，或在用户明确同意后发起更新任务。

## 7. 成果交付

以下成果必须支持查看历史版本、复制和下载：

- 岗位需求；
- JD；
- JR；
- 全景分析报告；
- 候选人岗位匹配分析；
- 候选人专属面试题。

候选人专属面试题必须支持下载为排版后的 PDF。PDF 至少包含：

- 岗位名称；
- 候选人名称或验收用匿名标识；
- 生成时间和使用的岗位版本；
- 每道题的验证目标；
- 针对该候选人的出题原因；
- 递进追问；
- 有效证据或优秀回答要点；
- 风险信号；
- 面试记录区域。

PDF 由后端基于正式成果版本生成，使用稳定文件名并登记为 Agent Artifact，以便网页、管理平台和后续会话继续下载。下载权限沿用岗位和候选人授权，不能暴露对象存储内部路径。

## 8. 执行状态与失败处理

长任务在消息流中展示用户可理解的真实阶段，例如：

- 正在理解招聘需求；
- 正在生成 JD/JR；
- 正在采集公开岗位；
- 正在分析招聘方向；
- 正在解析简历；
- 正在分析岗位匹配；
- 正在生成面试题和 PDF。

不得向业务用户暴露内部队列名、原始状态码或无上下文的“执行已中断”。

失败处理规则：

- 单家公司采集失败不影响其他公司的采集和分析；
- 联网失败时保留最近一次有效分析，标明时效并允许单项重试；
- AI 分析失败时保留已采集的公开事实，可单独重跑分析；
- 单份简历解析失败不回滚同批其他简历；
- Agent 中断时保留用户消息、附件和已产生结果；仅在尚未产生外部副作用或有效输出时安全自动重试一次；
- 附属数据读取失败只影响对应抽屉或卡片，不得使主对话变为只读；
- 身份或工作台整体服务失败时只显示一个统一状态，恢复后继续保留当前岗位、对话和输入草稿。

## 9. P0 验收

验收使用一个专用测试账号、至少三家公开招聘信息可核验的关注公司，以及三份合规脱敏简历。mock 简历只存在于测试夹具和验收账号，不作为产品功能。

必须通过以下端到端流程：

1. 在普通 HR 对话输入一个信息不完整的招聘需求；
2. Agent 追问并生成结构化岗位需求、JD 和 JR；
3. 用户修改一项要求，成果更新且旧版本仍可查看；
4. 用户确认入岗位库，Position 创建成功，当前对话不刷新、不丢消息；
5. 在全景分析添加至少三家关注公司，采集公开岗位并生成带来源的综合分析；
6. 回到原岗位对话，要求 Agent 参考全景分析修订 JD/JR；回答显示实际引用的分析版本和来源；
7. 用户确认修订，创建新的 JD/JR 版本，旧版本继续可查；
8. 上传三份脱敏 mock 简历，其中两份成功，一份通过测试注入故意失败；成功项分别形成草稿，失败项可单独重试；
9. 确认两个 Candidate，分别生成岗位匹配分析；
10. 为至少一名 Candidate 生成专属面试题；
11. 下载该面试题 PDF，核对岗位、候选人、版本、题目、追问、评价要点和风险信号；
12. JD、JR、全景分析、匹配分析和面试题均可复制、下载，刷新后仍存在；
13. Flywheel 中对应 assistant 消息存在且内容非空，新 Trace 的答案非空；
14. 管理平台可以查看消息、来源、附件和生成成果，并可预览或下载允许访问的文件。

硬性质量门槛：

- 全流程不要求重复粘贴岗位背景；
- 岗位、公司和候选人之间的错误引用数为零；
- 不出现“未记录 Agent 回答”、无意义的“执行已中断”或同屏多个重复“不可用”；
- 普通对话快速出现首个可见反馈，长任务持续显示执行进度；
- 外网采集失败不阻断岗位、简历和面试题流程；
- 所有正式成果均能从业务页面重新打开；
- 面试题 PDF 可下载且内容与当前成果版本一致。

## 10. 自动化测试边界

自动化测试至少覆盖：

- 从 Conversation 创建 PositionDraft、确认 Position 并原地绑定 Conversation；
- JD/JR 分模块版本、确认和并发冲突；
- 全景数据去重、版本创建、来源追踪和过期结果回退；
- 岗位 Agent 只读取匹配且有权访问的全景分析；
- 单份和批量简历独立解析、失败隔离和幂等重试；
- PositionCandidate 上下文完整性和跨岗位隔离；
- 匹配分析的证据、差距、风险和未知项契约；
- 候选人专属面试题成果及 PDF 生成、授权和下载；
- 页面切换、抽屉开关、岗位确认和任务状态更新不卸载当前对话；
- 流式阶段展示、断线恢复、安全自动重试和非空 assistant 消息；
- 端到端验收夹具不出现在生产产品入口。

## 11. 明确不在 P0 的范围

- 招聘网站企业账号登录、简历获取、沟通或投递；
- 候选人阶段流转、审批、排期、Offer 和入职；
- 自动联系候选人；
- 多候选人横向比较；
- 面试录音、转写和面试记录分析；
- 从历史会话批量回填岗位或候选人；
- 自动用全景分析覆盖已确认岗位；
- 在产品中生成 mock 候选人或 mock 简历；
- 与本闭环无关的恶意文件扫描等平台级增强。

## 12. 实施边界

实施复用现有 Conversation、Attachment、Position、PositionContextVersion、Candidate、PositionCandidate、Task、Artifact 和 Flywheel 底座，不重新实现 HR 工作台。

开发按两条可并行但需共同验收的工作流推进：

1. 全景分析的数据采集、版本化分析、页面和岗位检索接口；
2. 招聘闭环的对话草稿、岗位确认、候选人分析、面试题成果与 PDF。

两条工作流必须通过第 9 节同一条端到端验收链后，P0 才算完成。任何单独页面、接口或模型存在都不能作为完成依据。
