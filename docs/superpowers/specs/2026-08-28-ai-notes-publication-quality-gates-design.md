# AI 工程笔记统一发布质量门禁设计

## 背景与目标

AI 工程笔记已经形成稳定的阅读形态：Agent 大脑首页提供入口，笔记页采用左侧分类树与右侧 Markdown 正文，作者统一为“苍渊”，图示由 Mermaid 真实渲染。现有文章已经经过逐篇精读、旧组织痕迹清理、事实核验、图示补强与视觉调整，但质量要求分散在设计文档、文章专属测试和人工执行记录中。继续迁移时，如果仍靠会话记忆或每篇文章手动补测试，规则会逐渐遗漏或互相矛盾。

本设计把已经确认的要求固化为长期发布制度。核心原则是：

1. `draft: true` 允许内容持续打磨，但仍必须具备可解析的目录、文件和 frontmatter 结构；
2. `draft: false` 必须通过统一机器门禁，任何失败都阻止发布和部署；
3. 机器只判断能够客观证明的条件，内容价值、事实边界、重复度和视觉质量继续由精读审查负责；
4. 不以固定字数、固定图数或关键词密度代替质量判断；
5. 下一篇《LLM 应用系统架构》成为统一门禁的第一个新增文章样本。

## 方案选择

### 方案一：只维护写作规范

优点是改动最小，缺点是依赖作者和发布者记忆，无法阻止遗漏。随着文章数量增加，规范会变成建议而不是制度，因此不采用。

### 方案二：继续为每篇文章编写专属测试

文章元数据、目录顺序和关键图示可以被精确锁定，但大量规则会在测试中重复。新增文章需要主动登记到多个列表，最容易发生“文章已上线、真实渲染测试没有覆盖”的情况，因此只保留少量文章特有合同，不作为统一保障机制。

### 方案三：统一发布策略、自动发现测试、模板与人工复核结合

这是采用的方案。后端发布校验器承担统一机器规则；前端测试自动发现全部正式文章并使用锁定版本的 Mermaid 真实渲染；标准文档和模板降低创作偏差；人工清单承担无法可靠自动化的语义判断。现有部署验收会运行后端全量测试、前端全量测试和生产构建，因此无需新增 CMS 或独立发布系统。

## 质量模型

### 第一层：结构门禁

结构规则对草稿和正式文章都生效，继续由 `AiNotesRepository` 负责：

- 内容根目录只包含命名合法的分类目录；
- 分类必须存在合法 `_index.md`；
- 文章文件采用有序英文 slug 文件名，不允许符号链接和未知文件；
- frontmatter 字段完整、类型严格、slug 合法；
- `publishedAt` 不早于 `2026-05-25`，不晚于校验当天；
- `updatedAt` 不早于 `publishedAt`。

草稿可以含未清洗正文、未完成引用和暂时不能渲染的 Mermaid，但不能破坏仓库结构或 frontmatter 解析。草稿不会进入 API 目录和正式文章自动渲染集合。

### 第二层：正式发布机器门禁

统一发布策略只对 `draft: false` 生效，至少检查：

- `author` 必须精确等于 `苍渊`；
- `motto` 必须精确等于 `博观而约取，厚积而薄发。`；
- 正文不得包含一级 Markdown 标题，页面标题由 frontmatter 唯一提供；
- 正文不得包含原生 HTML；
- frontmatter 与正文不得命中旧组织、旧站点或已确认的遗留标记；
- Markdown 链接和图片地址只允许相对地址、`http`、`https` 与 `mailto`；
- 每个 Mermaid 块必须同时包含非空 `accTitle` 与 `accDescr`；
- 正式文章全集中的 Mermaid `accTitle` 和 `accDescr` 分别唯一；
- Mermaid 若使用分组背景，不得把 `#F8FAFC` 等中性灰色作为大分组画布；默认分组画布由平台统一设置为 `#FFFFFF`；
- Mermaid 可以保留 `#F3F4F6` 中性基础设施节点，节点语义色与白色画布是两条不同规则；
- 每个 Mermaid 至少包含 `classDef` 或显式 `style`，但不强制文章达到固定图数。

统一规则由后端发布校验器执行，而不是散落在五篇文章的专属测试里。错误继续对外收敛为通用的 `AiNotesContentError`，避免通过生产错误泄露被拦截的遗留词、路径或正文；测试通过最小失败样例定位具体规则。

### 第三层：真实渲染门禁

前端 Mermaid 集成测试不再维护手写文章文件列表，而是扫描内容目录、解析 frontmatter，只选择 `draft: false` 的文章：

1. 自动提取每篇正式文章的全部 Mermaid 块；
2. 使用项目锁定的 Mermaid 版本和生产 `AI_NOTES_MERMAID_CONFIG` 渲染；
3. 经过与生产一致的 DOMPurify SVG 清洗链；
4. 拒绝渲染错误、`script`、`foreignObject` 和缺失的无障碍元数据；
5. 验证默认分组画布最终输出为白色，而不是只断言配置对象；
6. 自动检查全集标题和描述唯一性。

因此，新增正式文章一旦进入内容目录，就自动进入真实渲染门禁，不需要修改测试中的文章登记表。文章专属测试只保留标题、slug、目录位置和关键架构语义等确实属于该文章的合同。

### 第四层：人工精读与视觉门禁

下列条件不能可靠地由规则证明，必须在每篇文章发布前逐项确认：

- 从头到尾精读全部旧源稿，关键词扫描只能用于精读后的查漏；
- 与已上线文章和后续专题逐节去重，先明确本篇负责与不负责的边界；
- 产品能力、协议、标准、安全与性能结论使用迁移当天的一手资料核验；
- 区分公开事实、工程抽象和作者建议，不恢复旧公司、旧项目、旧日期、营销数字或无依据预测；
- 图前说明观察目标，图后解释关键关系，移除图后正文主结论仍然成立；
- 每张图只回答一个主要问题，过宽、过密或过高时拆图；
- 桌面约 `1440×900` 与手机约 `390×844` 真实检查正文、表格和所有图；
- 检查正文图内嵌阅读、点击大图、滚轮缩放、拖拽、关闭和滚动位置恢复；
- 独立审查 Critical 与 Important 清零后才能正式发布。

人工清单必须写进统一标准文档，但不增加 `reviewed: true` 一类可轻易勾选却无法证明质量的 frontmatter 字段。

## 仓库结构

实现阶段新增或调整以下职责边界：

- `backend/app/ai_notes/publication_policy.py`：正式文章统一机器规则、Mermaid 元数据提取和全集唯一性校验；
- `backend/app/ai_notes/validation.py`：编排目录加载、遗留标记、链接与统一发布策略，保持单一公共入口；
- `backend/tests/test_ai_notes_publication_policy.py`：每条统一规则的最小失败样例与成功样例；
- `backend/tests/test_ai_notes_production_content.py`：只保留真实生产目录、文章特有元数据、目录顺序和关键内容合同；
- `webui/src/components/ai-notes/MermaidDiagram.integration.test.tsx`：自动发现全部正式文章并真实渲染，不维护手写生产文件列表；
- `docs/standards/ai-engineering-notes.md`：作者可读的写作、图示、事实核验和发布清单；
- `docs/templates/ai-engineering-note.md`：不参与运行时扫描的文章起始模板，包含标准 frontmatter、正文骨架和白底 Mermaid 示例。

不在内容目录放置模板或说明文件，避免破坏内容仓库“分类目录之外不允许未知文件”的安全边界。

## 数据流与发布行为

正式发布链路如下：

```text
Markdown 草稿
  -> 结构校验
  -> 精读、重写、事实核验与图示设计
  -> draft: false
  -> 后端统一发布策略
  -> 前端自动发现与真实 Mermaid 渲染
  -> 后端/前端全量测试与生产构建
  -> 独立内容审查
  -> 桌面/手机视觉验收
  -> 受控部署与线上核验
```

任何机器门禁失败时，部署流程在上传和切换生产版本之前停止。人工门禁失败时，文章恢复或继续保持 `draft: true`；其他已发布文章不受影响。不得为了让校验变绿而删除合理的风险说明、引用或语义色，也不得通过放宽统一规则绕过单篇问题。

## 模板内容

标准模板提供以下默认值和提示：

- 标题、slug、description、日期与 tags 的填写位置；
- 固定作者和座右铭；
- 默认 `draft: true`；
- “问题与边界、系统模型、关键机制、失败与权衡、落地检查清单、参考资料”的可删减骨架；
- 使用 `flowchart TB` 的白底 Mermaid 示例，包含唯一 `accTitle`、`accDescr`、固定语义 `classDef` 和白色大分组；
- 提醒作者根据问题选择结构，不机械保留全部章节，也不要求固定图数。

模板是起点，不是文章格式合同。正文结构可以调整，只要统一发布规则和人工质量门禁通过。

## 测试策略

### 后端单元测试

- 每条统一规则先写失败测试，确认旧实现会接受不合格正式文章；
- 同一问题在 `draft: true` 时不触发正式发布规则；
- 作者、座右铭、H1、HTML、Mermaid 元数据、标题/描述重复和灰色分组分别使用最小样例；
- 危险链接和遗留标记继续验证错误不泄露正文；
- 当前五篇文章和新增《LLM 应用系统架构》必须通过全集校验。

### 前端真实渲染测试

- 自动发现结果与后端正式目录数量一致；
- 每个发现的 Mermaid 块都真实渲染并清洗；
- 新增一个未登记文件的测试夹具时，测试能够自动包含它；
- 默认分组最终 SVG 为 `#FFFFFF`，节点语义色仍被保留。

### 发布回归

- 后端 AI 笔记 API、仓库、发布策略和生产内容测试全部通过；
- 前端全量测试通过；
- TypeScript 与 Vite 生产构建通过；
- 部署脚本现有本地门禁继续执行后端全量、前端全量和构建；
- 上线后核对 release、六个核心服务、公网健康检查、文章目录和认证后的真实页面。

## 迁移衔接

当前《LLM 应用系统架构》草稿已经完成全文精读、事实核验、正文重写、三张 Mermaid、独立内容审查和模拟发布测试。统一门禁落地后，需要：

1. 将分支更新到最新白底 Mermaid 版本；
2. 让草稿通过新的统一发布策略和自动发现渲染测试；
3. 完成桌面与手机真实视觉验收；
4. 设置 `draft: false`，独立复审、合并、部署和线上核验；
5. 再开始下一篇，不并行追求文章数量。

## 非目标

- 不新增 CMS、在线编辑器、数据库文章模型、评论、点赞或搜索；
- 不自动评判文章观点是否正确、是否有深度或是否与旧文语义重复；
- 不使用固定字数、固定章节数、固定图数或引用数量作为发布标准；
- 不要求全部图统一为 TB，确有必要的短横向流程可以保留，但必须通过手机视觉验收；
- 不把中性基础设施节点的灰色语义色误判为灰色画布；
- 不改变已确认的首页入口、左侧目录树、Markdown 阅读页和图片查看交互。
