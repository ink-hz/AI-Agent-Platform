# SDK 原生需求工作台设计

## 决定与范围

`https://agent.orbbec.com.cn/sdk/` 直接提供 SDK 团队的日常需求界面。首版覆盖需求列表、筛选、详情、创建、编辑、指派、评审及“我的任务”列表和详情。禅道继续保存需求、任务和操作历史；平台只保存钉钉与禅道账号绑定、原计划来源字段、幂等记录和必要审计。现有 2026 Q4 的 67 条需求原位呈现，不再导入一份页面副本。

页面使用独立的 SDK 布局：简短顶栏、需求与我的任务两个主入口、可检索的列表和清晰的详情区。打开 `/sdk/` 时首先看到真实需求，保留 `/sdk/requirements/{id}` 深链接。平台账号与登录沿用现有钉钉机制。现有完整禅道 IP 入口保留给管理员处理首版未覆盖的功能，但不是日常操作的必经跳转。

## 方案比较

1. **平台原生页面 + 个人禅道 API 会话（采用）**：平台后端按当前员工取得个人禅道会话，以该员工身份调用私网禅道 API。页面源和平台会话保持在平台自己控制的代码内，禅道记录真实操作者。
2. 完整禅道反向代理到 `/sdk/`：禅道的脚本会与平台 API 成为同源；这扩大平台会话受禅道页面脚本影响的范围，因此不采用。
3. 在 `/sdk/` 内嵌独立 IP 的禅道页面：跨站 Cookie 和禅道的框架限制会使登录与交互不可靠，也不能消除 IP 入口，因此不采用。

当前安装的禅道 22.6 已通过只读验证：`apilogin` 返回的个人 `zentaosid` 可作为 `Token: ss_<session>` 调用 API v2；有会话请求读取现有需求返回 200，无会话和无效会话返回 403。此验证没有修改业务数据。

## 身份与权限

每个请求先验证平台会话、目录新鲜度、员工状态与 SDK 准入，再从唯一绑定读取禅道账号。首次进入沿用现有自动开通与绑定逻辑。服务端为该员工取得禅道会话，短时保存在进程内并按员工、账号隔离；会话 ID 和 Token 不返回浏览器、不写日志。过期或禅道拒绝时丢弃会话，重新登录一次。目录硬过期、撤权或停用时停止读取和写入。

后端仅转发固定的禅道 API 路由、字段与当前 SDK 产品 ID。禅道的产品和权限组仍是最终授权边界。创建、编辑、指派、评审均使用个人会话，禁止复用 `sdk-api` 服务账号写入，也不以 `needNotReview=1` 绕过评审。创建时让员工选择评审人；没有评审人的草稿不得自动变为已通过。

## 数据呈现与操作

需求列表使用禅道产品需求 API 的分页数据，显示标题、状态、优先级、提出/录入人、当前负责人、创建和指派日期；可按关键词、状态和负责人筛选。详情显示需求描述、验收标准、来源、评审历史以及关联任务。禅道富文本在浏览器经过白名单净化后显示，不执行来源 HTML 中的脚本。

2026 Q4 来源需求依据禅道 `sourceNote` 中的 `2026年Q4上线版本` 标识形成快捷视图，来源栏目、原责任人、原计划日期和未知提出人从现有 `sdk.plan_story_sources` 读取。界面区分“业务提出人”“禅道录入人”“当前负责人”：源文件没有提出人时明确显示“原计划未提供”，不猜测为导入人。原计划日期只作为来源信息展示，不伪装成禅道实际完成时间。新需求以当前员工为录入人，表单单独填写业务提出人、负责人、优先级、场景和验收标准；负责人必须从有绑定的 SDK 成员中选择。禅道无独立字段的业务提出人由平台保存结构化补充信息，并在禅道来源说明中留可读标识。

创建需求先写入以员工和 `request_id` 唯一的意图，再使用个人会话创建禅道草稿并回读绑定 ID。超时或未知结果进入“待核对”，不能再次盲目创建；详情与列表始终以禅道读回为准。指派与评审在提交前核对需求版本和当前状态，冲突时提示刷新；请求完成后读回确认。我的任务按个人会话读取禅道任务，显示任务名、状态、负责人、开始和截止日期及关联需求。

## 发布与验收

后端测试覆盖身份撤权、个人会话隔离、无效会话重建、权限拒绝、字段映射、创建幂等和不确定结果、评审与指派冲突。前端组件测试覆盖列表、详情、加载与错误状态，以及来源人员和实际人员的区分。使用隔离禅道 22.6 实例做真实 API 场景，核对创建者和评审者为各自员工。生产发布只更新平台 API 与前端镜像，不修改共享 Nginx 配置；发布后通过 HTTP 和资源哈希核对 `/sdk/`、平台健康及行政服务静态资源。最终浏览器交互由业务方按仓库约定验收。
