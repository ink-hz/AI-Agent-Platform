# HR 拆仓方案：参照 AI-ADMIN-Agent，同机独立运行

状态：本方案已按用户后续明确授权于 2026-09-15 完成生产切换；准确运行版本、验证与未验收边界见[同机切换发布记录](../../releases/2026-09-15-hr-same-host-cutover.md)。下文保留实施前设计基线，不据其中将来时描述否定当前状态。本版替代此前的服务边界方案；旧 A–C 实施计划停止，不再据其授权继续施工。

## 1. 目标与边界

把当前 HR 的代码、依赖、测试和发布入口放到 `AI-HR-Agent`，像 AI-ADMIN-Agent 一样，在同一台服务器上独立运行、独立更新。现有 HR 页面和业务行为保持不变。

选择同机独立应用，是因为用户明确要求参照 Admin 的隔离方式。平台安装 HR 包并统一运行不符合该要求；此前新增的跨服务签名代理和 mTLS 体系又超出了本次拆仓需要。两条路线均不继续。

这次的隔离指独立仓库、安装目录、Python 环境、前端构建、服务进程、配置与发布操作。**不把数据库和附件存储重新划成安全隔离域**：继续使用现有数据库、表、角色、加密格式及附件存储访问方式，不借拆仓做权限与数据架构迁移。

同库同角色是本轮已接受的取舍：HR 进程若被攻破，其数据库可达范围与使用同一角色的平台进程相同；本次的代码/进程隔离不构成数据库权限隔离。六条跨 schema 复合外键及其现有 REFERENCES 授权保持不动。

本次不做界面重设计、新建岗功能、通用 SDK、第三个共享仓库、独立数据库、通用服务契约框架、证书管理或逐请求签名。

## 2. 参照的实际部署方式

已核对 Admin 当前仓库代码、平台 Nginx 配置及发布记录，未重新连接生产：

- Admin 有自己的 `/opt/ai-admin-agent`、`.venv` 和 systemd 服务。
- 平台 Nginx 的 `/office/*` 直接转到 `http://127.0.0.1:8011`，业务请求不经平台 API 转发。
- Admin 用用户的现有平台 Session Cookie，向本机 `http://127.0.0.1:8080/api/v1/account` 查询身份。
- Admin 自行处理业务、数据库迁移和发布；平台负责共享登录与入口。

依据：平台 [`agent-domain.nginx.conf`](../../../deploy/cloud/agent-domain.nginx.conf) 的 `/office/` location；Admin 仓库 `src/service_portal/platform_identity.py`、`src/service_portal/identity_provider.py`、`deploy/systemd/ai-admin-office-notification-worker.service`。参考 Admin 的部署和身份接入，不把 Admin 的业务、数据库结构或全部依赖搬进 HR。

HR 的目标路径：

```text
浏览器 → 同机 Nginx
          ├─ /hr/*、/api/hr/* → HR API（127.0.0.1:8012）
          │                    ├─ 提供 HR 前端构建产物及业务接口
          │                    ├─ 查询平台现有 account 接口核实登录
          │                    └─ 访问现有 HR 数据和附件读取逻辑
          └─ 登录、账号、/api/v1/attachments/* → 原平台 API

HR Worker → 原数据库、附件存储和模型提供方
```

`8012` 为拟用回环端口，当前仓库配置中未发现占用；安装前检查服务器实际监听，发生冲突时只调整该服务及对应 Nginx 配置，不改变结构。外部 HTTPS 沿用 Nginx。HR API 与 Worker 分别由 `ai-hr-agent.service`、`ai-hr-worker.service` 管理；前端由 HR API 提供，不另增加 Web 容器。API 启动不顺便启动 Worker。

Vite `base` 固定为 `/hr/`，构建静态文件 URL 为 `/hr/assets/*`；Nginx 增加专用 `^~ /hr/assets/` location 直达 HR，不落入平台 `/assets/`。HR API 先挂载该静态目录，资源不存在返回 404；仅未匹配的 `/hr/*` 页面 GET/HEAD 回退到 `index.html`，支持岗位与情报深链接刷新。`/api/hr/*` 的未知接口返回 404，不回退 HTML；页面保留 position/work 查询参数。

## 3. 代码怎么分

| 内容 | 处理 |
|---|---|
| `backend/app/hr_agent/` 当前 Hannah 业务 | 迁入 HR；循环、工具、工作、预算、租约、恢复、标准和成果一起保留 |
| `backend/app/hr/` 当前岗位、官网版本、资源、来源与研究读取 | 按实际调用迁入；混合文件只取当前仍使用的方法 |
| 当前 HR 前端及必要展示组件、API 客户端 | 迁入 HR，自有依赖和构建；保留 `/hr/`、position/work 参数与登录回跳 |
| 当前知识资料、发布工具、业务测试和两份根文档 | 跟随 HR，记录来源提交；不搬用户私有临时材料 |
| HR 仍依赖的平台底层读取与加密代码 | 定点复制必要实现并调整 import；保留原调用语义，不复制整个平台应用，不重新设计一套接口 |
| 登录、共享附件上传/删除/擦除、平台入口及其他 Agent | 留在平台 |

已核对当前 HR 前端不引用 DirectAgentWorkspace/useDirectWorker，无需搬迁 DirectWorker 底座。平台清理清单包含 DirectAgentWorkspace 的五个 HR 专属死 prop；删除前以全仓调用点和 Marketing 回归确认其未使用。

新 HR 仓库安装、测试和运行不读取兄弟仓库目录，不依赖源码软链接。平台也不安装 HR 业务包。复制的少量底层实现记录来源；实际修改这些共享语义时再同步两边，不建立新的包发布体系。

旧 HR 聊天、旧标准/成果、候选人历史入口、情报归档、MetaBot/DirectWorker 专用链路不迁入、不恢复。09-14 当前岗位闭环已在主线完成；从已完成代码承接，不重开旧计划。

## 4. 三处必须接好的依赖

### 登录与 HR 使用权限

沿用 Admin 的会话接入方式：HR API 读取浏览器的平台 Session Cookie，向固定本机 account 地址核实，成功后使用平台返回的 internal_user_id，不信任客户端自报身份。未登录返回 401，权限不足返回 403，平台不可用返回 503；登录跳转保留原 HR 地址和查询参数。

写请求保留现有 Origin、CSRF 和只读状态限制。account 查询只转送需要的 Session/CSRF Cookie；平台会校验 CSRF Cookie 并回传有效 token，HR 核对非空 token 与 `X-CSRF-Token`，同时校验配置的同源 Origin。不得把“account 查询成功”当成自动允许写入。

目前平台中央 `control_plane/authorization.py` 用 `_HR_POSITION_ROUTES` 放行路由，再由 router dependency 检查 HR 权限和 owner，并从该表派生 `_HR_POSITION_MUTATION_ROUTES` 统一阻止目录硬过期写入。分流后中央层不再被经过：HR 应用从实际注册的 HR 路由集中派生非 GET/HEAD/OPTIONS 集合，由一个统一入口执行会话、Origin/CSRF 和 hard_stale_read_only 写阻断，返回 503；各业务 router dependency 继续核对 HR 使用权与 owner。不要在各写路由手抄同一逻辑；对全部已注册写路由做硬过期 503 参数化回归。只注册当前实现，未实现路径自然 404；这是防御职责迁移，不是默认出现漏洞，也不恢复旧路由清单。

登录不等于获得 `hr-bot` 使用权。API 和无浏览器会话的 Worker 继续使用现有 `resolve_agent_use_decision_v41` 校验持久化 owner 的 HR 使用权限；保留恢复、发送前复核与对象归属检查。Worker 不保存浏览器 Cookie。现有只读行为按读写分别保留，不让普通 GET 误走模型发送授权。

这里不新增身份协议、mTLS listener、签名断言或平台业务转发代理；复用 account 与现有数据库授权逻辑即可。

### 数据库与加密

继续连接原 PostgreSQL，保留 `platform_hr`、`platform_hr_agent`、原表名、角色与授权、ID、外键、密文、版本、预算和租约。现有跨 schema 查询、附件源锁和 lane/drain 函数原样使用。本次不应用旧实验分支的 108 权限迁移，不转移表所有权，不新增 HR owner/migrator/API/Worker 四套角色，也不在 HR 仓库重放平台 001–107 建库历史。

现有迁移由平台已有流程管理；启动只检查依赖，不运行 DDL。常规 HR 代码更新只发布 HR；未来确需改 schema 时提交对应迁移并协调一次数据库升级，不将“所有未来变更完全独立”作为本轮承诺。

102–105 的 lane/drain 闸门仍在平台 `platform_control`，切换/排空由平台侧数据库操作控制。HR 常规代码可独立发布，但不能通过纯 HR 发布修改该协议；本轮明确接受这个耦合。

必要的 ContentCodec/Keyring 实现保持当前字节格式。保留两仓相同的合成黄金向量及旧版本读回测试，避免复制实现发生漂移；不重新加密已有业务数据。

### 附件与下载

上传、删除、擦除和公共下载仍走平台原 `/api/v1/attachments/*`。HR 材料解析继续使用现有按 owner 查询元数据、核对删除/过期状态、读取准确对象版本和校验摘要的实现，使用已有配置，不把这些调用批量改为 HTTP。

岗位资源和附件关系仍由 HR 校验。现有 HR 资源票据入口在确认岗位归属后，携带当前会话与必要 CSRF 信息调用平台已有的附件 ticket 接口；票据由平台生成并由平台原下载接口消费，不在两个进程中各建一份票据内存。Worker 的正文读取沿用原存储访问，不借用用户下载票据。

因此这里只需接现有下载票据接口，不新增此前 resolve/read/authorize/capabilities 一整组附件服务。若实际接口回归暴露原下载路径缺陷，只修该缺陷并单独记录，不能借题扩成附件重构。

## 5. 怎么搬、怎么切

1. **按主线重新整理迁入代码。** 用当前平台 `master` 的准确提交作基线；对已创建的 HR 仓库逐项保留有效搬迁和测试，撤出旧实验的通信、权限和部署改造。调整入口、import、构建及上述必要适配，不重写业务。
2. **在本地验证同机独立运行。** 使用 HR 自己的依赖，验证页面资源可提供、当前 API 能工作。暂不改变线上入口，也不新增一套测试平台。
3. **安装并切换一次。** 获得发布授权后，准备同机 HR 目录、venv、前端产物、配置和两个 systemd 服务；Nginx 将 `/hr/` 与 `/api/hr/` 指向 HR。平台解除 HR 路由装配，停止原 HR Worker，再启用新的 Worker；沿用既有租约与排空步骤，不改 lane 协议。任何时刻只保留一个正式 HR 执行来源。
4. **收尾。** 平台删去已经迁出的 HR 专属代码与构建依赖，保留入口、必要集成和历史记录。新代码只在 HR 维护；切换前需要的生产修复仍先走平台主线并显式同步。代码归并、发布提交与业务验收分别记录。

发布核对平台与 HR 的准确提交；回退恢复原 Nginx 路由和原 HR 进程，停止新进程。数据库结构与密文未改变，不做数据回滚。不得整分支合并旧实验实现，也不得清除未提交文件或用户材料来“重做”。

验证只围绕拆仓影响：现有 HR 业务回归；真实会话的读取/写入、CSRF、撤权和跨 owner 拒绝；材料上传后解析/下载及不可用状态；幂等提交、准确成果/标准读回；独立 Worker 的启动、停止与一次中断恢复；前端组件测试和构建。使用一次性数据库与自有进程，模型替身明确说明。浏览器和页面验收交用户，未经授权不调用生产业务或发布。

拆仓不改变五工具、逐项标准确认、当前来源和研究界面、真实个人材料处理边界，也不新增计量看板。已有 per-work 用量保持原样。
