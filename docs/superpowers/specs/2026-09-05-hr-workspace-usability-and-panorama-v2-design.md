# HR 智能工作台可用性与招聘全景分析 V2 设计

**日期：** 2026-09-05

**状态：** 用户已确认产品方向，等待书面设计复核

**范围：** HR 智能工作台对话、岗位详情、会话材料与招聘全景分析

**上位设计：** `2026-09-04-hr-p0-recruiting-closed-loop-and-panorama-design.md`

## 1. 设计结论

本轮不再增加新的功能入口，而是把 HR 当天必须使用的工作面做对：

1. 对话始终占据最大、最稳定的工作区域；
2. 会话材料和岗位资料默认收起，从右侧覆盖打开，不挤压、不重载对话；
3. 官网同步岗位直接展示完整官网事实，不用空的“内部岗位理解”冒充岗位资料；
4. 全景分析从少量示例升级为 10 家公司的社招、校招共同情报库；
5. 所有情报都区分公开事实、AI 推断和未知项，并可回到来源证据；
6. 失败局部隔离，未采集不得显示为 0，附属能力失败不得阻断主对话。

本设计细化并覆盖既有设计中与上述结论冲突的页面布局和全景分析展示。岗位、候选人、成果、
附件、Conversation、Turn 和 Agent 执行底座继续复用，不重新建设。

## 2. 当前问题与根因

### 2.1 对话工作面被压缩

当前首页和岗位页的输入区都不足以承载粘贴 JD、候选人材料、面试要求或长篇修改意见。会话材料
以固定右栏存在时还会继续压缩消息区。用户打开岗位资料或切换岗位页签时，也缺少“对话必须保持
原位”的明确产品约束。

### 2.2 官网岗位数据存在，但页面没有使用

运行数据已经保存官网岗位与 `OfficialPositionVersion`。官网版本包含职责、任职要求、地点、类别、
学历、薪资、人数、状态、来源版本和快照时间等字段，后端也已有官网版本列表及详情接口。

当前前端岗位资料抽屉只读取岗位基础摘要，然后直接展示内部 `PositionContextVersion`。因此类似
“DQE 工程师（数采设备）”的真实官网岗位虽然已有完整资料，页面仍只显示标题、部门、地点和
“0 个待确认草稿 / 历史版本 0”，造成“岗位资料丢失”的错误感知。

这不是模型未配置，也不是官网岗位库为空，而是前端数据读取与信息层级错误。

### 2.3 全景分析只搭了壳，没有形成可用情报

现有全景分析缺少明确的公司全集、社招与校招分轨、月度基线、公司横向比较和可核验证据。把单一
公司做成“校招专题”不能回答业务真正的问题：友商在招什么、研发资源投向哪里、产品与业务可能
如何变化，以及这些变化对当前岗位意味着什么。

### 2.4 历史 HR 对话没有充分转化成产品输入

截至本轮复核，本地 Flywheel 中可识别 24 个 HR 会话、190 个 Turn。历史需求不仅包含岗位和面试，
还包含公司招聘情报、薪酬研究、学校与实验室人才来源、技术方向聚类等任务。明确出现的组织包括
联合光电、智元、影石、华为及多所学校和研究机构。

历史对话只作为需求证据和待确认关注池，不直接把所有偶然提及的公司加入重点监控，也不把学校、
实验室与友商混为一类。

## 3. 产品边界

### 3.1 本轮必须完成

- 放大首页和岗位页对话输入区；
- 把会话材料、岗位资料改成默认关闭的右侧覆盖抽屉；
- 保证开关抽屉、切换岗位资料视图时当前对话不卸载、不刷新、不丢输入草稿；
- 读取并展示官网岗位完整当前版本和历史版本；
- 正确区分官网岗位事实与内部岗位理解；
- 建立 10 家公司的共享招聘情报目录；
- 每家公司同时支持社招和校招数据；
- 建立首月基线、月度变化、来源证据和分析版本；
- 支持公司、招聘类型、月份、地点和技术方向筛选；
- 支持岗位明细及分析成果 Excel、PDF 下载；
- 支持岗位 Agent 按需读取相关全景分析结果并保留引用。

### 3.2 不在本轮范围

- ATS 流程、审批、投递、面试排期、Offer 或入职；
- 登录招聘网站企业账号、绕过反爬或获取非公开数据；
- 把网页爬取失败伪装成完整数据；
- 自动用全景分析覆盖已确认的 JD、JR 或岗位画像；
- 为当前少量授权用户建设复杂租户、席位或审批系统；
- 把历史对话中所有公司自动加入重点监控；
- 重新实现 Conversation、附件、Artifact、流式执行或模型调用底座。

## 4. 页面信息架构

一级导航保持简单：

- 对话；
- 岗位；
- 全景分析；
- 人，仅在已有能力可用时显示。

对话仍是 `/hr/` 的默认首页。岗位和全景分析是独立工作场景，不能成为覆盖在对话上的配置后台。

## 5. 对话工作面设计

### 5.1 首页

首页采用“历史会话 + 全宽对话画布”结构。右侧不常驻任何材料栏。

- 空对话输入区桌面高度目标为 320–420px；
- 有消息后的输入区允许自然收缩，但可输入区域不得退回单行或窄条；
- 附件和图片入口固定在输入框下方左侧；
- Enter 发送，Shift+Enter 换行；
- 发送、停止和重试状态不得改变输入区横向结构；
- 不展示“18 个获授权用户”等与当前任务无关、无法解释的产品文案；
- 不使用把模板文字简单填入首句的低价值快捷问题占据首屏。

### 5.2 岗位对话

岗位页默认进入该岗位的持续对话。页面头部只保留：返回岗位、岗位名称、部门/地点、状态、
“会话材料”和“岗位资料”两个入口。

- 岗位输入区桌面高度目标为 160–220px；
- 当前岗位、明确启用的材料和后续成果继续进入同一上下文；
- 创建新对话、打开抽屉或切换资料子视图不得重载现有消息；
- 不在对话上方长期堆放“生成 JD、生成 JR、画像、搜寻策略、面试方案”按钮墙；
- 常用任务如需保留，只能作为输入区附近的紧凑意图入口，并必须触发真实能力；不可用能力不展示。

### 5.3 右侧覆盖抽屉

“会话材料”和“岗位资料”使用统一交互：

- 默认关闭；
- 从右侧覆盖当前页面，不改变对话列宽；
- 桌面端宽度随内容调整，最大不超过可视区，背景保留可识别的对话上下文；
- 点击遮罩或关闭按钮、按 Esc 均可关闭；
- 关闭后焦点回到打开抽屉的按钮；
- 移动端使用接近全屏的底部或侧向抽屉；
- 抽屉内部独立滚动，页面主体仍保持当前位置；
- 两个抽屉互斥，任何时刻最多打开一个。

会话材料抽屉承载本轮启用、已上传材料和生成结果。岗位资料抽屉承载官网岗位、内部理解、候选人、
岗位材料与成果。两者不得再以固定栏挤压对话。

## 6. 官网岗位资料设计

### 6.1 信息层级

岗位资料打开后默认显示“官网岗位原文”，而不是空的内部上下文。

第一层是岗位摘要：

- 岗位名称；
- 部门；
- 地点；
- 官网岗位编号；
- 官网状态；
- 最近成功同步时间。

第二层是完整官网当前版本：

- 岗位职责；
- 任职要求；
- 类别与子类别；
- 学历；
- 用工类型；
- 招聘人数；
- 薪资或官网公开待遇；
- 来源版本、首次/最后观测时间和来源证据。

不存在或官网未公开的字段显示“官网未公开”，不能留成误导性的空白，也不能由模型补写。

第三层是官网历史版本。用户可选择历史时间点查看字段变化，复制岗位原文，或下载当前/指定版本。

### 6.2 官网事实与内部理解分离

“内部岗位理解”作为独立子页或明确分区，包含已确认上下文、待确认草稿和历史版本。官网岗位尚未
形成内部理解时，显示：

> 尚未形成内部岗位理解。可以在对话中让 HR Agent 基于官网岗位继续澄清、生成 JD/JR 或人才画像。

不得再用“0 个待确认草稿”“历史版本 0”作为岗位资料的主要内容。官网版本不需要先转换成内部
上下文，才能被展示或进入 Agent 的岗位基线。

### 6.3 Agent 上下文

岗位对话每次执行自动携带精确的官网当前版本；如已有已确认内部岗位理解，再叠加内部版本。两者的
来源和版本号分别记录：

```text
岗位身份
+ 官网当前事实版本
+ 内部已确认岗位理解（如有）
+ 本轮明确启用的材料
+ 当前会话上下文
+ 本轮用户请求
```

官网版本更新不覆盖内部版本。Agent 可以提出差异和修改建议，但只有用户确认后才能形成新的内部
岗位理解版本。

## 7. 岗位任务的 Agent 智能设计

### 7.1 当前能力判断

现有实现不是完全没有上下文。任务执行前已经能够锁定并注入：

- 精确官网岗位版本及完整官网事实；
- 当前已确认内部岗位上下文；
- 当前 Conversation 摘要和近期消息；
- 用户本轮明确选择的岗位材料，并发放真实附件读取授权；
- 候选人任务中的候选人事实、精确简历版本和人工纠正；
- 任务类型、对象 ID、版本 ID 和输入哈希。

任务结果也可以形成岗位上下文草稿，用户确认后进入新的已确认版本，供后续任务复用。这些能力解决了
跨岗位串数据、附件只显示不读取、恢复后输入漂移和 AI 结果冒充人工确认等底座问题。

但当前 5 个岗位任务主要依靠不同的一句固定提示，共用一份宽泛上下文；全景分析只在用户文本出现
显式触发词或公司名时检索；候选人专属面试题也没有把最新匹配分析声明为必需依赖。因此当前状态是
“可靠地给 Agent 一包资料”，尚未达到“针对招聘任务智能组装最相关证据并复用此前成果”。

### 7.2 任务上下文组装原则

每项任务都使用一个可审计的 `HrTaskContextManifest`。它是现有 `position_task_records` 和上下文 Envelope
的契约增强，不另建任务系统，也不复制原始文件；它只记录本轮实际使用的对象、版本、原因和内容哈希。
上下文分为四层：

1. **共同基线：** 岗位身份、官网当前版本、当前已确认内部上下文、会话摘要和当前用户要求；
2. **任务必需输入：** 该任务不能缺少的岗位模块、候选人分析或材料；
3. **相关增强输入：** 根据任务意图检索的全景情报、历史成果和人工反馈；
4. **边界声明：** 未知项、过期信息、未被选择材料和禁止自动覆盖的正式数据。

系统不能把所有历史内容无差别塞给模型。每条被注入的信息必须说明 `source_type`、`source_id`、
`version_id`、`selected_reason` 和 `content_sha256`。任务恢复时复用原 Manifest，不因数据后来变化而
静默换输入。

### 7.3 各任务输入与输出契约

| 任务 | 必需上下文 | 按需增强 | 正式输出 |
| --- | --- | --- | --- |
| 岗位需求 | 官网事实或用户描述、当前会话澄清结果 | 相关材料、明确要求参考的全景情报 | 使命、预期成果、约束、未知项 |
| JD | 岗位使命、官网职责/要求、已确认修改 | 目标受众、公开市场用语、用户选定材料 | 可发布 JD、变化说明、未确认项 |
| JR | 岗位使命、预期成果、当前 JD、能力约束 | 团队补充材料、相邻岗位证据 | 职责、必须/加分/可培养、评价口径 |
| 人才画像 | 使命、JR、能力与未知项 | 相关公司、学校、实验室及全景证据 | 画像维度、优先级、证据、反例、未知项 |
| 搜寻策略 | 已确认人才画像、地点、关键能力 | 全景招聘情报、人才来源池、公开市场信号 | 目标公司/机构、关键词、渠道方向、排除条件 |
| 岗位面试方案 | JR、能力模型、风险和待验证项 | 岗位历史反馈、相关材料 | 结构化能力维度、题目、追问、评价锚点 |
| 候选人匹配 | 精确岗位版本、候选人事实、精确简历版本 | 该候选人的人工纠正 | 证据、匹配、差距、风险、未知、待验证问题 |
| 候选人专属面试题 | 匹配分析最新有效版本、岗位面试标准、候选人材料 | 人工纠正和此前验证结果 | 专属题目、出题原因、追问、强证据、风险信号、PDF |

任务缺少必需上下文时，不应假装生成完整成果。Agent 应在同一对话中提出最少量澄清问题，或明确说明
只能生成哪一部分草稿。系统不得为了让按钮“成功”而退化成普通无上下文回答。

### 7.4 智能检索规则

- 搜寻策略和人才画像默认检索与岗位方向相关的最新有效全景分析，不再依赖用户写出“竞品”关键词；
- JD/JR 仅在用户要求市场对标或上下文明确需要外部证据时检索，避免无关情报污染岗位事实；
- 岗位面试方案优先复用 JR、能力模型和未知项，不默认检索外部公司；
- 候选人专属面试题必须读取当前岗位版本下最新有效匹配分析；没有匹配分析时先生成匹配分析或请求用户
  确认，不得静默跳过；
- 用户点名公司时限定公司范围；未点名时根据岗位技术方向检索，但最多注入经过排序和字节预算限制的
  相关证据；
- 过期情报可以作为最后有效版本使用，但必须携带年龄并在回答中说明。

### 7.5 结构化输出与后续复用

每类岗位任务都有独立结构化输出契约，不能只把整段 Markdown 塞进一个 `text` 字段。用户仍看到自然
语言答案，但系统同时得到可验证的模块数据、引用、未知项和版本关系。

- 任务结果先形成草稿，保留来源 Conversation、Turn、材料、情报版本和模型版本；
- 用户可确认全部或部分模块；
- 确认后生成新的岗位上下文版本，不覆盖历史；
- 后续任务优先读取已确认版本，未确认草稿只在用户明确要求继续修改该草稿时使用；
- 新输出显示“本次实际参考了什么”，让用户能判断 Agent 是否真的使用了岗位、材料、候选人和情报；
- 同一输入、任务和请求 ID 的重试保持幂等，不重复生成业务对象。

## 8. 招聘全景分析 V2

### 8.1 初始公司全集

首批建立 10 家公司的统一情报目录：

1. 联合光电；
2. 速腾聚创；
3. 禾赛科技；
4. 拓竹；
5. 创想三维；
6. 智能派；
7. 知象光电；
8. 先临三维；
9. 思看科技；
10. 智元机器人。

这 10 家公司都必须同时具备社招和校招视角。某家公司没有发现某类公开岗位时，显示“本次未发现”
并列出已检查来源，不得将其解释为该公司没有招聘。

历史对话中出现的影石、华为等公司进入“待确认关注池”；学校、实验室、研究院和专业社区进入单独
的人才来源池，不混入公司榜单。

### 8.2 页面结构

全景分析使用以下主视图：

- **总览：** 10 家公司规模、变化、技术方向和关键异常；
- **社招全量：** 当前有效公开岗位及月度变化；
- **校招全量：** 校招、应届和实习岗位及招聘批次；
- **产品与业务方向：** 从公开岗位证据形成的投入信号与推断；
- **岗位明细：** 可筛选、排序、查看原文和导出；
- **来源证据：** 来源覆盖、采集时间、成功/失败和内容版本。

用户可按公司、社招/校招、月份、城市、岗位族、技术方向和状态筛选。切换视图保留筛选条件。

### 8.3 社招分析

社招至少分析：

- 在招岗位总量与月度变化；
- 新增、内容变化、持续在招和疑似下线；
- 光学、硬件、结构、软件、算法、制造工艺、质量等技术方向；
- 资历、学历、关键技能和地点分布；
- 重点团队或能力集群；
- 可能的产品路线、业务方向和扩张信号。

最后一项属于 AI 推断，必须附支撑岗位、置信说明和替代解释，不得包装成公司已确认战略。

### 8.4 校招分析

校招不是智元单家公司专题。10 家公司都应分析：

- 校招、应届与实习岗位数量；
- 招聘批次、发布时间和可能的截止时间；
- 技术方向与岗位族；
- 专业、学历和院校倾向；
- 城市和工作地点；
- 目标学校、实验室或竞赛线索，仅限公开证据；
- 官网公开薪资或待遇；
- 月度新增、变化和疑似下线；
- 公司间需求结构对比。

不能从岗位学历要求推导候选人的个人属性，也不能把未公开薪资估算成官网事实。

### 8.5 月度基线与变化

首次完整采集形成基线月，不伪造上月同比。第二个月起才能稳定产生：

- 新增岗位；
- 岗位内容变化；
- 连续在招；
- 疑似下线；
- 技术方向占比变化；
- 城市、学历和资历结构变化。

岗位下线至少需要来源消失、重复核验或其他可解释信号，不能因单次采集失败直接判定。历史快照不可
覆盖；内容哈希未变化时只更新观测记录，不重复制造等价版本。

### 8.6 事实、推断与未知

每条报告内容都标记类型：

- **公开事实：** 可回到招聘官网或其他明确公开来源；
- **AI 推断：** 基于一组事实形成的技术投入或业务方向判断；
- **未知：** 来源没有公开、采集未覆盖或证据不足的信息。

报告中的数字必须能回到参与计算的岗位集合；趋势必须能回到两个或更多时间快照；推断必须列出主要
证据。用户应可从结论进入岗位原文和来源链接。

### 8.7 共享与个人选择

公开公司目录、来源配置、岗位快照和基础分析在 HR 授权用户间共享采集结果，避免重复抓取和互相不
一致。用户个人只保存关注、筛选和阅读偏好。

当前阶段沿用现有 HR 访问控制，不建设“18 个席位”或新的复杂租户权限。共享仅发生在 HR 工作台
授权边界内，不向其他 Agent 或未授权用户开放。

## 9. 采集、分析与证据流程

每家公司分别维护经过核验的公开来源，并为来源标记 `social / campus / mixed`。优先级为：

1. 公司官方招聘页面；
2. 公司官方校招页面或官方招聘公众号可公开访问页面；
3. 公司明确授权或稳定引用的招聘平台页面；
4. 其他公开来源，只用于补充且明确标记来源级别。

执行流程：

```text
来源核验
→ 逐来源采集
→ 内容规范化与去重
→ 公司身份、社招/校招和岗位族分类
→ 保存公开岗位快照
→ 计算基线或月度变化
→ 生成版本化分析
→ 发布带证据的报告
→ 供岗位 Agent 按需检索
```

采集任务按公司和来源隔离。一个来源失败不回滚其他成功来源，一个公司失败不阻断其他公司。AI 分析
失败时仍保留已采集公开事实，并允许只重跑分析。

## 10. 岗位 Agent 如何使用全景分析

岗位 Agent 只在任务相关时按需读取，不把整份全景报告塞进每轮上下文。检索条件由当前岗位、技术
方向、地点、用户点名公司和任务意图共同形成。

读取结果必须包含：

- 使用的分析版本和生成时间；
- 参与分析的公司、岗位和月份；
- 相关公开事实；
- 明确标记的 AI 推断；
- 未知项和时效限制；
- 可回溯来源。

如果没有满足时效的结果，Agent 应说明“现有情报截至何时”，并让用户选择是否更新；不得静默使用
过期结果，也不得在普通岗位对话中无提示地发起大规模采集。

## 11. 下载与成果

以下内容支持下载：

- 官网岗位当前版本和指定历史版本；
- 当前筛选条件下的社招/校招岗位明细 Excel；
- 公司或公司组的全景分析 PDF；
- 岗位需求、JD、JR、匹配分析和候选人专属面试题等既有正式成果。

Excel 至少包含公司、招聘类型、岗位、地点、岗位族、技术方向、状态、首次/最后观测时间、来源 URL
和证据状态。PDF 展示分析口径、时间范围、事实、推断、未知项和主要来源。

下载由后端生成稳定成果并登记为 Artifact，不暴露对象存储内部路径；网页、管理平台和后续会话可以
在授权范围内继续预览或下载。

## 12. 状态与错误设计

- 主对话可用时，岗位资料、材料、候选人或任务状态接口失败不得把账号变成只读；
- 不再同屏重复多个“暂时不可用”；每个抽屉只显示自己的局部状态和重试；
- “未采集”“采集失败”“本次未发现岗位”和“确认没有岗位”是不同状态；
- 全景页面始终保留最近一次有效结果，并显示数据时间、失败来源和重新采集入口；
- 对话运行中展示来自 MetaBot 的真实中间阶段和已产生内容；
- 不向用户展示无上下文的“执行已中断”、内部任务名或原始错误码；
- 仅在恢复旧 Session、尚未产生外部副作用或有效输出时安全自动重试一次；
- 附件冲突、重复上传和 409 应恢复或复用幂等记录，不让用户反复选择文件。

## 13. 可访问性与响应式

- 正文字号和对比度达到内部长期阅读要求，不使用大面积浅灰小字；
- 所有主要交互可通过键盘完成；
- 点击目标不小于 44px；
- 抽屉具有焦点管理、Esc 关闭和可读标题；
- 375px 宽度无横向滚动；
- 移动端附件入口、发送按钮和下载入口始终可触达；
- 长内容区域拥有明确且可工作的滚动容器。

## 14. 验收标准

### 14.1 对话与抽屉

1. `/hr/` 首屏对话输入区达到约定高度，附件入口位于输入框下方；
2. 岗位对话输入区达到约定高度；
3. 会话材料和岗位资料默认关闭，打开时不改变对话宽度；
4. 打开、关闭抽屉及切换资料子页后，当前消息、滚动位置、输入草稿和已选附件不丢失；
5. Enter 发送、Shift+Enter 换行、上传、停止、失败重试、复制、反馈和下载正常；
6. 对话能显示真实流式内容或中间处理阶段，不长时间停留在无反馈状态。

### 14.2 官网岗位

1. 用真实 DQE 官网岗位验收，页面可见职责、要求及官网已有的其他完整字段；
2. 官网版本、内部岗位理解和待确认草稿分区明确；
3. 没有内部理解时使用准确空状态，不再让用户误以为官网资料为 0；
4. 官网历史版本可查看、复制或下载；
5. 岗位对话的执行记录能够证明使用了精确官网版本。

### 14.3 任务智能

1. 每项任务保存本轮 `HrTaskContextManifest`，可核对实际使用的对象、版本、原因和哈希；
2. JD、JR、人才画像、搜寻策略和岗位面试方案分别使用独立输入与输出契约；
3. 搜寻策略和人才画像在存在相关有效情报时自动检索，不依赖用户写出触发词；
4. 候选人专属面试题锁定同一岗位上下文版本下的最新有效匹配分析；
5. 用户选择的材料获得真实读取授权，未选择材料不进入任务；
6. 每项结果可见“本次参考”摘要，并能回溯官网版本、上下文、材料、候选人分析和情报来源；
7. 输出草稿经用户确认后进入新版本，下一项任务真实复用该确认版本；
8. 缺少必需输入时 Agent 澄清或降级为明确的部分草稿，不返回貌似完整的无依据成果。

### 14.4 全景分析

1. 页面可见全部 10 家公司；
2. 每家公司都有社招和校招来源状态，不以智元替代整体校招；
3. 首次采集建立基线且不展示虚构同比；
4. 第二期快照能正确识别新增、变化、持续在招和疑似下线；
5. 总览、社招、校招、产品与业务方向、岗位明细、来源证据均可使用；
6. 公开事实、AI 推断和未知项在页面和下载成果中可区分；
7. 任一结论可回溯到参与计算的岗位与来源；
8. Excel 和 PDF 可下载，内容与当前筛选及分析版本一致；
9. 单家公司或来源失败时，其余公司仍完成，页面保留上次有效数据；
10. 岗位 Agent 能按需读取相关分析，回答中记录实际使用的版本与证据。

### 14.5 回归边界

1. 已有 HR 对话、附件、生成成果和岗位数据不丢失；
2. 不修改 Office、FAE、VOC、Marketing 或其他 Bot；
3. 不修改共享 Nginx；
4. 管理平台仍可查看允许访问的消息、附件、来源和成果；
5. 所有改动通过前后端单元、契约、集成和浏览器端到端验证后才能发布。

## 15. 实施优先级

按业务可用性排序，不按数据表排序：

### P0-A：今天能够稳定对话

- 放大输入区；
- 会话材料与岗位资料覆盖式抽屉；
- 对话不卸载；
- 流式反馈、滚动、上传冲突和错误状态回归。

### P0-B：已有官网岗位真正可用

- 前端接入官网版本接口；
- 展示完整当前版本、来源和历史；
- 正确区分官网事实与内部理解；
- 岗位执行注入精确官网版本；
- 为岗位任务建立按任务区分的输入选择与结构化输出契约。

### P0-C：招聘闭环继续跑通

- 对话生成岗位需求、JD、JR；
- 用户确认入岗位库；
- 上传测试简历并形成候选人；
- 生成匹配分析和候选人专属面试题 PDF；
- 证明后续任务真实复用此前已确认成果，专属面试题真实复用匹配分析。

### P0-D：全景分析达到业务可看标准

- 10 家公司目录与经核验来源；
- 社招/校招全量基线；
- 分析、证据、筛选和下载；
- 岗位 Agent 按需读取。

P0-A 与 P0-B 完成后即可先进行业务试用，但 P0-C 和 P0-D 未通过前，不能宣称 HR 智能工作台完整
需求已经完成。

## 16. 发布约束

发布只涉及 Platform 的 HR 应用和明确需要的 HR 数据迁移/任务，不得修改其他应用或共享 Nginx。
发布必须遵守生产磁盘与 Release 纪律，包含发布前后 `df -B1 / /data`、staging 清理、当前与两个回滚
版本、镜像保留、HTTP 验收和跨应用修改声明。
