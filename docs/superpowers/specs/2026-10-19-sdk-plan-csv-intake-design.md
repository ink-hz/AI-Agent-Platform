# SDK 年度任务计划 CSV 接入设计

日期：2026-10-19。适用来源：用户提供的 2026 年 SDK 任务计划 CSV。首批源文件仅保留在本地工作区，不提交原文到代码仓库。

## 目的与边界

现有 SDK 工作台把经过场景、设备和验收标准定义的需求写入禅道，再由平台评审、拆任务和登记打包测试证据。年度 CSV 是任务计划：67 条任务分布在 17 个栏目下，另有 2 条仅作栏目标题；多数任务没有场景、设备和验收标准。该表不能直接作为已定义、已评审的禅道需求，也不能因“开发中”文字自动进入发布流程。

首版接入应让有 SDK 权限的员工能在 `/sdk/` 查看原始计划、按栏目与优先级筛选、打开来源行，并把选中条目整理成正式需求草稿。提交正式需求仍须填写现有四个必填字段，经用户确认后调用当前需求创建链路；禅道 ID 只在写入成功或对账完成后生成。原始表的责任人姓名只是来源文本，不自动映射企业身份或授予角色。GitLab 事件继续不接入。

## 方案比较

1. **独立的计划接入区（采用）**：平台控制库保存原始批次和逐行快照，提供导入预览、列表及逐条转需求。来源与正式需求可追溯，缺字段时仍可先使用计划。代价是增加两张表和一组受权接口。
2. **CSV 直接批量创建禅道需求**：实现快，但会把任务标题误当成业务需求；用自动生成的验收标准会污染评审与发布门槛，因此不采用。
3. **仅离线生成整理表**：现在已可交付校验后的整理 CSV，但团队无法在平台协作、标注或追踪转化，不能满足“平台直接用起来”。作为上线前过渡材料保留。

## 数据与接口

- 上传上限 2 MiB，接受 UTF-8 或 UTF-8 BOM 的 CSV；表头前十列必须依次是`平台,任务,责任人,版本,开始时间,结束时间,优先级,风险点,完成情况,备注`，后续列只允许空值。不能解析、重复表头、超限、无任务或多于 1000 条非空行时整个文件拒绝，返回确定错误，不写半批。
- CSV 逻辑记录从第 2 条编号，同时保留原文件起始物理行号；有“平台”的行更新当前栏目，空平台行沿用当前栏目；任务为空的非空行记录为分类标题。保留十列原文、完整栏目文本、两个位置编号和来源文件 SHA-256。换行和同名任务不合并；不得从任务名称猜测设备、验收标准、完成状态或企业责任人。
- `sdk.plan_imports` 存批次、上传者、文件名、摘要、条目数、时间；`sdk.plan_rows` 存批次内行号、类别、栏目、原始列和后续关联的禅道需求 ID。导入在一个事务内完成。相同文件摘要再次上传返回已有批次；不同内容即使文件名相同也生成新批次。旧批次可追溯，不自动删除或覆盖。
- API 使用现有企业会话、SDK 角色、同源 Origin 与 CSRF。`contributor` 可上传与查看；`reviewer`、`release_manager` 可查看；平台 owner 管理成员但不默认获得内容读取权。上传者身份由服务端确定，不接受客户端传来的 actor。列表分页、逐行详情均按 SDK 权限校验。
- “转为需求”在页面预填标题与来源备注，但场景、设备/平台和验收标准仍需人工填写。提交使用既有幂等请求 ID 与禅道对账机制。绑定源行与正式需求的步骤须支持重放，并在禅道结果不确定时等待对账，不重发创建请求。相同源行不能绑定多个需求。
- 展示时明确标注“年度计划原始条目／尚未形成正式需求”；优先级、原计划状态和责任人原样显示，空值显示“未填写”。筛选只影响阅读，不改变源记录。前端不把原始备注作为 HTML 渲染。

## 验收

先用用户这份 CSV 的脱敏夹具验证 67 条任务和 2 条栏目行、17 个栏目、跨空行继承、同名任务、BOM、单元格内换行及空字段。接口验证重复上传幂等、越权、CSRF、文件大小与格式拒绝、事务回滚，以及正式需求创建/对账后准确绑定。生产发布后用真实员工会话做最小上传和读回，记录批次摘要与条目数；浏览器页面验收由用户完成。没有生产禅道与服务账号时，只能开放原始计划阅读，正式需求写入必须保持关闭；完整 SDK 发布仍须单测、真机和审批证据。
