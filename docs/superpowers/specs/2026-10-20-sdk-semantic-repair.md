# 2026 SDK 需求来源修复

## 已确认的原因

年度计划的十列被原样存入 `sdk.plan_rows`，但转入禅道时只把任务标题、优先级和 HTML 来源表写入需求。禅道的 `openedBy` 是导入服务账号，不是业务提出人；`assignedTo` 全为空。原表没有提出人列。原表的开始、结束时间只出现在正文，禅道需求本身没有计划起止日期列。部门准入之前只包含应用 SDK 组，而目录中的 3D 传感技术研发中心包含 301 名在职员工、19 个部门。

## 修复契约

1. 以原文件 SHA、逻辑记录号及每条需求正文的导入标识精确连接 67 条已存在需求，不按行号或标题模糊猜测，不新建重复需求。
2. 十列均解析为结构化来源数据；日期按原值和 ISO 日期并存，优先级只映射明确的高、中、低。提出人单独保留为未知，导入账号继续作为审计创建者。`责任人` 是接收/执行责任人，不当作提出人。
3. 仅对单人、无疑问符、在当前中心目录中唯一匹配的责任人建立个人禅道账号并原生指派。多人、别名、问号和重名进入待确认清单，保留原文，不擅自挑选。预建账号无组和产品权限；本人首次从钉钉进入时校验目录身份、绑定预建账号并开通访问。
4. 在控制库持久化每条需求的来源字段、匹配状态、原计划时间及禅道 ID。禅道现有正文继续展示原计划时间；需求创建时间不被改写。原文件的“开发中”不改变禅道需求流程状态。
5. 研发中心作为唯一默认准入部门，子部门由目录闭包覆盖。离职、停用和移出范围仍按现有访问同步收回权限。

## 验证和回滚

修复前备份控制库、禅道库及原权限策略。先生成只读匹配报告，核对 67 条唯一对应和待确认原因；再逐条预建账号和指派，每条读回。中途失败可按导入标识续跑。抽查单人、多责任人、缺日期及含日期需求；验证中心内、中心外的准入以及既有手工绑定账号。发布只替换平台 API，不改 Nginx 或行政服务。
