# HR 运行底座重构：设计与迁移边界

## 决策与产品边界

用户已批准整体重构。目标采用统一的持久执行底座，而不是继续维护 HR 专用的第三套任务系统。直接对话确定性路由到 HR Bot，不额外调用模型规划；复杂协作才使用 Brain 规划。现有 Mission 是迁移适配层，不是目标运行模型。

核心验收场景：普通对话 → 岗位需求/JD/JR → 确认入库 → 简历 → 匹配分析 → 面试问题 → PDF 下载。聊天是主界面，岗位提供版本化上下文。官网职责和要求、用户明确启用的材料、候选人范围和情报引用必须在执行前形成可追溯的上下文清单。

全景情报保持本地 code + GPT 采集分析、生产只导入并读取的边界；原始证据、Markdown 分析、分层摘要与来源独立保存。此次不增加线上爬虫、立即更新按钮、ClamAV 或新的业务访问限制。

## 现状证据与限制

- 2026-09-07 观察到 execution job 已 completed，而对应 Mission delegated、Run queued、Turn accepted，尚无 assistant 消息。该样本不是整体失败率。
- 同批 Relay 事件有 `agent.thinking_summary` 和最终 `agent.result`；旧 `MissionRepository.apply_relay_events` 的私有白名单不接受前者，导致整批事务回滚。这是可用真实 PostgreSQL 重放验证的协议不一致。
- 当前 SSE GET 会调用事件投影写库；页面仅在流结束或报错后读快照，连接存活但不推进时无法自行发现答案。
- 当前直接执行把附件就绪当成文字回答的前置条件；终态投影还把引用/附件绑定与回答放在同一事务，附件异常能回滚文字回答。
- V1 在 API 内运行；V2 worker 的模型步骤、adapter reconciliation 和 reaper 也存在串行耦合。迁移到 V2 不等于这些问题自然消失。
- 飞书原生 MessageBridge 与网页 API 入口不同；本地测试通过不等于飞书已经验收。
- 岗位表行数含用户范围副本，不能作为独立官网岗位数；候选人等统计在核实查询权限前不作为全局数量结论。

## 目标边界

```text
网页 / 飞书入口
  → 幂等接收 Turn + 冻结上下文 + 持久任务
  → 独立执行 Worker → HR Bot（直接模式无规划调用）
  → 持久事件 / 单一终态 / 非空回答
       ├─ 网页读取：快照为准，SSE 提供低延迟通知
       ├─ 成果登记：附件与引用独立重试，不回滚文字
       └─ 飞书投递：独立 outbox，回执与执行成功分开记录
```

Turn 是用户操作身份，Attempt 是执行身份，Delivery 是交付身份。恢复已有结果不重跑模型；重跑只能创建新 Attempt/Turn 并保留失败证据。模型超时、连接故障和渠道投递失败不能混为一种状态。

## 分段迁移（不能把第一段宣称为完整重构）

1. **结果链路拆分**：先使现有持久结果可靠进入对话，建立成果投影的独立持久恢复记录，解除网页对 SSE 成功的依赖；这是本次实施计划的范围。
2. **执行所有权迁移**：抽取独立直接执行入口，复用 V2 的租约、事件游标、超时回收和 adapter，不伪造模型响应或 tool call。API 不再负责执行推进；模型调用、adapter 收口、投影各自独立调度。迁移开关只覆盖 HR，新旧执行器不能同时领取同一 Turn。
3. **读模型与业务上下文收口**：SSE 纯读取；岗位任务和普通对话使用同一提交契约，冻结官网版本、材料和候选人范围。业务成果登记由 assistant 结果驱动且可重放。
4. **飞书适配与切换**：明确平台身份和旧会话映射，原生入口接入同一 Turn/Attempt；渠道投递使用持久 outbox。发送给业务前遵守既有确认范围，不自动重发历史业务消息。

每段可单独验证，但仅在四段及真实业务闭环验收全部通过后称“重构完成”。不以服务 healthy 或 mock 测试替代业务验收。

## 第一段不变量

- 接受合法 Relay 事件的连续游标；公共投影仍使用严格白名单，不泄露原始日志或私有推理。
- 一条持久终态最多生成一条回答和一组完成事件；进程重建后可重放。
- 已验证的非空文字回答先提交。附件未就绪/绑定失败不使文字 Turn 回滚或失败。
- 成果投影任务与回答同事务创建；独立事务执行，重试次数和下次时间持久化，失败项目不能阻塞其他项目。
- 成果绑定继续验证 owner、conversation、task、agent 和就绪状态；拆分事务不降低授权校验。
- 快照轮询只读、不重发消息；SSE 卡住也能发现完成。组件卸载/切换会话要取消请求和定时器。
- 材料列表失败不能阻止已有对话和回答加载。
- 不修改生产数据，不重新执行业务任务，不改其他应用或共享 Nginx。

## 验证与上线约束

第一段使用本地临时 PostgreSQL 重放真实协议形状，验证游标、回答唯一性、附件失败隔离、持久重试与进程重建；前端模拟悬挂 SSE，验证仍能读到答案且无重复 POST。回归原有对话/附件/HR 任务测试并构建前端。

上线需另行完成：当前版本与回滚目标确认、备份和新增迁移验证、HR 定向切换、真实非空回答/文件下载/Trace/Flywheel/飞书回执验收。遵守用户磁盘纪律：`df -B1 / /data`、根盘至少 25GB、预计至少 20GB、发布后不超过 75%，staging 仅 `/data/staging/<application>/<deployment_id>/` 且精确 trap 清理；只留当前和两个回滚，不动其他应用。
