# HR Agent 第一阶段岗位智能工作台设计

**日期：** 2026-09-04

**状态：** 已获产品方向授权，等待 TDD 实施计划

**上位需求：** `2026-09-03-hr-position-lifecycle-workbench-requirements.md`

## 1. 设计结论

第一阶段面向用户交付完整的“岗位智能 + 人才与组织情报”，不是只有岗位列表的数据壳。
内部按 R1.1、R1.2、R1.3 顺序建设，但三个里程碑完成后作为同一期产品交付：

1. R1.1 岗位主线：存量岗位进入、岗位持续对话、材料和成果归属；
2. R1.2 岗位智能：岗位上下文版本、JD/JR、人才画像、搜索与面试标准；
3. R1.3 人才情报：关注对象、公开岗位快照、变化和岗位策略建议。

本产品只建设直接增强 AI 理解、分析、生成、证据和复盘能力的数据与交互。它不是 ATS，
不替代北森，不建设招聘审批、流程阶段、排期、Offer、入职、自动联系、自动淘汰或自动录用。
北森、OA、猎聘、BOSS 直聘等外部业务系统全部留空，不建设占位页面、模拟接口或预埋字段。

## 2. 用户价值与成功闭环

第一阶段必须让用户完成以下闭环：

```text
官网岗位 / 历史岗位 / 新岗位需求
  → 进入统一岗位工作台
  → 持续对话并使用明确的岗位材料
  → 生成和修订 JD、JR、人才画像、搜索与面试标准
  → 用户确认形成新的岗位上下文版本
  → 关注公司、学校、研究机构或专业社区
  → 获取公开岗位事实和变化
  → 生成有证据的人才与组织情报
  → 将建议应用为新的岗位上下文草稿
  → 用户确认后进入下一版岗位上下文
```

用户不需要理解 Conversation、Turn、Run、Trace、Adapter、数据库主键或内部版本号。版本号只在
比较、追溯和冲突处理时以自然语言出现。

## 3. 页面信息架构

采用岗位主线型三栏工作台。

### 3.1 岗位入口

左侧提供：

- 全部岗位；
- 官网同步；
- 内部岗位；
- 待确认岗位；
- 岗位名称或完整 J 编号搜索；
- “新建岗位”入口。

中心区域展示岗位卡片和同步健康，不展示招聘漏斗、阶段、负责人绩效或 ATS 状态。
官网状态和内部状态分别显示：官网状态是事实，内部状态仅为 `draft / active / archived`。

### 3.2 岗位工作台

进入 Position 后：

- 左栏：返回岗位、该岗位的 Conversation、新建岗位对话；
- 中栏：`对话 / 岗位上下文 / 人才情报 / 成果`；
- 右栏：当前岗位材料和生成成果，默认可折叠；
- 默认页仍为持续对话，不先展示复杂仪表盘。

第一阶段不显示候选人一级入口。候选人结构化对象在第二阶段完成前，不制作空页面或灰色按钮。
现有简历分析、候选人搜索和候选人专属面试题仍可作为普通 HR 对话任务使用，但不会在第一阶段
形成正式 Candidate 主档。

## 4. 岗位进入规则

### 4.1 官网岗位

`hr-jd-sync` 当前注册表中的全部岗位幂等投影为正式 Position：

- Platform 为每个岗位生成不可变 `position_id`；
- 完整 J 编号只作为 `official_site` 来源标识，不作为 Platform 主键；
- 官网标题、地点、部门、JD、内容哈希、状态和观测时间按版本保存；
- 官网更新只改变官网事实，不覆盖内部岗位上下文；
- 同步失败保留最后有效版本，并显示最后成功时间。

### 4.2 历史 HR 对话

历史 Session 已经恢复，本阶段不重放 Turn、不改写消息、不伪造历史回答。

执行一次只读识别：

- 出现唯一、完整且能核验的 J 编号时，关联对应官网 Position；
- 内部岗位、旧岗位或名称存在歧义时，生成 PositionDraft；
- 一个历史会话明显包含多个岗位时，只生成多个带来源证据的草稿，整个会话保持未绑定；
- 同名岗位不自动合并；
- 用户可以确认新建、合并到已有岗位或忽略草稿；
- 所有识别结果保留来源 Conversation、消息序号、规则版本和处理时间。

### 4.3 新岗位草拟对话

用户无需先填表。新需求先进入岗位草拟对话，Agent 生成 PositionDraft。用户明确确认后，系统在
一个事务内创建 Position、确认草稿并绑定当前 Conversation。未确认的草稿不成为正式岗位，
不进入岗位材料和岗位上下文。

## 5. 核心对象

### 5.1 Position

保存不可变 `position_id`、来源类型、基础岗位事实、官网来源引用、官网状态、内部状态、创建与
更新时间。岗位名称可以重复或变化。

### 5.2 PositionDraft

保存从新对话或历史对话提取的岗位提议、未知项、来源证据和状态：
`proposed / confirmed / merged / dismissed`。它不是正式 Position，也不能承载候选人和已确认结论。

### 5.3 PositionConversationBinding

一个 Position 可以有多个 Conversation；一个 Conversation 最多绑定一个 Position。

- 既有岗位的新 Conversation 创建时立即绑定；
- 草拟 Conversation 在用户确认建岗时绑定；
- 历史单岗位 Conversation 可以在识别或人工确认后绑定；
- 多岗位历史 Conversation 保持未绑定；
- 误绑定通过带审计记录的纠正操作处理，不能静默覆盖。

### 5.4 PositionContextVersion

岗位上下文由结构化内容和可阅读摘要组成，至少覆盖：

- 岗位使命与预期成果；
- 当前 JD 和内部 JR；
- 必须、加分和可培养能力；
- 优选人才画像；
- 搜索关键词、目标组织和相邻人才来源；
- 筛选与面试评价标准；
- 已确认岗位经验；
- 未知项和待验证假设。

AI 只能创建草稿。用户确认后生成不可修改的新版本，并记录它替代的版本。官网 JD 变化只产生
冲突提示，不自动重写岗位上下文。

### 5.5 PositionMaterialBinding 与 PositionArtifactBinding

附件字节继续由现有 Attachment Service 保存，不复制文件。

- 用户上传文件默认属于 Conversation；
- 用户明确执行“设为岗位材料”后，才建立 PositionMaterialBinding；
- 用户可以停用岗位材料，停用不会删除原附件；
- Agent 只能读取当前 Position、当前 Turn 明确启用且仍有效的材料；
- 在已绑定岗位的 Conversation 中生成的 JD、JR、画像、人才地图和面试方案，自动登记为岗位成果；
- 成果继续使用现有 Artifact 与 ArtifactVersion，保存来源 Conversation 和 Turn。

### 5.6 TalentSource 与 PositionTalentSource

TalentSource 表达可跨岗位复用的公司、学校、实验室、研究机构或专业社区。
提到组织名称不会自动长期关注；用户确认后才建立 PositionTalentSource，记录与岗位的关系、理由、
优先级、公开身份、批准的公开来源、最近核验时间以及是否启用定期摘要。

### 5.7 PublicJobSnapshot 与 TalentInsightVersion

关注公司可产生不可覆盖的公开岗位快照。快照包含来源 URL、采集时间、岗位事实、内容哈希和采集
结果。相邻快照形成新增、修改、疑似下线和重新出现差异。采集失败不会生成空快照，也不会把岗位
标记为下线。

TalentInsightVersion 分别保存：

- 公开事实；
- AI 推断；
- 证据和来源时间；
- 未知项和置信限制；
- 对当前 Position 的画像、搜索和面试建议。

建议不会直接修改 PositionContextVersion，只能生成待确认草稿。
用户可以为已确认的关注对象开启定期摘要。定时任务只核验批准的公开来源；没有新快照或有意义
变化时不生成摘要、不制造通知。关闭关注只停止后续任务，不删除历史证据。

## 6. 对话上下文组装

第一阶段完成后，HR Agent 每次岗位对话的输入顺序为：

```text
当前 Position 基础事实
+ 当前已确认 PositionContextVersion
+ 与当前问题相关的已确认 TalentInsightVersion
+ 本轮显式启用的 Position/Conversation 材料
+ 当前 Conversation 的有效摘要和近期消息
+ 用户当前请求
```

上下文必须附带不可混淆的 position_id、context_version_id 和材料 ID。若岗位绑定、上下文版本或
材料授权无法验证，本轮执行直接失败并给出可恢复提示，不能降级为无岗位上下文继续生成。

## 7. Agent 行为和旧规则调整

现有 HR Bot 继续禁止把候选人、简历、用户对话和模型结论写入 FAQ、知识库、官网 JD 注册表、
岗位校准文件或共享训练语料。

`role-calibration` 的旧约束需要调整：

- 从“当前会话只能对应一个岗位”改为“Platform Conversation 最多绑定一个 Position”；
- 既有已确认岗位校准只读导入为 PositionContextVersion，并保留原 J 编号、版本和确认时间；
- 导入完成后 Platform 成为岗位上下文事实源；旧本地校准状态先只读保留，验证一致后再单独退役；
- Agent 只通过 Platform 结构化接口创建草稿、请求确认和读取当前版本，不直接读写数据库文件；
- 用户确认、部分确认和纠正语义继续沿用，点赞、沉默和继续讨论仍不构成确认。

## 8. 服务边界和数据流

新增 Platform HR 业务域，负责 Position、草稿、上下文版本、岗位归属和人才情报。它复用而不复制：

- Platform Conversation/Turn：持续协作和长任务；
- Attachment Service：文件、预览、下载、授权和保留；
- ArtifactVersion：生成成果版本；
- Conversation feedback：点赞、倒赞、文字反馈和管理复审；
- HR MetaBot Runtime：分析、生成和公开网页研究；
- `hr-jd-sync`：官网事实采集与状态判断。

官网投影和公开研究结果必须通过有身份、幂等、可审计的结构化写入进入 Platform。浏览器不直接
访问 AgentOps 文件，Platform 也不在用户请求线程中读取任意运行时目录。

## 9. 主要产品操作

- 查看、筛选和搜索岗位；
- 查看官网同步健康与岗位事实版本；
- 开始岗位草拟对话；
- 确认、合并或忽略岗位草稿；
- 在岗位内新建和继续 Conversation；
- 将会话材料设为岗位材料或停用；
- 生成、比较和确认岗位上下文；
- 查看、预览和下载岗位成果；
- 关注或取消关注人才来源，并开启或关闭定期变化摘要；
- 请求核验公开岗位并查看变化；
- 生成情报分析；
- 将情报建议应用为岗位上下文草稿。

取消关注只停止后续采集，不删除已经用于岗位决策的历史快照和分析。

## 10. 并发、错误和恢复

- 所有确认、合并、绑定和版本创建使用乐观版本或幂等键；
- 两个页面同时确认同一草稿时，只有一次创建 Position；
- 两人同时修改岗位上下文时，后提交者看到差异并重新确认，不能覆盖新版本；
- 官网同步失败保留最后有效版本；
- 公开研究部分失败保留已核验结果，显示覆盖范围并允许恢复；
- 附件仍在处理、隔离、过期或被删除时不得进入 Agent 上下文；
- Worker 重启、浏览器刷新或断网不终止真实任务；
- 历史识别可以安全重跑，相同规则版本和来源消息不会产生重复草稿；
- 所有失败状态使用用户语言，不展示内部 Trace 或数据库错误。

## 11. 权限、隐私和证据

- 继续使用 Platform 现有登录、Owner 边界、CSRF、附件授权和审计能力；
- Position、材料、成果、关注对象和情报读取必须经过同一用户/组织边界；
- 不从姓名、照片、学校或公司直接推断受保护属性或能力；
- 公开可见不等于允许无限收集，不建设无边界职位聚合器；
- 事实、用户材料、公开证据、AI 推断和未知项在存储与界面上分开；
- 第一阶段不创建 Candidate，不把人才线索悄悄持久化为候选人。

## 12. 验收标准

1. 官网注册表中的现有岗位全部幂等进入 Position，重复同步不产生重复岗位。
2. 历史唯一 J 编号会话能够正确关联；多岗位和歧义会话不会被错误绑定。
3. 用户可以确认、合并或忽略历史 PositionDraft。
4. 新岗位可以通过自然语言形成草稿，确认后一次性建岗并绑定原 Conversation。
5. 一个 Position 可以有多个 Conversation，一个 Conversation 不会同时属于多个 Position。
6. 用户上传材料不会自动成为岗位公共材料；显式设置后才可被其他岗位对话启用。
7. 岗位成果可预览、下载、查看来源 Turn 和历史版本。
8. JD、JR、画像、搜索与面试标准可以生成、修改、比较并经用户确认形成新版本。
9. 官网 JD 更新不会覆盖内部上下文，冲突会被明确提示。
10. Agent 执行使用正确的岗位上下文版本，跨岗位材料引用事件为零。
11. 用户可以关注目标公司等人才来源，并查看公开来源与最近核验时间。
12. 相邻公开岗位快照能正确识别新增、修改、疑似下线和重新出现。
13. 网络或采集失败不会清空最后有效快照，也不会被解释为停止招聘。
14. 情报分析区分事实、推断和未知项，并能生成待确认的岗位调整建议。
15. 定期摘要只在产生新快照或有意义变化时生成，无变化时不会制造通知。
16. 刷新、断网和 Worker 重启后，长任务和成果仍能恢复。
17. 第一阶段页面不存在北森、OA、第三方招聘平台、候选人流程或其他占位功能。

## 13. 内部实施里程碑

### R1.1 岗位主线

建立 HR 业务域、Position/PositionDraft、官网投影、历史识别、Conversation 绑定、材料与成果归属，
完成岗位入口和岗位持续对话。

### R1.2 岗位智能

建立 PositionContextVersion、确认与版本冲突处理、结构化 Agent 上下文注入、JD/JR/画像/搜索和
面试标准成果，以及既有岗位校准的只读导入与切换。

### R1.3 人才与组织情报

建立 TalentSource、PositionTalentSource、PublicJobSnapshot、变化计算、TalentInsightVersion、
公开研究恢复，以及从情报建议到岗位上下文草稿的确认闭环。

三个里程碑均通过后才称为产品第一阶段完成。每个内部里程碑必须可以独立回滚，不得依赖未实现的
外部系统或候选人对象。

## 14. 明确推迟

以下能力进入第二或第三阶段：

- Candidate、CandidateDocument 和 PositionCandidate；
- 批量简历结构化导入和跨岗位候选人复用；
- CandidateAnalysisVersion 和 CandidateEvaluation；
- 候选人专属面试方案的结构化归属；
- 面试记录结构化分析、HumanFeedback、多候选人比较和岗位复盘。

现有 HR Agent 仍可在 Conversation 中完成相关分析和文件交付，不因结构化能力尚未上线而退化。

## 15. 发布边界

本设计授权产品和代码开发，不自动授权生产发布。生产发布必须单独执行磁盘门禁、应用隔离、
回滚保留、HTTP 验收和发布报告；不得修改其他应用或共享 Nginx。
