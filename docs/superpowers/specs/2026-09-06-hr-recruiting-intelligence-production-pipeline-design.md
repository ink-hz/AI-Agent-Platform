# HR 招聘情报后台生产管线与工作台消费架构

**日期：** 2026-09-06

**状态：** 待确认

**适用范围：** HR 招聘全景分析、岗位工作台、HR Agent 情报上下文

**优先级：** P0，可用性优先

## 1. 决策摘要

招聘情报改为“后台生产、前台消费”架构：

```text
公开来源
  → 代码采集与结构化清洗
  → 证据和岗位快照入库
  → GPT 聚类、比较与分析
  → 原子发布情报版本
  → HR 工作台展示 / 岗位任务检索使用 / HR Agent 引用
```

HR 工作台不是爬虫控制台。业务用户打开页面即可看到系统已经准备好的结果，不负责发起、等待、
重试或排查采集任务。

以下产品决策为硬约束：

- HR 业务页面不出现“立即更新”；
- HR 业务页面不提供“添加关注公司”、来源维护、运行任务或重试采集入口；
- 普通 HR 对话、生成 JD/JR、人才画像、搜寻策略和面试方案时，不启动实时联网爬取；
- 长耗时采集与分析不得占用 HR Bot 对话执行槽位；
- 前台只读取已成功发布的数据版本，后台失败不得破坏上一份有效结果；
- 事实、AI 推断、未知项和信息来源必须分开呈现。

## 2. 要解决的问题

当前实现把多公司、多渠道的采集和分析绑定为一次 HR Agent 在线任务。真实运行中，一次 10 家公司、
29 个渠道的执行持续三十多分钟仍未形成最终回答，并暴露出以下结构性问题：

- 用户必须主动触发并等待，工作台成为了运维界面；
- 单个长任务失败会拖累整批公司，并占用 HR Bot 执行容量；
- 流式中断、最终消息缺失和任务状态不一致会让页面长期显示“运行中”；
- 临时执行产物没有成为稳定、可复用、可审计的数据资产；
- 岗位任务无法可靠复用已经收集的公司、岗位和技术路线情报；
- 页面暴露了业务用户不需要理解的采集状态、控制按钮和异常处理。

本设计首先保证业务可用，再逐步提高数据覆盖率。部分来源失败时，可以发布明确标注覆盖范围的结果，
不能让整个工作台不可用。

## 3. 产品边界

### 3.1 本期包含

- 重点公司及其公开招聘渠道目录；
- 官网社招、校招及已批准公开来源的岗位采集；
- 原始证据、标准化岗位、快照和变化记录；
- GPT 生成的公司分析、技术方向聚类、招聘资源信号、横向比较和校招专题；
- 最新有效全景报告及历史版本；
- 工作台中的结果展示、来源追溯、搜索筛选和文件下载；
- 岗位任务按需检索相关情报并注入 Agent 上下文；
- 后台定时运行，以及管理员通过命令或受控内部接口进行补采和回填。

首批公司目录至少保留当前已经梳理的重点企业，包括速腾聚创、禾赛科技、拓竹科技、创想三维、
智能派、知象光电、先临三维、思看科技，并纳入 HR 历史 Session 中已经明确研究过的企业。具体公司
清单属于可维护数据，不硬编码在页面组件中。

### 3.2 本期不包含

- 面向业务用户的采集配置、任务编排和故障处理；
- 无边界的全网职位聚合；
- 北森、OA、猎聘或 BOSS 直聘企业账号集成；
- 根据推断自动修改岗位、候选人或招聘流程状态；
- 为了追求全量覆盖而阻塞发布已有可信结果。

## 4. 系统分层与职责

### 4.1 情报生产层 `hr-intelligence-producer`

这是独立于 HR Bot 对话执行的后台能力，负责：

1. 读取受控的公司和来源目录；
2. 按“公司 × 渠道”拆分采集单元；
3. 使用确定性代码抓取、解析、清洗、去重和计算内容哈希；
4. 保存原始证据与标准化岗位快照；
5. 对成功获得的证据调用 GPT 进行聚类、归纳和比较；
6. 校验分析结果的数据契约和证据引用；
7. 生成不可变版本，并原子更新“当前已发布版本”指针。

生产层可由定时任务启动，也可由系统管理员在后台通过命令或受保护内部接口启动。它不能通过 HR
业务工作台启动，也不能占用面向用户的 HR Agent 会话。

### 4.2 证据与版本存储层

每次采集必须保存可审计的数据链：

```text
CollectionBatch
  └─ SourceCollectionAttempt
       ├─ RawEvidence
       └─ PublicJobSnapshot

PublishedIntelligenceVersion
  ├─ CompanyIntelligence
  ├─ JobCluster / CampusTopic / Comparison
  ├─ Fact / Inference / Unknown
  └─ EvidenceReference
```

关键规则：

- `RawEvidence` 保存来源 URL、渠道、抓取时间、内容哈希、解析状态和可复核正文或归档引用；
- `PublicJobSnapshot` 保存标准化岗位事实，并支持与上一有效快照比较；
- `PublishedIntelligenceVersion` 不可原地覆盖；
- 页面和 Agent 默认读取最新“已发布且有效”的版本，而不是最新一次尝试；
- 失败尝试保留诊断信息，但不替换上一份有效快照和报告；
- 相同来源内容哈希未变化时，不重复生成同一份事实，也不强制重复调用 GPT；
- 临时文件、模型输出草稿或会话消息不能作为正式数据源。

### 4.3 GPT 分析编译层

GPT 只基于已经入库并带来源的证据工作，不自行声称完成了未验证的联网采集。分析采用分层编译，
避免把所有公司和渠道塞入一次超长调用：

1. 单公司事实摘要与岗位技术方向聚类；
2. 社招、校招专题分析；
3. 多公司横向比较；
4. 面向岗位任务的可检索情报片段；
5. 最终报告组装与质量校验。

每条分析结论必须携带：

- 对应事实或证据引用；
- 来源 URL 与观察时间；
- 结论类型：事实、AI 推断或未知；
- 适用公司、岗位族、技术方向和时间范围；
- 置信限制或覆盖范围。

没有证据的公司不得生成貌似完整的结论。来源失败应明确显示“本版本未覆盖”及最后有效时间。

### 4.4 HR 工作台消费层

全景分析首页默认打开最新有效版本，核心内容按业务阅读顺序组织：

1. 结论摘要：主要招聘方向、变化和机会；
2. 公司视图：岗位数量、技术聚类、产品与业务信号；
3. 社招专题与校招专题；
4. 横向比较：公司、方向、地点和岗位族；
5. 来源与覆盖：每家公司使用了哪些渠道、观察时间、成功或缺失情况；
6. 结果下载：PDF、Excel 和 Markdown。

页面只提供阅读和使用结果所需的筛选、搜索、切换、复制、下载及“带入岗位”的动作。页面不展示
采集任务进度条、轮询状态、执行日志、运行按钮或来源编辑表单。

可见的数据新鲜度表达为“数据截至时间”和“来源覆盖情况”，而不是要求用户处理后台任务。如果没有
任何已发布版本，页面应显示清晰的空状态和最近一次可用数据说明，不提供“立即更新”。

### 4.5 岗位任务与 HR Agent 消费层

岗位任务执行前，由服务端根据以下信息检索最新有效情报：

- 当前 `position_id` 和岗位上下文版本；
- 岗位族、技术方向、地点、职级和关键词；
- 用户明确选择的目标公司或人才来源；
- 任务类型：JD、JR、人才画像、搜寻策略、简历分析或面试方案。

检索结果以受控上下文块注入 HR Agent，包含相关事实、推断、证据 URL、数据版本和观察时间。普通任务
不触发后台采集；没有足够情报时，Agent 明确说明缺口，并继续使用岗位事实完成可完成部分。

不同任务使用不同的相关性规则：

- JD/JR：参考同类岗位能力、职责表达与市场要求；
- 人才画像：参考目标公司的团队方向、岗位族和能力组合；
- 搜寻策略：参考目标公司、地点、相关岗位名称与技术关键词；
- 简历分析：只使用与候选人经历和当前岗位直接相关的情报；
- 面试方案：从岗位风险、竞品能力模型和待验证项生成问题，不复制外部 JD。

## 5. 后台运行模型

### 5.1 调度

- 定时器按照来源类型和业务时效配置周期，不由前端决定；
- 每个批次生成唯一 `batch_id`；
- 每个“公司 × 渠道”独立执行，设置超时、有限重试和并发上限；
- 动态网页、普通 HTML、公开 API 等来源使用独立适配器；
- 单个来源失败不阻塞其他来源入库和后续分析；
- 完成质量门禁后才发布新版本。

### 5.2 发布门禁

发布前至少验证：

- 数据契约合法，岗位标识和来源引用可追踪；
- 成功来源与失败来源均有清晰记录；
- 事实均能回指证据，推断没有伪装成事实；
- 新版本覆盖度未发生无法解释的断崖下降；
- 分析结果不是空壳，下载文件能够生成；
- 版本写入完成后再一次性切换当前版本指针。

覆盖度低于门槛时，批次可以保存为“未发布”，继续保留上一发布版本。满足最低可信门槛但并非全量时，
允许发布“部分覆盖”版本，并在页面明确标注缺失来源。

### 5.3 失败恢复

- 网络和来源失败采用指数退避，重试次数有上限；
- 解析失败与网络失败分开记录；
- GPT 调用失败只重试对应分析单元，不重跑全部采集；
- 使用 `batch_id + source_id + content_hash + analyzer_version` 保证幂等；
- 后台进程异常后可从已落库的单元继续，不依赖某条 Session；
- 状态回收由生产管线自己的租约与超时机制负责，不借用 HR 对话状态；
- 上一有效发布版本始终可读。

## 6. API 与权限边界

HR 业务前端仅调用读取接口，例如：

```text
GET /api/hr/panorama/current
GET /api/hr/panorama/versions
GET /api/hr/panorama/versions/{version_id}
GET /api/hr/panorama/versions/{version_id}/sources
GET /api/hr/panorama/versions/{version_id}/downloads/{format}
```

现有从 HR 页面调用的 `POST /api/hr/panorama/runs` 必须删除。生产、来源维护和补采接口不得暴露在 HR
业务路由和组件中；如确需保留，只允许后台任务身份或系统管理员经内部边界调用，并记录审计信息。

“能访问 HR 工作台”即表示用户可阅读其授权范围内的已发布情报，不应在页面中出现可访问却到处提示
无权限的割裂状态。生产权限与业务阅读权限完全分离。

## 7. 工作台改造范围

### 7.1 删除

- “立即更新”按钮及所有同义入口；
- “添加关注公司”和业务侧来源编辑；
- 公司勾选后启动运行的交互；
- 采集中脉冲、进度事件、主动轮询和本地 `active run` 恢复；
- 让用户刷新、重试或排查采集任务的提示；
- 把一次 HR Agent 运行当作全景报告来源的前端逻辑。

### 7.2 保留并强化

- 公司、社招、校招、技术方向和横向比较视图；
- 每家公司明确的信息来源、抓取时间和覆盖状态；
- 事实、推断和未知项的视觉区分；
- 历史版本与变化对比；
- PDF、Excel、Markdown 下载；
- 从情报结论进入相关岗位或将结论作为岗位任务参考；
- 最新数据截至时间、后台异常时的最后有效版本提示。

### 7.3 体验原则

- 打开即有结果，不要求先操作；
- 默认展示业务结论，来源细节可展开核验；
- 后台故障降级为数据新鲜度提示，不让整个页面不可用；
- 不展示内部执行术语、Trace、任务租约或模型调用状态；
- 不用假数据填充没有证据的公司。

## 8. 兼容与迁移

- 复用已有公司目录、来源配置、公开岗位快照、报告视图和下载能力；
- 将来源维护入口迁出 HR 工作台，不删除已配置来源；
- 旧的全景运行记录保留为审计历史，不再作为当前页面状态；
- 已恢复的首批真实采集结果经过契约校验和来源核验后，可导入生产管线形成首个发布版本；
- 不伪造成 HR Agent 历史回答，也不从临时文件直接向前台供数；
- 旧版 POST 运行接口在前端引用清零后下线或收紧为内部接口；
- 保留现有最新有效报告，迁移期间页面不断供。

## 9. 分期

### P0：达到业务可用

1. 建立独立后台生产入口和分单元运行模型；
2. 复用现有来源目录完成首批公司和 HR 历史 Session 企业清单整理；
3. 建立证据、快照、分析和发布版本的数据链；
4. 产出并发布首个经过核验的真实全景版本；
5. 工作台删除所有采集操作，默认展示最新有效结果及来源；
6. 岗位任务能检索并使用相关情报，且不发起实时爬取；
7. 保留现有 PDF、Excel、Markdown 下载；
8. 后台失败时继续展示上一有效版本。

### P1：提高覆盖与持续性

- 增强动态网站和复杂招聘门户适配器；
- 完善定时调度、增量更新、告警和质量趋势；
- 增加月度变化、公司对比和校招专题的历史趋势；
- 提升岗位与情报的自动相关性检索；
- 建设独立的管理员数据质量视图，但不进入 HR 业务工作台。

## 10. 验收标准

### 10.1 架构验收

- 一次 10 家公司、多个渠道的采集不会创建一条长时间运行的 HR Bot 会话；
- 公司或渠道失败彼此隔离，成功结果可以继续进入质量门禁；
- 后台进程中断后能够从持久化单元恢复；
- 新版本发布失败时，当前有效版本和下载仍可使用；
- 普通岗位任务只读取已发布情报，不等待联网采集。

### 10.2 前端验收

- HR 工作台任何位置均不存在“立即更新”或同义运行按钮；
- 前端代码不再调用 `POST /api/hr/panorama/runs`；
- 页面打开即展示最新有效全景结果；
- 每家公司都能查看其来源渠道、URL、观察时间和覆盖状态；
- 社招、校招、公司、技术方向和横向比较可以直接使用；
- PDF、Excel、Markdown 下载有效；
- 后台最新批次失败时，页面仍展示上一有效版本并标明数据截至时间；
- 页面没有要求业务用户处理采集错误、刷新任务状态或重新运行的文案。

### 10.3 Agent 验收

- 生成 JD/JR、人才画像、搜寻策略和面试方案时，能按岗位相关性引用已发布情报；
- Agent 输出能标明事实来源和数据时间，不把 AI 推断说成内部事实；
- 情报缺失不会导致岗位任务整体失败；
- 同一份已发布结果可以被全景页面、不同岗位和多个会话复用；
- 测试可以证明一次普通 HR 对话不会触发招聘情报联网采集。

### 10.4 质量验收

- 单元测试覆盖解析、去重、内容哈希、幂等、有限重试和失败隔离；
- 集成测试覆盖快照入库、分层分析、原子发布和上一有效版本回退；
- 契约测试覆盖事实、推断、未知项和证据引用；
- 前端测试覆盖只读消费、来源展示、版本降级和下载；
- 端到端测试使用真实结构的固定样本，禁止用无来源假结论冒充验收数据。

## 11. 成功定义

HR 用户无需理解或操作采集系统，就能稳定查看有来源、可追溯、可下载的招聘情报；岗位任务和 HR
Agent 能直接使用这些结果提升 JD/JR、人才画像、搜寻和面试质量。后台可以持续补充和更新数据，
但任何一次采集或模型失败都不会让现有工作台失去可用结果。
