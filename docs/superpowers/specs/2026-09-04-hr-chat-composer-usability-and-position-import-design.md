# HR 对话首页可用性与岗位数据补齐设计

日期：2026-09-04  
状态：用户已确认设计方向，待实施

## 1. 目标

HR 智能工作台首页必须首先是一块可长期使用的 AI 对话工作面，而不是带有小输入框和装饰性
快捷语句的表单。同时，岗位页必须展示真实的官网岗位和从既有 HR 对话中发现的岗位，不能以空
页面冒充完成。

本次同时解决四个已经由用户现场指出的问题：

1. 新对话输入区过小，不能承载岗位说明、候选人材料和复杂招聘任务；
2. 图片与文件入口位于输入区外部上方，操作顺序不符合聊天产品习惯；
3. 两个快捷问题只会代填第一句话，没有独立业务价值；
4. 字号小、文字浅、背景过亮，且生产岗位库实际为零条。

## 2. 已确认的产品决策

### 2.1 对话是首页唯一主任务

- 删除新对话页的 `example_tasks` 快捷按钮；
- 不以其他预制 Prompt 替换，不自动发送，不新增结构化向导；
- 去掉“直接交给 HR Agent”这类表单标题；
- 欢迎文案保持简短，把视觉和操作焦点交给输入区；
- 左侧继续保留真实对话历史，不改变会话、Turn、恢复和未读语义。

### 2.2 大输入区

- 桌面端输入工作面使用接近主内容列的完整宽度；
- 文本区默认高度采用 `clamp(220px, 28vh, 340px)`，并允许用户继续纵向拉伸；
- 移动端默认高度不低于 160px，发送按钮仍保持触控友好；
- 输入区使用 16px 正文字号和清晰占位提示；
- 空文本但有已就绪附件时仍可开始对话，维持现有行为。

### 2.3 附件属于输入框底部

采用现有 FAE 的正确信息结构，但不复制其业务代码：

```text
┌──────────────────────────────────────────────┐
│ 描述招聘任务、粘贴岗位说明或候选人资料……       │
│                                              │
│                                              │
├──────────────────────────────────────────────┤
│ ＋ 添加图片或文件   已选附件/处理状态      发送 │
└──────────────────────────────────────────────┘
```

- `AttachmentUploader`、已选附件、上传状态和错误信息移入同一个 composer；
- 附件区域位于文本区下方，发送按钮位于右下；
- 继续支持选择、拖放和粘贴；
- 继续执行每条最多 5 个、合计 50 MB、类型限制、处理状态和失败重试约束；
- 不改变附件授权、存储、下载、Session 材料或 Agent 输入协议。

### 2.4 可读性

- 主内容背景从高亮蓝白渐变改为稳定的浅灰工作面，内容面保持白色；
- 正文使用深色高对比文字，辅助文字不得以极浅灰承担关键信息；
- 欢迎说明和附件说明至少 14px，主要输入和按钮至少 16px/14px；
- 蓝色仅用于当前导航、焦点、主按钮和少量状态，不铺满大面积背景；
- 保留清楚的 hover、focus-visible、disabled 和错误状态；
- 桌面和移动端都不得因增大 composer 挤掉发送或附件操作。

## 3. 组件边界

`DirectAgentWorkspace` 继续负责通用会话创建状态和提交协议，但增加明确的展示能力参数，使 HR
可以关闭快捷任务并使用一体化 composer。组件不根据 `agentId` 偷偷改变业务行为。

建议边界：

- `showTaskStarters?: boolean`：HR 传入 `false`；其他 Agent 默认维持现状；
- composer 内部固定顺序为文本区、附件区、底部操作区；
- HR 的尺寸、颜色和密度继续由 `data-agent-id="hr-bot"` 范围内 CSS 控制；
- 附件上传状态仍由现有 `AttachmentUploader` 维护，不重建第二套上传状态机。

## 4. 岗位数据补齐

### 4.1 现场证据

2026-09-04 生产控制库检查结果：

- `platform_hr.positions`：0 条；
- `platform_hr.position_import_evidence`：0 条。

根因不是前端过滤，而是生产导入从未执行。现有发布记录
`docs/operations/2026-09-04-hr-position-spine-r11-release.md` 明确写着“代码验收通过，尚未发布
生产”，并要求生产运行前单独确认 owner、官网快照、密钥和 run-id。之后虽然应用代码被发布，
一次性导入步骤没有进入发布或单独运维流程。

### 4.2 数据来源

- 官网岗位：复用 `/Users/neo/Developer/work/Orbbec-Agent-Team/services/hr-jd-sync`；
- 不直接使用 `reports/hr-validation/orbbec-social-jobs-2026-07-24.json` 作为当前事实；
- 先运行现有同步与健康检查，读取其 `current/jobs.json` 最新有效发布快照；
- 历史岗位：复用 Platform 已恢复的 HR Conversation，通过现有
  `app.hr.import_cli` 发现明确岗位和待确认草稿；
- 不重放 Turn、不伪造 Assistant 回答、不修改原会话正文。

### 4.3 导入流程

1. 核验 `hr-jd-sync` 状态、最后成功时间、快照版本和岗位计数；
2. 解析现有 HR 授权用户，明确要导入的 owner，不把一个用户的私有对象暴露给其他用户；
3. 使用固定 `run-id` 对每个目标 owner 执行 `--dry-run`；
4. 对照官网岗位数、历史明确岗位数、待确认草稿数和歧义数；
5. 计数合理后用同一 `run-id` 执行 `--apply`；
6. 重跑相同命令验证幂等；
7. 通过生产 API 和网页确认岗位列表非空、岗位详情可开、历史会话未被改写。

官网岗位作为 `official_site` Position；历史明确岗位按既有规则创建或绑定，歧义项保留为
PositionDraft，不能自动猜测合并。

## 5. 错误与边界

- 官网同步失败时保留最后有效快照，不清空现有 Position；
- 没有可证明为最新有效的官网快照时停止导入并报告；
- owner、数据库、密钥或内容 keyring 不明确时失败关闭；
- UI 修改不触碰 MetaBot、FAE、VOC、Office、Marketing 或共享 Nginx；
- 数据写入只进入 Platform Control PostgreSQL，不进入 Release 目录；
- 发布继续遵守根盘、`/data` staging、Release 和 Docker 保留纪律。

## 6. 验收标准

### UI

- HR 新对话页不存在 `.agent-task-starter`；
- 默认文本区在桌面端明显大于当前 110px，并在移动端不低于 160px；
- DOM 顺序为 textarea → 附件区 → 底部操作区；
- 文件选择、拖放、粘贴、仅附件提交、失败重试和 5 个/50 MB 限制保持通过；
- 关键文字字号和对比度测试通过；
- WebUI 全量测试与 production build 通过。

### 数据

- 官网最新有效快照健康检查通过；
- dry-run 与 apply 的岗位和草稿计数有记录；
- 生产 `platform_hr.positions` 非零，且包含 `official_site`；
- 对同一快照与 run-id 重跑不新增重复对象；
- 岗位列表和至少一个岗位详情在真实登录态可访问；
- 原 HR Conversation 和 Turn 计数不因导入改变。

### 发布边界

- 只发布 Platform/HR WebUI 和本次明确需要的 Platform 代码；
- FAE 容器指纹和 Nginx 配置指纹发布前后相同；
- Office、FAE 与 HR 入口在线验收通过；
- staging 清空，并输出完整磁盘与版本保留报告。
