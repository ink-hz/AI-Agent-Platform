# HR 方法论与思维模型：存储及上下文融合设计

日期：2026-09-08

状态：根据用户明确纠正重写。用户已确认核心机制：先理解输入，由 Agent 选择知识，再组装本轮提示词处理。本文取代此前固定场景路由、方法编译和程序化思考检查方案。

## 1. 目标

把专业方法论与思维模型组织为 Agent 可以发现、理解、按需使用的认知资源，提高问题理解、证据分析与建议质量，同时支持用户浏览学习。

核心链路：

```text
用户输入 + 当前业务上下文 + 轻量知识索引
→ Agent 理解问题，选择相关方法论与思维模型
→ 读取选中的专业内容
→ 组装本轮任务上下文
→ Agent 结合材料进行分析和交付
```

选择权属于 Agent。场景描述帮助理解用途和发现资源，不是关键词触发器。允许选择多个资源、暂不选资源、先向用户澄清，以及发现问题变化后调整选择。

## 2. 存储方式

采用版本控制下的 Markdown 文件。一份方法论或模型一份文件，正文同时供 Agent 和用户阅读。轻量索引描述有哪些知识、帮助解决什么问题及文件位置。

```text
hr-knowledge/
├── index.md
├── models/
│   ├── evidence-based-reasoning.md
│   ├── task-competency.md
│   └── strategic-fit.md
└── methodologies/
    ├── job-analysis.md
    ├── competency-profile.md
    ├── candidate-evidence-review.md
    └── structured-interview.md
```

该结构是知识存储设计，不表示上述全部资源已经完成。首批研究材料暂放在 `docs/research/hr-methodology/`；业务集成时复用同一正文，不复制维护第二套提示词知识。

文件头只保留必要元数据，例如：

```yaml
---
id: job-analysis
title: 岗位分析
kind: methodology
domains: [recruiting, organization-design]
revision: 1
---
```

用途、来源和适用边界写在正文中。索引使用标题、简短用途说明、适用问题示例和相对路径；按当前资源规模保持简洁，避免把正文复制进索引。

完整 HR 知识分类包括：人力战略与规划、组织与岗位、招聘甄选、人才盘点与发展、绩效、薪酬激励、员工关系与体验、组织发展与变革、HR 数据与循证分析。分类用于知识组织，同一资源可以跨领域使用。首批深入招聘核心场景；专业知识研究范围不由当前业务按钮决定。

## 3. 资源正文怎么写

思维模型重点说明：

- 帮助从什么角度理解问题；
- 核心概念与关系，以及这些关系为何有用；
- 应关注哪些证据、其他解释和情境差异；
- 适用边界、局限、常见误用；
- 一个具体案例，以及可追溯的来源。

方法论重点说明：

- 它帮助完成什么工作、解决什么问题；
- 如何开展分析，通常需要哪些信息；
- 信息不足或证据冲突时如何继续思考；
- 可借助哪些模型，以及如何结合；
- 分析结果通常如何表达、怎样用于下一步工作；
- 案例、反例、限制与来源。

这些是内容写作指导，不是强制执行流程。Agent 可以根据情况调整方法，不要求机械跑完固定步骤或返回固定评分字段。自行整理的组合方法明确标为工作台适配，不伪称书中原有完整模型。

## 4. Agent 怎样选择

先让 Agent 看到当前请求、必要的业务背景和知识索引。它根据问题的目标、情境、已知材料与未知项判断哪些知识值得使用。

选择提示词可采用以下简洁意图：

> 先理解用户真正要解决的问题。参考知识索引，选择对本轮分析有帮助的方法论或思维模型。选择依据是当前问题及情境，而非词语是否出现。可以组合多个资源，也可以不选择；如目标尚不清楚，先澄清。不要为了套用某个模型改变用户的问题。

资源选择通过可用的读取工具完成。若现有 Runtime 可直接读取知识目录，则使用该能力；若需要由 Platform 提供读取接口，接口按资源 ID 返回正文即可。存储服务负责提供已存在的内容，不能替 Agent 决定使用什么方法。

不强制额外增加一次独立模型调用：同一 Agent 在已有工具循环中先读索引、选择并读取正文、再继续处理即可。只有现有 Runtime 不支持这一过程时，才拆成选择与处理两次调用，并保持选择仍由模型完成。

不要求输出内部推理过程。需要展示时给出简短的资源选择理由和可公开的分析依据即可。

## 5. 怎样融合进提示词

每轮任务上下文由以下内容组成：

```text
已有 Agent 职责、能力和行为要求
+ 当前用户问题
+ 当前岗位、候选人及已确认业务上下文
+ Agent 选中的方法论与思维模型正文
+ 本轮明确启用的材料与相关情报
```

这里改变的是本轮上下文，不需要反复改写全局系统提示词。方法知识提供专业思考依据；岗位、候选人和情报提供本次事实，两者保持清晰区别。

正文作为参考知识由 Agent 理解应用。不能仅在提示词末尾添加“请使用某某模型”就认为完成融合，也不能把方法出处当成候选人的业务证据。

对后续追问，Agent 根据当前问题判断是否继续沿用、补读或更换方法。避免每轮加载整库；索引和必要内容按需提供。对同一已发起任务的技术重试，沿用其既有输入快照，避免恢复时悄悄切换版本。

## 6. 一个例子

用户说：“这个岗位一直招不到人，帮我看看。”

Agent 结合现有岗位和招聘反馈理解问题，可能先读取岗位分析、人才来源研究及岗位吸引力相关资源。它可以提出不同解释：需求是否过严、人才供给是否有限、工作内容是否缺乏吸引力、评价方式是否错过合适人才。

如果目前只有 JD，没有搜寻和反馈材料，它应澄清证据缺口；不能直接断定是渠道问题。若发现业务实际需要的能力与 JD 条件不一致，则重点使用岗位分析与要求校准。若需求合理而直接人才稀缺，则进一步考虑相邻能力与人才来源。

这些选择源于 Agent 对输入和证据的理解，不由“招不到人”这个词绑定固定的方法链。

## 7. 首批核心场景与知识建设

先围绕需求澄清、画像形成、人才搜寻、候选人证据分析、面试验证、候选人比较与反馈校准整理知识。它们是研究和试用的核心场景，不是固定执行状态机，也不是模型数量上限。

每个场景考虑不同情境，例如：同领域成熟人才、跨行业候选人、应届生、信息不足、证据冲突。把这些差异写入用途说明、案例和限制，帮助 Agent 作判断，而不是编码成条件分支。

面试证据可能反过来支持或挑战岗位画像。方法内容应引导 Agent 形成有证据的调整建议，由用户确认后进入后续业务上下文，不把单个案例自动推广为通用规则。

## 8. 展示与使用共用知识

用户可按业务问题、领域、方法论或思维模型浏览已完成内容。场景与资源的相关性用于帮助发现，不代表唯一正确的搭配。

资源详情展示用途、正文、案例、来源及关联视角。“带着这个方法讨论”表达用户的明确偏好，Agent 仍可以说明适用限制或建议补充资源。

任务中可以展示 Agent 实际读取或引用了哪些知识，以及简短的使用理由。读取过某份资源不等于已证明正确运用了它，不能按任务完成状态自动生成“方法已执行合格”的结论。

前端和 Agent 使用同一内容源。首批先将专业资源和上下文融合打通，页面建设服务于知识理解与任务使用。

首先核对现有 Runtime 的知识发现与读取能力，再选择最小的接入位置；不先造固定路由器、场景分类器服务或方法编译框架。不得为了接入方法库重新设计整个对话服务。

## 10. 如何判断是否有帮助

使用真实或明确标注的教学场景对比 Agent 接入前后的回答，重点观察：

- 是否更准确理解了问题，而不是过早给方案；
- 是否提出更关键的问题、发现遗漏的证据；
- 是否考虑了情境差异、冲突证据与其他解释；
- 是否选择并恰当地调整了方法；
- 是否形成更有依据、更可验证的建议。

保留具体输入、选用资源及输出供复盘。评价依赖业务内容与实例，不用关键词命中、格式字段齐全或固定步骤计数替代思考质量。
