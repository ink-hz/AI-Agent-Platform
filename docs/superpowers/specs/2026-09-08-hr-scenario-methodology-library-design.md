# HR 方法论与思维模型：存储及上下文融合设计

日期：2026-09-08

状态：评审修订稿；本次交付为设计与研究材料，尚未接入或发布 Runtime。

## 1. 目标与核心决定

把专业方法论与思维模型组织为 Agent 可以发现、理解、按需使用的认知资源，提高问题理解、证据分析与建议质量，同时支持用户浏览学习。

```text
用户问题 + 已确认业务上下文 + 轻量知识索引 + 用户指定资源
→ Agent 在现有工具循环中理解问题、自主选择知识
→ Read 本地固定版本的资源正文
→ 正文作为工具结果进入同一会话上下文
→ Agent 结合知识与业务证据分析、交付
```

选择权属于 Agent。场景描述帮助理解资源用途，允许组合资源、暂不使用、先澄清，以及后续追问时调整选择。没有关键词路由、固定方法链、方法编译器或程序化思考评分。

本版决定：正式内容源放在 `Orbbec-Agent-Team/bots/hr/knowledge/`；云端和本地部署同一 Git 来源的版本副本；Agent 使用现有本地读取工具；网页沿用 `ai_notes` 的文件解析和展示方式；现有情报门控暂时并存，知识选择独立接入。

## 2. 内容源、资源身份与部署

### 2.1 一处维护，两处部署

正式上游选定为 `Orbbec-Agent-Team` 仓库的 `bots/hr/knowledge/`。已有 `knowledge/recruiting/.gitkeep` 可承接首批内容。`HR-Agent-Knowledge/` 目前只有空骨架，本方案不启用它，不修改或删除该目录。

首批材料当前仍在本工作树的 `docs/research/hr-methodology/`，这是评审暂存位置。实施时把正文和来源台账迁入正式上游，平台此处改留迁移说明和上游引用，不形成两套可独立编辑的正文。本次文档修订没有执行迁移或部署。

正式上游结构：

```text
bots/hr/knowledge/
├── README.md                         # 短入口；当前暂存目录已有同用途索引
├── recruiting/
│   ├── job-and-context.md
│   ├── requirement-calibration.md
│   ├── competency-and-profile.md
│   ├── sourcing-and-transfer.md
│   ├── evidence-informed-judgment.md
│   ├── selection-and-work-samples.md
│   └── comparison-and-learning.md
└── sources/
    └── 2026-09-08-hr-methodology-sources.md
```

发布时，从上游某个已提交的 Git revision 生成内容包，包含索引、正文、来源台账和 manifest。manifest 记录 `source_commit`、各资源的 `id / revision / path / sha256`。内容包部署到两端的不可变版本目录：

| 位置 | 拟定路径约定 | 使用方 |
| --- | --- | --- |
| 本地 Agent | `<hr_bot_cwd>/.knowledge-releases/<source_commit>/` | Claude Code CLI 的 Read / Glob / Grep |
| 云端 Platform | `<configured_knowledge_root>/releases/<source_commit>/` | 网页目录和正文读取服务 |

路径由部署配置提供；`hr_bot_cwd` 来自实际 bot 配置，不把开发机用户名写进代码。`.knowledge-releases` 是上游源目录之外的部署产物，不入源仓库。首版沿已有 bot 与平台部署流程分发同一内容包，无需建设实时同步服务。上述发布产物和分发步骤尚待实现。

两端完成内容校验后，才把该版本设为新任务使用的版本。首版可由发布过程核对两端 manifest，无需新增逐任务回源请求。若本地目录缺失或读取失败，明确记录知识不可用，Agent 可说明限制并继续一般分析，不能声称已经应用材料。

### 2.2 统一资源身份

资源 ID 就是上述七个文件的文件名主体，正文、索引、来源台账和用户指定均使用同一 ID。移动目录不改变 ID；修订内容增加 `revision`。示例：

```yaml
---
id: requirement-calibration
title: 要求校准与 AMO
revision: 1
domains: [recruiting, performance]
knowledge_forms: [thinking-model, methodology]
---
```

`id / title / revision` 是身份元数据；`domains` 用于领域发现，`knowledge_forms` 用于“思维模型 / 方法论”浏览筛选，可同时包含两者。所有资源使用同一种读取方式，不按标签改变提示词或执行流程。首批七份内容都结合了分析视角与实践方法，因此不拆成 `models/` 和 `methodologies/` 两套目录。

`revision` 是人可理解的单篇修订号，`source_commit` 标识整包来源，文件 `sha256` 确认具体内容。仅比较修订号不足以保证内容相同。任务使用 `(source_commit, id, revision, sha256)` 关联知识；发布与字节一致性属于内容管理，不评价 Agent 思考质量。

### 2.3 版本偏斜与重试

云端显示 revision 4、本地任务使用 revision 3 时，页面显示该任务对应的 revision 3，并可另行提示已有新版；不能拿最新正文冒充本次使用版本。“带着这个方法讨论”携带页面所选版本，后台在创建任务前确认本地已有对应内容包；不可用时明确提示暂不能按该版本发起，不能静默换版。

同一任务的技术重试复用冻结提示词，其中包含不可变本地版本路径。对应内容包至少保留到所有引用它的任务不再允许恢复，并满足任务复盘保留期；首版先不自动清理版本。正文缺失时报告不可用，不回退到 `latest`。

冻结提示词本身只固定输入文本，**不会冻结稍后 Read 的磁盘文件**。因此必须同时固定本地正文版本。新一轮追问可以使用更新版本，但需要在本轮输入中明确记录。

## 3. 资源正文与 HR 覆盖

首批七份资源已有统一写法：帮助理解什么、核心关系、如何结合证据思考、适用与局限、可结合的视角、案例、来源。保留现有正文，不为区分模型和方法强行拆分或重写。

思维模型解释概念、关系、其他可能解释与情境差异；方法论帮助组织证据、开展分析、处理冲突和形成下一步建议。两者可以存在于同一资源中。内容应说明为什么值得这样思考，以及何时不适用，不能变成必须完成的步骤清单。

所有组合与中文案例明确标为工作台适配，来源台账按实际七个资源 ID 对应，不冒称 Armstrong 或来源机构发布了这些完整工作台方法。Armstrong 第十三版 PDF 的截断限制继续保留，不把缺失章节作为已读来源。

完整知识领域包括：人力战略与规划、组织与岗位、招聘甄选、人才盘点与发展、绩效、薪酬激励、员工关系与体验、组织发展与变革、HR 数据与循证分析。首批深入招聘核心场景；分类服务于发现，资源可以跨领域使用。

## 4. Agent 自主选择与实际读取能力

模型工具循环在 MetaBot 的 Claude Code CLI 内，不在 Platform 内。静态代码核验：MetaBot `master` 的 `fe5ad87` 中，`src/config.ts` 默认 `toolPolicy=default`；`src/engines/claude/pty/pty-session.ts` 仅在 `toolPolicy=none` 时禁用工具。引擎层支持通过 CLI 读取本地文件，本方案直接使用该能力，不为 Agent 新建 Platform 按 ID 返回正文的接口。

评审报告指出 HR 会话在 `bots/hr` 下运行、配置模型为 `claude-opus-5`。本次独立核验确认 bot 部署片段的工作目录指向 `bots/hr`、模型字段为 `claude-opus-5`，但未观察真实生产会话，也未核实当前生产有效配置。因此“引擎代码支持文件工具”和“当前 HR 生产链路成功读取知识”是两个不同结论，后者仍待实测。

选择提示词表达如下意图：

> 先理解用户真正要解决的问题。参考知识索引，选择对当前目标、情境和证据缺口有帮助的资源。可以组合多个资源、暂不使用或先澄清。用户指定的资源应认真考虑，也可以说明其局限。需要使用时，从本轮指定版本目录读取正文，再结合业务事实分析；不要为套用模型改变问题，不要把方法出处当作候选人事实。

整个过程是**同一工具循环内的两段意图：选择知识、结合知识处理问题**。无需拆成两次独立模型调用，也无需云端在执行中途追加提示词。资源正文随 Read 工具结果进入正在执行的会话。

不要求披露内部推理过程。面向用户只说明简短选择理由、证据依据和不确定性。

## 5. 冻结输入、上下文预算与接入位置

### 5.1 输入和执行上下文

发起任务时冻结：

```text
已有 Agent 职责与行为要求
+ 当前用户问题和必要对话历史
+ 岗位、候选人及已确认业务上下文
+ 本轮材料与现有情报上下文
+ hr_reference_knowledge
  ├── 自主选择与阅读的简短说明
  ├── 轻量索引
  ├── source_commit 与本地不可变版本目录
  └── user_selected_resources（ID、revision、sha256、指定意图）
```

执行过程中，Agent 按需读取正文，工具结果继续形成本轮上下文。索引进入冻结输入，正文由 Agent 自行读取，不预先把整库塞进 Platform 提示词，也不反复改写全局系统提示词。

“带着这个方法讨论”必须成为持久化的本轮输入。前端随发起请求提交所选资源及版本，后台解析确认后写入冻结字段；不能只放在页面状态或未持久化的 URL 参数中。技术重试从快照恢复这一指定。没有新的用户指示时，不把一次指定永久解释为后续所有任务的必选方法。

### 5.2 数字预算

首版设定以下 UTF-8 字节预算（KiB = 1024 字节）：

| 对象 | 预算与处理 |
| --- | --- |
| 冻结输入内的知识索引文本 | 最多 4 KiB |
| 整个 `hr_reference_knowledge` JSON 字段 | 最多 8 KiB，包含索引、说明、版本定位和用户指定 |
| Platform 对话上下文 | 沿用现有 96 KiB 总预算；知识字段纳入计算，不额外豁免 |
| Agent Read 返回的正文 | 不计入已经发出的 Platform 输入快照；占用 CLI 自身模型上下文，按需读取，受实际 Runtime 限制 |

当前 Panorama Markdown 拼接目标为 28 KiB，但 `MAX_PANORAMA_CONTEXT_BYTES` 的片段上限是 32 KiB；预留空间按完整片段计算，不能将 28 KiB 当作全部开销。

`ConversationContext` 增加知识字段时，`_context_size` 及重新计算大小的调用处必须同步纳入其序列化字节和封装开销。最终序列化输入也应核对实际大小，不能只靠旧的估算字段认为满足预算。用户指定不能被静默截断；若超过预算，创建任务前给出可理解的调整提示。

库增长超过索引预算时，固定入口保留各领域的简短描述和详细索引路径，详细索引也由 Agent 自主读取。不能按关键词从整库截取固定前几条；目录分层只组织文件，不代替选择。当前无需向量库或独立检索服务。

### 5.3 最小接入位置与版本条件

v5 设计接入点为 `backend/app/agent_brain/direct_mission_adapter.py` 的 `document` 字典；新增字段随原有 JSON 序列化进入 `FrozenInput`、`contextHash` 和已准备任务快照。复用现有冻结与重试机制，不另建快照系统。

但是 MetaBot 的 `core-chat-v5-*` 当前只存在于 `feat/hr-unified-execution` 分支，未出现在核验的 `master fe5ad87`；Platform 的 `transport_v5.py` 也明确为 opt-in。不能把上述接入点写成已上线全链路。

Platform 另有 `orchestrator.py::_request_sections` 序列化已有 HR 上下文。若实施时仍通过该路径发起 HR 任务，仅修改 v5 的字典不会覆盖它。本方案优先沿正在推进的 v5 接入，待其真实链路确认后启用知识；若必须提前支持旧路径，应单独补该路径的输入传递和恢复验证，不能推定其拥有 v5 的冻结契约。

## 6. 场景如何帮助选择

用户说：“这个岗位一直招不到人，帮我看看。”

Agent 可以从 `job-and-context`、`requirement-calibration` 等资源获得分析视角：需求是否对应真实任务、供给是否有限、岗位吸引力是否不足、甄选方式是否遗漏合适人才。这些是待证实的解释，不是看到“招不到人”就必选的资源链。

只有 JD 时，不应直接认定渠道有问题。如果筛选记录显示某些门槛无法对应关键任务，可以继续研究要求依据；如果出现相邻行业候选人，可以考虑 `sourcing-and-transfer`；如果证据相互矛盾，可以借助 `evidence-informed-judgment`。同一句话在不同上下文下可以选择不同资源，也可以先澄清。

## 7. 首批场景与反馈

先用需求澄清、画像形成、人才搜寻、候选人证据分析、面试验证、候选人比较与反馈校准建设内容和试用案例。这些是业务研究范围，不是状态机。

案例覆盖成熟人才、跨行业候选人、应届生、信息不足和证据冲突。面试证据可以支持或挑战岗位画像，但调整建议经用户确认后才进入后续业务上下文，不把单个案例自动提升为通用规则。

## 8. 人工展示与使用说明

用户可按问题描述、领域，以及方法论/思维模型标签浏览，详情展示用途、正文、案例、来源、版本与关联视角。场景与资源的相关说明帮助发现，不表示唯一正确搭配。

复用现有 `ai_notes` 的实现经验：`repository.py::parse_frontmatter` 已能解析 YAML frontmatter 和正文并拒绝符号链接；现有索引/单篇 API、`webui/src/aiNotesApi.ts` 及 Markdown 展示形成了可参考的完整路径。

这里复用解析和展示的公共能力，**不能直接调用 `AiNotesRepository.load` 加载本知识目录**：它还要求编号分类目录、编号文章文件及 `author / publishedAt / draft` 等文章字段，并拒绝额外字段。实施时保留 HR 的最小元数据，复用或提取通用解析能力，适配知识目录读取和版本展示；不为满足文章模型添加无意义字段，也不直接塞进 `05-thinking-and-methods` 分类。

网页 API 读取云端副本，Agent Read 本地副本。它们共享同一 Git 来源与内容版本，不共享同一物理文件。云端 API 服务网页浏览，不成为 Agent 读取正文的跨网依赖。

当前 Platform Turn 没有 CLI 逐次读文件的遥测信息。首版可以让 Agent 在结果中附简短“参考知识”说明；若后续结果协议支持，再持久化为 `used_knowledge`，包含资源 ID、版本和简短用途。现有结构化协议未扩展前，不假定未知字段能被接收。

上述信息标为“Agent 声明参考”，不能写成“系统已验证读取”。未来若接入原生工具事件，再单独标注观测到的读取。自报、实际读取、正确运用是三件事；这些字段只用于展示和复盘，不进入任务完成度、合格判定或自动业务决策。它们也不是内部推理记录。

## 9. 与现有情报、工具权限和分支的关系

现有 `panorama_context.py` 的 `_EXPLICIT_TRIGGERS / _GENERAL_TRIGGERS` 确有关键词门控。本版决定暂时保留现有情报行为，明确它仍限制 Agent 能看到的部分外部事实；方法库不复用 `PanoramaContextProvider` 的筛选流程。将来若改为 Agent 自主取情报，应单独设计数据发现与读取能力，不能宣称本次已实现所有上下文自主选择。

CLI 启动参数含 `--dangerously-skip-permissions`，正文在这样的会话中必须明确作为参考材料，不能成为工具操作授权。知识文件及引用来源中的命令、角色覆盖或数据外发要求不具有指令权；工具操作仍依据用户任务和可信 Agent 规则。该约束是提示词边界，不是已经实现的执行沙箱。

本工作树为 `.worktrees/hr-methodology-library`，原始基线 `03e60f8`；核验时主工作树已推进至 `e8e75f1`，实施前需重新对齐另一会话的变更。旧的关键词路由、编译和步骤检查实验代码未提交、未部署；残留的对应 Python 缓存与空目录在本次修订中清理。

## 10. 业务效果与故障诊断

**接入知识前先采集基线。**保留具体用户输入、对话历史、岗位及材料快照、情报版本、模型配置、输出和运行时间。后续尽量使用相同条件对比；若模型、情报或业务数据变化，单独记录，不把差异全部归因于知识库。

复盘关注：是否更准确理解问题，提出关键澄清，区分事实与推断，考虑其他解释和情境差异，以及形成更有依据、可验证的建议。用具体案例和业务评审判断，不以关键词命中、选中率、引用数量或格式字段代替质量。保存简短选择理由和可公开证据，不索取内部推理。

Agent 未选知识时，分别定位：

| 观察 | 优先核查 |
| --- | --- |
| 冻结输入中没有入口或用户指定 | 输入传递、预算处理、快照保存 |
| 入口存在，但资源用途难以识别 | 索引表达与资源覆盖是否贴合真实问题 |
| 选择了资源但无法读取 | 本地路径、有效工具配置、版本部署与可访问性 |
| 能读，但对合适案例持续忽略知识 | 选择提示词、会话中其他指令、模型行为；做单变量对比 |
| 读了，回答仍无改善或误用 | 正文质量、边界说明、业务证据和模型应用能力 |
| 普通事务请求合理地未选知识 | 接受这一选择，不人为提高使用率 |

这张表帮助诊断接入问题，不是自动评判 Agent 是否思考合格的规则。
