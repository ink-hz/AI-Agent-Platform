# HR Agent 顶级招聘情报 Markdown 层设计

**日期：** 2026-09-06

**状态：** 已确认设计，待实施计划

**适用范围：** HR 招聘情报本地工厂、不可变 HR Intelligence Bundle、HR Agent 情报检索与上下文注入

**前置设计：** `2026-09-06-hr-local-intelligence-factory-design.md`

## 1. 背景与问题

当前本地情报工厂已经能够生成可验证的不可变 Bundle，保存公开招聘证据、规范化岗位、确定性聚合、AI 分析及 Markdown、PDF、Excel 报告。首个真实 Bundle 已覆盖 12 家目标公司，并形成 3437 条可追溯岗位快照。

现有成果仍有两个直接影响 HR Agent 使用效果的问题：

1. `report.md` 面向人工下载，包含大段聚合 JSON 和完整岗位目录，内容过长且噪声较高，不适合直接注入模型。
2. HR Agent 当前不读取 Markdown，而是在运行时从 `analysis.json` 和 `normalized-jobs.jsonl` 临时选择少量数据并拼装 JSON 上下文。这种方式只能提供局部事实，不能稳定表达公司画像、技术树、产品路线、人才竞争、反证和行动建议。

因此，“已经生成分析结果”并不等于“Agent 已经充分使用分析结果”。本设计增加专门面向 Agent 的分层 Markdown 情报层，同时提升招聘情报的清洗质量、来源宽度、分析深度和任务可用性。

## 2. 目标

本期必须实现：

- JSON、JSONL 和原始证据继续作为机器校验、审计和重算的事实底座；
- 将已接受的分析结果编译为结构稳定、证据化、可按主题检索的 Markdown；
- HR Agent 在对话问答、JD、JR、人才画像、搜寻策略、简历分析和面试题任务中统一使用该情报层；
- 每轮只注入与任务相关的 Markdown 片段，不读取整份报告；
- 同一 Turn 固定 Bundle 和片段哈希，保证重试、审计和回放一致；
- 在本地补充多源公司情报、二级技术树、人才竞争和奥比行动建议；
- 保持生产环境只校验、导入、发布和读取不可变 Bundle，不提供采集、分析、更新或恢复入口。

## 3. 非目标

本期不做：

- 不以 Markdown 替代结构化事实、证据索引或 Bundle Manifest；
- 不在生产环境运行爬虫、模型、分析器或定时任务；
- 不在 HR 工作台增加“立即更新”“重新分析”“重试采集”等操作；
- 不为单次基线伪造月度趋势、HC、预算、招聘完成率或真实研发投入；
- 不立即引入向量数据库。现阶段先用确定性元数据索引和受限全文匹配完成检索闭环；
- 不原地修改已经完成的 Bundle。任何内容或契约变化都必须产生新的 Bundle ID。

## 4. 总体架构

```text
公开招聘来源、官方产品与经营材料、历史快照
                        ↓
             本地采集、清洗、规范化
                        ↓
       JSON/JSONL 事实、聚合与证据底座
                        ↓
              本地 GPT 深度分析
                        ↓
          分层 Agent Markdown 情报包
                        ↓
       本地质量门禁与不可变 Bundle 构建
                        ↓
          生产一次性校验、导入与发布
                        ↓
       HR Agent 按任务检索和固定版本注入
```

架构职责分为五个独立单元：

1. **事实底座**：保存来源、证据、规范化岗位、聚合和分析对象。
2. **Markdown 编译器**：只根据已验证的结构化输入生成稳定 Markdown，不自行产生新事实。
3. **片段索引器**：为 Markdown 章节建立确定性路由元数据和完整性哈希。
4. **情报检索器**：根据任务、岗位和用户问题选择相关片段并控制上下文预算。
5. **Turn 固定器**：记录本轮实际使用的 Bundle、片段和哈希，保证重试一致。

任一单元可以独立测试。Markdown 编译失败不能污染结构化事实；检索失败可以受控降级到现有 JSON 检索，但必须记录降级原因。

## 5. Bundle v2 契约

### 5.1 文件结构

新版 Bundle 保留现有文件并新增 `agent/`：

```text
hr-intelligence-bundle/
├── manifest.json
├── source-catalog.json
├── source-coverage.json
├── raw-evidence-index.json
├── normalized-jobs.jsonl
├── aggregates.json
├── analysis.json
├── analysis-usage.json
├── report.md
├── report.pdf
├── report.xlsx
├── agent/
│   ├── index.md
│   ├── executive-brief.md
│   ├── companies/
│   │   └── <company-key>.md
│   ├── directions/
│   │   └── <direction-key>.md
│   ├── topics/
│   │   ├── social-recruiting.md
│   │   ├── campus-recruiting.md
│   │   ├── internships.md
│   │   ├── product-routes.md
│   │   ├── talent-competition.md
│   │   ├── geography.md
│   │   └── trends.md
│   ├── tasks/
│   │   ├── jd-jr.md
│   │   ├── talent-profile.md
│   │   ├── sourcing.md
│   │   ├── resume-review.md
│   │   └── interview.md
│   └── chunk-index.json
└── checksums.sha256
```

`report.md` 继续供人阅读和下载，但移除完整岗位清单和大段原始 JSON。原始岗位仍通过 Excel、结构化文件和工作台筛选访问。`agent/` 是模型消费的精炼语义层。

### 5.2 Markdown 元数据

每个 Markdown 文件使用受限 YAML Front Matter：

```yaml
---
schema_version: 1
bundle_id: 00000000-0000-0000-0000-000000000000
observed_at: 2026-09-06T09:13:17+00:00
scope: company
scope_key: hesai
confidence: high
coverage: succeeded
evidence_count: 6
---
```

允许的字段和值由 Bundle Schema 固定。禁止任意嵌套对象、可执行标签、HTML、脚本、远程嵌入和未登记文件引用。所有文本使用 UTF-8 和 LF 换行。

### 5.3 统一章节结构

公司、技术方向和专题文档使用以下语义顺序：

```markdown
# 标题

## 核心判断
## 可引用事实
## 技术与产品路线研判
## 人才竞争信号
## 对奥比中光的启示
## 未知项与替代解释
## 证据
```

文档允许省略不适用章节，但不得将未知项写成确定事实。事实、确定性聚合和 AI 研判必须使用清晰标记：

- `事实 F-...`：可回指公开来源与证据；
- `聚合 A-...`：代码对当前 Bundle 的确定性统计；
- `研判 I-...`：AI 推断，必须列出依据事实 ID；
- `未知 U-...`：证据不足或未公开；
- `替代解释 X-...`：可能削弱当前研判的其他解释；
- `建议 R-...`：面向奥比招聘工作的行动建议。

### 5.4 片段索引

`chunk-index.json` 只负责路由，不复制分析正文。每条记录至少包含：

- `chunk_id`；
- Markdown 相对路径和章节标识；
- 内容 SHA-256 与 UTF-8 字节数；
- scope、公司、招聘类型、岗位族、一级和二级技术方向；
- 地点、职级、技能和任务类型标签；
- 证据 ID 列表；
- 优先级和有效观察时间。

索引中的每个片段必须与 Markdown 内容逐字节匹配。未被索引覆盖的正文、路径越界、重复片段 ID、孤立证据引用或超出大小限制都使 Bundle 验证失败。

## 6. 顶级招聘情报模型

### 6.1 证据与覆盖

每家公司必须明确展示：

- 已批准来源及其来源类型；
- 成功、确认空、部分成功、失败和未观察状态；
- 观察时间、响应内容哈希、解析器版本和限制；
- 招聘来源与非招聘来源之间是否完成交叉验证。

证据不足只能表述为“当前证据不足”或“当前来源未形成可规范化岗位”，不得表述为“没有招聘”。

### 6.2 多源公司情报

除公开招聘渠道外，本地工厂可以从经批准的公开来源采集并归档：

- 官方产品和解决方案页面；
- 官方新闻、发布会和公众号文章；
- 财报、招股书、ESG 与公开经营材料；
- 校招手册和宣讲材料；
- 公开专利、论文和技术活动；
- 经审核的行业媒体访谈。

影响产品路线、业务方向或人才竞争的重要研判，原则上必须同时具有招聘证据和至少一种非招聘证据。未完成交叉验证时必须降低置信度并说明原因。

### 6.3 二级技术树

一级技术方向保留光学、硬件、结构、软件、算法、制造工艺、质量、产品和供应链。二级技术方向至少覆盖：

- 光学：发射、接收、镜头、镀膜、杂散光、标定；
- 硬件：电子、嵌入式硬件、PCB、FPGA、芯片、器件、电源；
- 结构：机械、材料、模具、热设计、整机、自动化设备；
- 软件：嵌入式软件、驱动、中间件、客户端、后端平台、AI 基础设施、工具链；
- 算法：点云、SLAM、感知、影像、具身智能、运动控制、3D 生成、数据算法；
- 制造工艺：SMT、装配、镀膜、注塑、机加工、自动化、DFM、良率；
- 质量：研发验证、软件测试、硬件测试、PQE、DQE、供应商质量、可靠性、失效分析。

技术方向是多标签口径。报告必须明确计数可能重叠，不能将各方向数量直接相加为岗位总数。

### 6.4 公司级独立分析

每家公司必须产生具有区分度的：

- 技术能力树；
- 产品路线和商业方向；
- 从研发到量产及交付的组织链条；
- 当前紧缺人才和潜在能力缺口；
- 重点团队、城市及职级结构；
- 可争夺人才池和相邻行业来源；
- 对奥比中光的威胁、机会和行动建议；
- 支持证据、反证、替代解释及未知项。

不允许不同公司复用相同模板化推断。模型输出必须通过跨单元重复度检查；高相似度结论必须被拒绝或重新分析。

### 6.5 横向专题

情报包至少提供：

- 社招、校招和实习专题；
- 激光雷达与 3D 视觉竞争；
- 机器人感知和具身智能；
- 3D 打印与 3D 扫描；
- 光机电、芯片、算法及制造质量人才竞争；
- 地域人才集群；
- 产品路线与招聘组合的关系；
- 奥比人才池建设与优先级建议。

### 6.6 趋势边界

单次 Bundle 只能形成基线。只有在至少两个可比观察时间点、相同口径和可解释来源覆盖下，才能生成：

- 新增、关闭和持续开放岗位；
- 方向占比变化；
- 公司、区域和职级迁移；
- 校招窗口变化；
- 招聘扩张、收缩或资源迁移研判。

来源覆盖变化必须与真实岗位变化分开说明。没有可比历史时，`trends.md` 必须明确写明“当前为单次基线，不能判断月度趋势”。

## 7. HR Agent 检索与上下文注入

### 7.1 支持任务

Markdown 情报层默认覆盖：

- 一般招聘情报对话；
- JD 和 JR；
- 人才画像；
- 搜寻策略；
- 简历分析；
- 结构化面试题和面试方案。

### 7.2 查询理解

检索器从当前用户问题、岗位上下文和任务类型中提取：

- 明确点名的公司及别名；
- 岗位族、一级与二级技术方向；
- 产品、技能、地点、职级和招聘类型；
- 当前招聘任务及其输出目标。

查询理解使用确定性词典、别名表和规则，不在生产调用额外模型。

### 7.3 排序规则

排序优先级依次为：

1. 明确点名公司；
2. 当前岗位匹配的二级技术方向和岗位族；
3. 当前任务类型；
4. 地点、职级、技能和产品关键词；
5. 公司横向比较和专题；
6. 全局管理摘要。

`index.md` 中的口径、时效和使用边界始终加入上下文。其他片段按分数选择，去重后限制在当前 32 KiB 总预算内，并为用户输入和系统边界预留空间。

### 7.4 注入格式

模型接收到的是可读 Markdown，而不是整份 JSON：

```markdown
## 招聘情报上下文

> Bundle: ...
> 观察时间: ...
> 覆盖状态: partial

### 可引用事实
...

### 确定性聚合
...

### AI 研判
...

### 未知项与替代解释
...

### 当前任务建议
...
```

系统提示必须要求模型：区分事实与研判；不得将公开岗位数等同 HC；不得隐藏来源限制；写入岗位库的内容仍先形成待确认草稿。

### 7.5 Turn 固定与重试

首次执行时保存：

- Bundle ID 和 Manifest SHA-256；
- 选中的 chunk ID、内容 SHA-256 和顺序；
- 检索版本、查询特征和降级状态；
- 实际注入的 Markdown 文本或可验证定位。

同一 Turn 重试时只复用原记录，不重新选择最新 Bundle 或重新排序。新 Turn 可以读取新的已发布 Bundle。

### 7.6 降级

当 Markdown 文件缺失、哈希错误、索引无匹配或读取失败时：

1. 不使用未验证内容；
2. 记录结构化降级原因；
3. 使用当前 Bundle 的结构化事实检索作为降级上下文；
4. 不阻断 JD、JR、画像、搜寻、简历和面试任务；
5. 不在生产启动重新分析、重新采集或内容修复。

## 8. 面向任务的情报使用

### 8.1 JD/JR

提供行业通用能力、目标公司能力组合、二级技术关键词、资历与地点信号。Agent 必须将外部情报标记为建议，不得覆盖用户提供的岗位事实。

### 8.2 人才画像

输出核心能力、可迁移能力、目标公司、相邻行业、排除条件、验证重点和证据依据，避免只按同名职位搜索。

### 8.3 搜寻策略

输出公司池、团队线索、地域、关键词组合、相邻岗位、优先级和风险。低覆盖公司的缺失不得被解释为低竞争。

### 8.4 简历分析

将候选人经历与岗位需求、友商能力组合和产品阶段对照；不得仅因出现友商公司名称直接提高评分。结论必须落到具体经历和能力证据。

### 8.5 面试题

根据关键能力、行业失效场景、工程化难点和产品阶段生成问题，同时给出考察点、追问、好答案信号和风险信号。外部情报用于增强问题背景，不得泄露内部机密或把推断描述为候选人事实。

## 9. 数据清洗和比较口径

新版 Bundle 必须：

- 统一城市、区域和多地办公表达，消除已知脏值；
- 统一公司别名、招聘类型、学历、资历和技能名称；
- 识别重复岗位、重复渠道及可能的常年人才池；
- 保留原始值和规范化值，保证可审计；
- 公司横向比较同时展示绝对数量、公司内部占比、来源覆盖度和样本置信度；
- 对极大样本公司进行归一化展示，避免单家公司支配行业结论；
- 将分类“其他”作为待优化清单，不作为业务方向结论。

## 10. 错误处理和安全边界

- Markdown 编译、索引生成或验证失败时，不生成完成状态 Bundle；
- 已发布 Bundle 保持 last-known-good，不被失败构建替换；
- 所有路径必须位于当前 Bundle，禁止绝对路径、软链接和 `..`；
- Markdown 和索引必须进入 `checksums.sha256` 与 Manifest 文档索引；
- 生产导入器继续禁止公网、模型密钥、Collector 和模型客户端；
- 来源内容视为不可信数据，不能改变系统指令或触发工具；
- 公开岗位中的非必要个人信息在归档前清除；
- 新 Bundle 未经 Owner 对精确 Bundle ID 和精确代码 SHA 的确认不得导入生产。

## 11. 质量门禁

### 11.1 内容质量

- 100% 可引用事实具有来源 URL、证据 SHA-256 和观察时间；
- 100% AI 研判明确标识并引用依据事实；
- 每个重要研判至少提供一个替代解释或反证检查；
- 证据不足、失败和未观察状态不会被输出为零招聘或确定性结论；
- 公司级推断通过重复度检查，不存在跨公司复用的模板结论；
- 已知公司、地点、招聘类型和一级技术分类无脏值；
- 每家公司都能回答“在招什么、对应什么产品与能力、奥比应该怎么行动”；
- 单次基线不产生月度增减结论。

### 11.2 Bundle 完整性

- `agent/` 全部文件由校验和覆盖；
- Markdown Front Matter、章节、事实 ID 和证据引用通过 Schema 校验；
- `chunk-index.json` 与文件内容、片段哈希和路径完全一致；
- Bundle 严格校验不允许意外文件、孤立引用或超限片段；
- Markdown、PDF、Excel、JSON 和页面摘要对核心数字保持一致。

### 11.3 Agent 检索验收

建立不少于 30 个固定验收问题，覆盖六类核心任务、12 家公司、主要技术方向、部分来源和无证据场景。门槛为：

- 上下文相关率不低于 90%；
- 应有证据可追溯率 100%；
- 伪造来源数量为零；
- 明确公司查询不会优先返回其他公司；
- 未知项不会被改写为否定事实；
- 重试使用相同 Bundle、相同片段、相同顺序；
- 无 Markdown 时可以受控降级且任务仍可执行；
- JD/JR、画像、搜寻、简历和面试输出体现匹配情报，而不是通用模板。

## 12. 实施顺序

实施计划应依次完成：

1. 固定 Bundle v2、Markdown 和片段索引契约；

## 13. 发布边界

本设计获批不等于生产发布获批。开发和新 Bundle 生产全部在本地完成。生产阶段仍必须满足既有磁盘门禁、Release 纪律、共享服务器边界和发布报告要求。

任何代码变化或 Bundle 重建都会使先前发布批准失效。最终发布必须使用当时重新提交的完整代码 SHA 和 Bundle ID，且只影响 AI Agent Platform 的 HR 情报读取能力，不修改其他应用、共享 Nginx 或其他 Bot。
