# HR Agent R1.2 业务可用版设计

**日期：** 2026-09-04  
**状态：** 用户已确认“可用第一”，等待书面设计复核  
**上位需求：** `2026-09-03-hr-position-lifecycle-workbench-requirements.md`  
**前置设计：** `2026-09-04-hr-position-intelligence-release-1-design.md`  
**前置版本：** R1.1 已于本地提交 `c0550ef` 合入 `master`，尚未发布生产

## 1. 设计结论

R1.2 不再按数据表或技术层逐项交付，而是一次完成 HR 当天能使用的岗位与候选人智能闭环：

```text
打开已有真实岗位
  → 系统自动带入完整官网 JD 和当前已确认岗位上下文
  → HR 选择岗位材料并发起常用任务
  → HR Agent 生成 JD / JR / 人才画像 / 搜寻策略 / 面试标准
  → 结果可阅读、修改、比较和下载
  → HR 确认后形成新的岗位上下文版本
  → 新会话自动复用该版本，且不会混入其他岗位材料
  → 上传一份或一批简历，逐份形成待确认候选人
  → 基于同一岗位上下文完成匹配、比较和候选人专属面试题
  → HR 的纠正进入后续分析，AI 结论与人工判断始终分开
```

只有上述路径完整通过，R1.2 才算完成。单独建表、单独显示按钮或只在聊天中返回一段文本均不算
交付。

本设计根据用户最新确认，将 Candidate 最小闭环提前到 R1.2，覆盖前置设计中“第一阶段不创建
Candidate”和“候选人能力推迟”的旧边界；其他产品边界继续沿用前置设计。

## 2. 优先级与范围

### 2.1 本批必须完成

1. 现有官网岗位与已恢复 HR 会话能够通过受审计导入进入试点用户工作台；
2. 保存完整官网岗位事实版本，不再只保存标题、地点和内容哈希；
3. 建设 PositionContextVersion 草稿、确认、比较和并发冲突处理；
4. 每次岗位对话向 HR Agent 注入精确、可追溯的岗位上下文；
5. 建设岗位级材料与成果中心，跨该岗位多个会话查看、选择、预览和下载；
6. 提供 JD、JR、人才画像、搜寻策略、岗位通用面试方案五个快捷任务；
7. Agent 结果能够形成待确认上下文草稿，确认后供后续对话使用；
8. 建设 Candidate、CandidateDocument 和 PositionCandidate 的最小正式模型；
9. 支持单份及批量简历逐份解析、确认、失败隔离和重试；
10. 支持岗位匹配分析、候选人专属面试题和同岗位候选人比较；
11. 人工纠正单独保存并进入后续同岗位、同候选人分析；
12. 刷新、断网、Worker 重启和任务失败后能够恢复真实状态并重试。

### 2.2 后续增强但不阻塞 R1.2

人才组织情报的定期跟踪、面试记录深度分析、岗位复盘和从面试结果提出画像改版建议进入后续
增强。R1.2 仍可通过自由对话研究公开来源，但不把一次研究自动变成长期关注任务。

### 2.3 继续排除

不建设北森、OA、猎聘、BOSS 直聘接口，不建设候选人流程、排期、Offer、入职、自动联系、
自动淘汰或自动录用，也不制作这些能力的占位页面。

## 3. 用户工作流

### 3.1 首次进入

- 岗位页直接显示已导入的官网岗位、内部岗位和待确认历史岗位；
- 无数据时明确显示“尚未完成岗位数据准备”，不伪装成“没有岗位”；
- 官网岗位显示最后成功同步时间、来源版本和当前状态；
- HR 点击岗位后默认进入对话，不先经过配置向导。

### 3.2 完成一项岗位工作

- 页面顶部始终显示当前岗位和当前上下文版本；
- HR 可直接提问，也可选择五个快捷任务之一；
- 发起前可以从岗位材料中心勾选本轮材料；默认不自动全选；
- 执行中沿用现有长任务进度和恢复能力；
- 完成后聊天中显示答案，成果中心登记文件或结构化结果并提供下载；
- 若结果可更新岗位知识，页面显示“形成上下文草稿”，不会自动覆盖当前版本。

### 3.3 确认与复用

- 上下文草稿按模块展示变化：岗位使命、JD、JR、能力、画像、搜索、面试标准、未知项；
- HR 可以整体确认，也可以只确认选中的模块；未确认部分继续保留为草稿；
- 确认产生新的不可修改版本，并显示与上一版的差异；
- 之后新建或继续岗位对话时自动使用最新已确认版本；
- 旧任务与旧成果继续指向其实际使用的版本，不被重写。

### 3.4 简历与候选人

- HR 在岗位内上传一份或一批简历；每份文件拥有独立解析状态；
- 一份失败只影响该文件，其他文件继续完成；失败项可以单独重试；
- AI 提取稳定称谓、经历、项目、技能、未知项和来源，先形成 CandidateDraft；
- HR 明确确认后才创建 Candidate 和 PositionCandidate；身份不确定时不自动合并；
- 原始简历仍由 Attachment Service 保存，CandidateDocument 只记录业务归属和版本；
- 同一 Candidate 可以关联多个 Position，但匹配、面试和人工判断按 PositionCandidate 隔离。

### 3.5 匹配、比较与面试

- 单人匹配逐项区分证据、合理推测、未知项、冲突和待验证问题；
- “材料没有证明”显示为未验证，不能显示为候选人不具备；
- 专属面试题说明验证目标、针对该人的原因、追问、有效证据和风险信号；
- 同岗位比较只选择使用同一 PositionContextVersion 的分析；版本不同则提示重算或分组；
- 比较展示适配差异、证据覆盖和未知项，不只给总分或排名；
- HR 纠正独立保存为 HumanFeedback，后续分析自动带入，但不改写旧 AI 版本。

## 4. 数据模型

### 4.1 OfficialPositionVersion

保存官网岗位的不可覆盖事实版本：

- `official_position_version_id`、`position_id`、官网 J 编号；
- 标题、部门、地点、职责、任职要求及其他已发布字段；
- 来源版本、来源时间、内容哈希、首次与最后观测时间；
- 官网状态与状态原因；
- 原始快照证据引用。

新官网版本只更新 Position 的“当前官网版本指针”，不修改内部上下文。

### 4.2 PositionContextVersion

由以下记录组成：

- 不可变 `context_version_id` 与递增显示版本；
- `position_id`、状态 `draft / confirmed / superseded`；
- 结构化模块与可读摘要；
- 基于的官网版本、上一上下文版本；
- 来源 Conversation、Turn、ArtifactVersion 和材料 ID；
- Agent/模型版本、创建人、确认人和时间；
- 乐观并发 `row_version`。

同一 Position 最多一个当前 confirmed 版本。草稿可以并存，但确认必须声明基于哪个当前版本；
基线已变化时返回冲突并展示差异，不能覆盖。

### 4.3 PositionTaskRecord

不复制现有 Mission/Turn，只保存 HR 业务投影：

- 任务类型；
- 使用的 position、official version、context version；
- 本轮显式启用的附件 ID；
- 来源 Conversation/Turn 与输出 ArtifactVersion；
- 是否产生上下文草稿及其 ID。

它用于追溯“这份结果基于什么”，不建设新的任务引擎。

### 4.4 CandidateDraft 与 Candidate

CandidateDraft 保存单份简历或明确对话请求的解析提议、来源附件、解析状态、身份歧义和错误信息。
Candidate 保存用户确认后的稳定人才事实。对话出现姓名不代表自动创建 Candidate；跨文档合并必须
经用户确认。

### 4.5 CandidateDocument

记录 Candidate 与原始 Attachment 的关系、材料类型、版本、内容哈希、来源和有效状态，不复制文件
字节。每个解析和分析记录必须指向精确 CandidateDocument 版本。

### 4.6 PositionCandidate

以 `position_id + candidate_id` 表达候选人与岗位的关系，保存加入来源和当前使用的岗位上下文版本。
关系状态只表示是否启用分析，不表达投递、筛选、面试、Offer 或入职阶段。

### 4.7 CandidateAnalysisVersion 与 HumanFeedback

CandidateAnalysisVersion 保存不可覆盖的简历提取、岗位匹配和面试方案分析，记录岗位上下文、材料
版本、结论、证据、未知项、风险和 Agent/模型版本。

HumanFeedback 单独记录用户对具体结论的认可、否定、纠正和原因。重新分析可以引用反馈，但不得把
反馈改写成 AI 结论，也不得覆盖历史分析。

所有候选人对象按 owner 隔离，不记录与招聘判断无关的受保护信息。CandidateDocument 沿用现有
附件的一年保留、擦除和下载授权边界；附件被擦除后，业务关系保留最小审计状态但不得继续读取内容。

## 5. Agent 上下文与执行

Platform 在执行前组装不可变 `HrPositionContextEnvelope`：

```text
position identity
+ current official facts/version
+ current confirmed context/version
+ current Candidate and PositionCandidate identity when selected
+ confirmed candidate facts and exact document versions when selected
+ applicable HumanFeedback
+ explicitly enabled ready materials
+ current conversation summary/recent turns
+ current user request/task type
```

约束：

- Position、context version 和材料授权任一验证失败，本轮明确失败，不降级成普通无上下文回答；
- 只包含本轮显式启用且状态为 ready 的材料；
- Envelope 记录精确 ID 和内容哈希，任务恢复时继续使用原 Envelope，不静默换成新版本；
- HR MetaBot 收到用户可理解的岗位背景以及机器可验证的边界元数据；
- Agent 只能提交草稿建议，不能写 confirmed 版本或冒充人工确认；
- 候选人任务缺少 PositionCandidate、岗位上下文或材料版本时明确失败，不退化为跨岗位分析。

五个快捷任务只是可靠的任务意图和输出契约，不另建五套执行系统。自由对话与快捷任务共用同一
Conversation、长任务、附件和 Artifact 底座。

## 6. 岗位级材料与成果中心

岗位工作台提供可折叠右栏和独立完整视图：

- 材料：聚合该 Position 下所有会话中已明确晋升的用户附件；
- 成果：聚合该 Position 下所有已登记 ArtifactVersion；
- 每项显示名称、类型、状态、来源会话/任务、创建时间和版本；
- 支持预览、单个下载和沿用现有安全批量下载；
- 材料可停用但不删除原附件；停用后不能进入新任务；
- 处理中、隔离、过期或擦除中的附件不可选择，并显示用户语言原因；
- 历史附件和成果回填只建立业务绑定，不复制文件，不修改历史 Turn。

页面不得根据数量或当前会话附件推断岗位资源，所有列表由精确服务端关系返回。

## 7. 前端信息架构

保留三栏岗位工作台，不新增复杂管理菜单：

- 左栏：岗位内会话与新对话；
- 中栏：`对话 / 岗位上下文 / 候选人 / 成果`；
- 右栏：本轮材料选择，默认可折叠；
- “岗位上下文”页展示当前版、待确认草稿和历史版本比较；
- 对话输入区上方提供五个紧凑快捷任务；
- 候选人页提供批量简历导入、逐份状态、单人匹配、多人比较和专属面试题；
- 长任务、失败、恢复、草稿待确认和版本冲突都在当前工作流内显示；
- UI 不展示 Mission、Run、Trace、Adapter、数据库状态或内部错误码。

移动端改为单列：岗位头部 → 当前内容 → 底部对话输入；材料和版本历史使用抽屉，不横向压缩三栏。

## 8. API 边界

新增接口按 owner 和 position 精确授权，至少包括：

- 官网事实版本列表与详情；
- 岗位上下文当前版、历史版、草稿创建、模块化确认和差异；
- 岗位材料列表、启用/停用和本轮选择验证；
- 岗位成果列表及现有下载票据委托；
- 带任务类型、上下文版本和材料 ID 的岗位对话提交；
- CandidateDraft 批量创建、逐份状态、单项重试、确认与身份冲突处理；
- Candidate、CandidateDocument、PositionCandidate 列表与详情；
- CandidateAnalysisVersion 创建、读取和同版本比较；
- HumanFeedback 追加与读取；
- 受审计的历史材料/成果绑定回填命令。

所有写请求使用幂等键；确认使用基线版本和 `row_version`；跨 owner、跨 Position 或不可见资源统一
表现为不存在。

## 9. 真实数据准备

数据准备是可用性的发布门禁，不是开发后的人工备注：

1. 选择一个明确 HR 试点 owner 并核验 `hr-bot` 授权；
2. 固化真实已发布官网快照的版本和 SHA-256；
3. dry-run 输出官网岗位、历史 exact、draft、skipped、材料和成果绑定计数；
4. 使用同一稳定 run-id 执行可重放导入；
5. 对历史附件/成果只生成待核验绑定，跨岗位不确定项不得自动归属；
6. 页面抽样核对官网岗位、历史会话、材料、成果和下载；
7. 导入失败保留合法部分结果，并输出失败对象清单；同一 run-id 可继续收敛。

合入代码不会自动授权生产发布。生产数据写入仍需独立发布门禁与现场验收。

## 10. 错误与恢复

- 官网同步失败保留最后成功版本，并显示时间与失败状态；
- 上下文生成失败不产生空草稿；原任务可从失败点重试；
- 一个附件失败不使其他已选附件失效，但任务必须明确显示未使用的附件；
- 批量简历中一份解析失败不回滚其他草稿；重试复用原附件和稳定请求 ID；
- 同名、同邮箱或相似经历只产生合并建议，未经确认不合并 Candidate；
- 版本确认冲突保留用户草稿并提供差异，不要求重新生成；
- 下载失败沿用现有可重试票据，不暴露存储路径；
- Worker 或浏览器中断后恢复原任务、原上下文 Envelope 和原材料集合；
- 所有页面错误使用用户语言，且不把“同步失败”显示成“没有岗位”。

## 11. 并行实施边界

为缩短交付时间，按接口契约并行而不是串行排队：

- A 轨：OfficialPositionVersion、PositionContextVersion、确认与差异；
- B 轨：Agent Context Envelope、任务追溯和 HR MetaBot 输入；
- C 轨：岗位材料/成果查询、历史绑定回填；
- D 轨：工作台标签、快捷任务、材料选择和版本交互；
- E 轨：Candidate、文档、PositionCandidate、分析与人工反馈；
- F 轨：批量简历与候选人工作台交互。

先冻结 API/类型契约和数据库迁移，再由六轨分别 TDD；每轨使用独立工作树，禁止并发编辑同一文件。
集成顺序为 A/E → B/C → D/F，但开发和单元测试并行进行。

内部集成分三批完成：第一批冻结迁移、API 与类型契约；第二批同时打通岗位闭环和候选人数据闭环；
第三批接入 Agent、页面与恢复验收。三批只用于降低开发耦合，R1.2 对业务仍作为一个完整版本发布，
不会把半成品页面先交付生产。

## 12. 端到端验收

使用一个真实结构工程师或算法岗位完成以下场景：

1. 官网完整岗位事实和历史会话已在工作台可见；
2. HR 在旧会话上传的材料能够经明确绑定后出现在岗位材料中心；
3. HR 选择材料并生成人才画像，刷新页面后任务继续；
4. 结果可预览和下载，并能反查输入上下文版本与材料；
5. HR 修改并确认画像，产生 context v1；
6. 新建岗位会话，Agent 无需用户重复背景即可引用 v1；
7. 再生成 JD 或面试方案并确认部分模块，形成 v2；
8. v1 结果仍指向 v1，v2 成为后续对话默认上下文；
9. 批量上传至少三份简历，其中一份解析失败；另外两份形成独立草稿，失败项可单独重试；
10. 确认两个 Candidate，生成各自岗位匹配和专属面试题，每项可反查岗位与简历版本；
11. 纠正其中一条分析，重跑后新版本引用人工反馈，旧版本保持不变；
12. 两名候选人在同一岗位上下文版本下比较，展示证据覆盖、未知项和差异；
13. 尝试跨岗位候选人、跨岗位材料、过期附件或过期基线确认均被阻止；
14. 全流程不出现 ATS 功能、假数据、内部 Trace 或不可下载的“结果占位”。

## 13. 完成定义

R1.2 完成必须同时满足：

- 上述端到端场景通过；
- 后端、前端、数据库迁移、恢复和权限测试通过；
- 独立代码复审无 Critical/Important；
- 真实数据导入有 dry-run 记录，但未经单独授权不执行生产 apply；
- 使用真实或合规脱敏的岗位、简历和历史会话完成业务验收，不以 Mock 数据替代；
- 发布说明明确列出磁盘门禁、回滚版本、HTTP 页面和下载验收；
- 不修改其他应用、共享 Nginx 或无关 Bot。
