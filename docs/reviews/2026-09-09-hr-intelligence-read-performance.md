# HR 情报页面读取性能修复

用户报告 `/hr/panorama?company=robosense` 加载慢。2026-09-09 已将修复部署到生产，运行提交为 `294506af3c5946e4d59954faecf5e348f2302096`。

## 原因与实测

公司直达页先等待目录返回，再按目录中的 bundle 身份读取详情。生产 API 容器内、真实应用数据库角色的两轮服务调用实测如下；这些数字不包含浏览器登录、渲染和公网往返。

| 读取 | 修复前（秒） | 上线后（秒） |
| --- | --- | --- |
| 公司目录 | 0.578 / 0.582 | 0.3682 / 0.3713 |
| 速腾聚创详情 | 1.764 / 1.750 | 0.4213 / 0.3992 |
| 岗位分页 | 0.030 / 0.026 | 0.0255 / 0.0250 |

目录与详情的后端等待合计从约 2.34 秒降至 0.78 秒，减少约 67%。岗位默认按需展开，不是首次正文加载的主要成本。

详情响应只有 13,267 字节，但数据库中的 `analysis` JSON 有 157,049,778 字节（86 个单元，存储大小 72,698,792 字节），含生产时的请求与证据输入。旧查询在字段投影前调用 `jsonb_array_elements`，将大输入一起物化并写入临时磁盘；相关专题摘要的关联子查询又重复展开了同一份输入。新增相关专题放大了这个实现缺陷。

生产只读 `EXPLAIN (ANALYZE, BUFFERS)`：旧目录临时写入 19,489 块；旧详情读取 125,049 块、写入 86,071 块。关闭 JIT 不能消除该问题，因此没有调整数据库 JIT 配置。

## 修复

在 `panorama_repository.py` 中用 `jsonb_to_recordset` 先保留单元身份、类型、范围和响应四个字段，再通过物化 CTE 供现有展示投影复用。公司目录、公司详情、专题目录和专题详情共用这个预投影；相关专题不再重复展开完整生产输入。

原有授权读取函数、参数化查询、当前与固定 bundle 语义保持不变。没有数据库迁移、重新生产或导入情报，也没有用缓存掩盖查询成本。

## 验证

- 在同一生产快照下只读对比原查询与优化查询：上述四类返回对象完全相同，各两轮；优化查询临时写入为零。
- 新回归使用真实 bundle 和一次性 PostgreSQL、真实应用数据库角色及生产同等 4 MB `work_mem`，检查实际执行计划。旧代码以 19,489 个临时写入块失败；修复后公司目录、当前/固定公司及各专题查询均通过。
- 93 项后端测试通过，包含真实 HTTP、持久化登录与中央授权、12 家公司及 6 个专题、证据读取、选定引用持久化/重放、固定 bundle 读取和撤权拒绝，以及登录安全回归。
- 136 项相关前端测试通过，生产构建通过，Ruff 与 diff 检查通过。
- 生产发布后的目录、速腾聚创、专题和岗位服务读取正常；健康检查正常。只重建 API，其余容器与 Nginx 未改动。
- 公网健康接口返回 200；公司与专题接口对匿名请求仍返回 401。公网 JS/CSS 与合并后本地生产构建逐字节相同。

前端目录与详情串行关系仍存在；以上降幅只描述已测量的后端成本，不代表已测量用户登录会话的整页加载时间。本轮没有登录用户生产会话，也没有调用模型。
