# 机器人数据投入价值判断：7 个公开岗位原文可支持的画像、搜寻方向与经历核验动作（第 2 稿）

# 修订说明（第 2 稿相对第 1 稿）

本稿修正了上一稿三处与原文不符或过于绝对的表述，并把搜寻方向落到一个可执行的经历核验动作：

1. 第 1 节与 4.6 原写"成本侧完全缺席、全文没有成本任何表述"，与岗位 1 原文"降低人工成本"矛盾（该句上一稿自己在 2.1 已引用）。本稿区分：已明示的**自动标注替代人工、降低标注人工成本**这一目标，与**尚未提供**的量化核算口径、整体经济性、预算权限。
2. 第 5 节原写岗位 2"向 RL 组输出空间 Token"，改变了原文的接口对象。本稿按原文分列两项职责：向**端到端模型**输出空间 Token；**与 RL 组协同**提供动态场景下的状态预测（世界模型）。
3. 2.4 原写岗位 4"没有任何价值/评估表述"过于绝对。本稿保留原文"打通数据、训练、评测和模型发布流程"这一事实，再说明它为何不足以证明独立的数据投入价值决策能力。
4. 新增 3.F：一个用人方可直接执行的经历核验动作，用于检查候选人实际负责过的实验与投入取舍、其证据与责任范围，而不是凭会议、数据集名、公司背景或岗位头衔确认能力。

第 1 稿保留在历史修订中可追溯。

# 0. 本研究的范围与材料状态

唯一证据来源：用户本次选定材料（agibot 归档中定向选择的 7 个岗位完整 description/requirement，观察时点 2026-09-06，来源域 agirobot.jobs.feishu.cn）。材料首段自述：这不是 agibot 1,539 岗全量，也不是全部 3,437 岗全量；标题中的"子公司/业务部"文字属公开招聘表述，不构成法律实体认证；不把归档目录聚类当组织关系证据。本研究遵守该边界。

该材料为公开静态归档，只说明 2026-09-06 的观察结果，不能据此声称这些岗位当前仍在招或文案仍是这一版本；材料未经官网核验。

# 1. 用户目标拆开：材料支持哪一半，缺哪一半

用户目标是"判断机器人数据投入是否值得"。这需要两侧证据：**收益侧**（多一批数据带来多少能力提升）与**成本侧**（这批数据要花多少钱/人/工时/机时）。

- **收益侧**在材料中有大量、可定位的原文支持（第 2 节）。
- **成本侧有一个已明示的信号，但只有这一个**：岗位 1 原文"基于VLM/VLA大模型构建自动标注管线……降低人工成本"。这明确写出了一个成本方向的目标——**用自动标注替代人工标注，降低标注环节的人工成本**。因此不能说这组岗位对成本毫无意识。
- 但这个信号能支持的范围很窄。材料**未提供**：成本的量化核算口径（单条轨迹成本、采集站机时、标注单价、外部采购价均未出现）、数据投入的整体经济性视角（除标注人力外的采集、场地、设备、返工成本均未提及）、以及预算或采集排产的决策权归属。岗位 1 的"建立数据价值评估模型"、岗位 5 流水线中的"价值评估"，从上下文看是技术效用口径（样本对模型能力的贡献），不是经济性口径。

所以本研究能给出的是：材料支持去找**能用实验和指标判断数据边际效用、并据此改变采集与配比决策的人**，且该角色可能被期待以自动化手段压降标注人工投入；而"是否值得"当中的成本核算口径与预算权限，必须由用人方补充（第 6 节），既不能说这里没有成本信号，也不能据一句"降低人工成本"给这个角色补出一份完整的投入产出（ROI）职责。

# 2. 关键判断 → 对应岗位正文

## 2.1 与目标最直接对应的一条正文（岗位 1）
「优才-具身智能算法研究员（预训练方向）-觅蜂子公司」（public_job_key 7652174229690353971，校招）description 原文：
- "牵头制定数据混合策略：真机遥操作数据 : 无本体人类视频 : 仿真合成数据的最优比例，设计消融实验验证，**建立数据价值评估模型**"
- "设计主动学习策略，从海量数据中筛选高价值样本（失败轨迹、长尾场景）"
- "基于VLM/VLA大模型构建自动标注管线，对视频、轨迹、触觉信号进行结构化标注（动作阶段、接触事件、成功/失败标签），**降低人工成本**"

判断：这是材料中唯一把"不同来源数据该投多少"写成可验证方法（配比 + 消融实验 + 价值评估模型 + 主动学习筛样）的岗位正文，也是唯一同时出现成本方向目标的岗位。用户目标的技术内核对应这里。

## 2.2 收益度量口径的建设者（岗位 3、岗位 6）
- 岗位 3「数据模型和解决方案系统工程师-Genie业务部」（7662008887891544358）：第 1 条"数据采集链路、**数据质量评估**与闭环优化方案设计……遥操作、传感器、运控、任务执行等多源数据的统一定义、采集、标注、回流和使用"；第 3 条"模型评测体系设计……**任务成功率、泛化能力、稳定性、时延、资源消耗**等指标体系建设"。这是"收益怎么量"的口径供给方，视角是系统工程与跨团队推动（requirement 第 5、6 条：系统抽象、跨团队协作、接口定义、验证思维），学历门槛仅"本科及以上"。
- 岗位 6「数据闭环工程师(指标+数据集)」（7600669099098376457，社招）：运营指标树、看板、"机器人交互的离线评测指标"、"维护数据清洗和筛选的pipeline，用于测试数据集更新"；requirement 只要 SQL + Python（pyspark/requests/pytest），加分项是 **ASR/NLU/TTS 语音交互**。对应度量与数据集维护的执行层，但其评测对象在正文里是机器人运营与语音交互体验，与具身操作数据的价值判断不是同一件事（见 4.4）。

## 2.3 组织/资源侧的取舍者（岗位 5、岗位 7）
- 岗位 5「具身数据总监」（7662252061434284329，社招）原文："**场景化采样策略**：针对大量落地项目，如导购、装配、巡检等不同业务场景，确定Ego与真机（全局物理状态）数据的**最佳采集方案**"；"本体建模（Ontology）：定义……标准化结构，确保跨场景数据的可复用性与可查询性"；"数据闭环流水线：……回流原始数据 → 清洗/处理 → **价值评估** → 模型消费 → 反馈回写……注意数据隐私、安全合规"。这是最接近"在多个落地场景之间分配采集投入"的岗位。
- 岗位 7「具身数据平台产品经理」（7623604735216191785，社招）：中台覆盖"采集、标注、挖掘、分析、存储及复用"，要"精准响应研发、测试、落地等不同阶段的差异化数据需求"，并"平衡技术可行性与业务价值"。这是需求排序/优先级意义上的价值判断者，requirement 明确"5年以上数据领域产品相关经验……**有自动驾驶、大模型相关业务经验者优先**"。

## 2.4 评测链路的工程前提，而非投入取舍的判断者（岗位 4）
岗位 4「分布式数据平台研发工程师-灵犀业务部」（7677794196577536319，校招，2027 届）description 原文包含两条与判断能力相关的事实，须保留：
- 第 1 条"参与 PB 级数据存储与管理平台建设，支持数据检索、版本、权限和**血缘管理**"；
- 第 3 条"建设采训推一站式平台，**打通数据、训练、评测和模型发布流程**"。

因此不能说该岗与评估无关：**评测被明确写入其要打通的链路，血缘与版本也是把模型收益归因到具体数据批次的技术前提**。

但这三点不足以证明独立的数据投入价值决策能力：正文的动词是"建设""打通""支持"，交付物是把评测作为流水线的一环连起来并保证其可运行；正文没有指标定义、阈值判定、消融或对照实验，也没有"据评测结论改变采集或配比"的任何表述。requirement 全部是分布式系统与平台工程能力（Python/C++/Rust/Go/Java、Kafka/S3/Spark/Ray/Flink/Docker/K8s、2027 届本科起），不含实验设计或统计判断要求。结论：**岗位 4 提供的是归因与评测的工程前提，价值判断的口径与取舍不在其正文范围内。**

# 3. 应该到哪里找、找什么经历、为什么（材料支持的线索）

**A. 机器人学习的数据配比/数据策展研究者（最贴合 2.1）**
- 找什么：做过 data mixture / data scaling / data curation for robot learning 或 VLA 预训练数据策略，并以消融实验支撑过"某类数据要不要继续采"的结论；处理过 **Ego4D、Open X-Embodiment、HoloAssist 或自采真机混合数据**，有 Sim2Real 迁移实战。
- 为什么：这些数据集名与方法名都是岗位 1 的原文（含加分项"处理过Ego4D、HoloAssist或自采机器人混合数据，有Sim2Real迁移实战经验"），可作为检索词与经历对照，而非我们外加的偏好。
- 去哪里：CoRL/ICRA/RSS/NeurIPS/CVPR/ICCV/ECCV（岗位 1、2 加分项点名的会议）相关论文与开源仓库作者；具身基座模型团队的数据方向成员。会议与论文在原文里是**加分项**，不是门槛。

**B. 智能驾驶数据闭环 / 大模型预训练数据团队（跨域迁移，材料自身背书）**
- 找什么：corner case / 长尾难例挖掘、数据配比与去重、数据质量评估、采集排产与回流闭环的落地经历。
- 为什么：岗位 5 requirement 原文把"主流多模态大模型、**智能驾驶**、具身模型"并列为可替代的经验来源（"有至少一类数据工程相关落地经验"）；岗位 7 requirement 写"有自动驾驶、大模型相关业务经验者优先"。跨域迁移是材料明写的可接受路径。
- 与目标的关系：这类团队通常同时面对"采多少、采哪些、值不值"的现实约束，最可能带来收益侧与成本侧兼顾的经验——但该岗是否真要求成本核算，材料不支持，需核实。

**C. 评测/基准体系建设者（对应 2.2）**
- 找什么：建过任务成功率、泛化、稳定性、时延、资源消耗一类多维评测口径，并让它成为迭代决策依据的人（岗位 3 第 3 条）；或 SQL+看板+离线评测的度量执行者（岗位 6）。
- 为什么：没有稳定收益口径，"值不值"无法判断；这类经历可来自 AI 平台/模型评测/质量工程，不必限具身行业。

**D. 真机采集与遥操作链路一线经验（成本侧现实感的来源）**
- 找什么：遥操作数据采集、多相机标定/时间同步、采集站与场地排产、标注质检；参考岗位 3 第 1 条、岗位 5"真机交互、遥操作、仿真数据的统一接入与管理"、岗位 2"自动标定与数据预处理管线（多相机外参自标定、时间同步、空间对齐）"。
- 为什么：判断投入是否值得，需知道一条轨迹的实际获取代价来自哪里。材料支持"这些环节存在且要被设计"，并支持"标注人工成本是被点名要压降的对象"（岗位 1），但不支持"该岗负责整体成本核算"。

**E. 数据平台产品/中台经验（对应 2.3 的排序判断）**
- 找什么：主导过数据中台核心模块（采集、标注、分析）建设，能在多个需求方之间做资源取舍；岗位 7 requirement 的"5 年以上数据领域产品经验"是原文门槛。

## 3.F 可执行核验动作：一次"数据投入取舍"的责任与证据追溯

以上 A–E 只是方向。要避免用会议名、数据集名、公司背景或岗位头衔代替能力确认，建议在初筛后的技术面固定执行下面这一项动作（约 25–30 分钟），对每位候选人同样执行：

**指令（当场给候选人）**："请选一次**由你本人负责结论**的数据投入取舍——决定某类数据继续采、加量、改配比或停采。按下面六点讲，并说明当时留下了什么可查的痕迹。"

要求候选人依次给出：
1. **决策问题与备选**：当时要在哪些方案之间选（例如真机遥操作 : 人类视频 : 仿真合成的比例调整、某长尾场景是否加采、是否改自动标注替代人工）。至少两个真实备选，而非事后叙述的唯一路径。
2. **实验设计**：怎么验证的——消融/对照怎么切分、变量与不变量是什么、样本量与随机性怎么处理、有无验证集泄漏与重复数据的处理。
3. **判据指标与阈值**：用哪个指标、在哪个评测集上、提升多少算值得、显著性或波动如何判断；若涉及成本，成本按什么单位计（工时、机时、标注单价、返工率）。
4. **结论改变了什么**：最终改了哪条采集或配比决策，改动幅度多少，何时生效；如果结论是"不采/停采"，同样有效。
5. **责任与批准**：谁提出、谁执行、谁批准、谁反对过；候选人本人在其中的具体动作（写实验脚本？定指标？说服评审？只是参与讨论？）。
6. **事后验证**：这个结论后来被复验、被推翻还是无人回看；如被推翻，原因是什么。

**可核查痕迹（请候选人在合规范围内出示或复述其存在形式）**：实验记录/看板截图、消融结果表、评审或决策会的结论文档、数据版本与批次归因记录、代码或配置提交、上线前后的指标对比。允许脱敏，不要求提供雇主机密数据本体。

**判据（面试官按此记录，不打总分）**
- 通过的样子：能自然区分"我做的"与"团队做的"；说得出反面结论与代价；指标与结论之间有可复述的因果链；对自己没权限的部分明确承认。
- 不通过的样子：只讲用过的数据集或跑过的模型；指标提升无对照或无法说明来源；"我们决定"贯穿全程无法定位本人动作；面对"如果结论相反你会怎么做"无法回应。
- **无效替代品**：顶会论文数量、参加过某评审会、接触过某知名数据集、前雇主品牌、"总监/负责人"头衔——这些都不作为本项通过依据（岗位 1、2 原文亦把顶会论文列为加分项而非门槛）。

**按各岗证据边界调整同一动作**（避免用一份画像套所有岗位）
- **岗位 1、2（觅蜂子公司标签，校招研究方向）**：允许以课题/实习中的消融实验作为核验对象，但必须能出示实验设计与本人责任；不得把"实习或协助过的任务"当作独立交付经验。两岗 requirement 文本完全相同（见 4.1），因此本项只按各自 description 出题：岗位 1 问数据配比与价值评估，岗位 2 问空间表征与标定管线的输出规范（见第 5 节），不要求岗位 2 候选人有数据配比决策经历。
- **岗位 3（Genie业务部标签）**：核验对象换成"你定义的评测口径如何改变了一次迭代决策"，痕迹为指标定义文档与评测结论。
- **岗位 4（灵犀业务部标签）**：核验对象是"评测与发布链路的打通、版本与血缘归因是否真的能追到数据批次"，痕迹为平台设计与故障/回溯案例；本项不要求其具备投入取舍决策经历（见 2.4）。
- **岗位 5、6、7（标题无组织标签，归属与汇报线不可判）**：不得从"总监"头衔推断其有预算或排产决策权（见 4.5）；对岗位 5、7 应把追问落在"在多个业务场景/多个需求方之间实际排过什么序、放弃了什么"，并明确询问其当时的权限边界（是出结论还是拍决定）。
- 上述动作核验的是候选人经历，不能反向用于推断该公司现有能力或缺口。

# 4. 不支持上述判断的材料（必须保留）

4.1 **岗位 1 与岗位 2 的 requirement 文本完全相同**（同一套"三选一方向 + 编程 + 仿真器 + 软素质 + 4 条加分项"），但 description 一个是预训练与数据策略、一个是空间智能与三维重建。该系列 requirement 是方向共用模板：**不能把 requirement 当作各方向的针对性门槛**，也不能反推"要做数据价值评估就必须具备三维重建能力"。岗位关注点应以 description 为准。

4.2 **"自动标注、数据合成与数据策略"在岗位 1 requirement 里只是三组可替代方向之一**（原文"在以下至少一个方向有深入研究和项目经验"）。该岗允许录用只有 3D 重建或模仿学习背景的人。把"数据策略经历"设为硬筛条件会偏离原文逻辑；反过来，也不能因为 description 写了数据价值评估，就认定该岗现任或候选人一定具备这项能力。

4.3 **职责期待 ≠ 现状缺失**。岗位 1"建立数据价值评估模型"、岗位 5"价值评估"环节与"搭建……管道"都是期待完成的工作。据此不能推断该公司目前没有数据价值判断能力、没有采集管道，也不能推断这些是新设空白岗（可能是扩编、替补或分工细化）。

4.4 **"数据"关键词不构成同一能力池**。岗位 4 全篇是分布式平台工程（其评测相关事实见 2.4），岗位 6 的评测对象是运营指标与语音交互（ASR/NLU/TTS），两者正文均无数据投入取舍内容。把它们与岗位 1/5 拼成同一团队或同一画像，材料不支持。

4.5 **岗位 5 的标题与要求存在落差**。标题是"总监"，但 requirement 无年限、无团队管理、无预算/编制责任要求，且写"精通Python，熟练使用PyTorch数据处理生态"，形态更像资深实操 + 体系搭建者。不能据"总监"头衔推断其拥有采集预算或决策权。

4.6 **成本表述的准确边界**：7 个岗位中出现的成本表述只有岗位 1 的"降低人工成本"，指以自动标注管线替代人工标注。除此之外，全部 7 岗**未出现**预算、单价、采集工时、人力编制、供应商报价、投入产出/ROI 等表述。因此可以说"存在压降标注人工投入这一目标"，但**不能**说"这家公司在用经济口径衡量数据投入的整体值不值"，也不能说"完全没有成本意识"。这两个方向的推断都超出原文。

4.7 **样本是 7/1,539 的定向选择**。"公司没有专门负责数据成本核算的岗位""数据价值判断只由这几个岗承担"等否定性结论均不成立——未纳入的岗位可能更直接。

4.8 岗位 1、2 的加分项包含顶会论文与开源贡献，属加分而非门槛；论文数量本身不作为能力证明使用。

# 5. 用人实体与责任边界：哪些有材料支持

**有材料支持（仅作为公开招聘表述）**
- 招聘标题出现 3 个不同组织标签：**觅蜂子公司**（岗位 1、2）、**Genie业务部**（岗位 3）、**灵犀业务部**（岗位 4）；岗位 5、6、7 标题**无任何组织标签**。
- 渠道分层清晰：岗位 1–4 为校招（岗位 4 明写"2027 届"），岗位 5–7 为社招；两组分别取自两个不同的归档 SHA-256（21d3…6da7a 与 189b…f09d5）。
- 岗位 1、2 属同一招聘系列（同名"优才-具身智能算法研究员"、同一子公司标签、同一 requirement 文本）的两个方向，可称并行方向。
- **岗位 2 正文写明的两项对外职责，须分别表达**（原文："向端到端模型输出可消费的空间Token（如场景图序列、可操作实体列表、接触点坐标），并与RL组协同提供动态场景下的状态预测（世界模型）。"）：
  - ① **输出对象是"端到端模型"**：该岗要产出可被端到端模型消费的空间 Token（场景图序列、可操作实体列表、接触点坐标）——这是一项接口规范与数据产出职责。
  - ② **与 RL 组的关系是"协同提供状态预测（世界模型）"**：这是一项协作职责，协作对象是 RL 组，协作内容是动态场景下的状态预测，而不是向 RL 组交付空间 Token。
  - 边界：材料中唯一出现的内部团队名称是这里的"RL组"。这说明**招聘文案中提到了一个名为 RL 组的协作对象与一项协作期待**；不能据此认定该组的规模、职能范围、汇报关系，也不能认定这项协同已经在运行——招聘中的协作期待不等于已确认的团队组织事实。
- 责任分工在正文层面可辨的边界：数据配比与价值评估模型（岗位 1）／空间表征、标定管线与空间 Token 输出（岗位 2）／采集链路 + 模型评测体系 + 端边云闭环的系统方案（岗位 3）／PB 级存储、流水线与采训推链路打通（岗位 4）／跨业务场景采样策略 + Ontology + 闭环体系（岗位 5）／运营与交互质量指标（岗位 6）／数据中台产品化与优先级（岗位 7）。

**无法判断（材料明确不支持）**
- 觅蜂子公司、Genie业务部、灵犀业务部之间的组织层级、法律主体关系、是否同一产品线；材料首段已声明标题文字不构成实体认证、不把目录聚类当组织关系。
- 岗位 5（具身数据总监）是否管理岗位 3/4/6/7 的任一职能、是否同一汇报线；岗位 7 服务哪个业务部；岗位 6 归属哪个实体或产品线。
- 谁最终决定"这批数据继续采/停采"：岗位 1 写"牵头制定数据混合策略"，岗位 5 写"确定……最佳采集方案"，两者都有决定性动词，但相互关系与优先级未写。
- 编制性质（新增/替补）、职级、薪酬、地点、汇报对象、团队规模、面试流程、招聘紧迫度，全部无材料。
- 观察时点之后的有效性：不能声称官网当前仍有这些岗位或此版本文案。

# 6. 需要向用人方/市场补充核实的问题
1. 用户要找的人对应哪一类形态：算法研究侧（岗位 1 型）、系统评测侧（岗位 3 型）、体系与采样策略侧（岗位 5 型）、还是平台产品侧（岗位 7 型）？渠道与画像完全不同。
2. "是否值得"的成本口径由谁提供、以什么单位计（单条轨迹成本？采集站机时？标注单价？外部采购价）？材料只给出"降低标注人工成本"这一目标方向，没有任何核算口径。
3. 该角色是否有预算或采集排产的决策权，还是只出结论供他人决策？岗位 5 requirement 未写管理与预算责任。
4. 是否需要与外部采集/标注供应商或数据交易方打交道（材料未提；不能据岗位缺席推断没有外部合作）。
5. 血缘/版本与采训推链路（岗位 4）当前是否已可用？若不可用，数据价值归因缺少技术前提，会改变对候选人经验的要求。
6. 岗位 6 所属产品线是否与具身操作数据体系相关，或属独立的机器人运营/语音交互线。
7. 市场供给：本材料无法判断这类人是否稀缺（仅凭要求组合不能推断稀缺度），也不构成放宽门槛的依据；需另做市场侧取样。
