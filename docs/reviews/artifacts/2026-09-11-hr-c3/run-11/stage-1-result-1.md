# 「能判断机器人数据投入是否值得的人」：基于 agibot 归档 7 岗全文的搜寻方向与责任边界研究（观察时点 2026-09-06）

# 0. 本研究的范围与材料状态

唯一证据来源：用户本次选定材料（agibot 归档中定向选择的 7 个岗位完整 description/requirement，observed_at 2026-09-06，来源域 agirobot.jobs.feishu.cn）。材料首段自述：这不是 agibot 1,539 岗全量，也不是全部 3,437 岗全量；标题中的"子公司/业务部"文字属公开招聘表述，不构成法律实体认证；不把归档目录聚类当组织关系证据。本研究遵守该边界。

该材料为公开静态归档，只说明 2026-09-06 的观察结果，不能据此声称这些岗位当前仍在招或仍是这一版本。材料未经官网核验，故本成果 basis 为空（属普通 research，非标准/JD 类交付）。

# 1. 先把用户的目标拆开：材料支持哪一半，缺哪一半

用户目标是"判断机器人数据投入是否值得"。这在逻辑上需要两侧证据：**收益侧**（多一批数据带来多少模型能力提升）与**成本侧**（这批数据要花多少钱/人/工时/机时）。

- 收益侧在材料中有大量、可定位的原文支持（见第 2 节）。
- **成本侧在 7 个岗位正文中完全缺席**：全文没有出现预算、成本、单价、采集工时、人力编制、供应商报价、投入产出/ROI 任何表述。岗位 1 的表述是"建立数据价值评估模型"、岗位 5 是流水线中的"价值评估"环节，都是技术效用口径，不是经济性口径。

因此本研究能给出的是：**材料支持去找"能用实验和指标判断数据边际效用、并据此改变采集与配比决策"的人**；而"是否值得"里的成本口径、预算权限，必须由用人方补充（第 6 节问题清单），不能从这组材料推出。

# 2. 关键判断 → 对应岗位正文

## 2.1 与目标最直接对应的一条正文（岗位 1）
「优才-具身智能算法研究员（预训练方向）-觅蜂子公司」（public_job_key 7652174229690353971，campusrecruitment）description 原文：
- "牵头制定数据混合策略：真机遥操作数据 : 无本体人类视频 : 仿真合成数据的最优比例，设计消融实验验证，**建立数据价值评估模型**"
- "设计主动学习策略，从海量数据中筛选高价值样本（失败轨迹、长尾场景）"
- "基于VLM/VLA大模型构建自动标注管线……**降低人工成本**"（全材料中唯一出现"成本"二字，且指标注人力成本，不是采集投入的整体经济性）

判断：这是材料中唯一把"不同来源数据该投多少"写成可验证方法（配比 + 消融实验 + 价值评估模型 + 主动学习筛样）的岗位正文。用户目标的技术内核对应这里。

## 2.2 收益度量口径的建设者（岗位 3、岗位 6）
- 岗位 3「数据模型和解决方案系统工程师-Genie业务部」（7662008887891544358）：第 1 条"数据采集链路、**数据质量评估**与闭环优化方案设计……遥操作、传感器、运控、任务执行等多源数据的统一定义、采集、标注、回流和使用"；第 3 条"模型评测体系设计……**任务成功率、泛化能力、稳定性、时延、资源消耗**等指标体系建设"。这是"收益怎么量"的口径供给方，视角是系统工程与跨团队推动（requirement 第 5、6 条：系统抽象、跨团队协作、接口定义、验证思维），学历门槛仅"本科及以上"。
- 岗位 6「数据闭环工程师(指标+数据集)」（7600669099098376457，socialrecruitment）：运营指标树、看板、"机器人交互的离线评测指标"、"维护数据清洗和筛选的pipeline，用于测试数据集更新"；requirement 只要 SQL + Python（pyspark/requests/pytest），加分项是 **ASR/NLU/TTS 语音交互**。这条对应度量与数据集维护的执行层，但其评测对象在正文里是机器人运营与语音交互体验，与具身操作数据的价值判断不是同一件事（见 4.4 反证）。

## 2.3 组织/资源侧的取舍者（岗位 5、岗位 7）
- 岗位 5「具身数据总监」（7662252061434284329，socialrecruitment）description 原文："**场景化采样策略**：针对大量落地项目，如导购、装配、巡检等不同业务场景，确定Ego与真机（全局物理状态）数据的**最佳采集方案**"；"本体建模（Ontology）：定义……标准化结构，确保跨场景数据的可复用性与可查询性"；"数据闭环流水线：……回流原始数据 → 清洗/处理 → **价值评估** → 模型消费 → 反馈回写……注意数据隐私、安全合规"。这是最接近"在多个落地场景之间分配采集投入"的岗位。
- 岗位 7「具身数据平台产品经理」（7623604735216191785，socialrecruitment）：中台覆盖"采集、标注、挖掘、分析、存储及复用"，要"精准响应研发、测试、落地等不同阶段的差异化数据需求"，并"平衡技术可行性与业务价值"。这是需求排序/优先级意义上的价值判断者，requirement 明确"5年以上数据领域产品相关经验……**有自动驾驶、大模型相关业务经验者优先**"。

岗位 4「分布式数据平台研发工程师-灵犀业务部」（7677794196577536319，campusrecruitment，2027 届）：PB 级存储、"数据检索、版本、权限和**血缘管理**"、"采训推一站式平台"。血缘与版本是把模型收益归因到具体数据批次的技术前提，但该岗正文没有任何价值/评估表述——它是能力的基础设施，不是判断者。

# 3. 应该到哪里找、找什么经历、为什么（材料支持的线索）

**A. 机器人学习的数据配比/数据策展研究者（最贴合 2.1）**
- 找什么：做过 data mixture / data scaling / data curation for robot learning 或 VLA 预训练数据策略，并以消融实验支撑过"某类数据要不要继续采"的结论；处理过 **Ego4D、Open X-Embodiment、HoloAssist 或自采真机混合数据**，有 Sim2Real 迁移实战。
- 为什么：这些数据集名与方法名都是岗位 1 的原文（description 与加分项"处理过Ego4D、HoloAssist或自采机器人混合数据，有Sim2Real迁移实战经验"），可直接作为检索词与经历对照，而非我们外加的偏好。
- 去哪里：CoRL/ICRA/RSS/NeurIPS/CVPR/ICCV/ECCV（岗位 1、2 加分项点名的会议）中相关论文与开源仓库作者；具身基座模型团队的数据方向成员。注意会议与论文在原文里是**加分项**，不是门槛。

**B. 智能驾驶数据闭环 / 大模型预训练数据团队（跨域迁移，材料自身背书）**
- 找什么：corner case / 长尾难例挖掘、数据配比与去重、数据质量评估、采集排产与回流闭环的落地经历。
- 为什么：岗位 5 requirement 原文把"主流多模态大模型、**智能驾驶**、具身模型"并列为可替代的经验来源（"有至少一类数据工程相关落地经验"）；岗位 7 requirement 原文写"有自动驾驶、大模型相关业务经验者优先"。跨域迁移不是我们的推测，是材料明写的可接受路径。
- 与目标的关系：智驾数据闭环团队通常同时面对"采多少、采哪些、值不值"的现实约束，最可能带来收益侧+成本侧兼顾的经验——但成本侧是否真被该岗要求，材料不支持，需核实。

**C. 评测/基准体系建设者（对应 2.2）**
- 找什么：建过任务成功率、泛化、稳定性、时延、资源消耗一类多维评测口径，并让它成为迭代决策依据的人（岗位 3 第 3 条）；或 SQL+看板+离线评测的度量执行者（岗位 6）。
- 为什么：没有稳定收益口径，"值不值"无法判断；这类经历可来自 AI 平台/模型评测/质量工程，不必限具身行业。

**D. 真机采集与遥操作链路一线经验（成本侧的现实感来源）**
- 找什么：遥操作数据采集、多相机标定/时间同步、采集站与场地排产、标注质检；参考岗位 3 第 1 条与岗位 5"真机交互、遥操作、仿真数据的统一接入与管理"，以及岗位 2"自动标定与数据预处理管线（多相机外参自标定、时间同步、空间对齐）"。
- 为什么：判断投入是否值得，必须知道一条轨迹的实际获取代价从哪里来。材料只支持"这些环节存在且要被设计"，不支持"该岗负责其成本核算"。

**E. 数据平台产品/中台经验（对应 2.3 的排序判断）**
- 找什么：主导过数据中台核心模块（采集、标注、分析）建设，能在多个需求方之间做资源取舍；岗位 7 requirement 的"5 年以上数据领域产品经验"是原文门槛。

# 4. 不支持上述判断的材料（必须保留）

4.1 **岗位 1 与岗位 2 的 requirement 文本完全相同**（同一套"三选一方向 + 编程 + 仿真器 + 软素质 + 4 条加分项"），但 description 一个是预训练与数据策略、一个是空间智能与三维重建。这说明该系列 requirement 是方向共用模板：**不能把 requirement 当作各方向的针对性门槛**，也不能反推"要做数据价值评估就必须具备三维重建能力"。判断岗位关注点应以 description 为准。

4.2 **"数据合成与数据策略"在岗位 1 requirement 里只是三组可替代方向之一**（原文"在以下至少一个方向有深入研究和项目经验"）。因此该岗允许录用只有 3D 重建或模仿学习背景的人。把"数据策略经历"设为硬筛条件会偏离原文逻辑；反过来，也不能因为 description 写了数据价值评估，就认定该岗现任/候选人一定具备这项能力。

4.3 **职责期待 ≠ 现状缺失**。岗位 1"建立数据价值评估模型"、岗位 5"价值评估"环节、岗位 5"搭建……管道"都是期待完成的工作。据此不能推断该公司目前没有数据价值判断能力、没有采集管道，也不能推断这些是新设空白岗（可能是扩编、替补或分工细化）。

4.4 **"数据"关键词不构成同一能力池**。岗位 4 全篇是分布式平台工程，岗位 6 的评测对象是运营指标与语音交互（ASR/NLU/TTS），两者正文均无数据投入取舍内容。把它们与岗位 1/5 拼成同一团队或同一画像，材料不支持。

4.5 **岗位 5 的标题与要求存在落差**。标题是"总监"，但 requirement 无年限、无团队管理、无预算/编制责任要求，且写"精通Python，熟练使用PyTorch数据处理生态"，形态更像资深实操+体系搭建者。不能据"总监"头衔推断其拥有采集预算或决策权。

4.6 **全 7 岗无成本/预算/ROI 表述**（唯一的"降低人工成本"在岗位 1，指自动标注替代人工标注）。所以"这家公司在用经济口径衡量数据投入"这一判断，材料不支持。

4.7 **样本是 7/1,539 的定向选择**。因此"公司没有专门负责数据成本核算的岗位""数据价值判断只由这几个岗承担"等否定性结论均不成立——未纳入的岗位可能更直接。

4.8 岗位 1、2 的加分项包含顶会论文与开源贡献，属加分而非门槛；论文数量本身不作为能力证明使用。

# 6. 需要向用人方/市场补充核实的问题
1. 用户要找的这个人对应上述哪一类形态：算法研究侧（岗位 1 型）、系统评测侧（岗位 3 型）、体系与采样策略侧（岗位 5 型）、还是平台产品侧（岗位 7 型）？渠道与画像会完全不同。
2. "是否值得"的成本口径由谁提供、以什么单位计（单条轨迹成本？采集站机时？标注单价？外部采购价）？材料无任何成本口径。
3. 该角色是否有预算或采集排产的决策权，还是只出结论供他人决策？岗位 5 requirement 未写管理与预算责任。
4. 是否需要与外部采集/标注供应商或数据交易方打交道（材料未提，不能据岗位缺席推断没有外部合作）。
5. 血缘/版本能力（岗位 4）当前是否已可用？若不可用，数据价值归因将缺少技术前提，会改变对候选人经验的要求。
6. 岗位 6 所属产品线是否与具身操作数据体系相关，或属独立的机器人运营/语音交互线。
7. 市场供给：本材料无法判断这类人是否稀缺（仅凭要求组合不能推断稀缺度），也不构成放宽门槛的依据；需要另做市场侧取样。
