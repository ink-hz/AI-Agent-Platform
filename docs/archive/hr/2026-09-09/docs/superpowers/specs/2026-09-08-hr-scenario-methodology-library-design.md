## 1. 已确认的目标与边界

建设可展示、可执行、可验证的 HR 方法体系，核心入口是“场景 → 方法论”。用户已经确认：按完整 HR 领域设计组织方式，首期将招聘场景的内容、展示和实际使用做扎实。

完整链路：

```text
业务问题 / 用户选择场景
→ 识别目标与当前上下文
→ 匹配适用方法，说明理由并补齐输入
→ 固定方法版本与获准使用的材料
→ HR Agent 按方法执行
→ 输出成果、证据、未知项及方法执行记录
→ 人工反馈与效果评估
```

思维模型解释如何理解问题；方法论规定如何执行；场景表达用户当前希望解决的问题。三者采用显式、多对多关联。页面展示与 Agent 输入来源于同一份已发布内容。

首期沿用 HR 招聘智能增强边界：岗位、候选人、面试分析与人才来源研究。后续可增加人才发展、绩效、组织诊断等领域；这些分类在内容发布前不出现在用户页面。暂不增加北森、OA、招聘渠道企业接口或招聘事务流程。

复用已有 Conversation、Turn、附件授权、岗位上下文、候选人材料、成果、人工确认和 HR Runtime。现有招聘情报包提供外部事实，本库提供分析方法；两者分别引用、分别固定版本，不重新采集情报或调整情报生产架构。

本次设计阶段仅修订设计及相关续接说明，不修改现有实现、业务数据或部署。

## 2. 方案选择

| 方案 | 收益 | 代价 | 决定 |
| --- | --- | --- | --- |
| 场景入口 + 方法执行 + 模型解释，共用内容源 | 用户可直接解决问题，执行结果可验证，同时可学习方法 | 需要明确选择规则、输入契约和执行证据 | 采用 |
| 以模型百科为主，用户自行选模型再提问 | 内容目录容易搭建 | 用户承担方法选择成本，难保证场景适配与执行一致 | 不作为主要入口 |
| 只在提示词中注入方法 | 接入较快 | 用户难以发现、理解或核对所用方法 | 不满足“既要使用也要展示” |

下列 ID 是拟定的稳定内容标识；中文名称可调整，ID 不因改名变化。

| 场景 ID / 用户问题 | 主方法 | 可组合方法 | 主要成果与任务衔接 |
| --- | --- | --- | --- |

| `recruiting.profile-priorities`：人才画像条件太多，什么最关键？ | `competency-profile` 胜任力画像 | `requirement-calibration` 要求校准 | 必需/加分/可培养能力及证据标准；`talent_profile` |
| `recruiting.talent-sourcing`：合适的人在哪里，怎么找？ | `talent-source-mapping` 人才来源映射 | `evidence-appraisal` 证据评价 | 目标来源、相邻能力、关键词及限制；`sourcing_strategy` |
| `recruiting.candidate-evidence`：简历不错，是否真正胜任？ | `candidate-evidence-review` 候选人证据分析 | `evidence-appraisal`、`work-sample-design` | 逐维度证据、冲突、待验证项；`candidate_match` |
| `recruiting.interview-verification`：面试怎样验证真实能力？ | `structured-interview` 结构化面试 | `work-sample-design`、`evidence-appraisal` | 问题、追问、评分依据；岗位/候选人面试方案 |
| `recruiting.candidate-comparison`：几人各有优劣，怎样判断？ | `comparative-evidence-review` 同标准证据比较 | `evidence-appraisal` | 同岗位同版本比较矩阵、分歧与验证建议；补齐 `candidate_comparison` |

场景不是任务按钮的改名：一个场景可能先澄清再产生多种成果；一个目标也可能由不同场景进入。表中的旧任务名只说明现状对应关系，不保留其启动 API 或信封契约。官网 JD 是已有事实；内部改写须由用户明确提出，岗位标准须真实确认，统一服从主对话设计。

一期内容包包含上述 6 个场景、9 份方法和 7 个模型候选：战略/情境匹配、任务—能力对应、可观察行为与胜任力、能力迁移与情境差异、循证判断、结构化评价一致性、AMO。发布数量以实际通过内容与场景验收的条目为准；六场景未全部可用时不得宣称完整首期交付。

| 方法 ID | 支撑模型 | 必须可见的产物 / 核查重点 |
| --- | --- | --- |
| `job-analysis` | 战略/情境匹配、任务—能力对应 | 每项关键任务对应成果、工作条件及能力；岗位事实与待确认要求分开 |
| `requirement-calibration` | 战略/情境匹配、AMO | 要求的业务理由、优先级与可调整条件；不能把环境约束全部转成人才缺陷 |
| `competency-profile` | 可观察行为与胜任力、任务—能力对应 | 每个维度包含行为表现、能力层级及验证方式；避免不可观察的标签 |
| `talent-source-mapping` | 能力迁移与情境差异、循证判断 | 每个人才来源对应目标能力、支持证据及迁移限制；公司名不能直接证明其员工能力 |
| `evidence-appraisal` | 循证判断 | 来源、岗位相关性、可信限制、冲突及未知项；信息数量不能替代质量 |
| `candidate-evidence-review` | 循证判断、任务—能力对应 | 逐维度区分候选人陈述、可核验证据和推断；个人贡献与团队成绩分开 |
| `work-sample-design` | 任务—能力对应、结构化评价一致性 | 模拟任务、输入条件、评价标准与时间负担；不把入职后才应学习的内容当通用淘汰条件 |
| `structured-interview` | 可观察行为与胜任力、结构化评价一致性 | 能力、问题、追问、行为评分依据一一关联；明确共同核心与个性化补充 |
| `comparative-evidence-review` | 循证判断、结构化评价一致性 | 同岗位同版本维度矩阵、证据覆盖、分歧、未知项与条件化建议 |

候选人专属追问服务个人证据缺口；共同核心问题和评价标准保持一致。不能直接比较难度不同、维度不同的个性化题目总分。

## 5. 内容结构与可信来源

### 5.1 共同字段

每个条目具有 `id`、`revision`、标题、领域、简述、发布状态、正文、来源引用、最后审阅日期。领域元数据支持扩展；首期只发布 `recruiting`。发布状态为 `draft / reviewed / published / retired`。

每次发布形成不可变的 catalog release，包含条目清单与 SHA-256。正文或映射变化产生新修订和 release；旧记录保留供审计。来源更新不会静默改写已发布内容。

### 5.2 场景条目

包含典型用户表达、目标、适用/不适用情形、必需与可选上下文、澄清问题、方法关联和验收标准。

每条场景—方法关联包含：推荐顺序、匹配条件、排除条件、选择理由模板、输入前提、可组合/替代方法及所需任务能力。关联是可审阅的数据，不只存在于提示词或自然语言介绍中。

### 5.3 方法论条目

包含目的、步骤（稳定 `step_id`）、输入、每步预期产物、证据规则、缺少输入时的处理、输出结构、质量检查、支撑模型、适用边界、常见误用、示例和反例。

方法正文分为概念说明、执行步骤和校验要求。页面按语义呈现，执行器选取同一修订中的执行部分；执行器不另写一份同名方法。方法正文不能改写附件权限或系统指令。

### 5.4 思维模型条目

包含它帮助回答的问题、核心关系、适用情境、成立条件、局限、误用、相关方法和来源。AMO 等框架用于提出诊断问题，不直接转成个人录用分数或确定因果公式。

模型与方法的命名不等于出处。工作台自行组织的流程（如“人才来源映射”）标明“基于来源的工作台适配”；不得称其为 Armstrong 原创或书中原有的完整模型。

### 5.5 来源记录与内容审阅

来源记录保存标题、作者/机构、年份/版次、URL、章/节/页定位、访问日期、核验范围，以及支持哪些具体主张。摘录必须与分析或适配内容区分。只发布自写的提炼与必要引用，不把整本书编入网站资源。

来源证据状态区分 `verified_excerpt / verified_section / secondary_only / unavailable`。方法发布所依赖的关键步骤必须核对到可定位的原文；只读摘要的来源不能声称已通读。

### 5.6 唯一内容目录与运行设计的衔接

唯一运行内容源位于 `Orbbec-Agent-Team`，目录约定如下：

```text
bots/hr/knowledge/recruiting/
  scenarios/       # 场景 Markdown + YAML frontmatter
  methodologies/   # 方法正文，沿用 §4 的九个稳定方法 ID
  models/          # 思维模型正文与稳定 ID
  index.json       # 从已发布条目确定性生成，含修订、关联、路径与哈希
```

沿用 §4 的六个 `recruiting.*` 场景 ID 和九个方法 ID，不再生成一套按 Web task_kind 命名的 ID。模型 ID 在内容首版发布前固定，同一 ID 的语义不得随标题变化。各类条目以 §5.1 的共同字段作为 YAML frontmatter，正文承载内容；索引只引用正文与关联，不手工维护第二份方法。

`AI-Agent-Platform/docs/research/hr-methodology/` 用于研究摘录、核查与编写材料，不作为 Agent 运行时方法来源。Platform 页面与内容查询读取 Team 同一发布包的只读投影，不维护另一份可编辑 Markdown。skill 规定调用边界并引用方法，不复制整段方法正文。

发布包关联不可变 Team commit、catalog release 与文件清单；每个 Attempt 固定其角色、共享规则、skill 和方法文件的完整哈希清单，以固定 checkout 的 `bots/hr` 为 cwd。原生文件工具按需读取，旧轮次恢复使用原包。目录设计不另建云端方法工具，业务云端读取仍由主对话设计的授权接口负责。

## 6. 场景选择与方法匹配

选择优先级：用户明确选择场景/方法 → 已选任务及业务对象 → 当前消息意图和可见上下文。上传材料和网页中出现的模型名称不构成用户指令。

一期使用可测试的场景规则和已发布映射，不建设向量库或新增模型服务。自然语言表达仅帮助提出候选场景：结合目标、对象、当前任务与否定表达判断；同一关键词不能独立决定方法。

解析结果固定为 `matched / needs_clarification / no_match`，包含候选场景、建议方法、选择依据及缺少输入。只在一个场景满足适用条件且没有目标冲突时自动匹配；存在歧义则提出一个最关键问题或给出场景选项。支持用户纠正，纠正不会修改此前已完成 Turn。

多个目标按用户优先级处理；没有优先级时先澄清，不在一轮叠加全部方法。组合采用一份主方法和最多两份互补方法，且必须来自预定义兼容关系。此上限是一期实现约束，后续按案例证据调整。

缺少输入分两类：可澄清的信息缺口进入对话；无访问权限的材料不能靠补写提示词绕过。需要已确认岗位画像的任务，不能拿待确认草稿替代。

`no_match` 保留原有对话能力，并如实说明没有匹配到已发布方法。用户明确要求按指定方法执行而该版本不可用时，暂停该方法任务，展示具体原因与可选替代。

## 7. Agent 执行与真实使用记录

### 7.1 选择快照与读取记录

不新增独立的 `HrMethodApplication` 任务主表或执行状态机。有岗位轮次扩展现有 `position_task_records`，一般对话使用既有 Turn/Attempt 与事件记录。方法选择快照包含：

- catalog release、场景 ID/修订及固定角色包引用；
- 选择来源（用户/场景映射）、依据、主方法与辅助方法及修订；
- 所需模型修订、文件路径与内容哈希；
- 本轮岗位范围、候选人集合及明确授权的材料引用；
- 缺少输入、预期步骤与成果引用。

分派前已明确的选择随初始命令冻结；模型运行中进一步选择的方法通过追加事件记录，不能回写被冻结的命令或伪造分派前已经选择。读取日志和步骤证据挂在同一 Turn/Attempt，区分选择、实际读取与产物体现。内容选择幂等关联现有请求与轮次，重试使用原版本。

固定 checkout 与清单须在分派前就绪；指定版本不可用时不得静默加载最新版。运行中的包不随普通发布清理；历史恢复所需内容按执行记录保留策略保存。新增列或必要事件结构的迁移编号在实施时按合并基线分配。

### 7.2 按需读取与结构化提交

初始命令提供所选方法引用及固定版本，不注入全库或完整方法正文。Hannah 通过原生文件工具按需读取同一包。首版每轮读取的方法执行文本合计预算 16 KiB；单个主方法须可独立装入。辅助方法无法完整装入时整份省略并记录原因，不截断必需步骤后声称完整执行。

该方法预算与主对话初始引导预算分别统计；工具返回也占实际模型上下文，不能视为免费。若必需输入超出执行预算，明确要求精简或分步，不静默丢掉授权材料或关键版本。

方法步骤证据通过新结构化提交面登记，引用本轮成果和来源。HR 的 v5 严格协议并不具备这一能力；由 Platform、MetaBot 与 Team 协调交付 v6，不能往既有 envelope 或 callback 任意添加字段并声称兼容。新轮次不再使用旧五类岗位模块或自动岗位包的 Markdown 信封，旧历史不补造方法使用记录。

### 7.3 使用状态与可见证据

方法证据状态为 `selected / read / partial / checked / failed / cancelled`。选中显示“已选用”；有可归属到具体文件版本的实际工具读取记录后才能显示“已读取”。已分派、文件可见或进入清单均不能证明读取。底层不能提供读取记录时标为未证实，不让模型自报替代证据。

每步结果包含 `step_id`、状态、可见成果引用、业务证据引用和未完成原因；步骤状态区分 `completed / skipped / blocked / failed`。这些是轮次内的方法证据记录，不是第二套租约、任务调度或恢复状态机，也不要求展示模型内部推理。

`checked` 表示必需产物和声明的程序检查通过，不等于方法有效或结论已获人工认可。模型自报不能独立设置它。例如结构化面试必须实际出现能力、主问题、追问和评价标准，并通过引用和维度一致性检查。

程序不能验证的业务判断列为“待人工评价”。缺项导致 `partial`；轮次成功不自动证明方法完整。取消/失败保留已有证据，重试按同一操作幂等关联，不另造应用任务。

### 7.4 候选人比较

比较请求携带 2–10 个去重的 PositionCandidate ID、同一岗位和同一已确认上下文版本；逐一验证当前用户权限及所选材料。超出上限引导缩小批次。

每人证据独立分区，比较维度来自同一岗位标准。旧版本分析只可作为带版本标识的历史证据；当前版本下未验证的维度保留未知，不直接混合旧分数。需要重分析时显式说明并由用户发起。

输出逐维度事实、证据强弱、未知项、条件化结论和后续验证建议。人工结论保持独立，不触发淘汰、录用、联系或招聘阶段变化。

## 8. 展示与交互

### 8.1 页面组织

导航新增“方法库”，默认 `/hr/methods` 展示场景视图，支持切换“方法论”“思维模型”。使用真实问题作为场景标题，搜索覆盖场景表达、方法名称和模型名称。

拟定详情路由：`/hr/methods/scenarios/:id`、`/hr/methods/methodologies/:id`、`/hr/methods/models/:id`。版本深链接携带修订，历史执行点击进入当时版本。

场景页展示目标、适用条件、推荐方法、选择理由、材料清单、步骤概览、成果示例和“用于当前岗位”。示例标明教学示例，不混入真实候选人结果。

方法页展示怎么做、为什么做、每步产物、局限、来源及关联场景；模型页展示原理、误用和相关方法。已退役内容只能从有权限的历史任务链接查看，不能新发起。

### 8.2 从浏览到执行

在岗位内进入时保留岗位上下文；从方法库进入时先选择有权限的岗位/候选人，或进入需求澄清对话。浏览和选择不会自动创建业务对象或读取全部材料。

“用于当前对话”把意图文本填入主对话的可见、可编辑输入框，并保留所选方法及材料。点击时不启动任务；用户发送最终正文后沿用统一提交。结果保存与共同确认服从主对话设计，不走隐藏罐头消息或旧任务启动 API。

执行前选择说明允许用户改场景或方法。消息区保留对话宽度与滚动状态；执行后提供可展开的“本次方法”，含名称、理由、步骤产物、检查结果和未知项。来源、模型说明放在详情层，哈希等技术字段只供审计详情。

“本次参考”继续展示业务证据；“本次方法”展示分析方法。两者链接到同一任务，不能用方法来源替代候选人事实来源。

### 8.3 权限、错误与可访问性

公共方法内容使用现有 HR 访问授权，在认证 API 下读取。业务上下文和执行记录逐请求验证 owner/对象权限；内容目录不夹带真实候选人材料。只读账号可以浏览，任务启动遵守现有只读限制。

目录加载失败提供局部重试，不卸载当前对话。未发布、退役、缺少材料、权限不足、无匹配、执行不完整分别显示准确状态。

主要按钮支持键盘，焦点可恢复；375px 宽度可浏览与启动；打开详情或切换标签不丢失输入草稿、附件选择和滚动位置。

## 9. 模块边界与实现衔接

拟新增独立目录 `backend/app/hr/methods/`，拆为内容加载/校验、场景解析、方法引用编译、轮次使用记录、结果校验和读取 API。前端新增独立方法库组件目录，主对话增加浏览入口和方法引用展示，废弃任务组件不继续扩展。

内容采用版本控制下的受限 Markdown + 结构化元数据，发布时生成确定性目录索引。页面 API 与执行引用读取同一验证后对象；不建设首期在线 CMS。生产只消费已发布内容，不联网搜书或临时改写方法。

读取 API 提供场景/方法/模型列表、指定修订详情和候选匹配结果；统一对话提交负责启动轮次，授权的轮次记录接口负责读取使用证据。解析只返回可用方法和输入缺口，不执行业务任务。

此实现需要同时修改平台 HR 集成点和真实 HR Runtime 可接收/回传方法包的边界。平台侧打包成功不能代替 Runtime 实际执行验收；需用真实分派日志、产物和关联记录证明连通。复用现有执行器与持久运行底座，但 HR 按统一设计升级 v6；需要 Platform、metabot-dev、Orbbec-Agent-Team 三仓配合，不另造 HR Agent 或调度系统。

并行开发时，本会话负责方法内容、场景映射、选择与轮次使用记录、方法库展示；现有 HR 会话继续其工作台任务。实施前重新核对分支和改动，使用隔离工作树；共享任务、路由、类型和迁移逐项合并。保留其他会话的未跟踪文件及工作成果。

## 10. 验证与效果评估

本节定义内容质量核查与后续效果评价口径，不要求每次发布自动跑完整场景集或反复浏览器验收。按用户要求，具体工程改动优先做最小相关接口检查；必要发布门禁保留，真实业务由用户验证。下列完整案例评价需要单独安排，未执行时明确报告，不能把它作为本次删旧功能的前置。

### 10.1 内容与工程检查

- 发布验证检查 ID/修订唯一、映射目标存在、来源可定位、必需步骤完整、方法兼容关系、大小预算及可用执行通道。
- 列表、详情、执行包中的同一方法必须具有相同修订和哈希。
- 验证明确选择、自然语言变体、否定、歧义、多目标、纠正、无匹配、缺材料、版本退役和权限拒绝。
- 验证跨岗位/跨候选人隔离、旧版本重试、重复提交、部分输出、取消恢复和历史记录不伪造方法证据。
- 六场景均需端到端完成“发现 → 选择 → 执行 → 产物 → 使用记录”；界面交互由用户验收；需要自动页面检查时限定具体输入、展示或可访问性问题。

### 10.2 场景案例

每个场景至少 5 个固定案例：典型、信息不足、证据冲突、容易误判、边界或不适用，共至少 30 例。另设跨场景路由用例，保证每个场景含未见过的自然语言改写。

示例：候选人简历写“主导良率提升”，但只给团队成果。预期 Agent 分开个人职责与团队成绩，保留贡献未知，设计可验证的追问。失败表现为直接赋予高能力评分或把未提供证据写成能力不足。

同一输入、相同模型/配置与材料快照，对比接入前后输出；每例至少重复两次，记录原始结果和失败。候选人材料使用明确标注的教学样例或授权脱敏材料，不能进入正式业务档案。

### 10.3 内容效果评价目标

以下数值是本项目的初始验收目标，不是宣称已有研究证明或已经达到：

- 发布内容与跨对象权限的确定性检查全部通过；伪造证据引用为零。
- 固定路由集的预期场景/应澄清/无匹配决策正确率至少 90%；无权限材料使用与不适用方法强行执行为零。
- 六场景端到端可用；全部必需产物可追溯；展示的执行状态与记录一致。
- 对匿名随机顺序的基线/方法版结果评价：岗位相关性、证据充分性、可执行性、未知项处理，各 1–5 分。覆盖全部 30 例；平均总分至少提高 0.5 分（四维均分口径），每个场景均分不得下降。自动评估记录模型与评分依据；业务效果结论需要 HR 评审核验。实际评审人数、分歧及样本限制写入报告，不预设额外人员审批。
- 工程检查通过但 HR 效果目标未验证或未达到时保留未验证或试用标记，不能报告为已证明 Agent 升级。

评审记录按方法修订关联；人工纠正先作用于当前岗位/候选人上下文，通用方法更新需单独内容审阅，不自动把个案推广为全局规则。

## 11. 交付顺序

1. 按 §5.6 固定唯一内容结构、稳定 ID 和发布清单，与主对话设计共用协议和按轮记录，不另做旧任务适配器。
2. 编写并核验首批模型、9 份方法和六场景关系，保留典型/反例材料；先以岗位分析—证据分析—面试检查内容可执行性。
3. 在统一 v6 链路接通浏览、可编辑意图、按需读取、产物及使用证据，补齐候选人比较的授权输入与结果；实现可按依赖推进，不按入口分批上线维持旧链路。
4. 随 HR 三仓发布组合一次切换并删除废弃实现；只做必要工程及发布检查，用户验证业务。内容效果按 §10 如实报告，不为宣称质量提升而补造记录。本文仍是设计，不构成已实施或已发布的证明。

六场景未全部可用时不能宣称完整内容首期交付；这不要求旧五按钮或岗位包链路继续运行。方法库只有页面、提示词或目录，也不等于执行已经连通。

## 12. 本设计自查

- 产品范围：六个招聘场景，未来领域只有分类扩展能力。
- 双重目标：展示与执行共用已发布内容；使用状态由执行记录与产物证明。
- 真实性：来源核验范围与研究适配明确；文件缺失章节未伪装为已读；教学案例与真实记录分开。
- 一致性：场景/方法/模型多对多；内容发布与运行快照版本明确；旧 Turn 不升级版本。
- 现有差距：候选人比较启动与多候选人作用域明确列为新增工作。
- 外部边界：没有新增业务系统接口、招聘事务自动化、全库注入或情报采集。
- 待下一步：用户审阅本详细设计后进入实施计划；上述路径和接口为设计方案，未声称已实现。
