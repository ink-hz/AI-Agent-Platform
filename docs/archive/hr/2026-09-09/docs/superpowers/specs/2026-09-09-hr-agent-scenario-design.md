## 1. 要做成什么

Hannah 帮助招聘团队和用人经理理解岗位、发现人才、判断证据、准备面试，并利用实际反馈改善下一轮招聘。她能围绕同一件工作持续推进，也能接受一次独立咨询或公司研究。

用户说清目标并提供或选择可用材料后，Hannah 判断已知、未知和下一步，自主读取材料、选用专业方法、调查与验证，交付可讨论、修改和继续使用的成果。常规对话不必先填表、建岗位或选择工作流；需要保存对象归属、使用敏感资料或确认长期标准时，才提出相应要求。

设计顺序：工作场景 → 用户意图 → 材料与业务对象 → Agent 能力 → 交互与成果 → 运行架构。完成目标设计后，再选择已有实现。FAE 证明直接工具循环值得参考，但它的模块、规则、预算和状态模型不是 HR 的约束。

主要使用者是招聘团队、HRBP、用人经理、技术面试官及承担招聘职责的业务负责人。Hannah 负责理解与专业处理，工作台负责输入、选材、阅读和继续工作，平台负责可信身份、业务状态与可靠执行；三种职责不预定对应三个仓库或三个进程。

当前范围不自动联系候选人、不作录用/淘汰决定或薪酬承诺、不自动发布或覆盖官网 JD，也不把候选人原始材料写入共享知识。Offer、编制审批、入职等 ATS 后段能力需单独立项。“共同确认”不默认等于已经存在多人签字的审批系统。

## 2. 六类核心工作

下列场景是需求分析视角，不是六条固定执行链，不要求分类准确才能开始，也不要求各场景使用同一种方法或输出结构。

| 工作场景 | 用户真正要解决的问题 | Agent 应怎样推进 | 关键材料 | 可继续使用的成果 |
| --- | --- | --- | --- | --- |
| 岗位与需求校准 | 想招的人究竟要解决什么问题；条件是否合理 | 理解业务任务，辨别真实门槛和文案，澄清会改变要求的问题 | JD、业务目标、组织情境、用人经理补充、已确认要求 | 岗位理解、JD/JR 草案、待确认要求、已确认标准 |
| 人才搜寻与吸引 | 去哪里找；哪些相邻经历值得考虑；怎样介绍岗位 | 从工作与能力推导人才来源，研究公司/项目，查公开线索并核对身份 | 岗位画像、公司/专题情报、公开专业资料、既有搜寻反馈 | 搜寻策略、来源地图、人才线索、沟通草稿 |
| 候选人评估 | 这个人有哪些证据；哪些还不知道；下一步验证什么 | 阅读完整简历与相关成果，把经历和任务对应，比较证据并找反证 | 当前评价基准、简历、项目、公开成果、真实反馈 | 候选人证据分析、待验证问题；不以精确总分代替判断 |
| 面试准备与记录 | 针对这个人问什么；实际回答支持什么判断 | 根据已有证据设计追问；收到真实记录后再更新判断 | 岗位、候选人资料、已有分析、面试方案、实际记录 | 面试方案、记录整理、新证据与剩余分歧 |
| 招聘复盘与改进 | 搜寻偏了、要求不合理，还是评估意见未对齐 | 查找相关成果和反馈，比较假设，提出下一批动作与标准修改建议 | 招聘目标、实际搜寻过程、评估与反馈、当前要求 | 有证据的复盘、行动建议、待确认标准调整 |
| 公司与专题研究 | 对方在做什么、怎样分工、在买什么能力；对我们的招聘有何启发 | 阅读完整岗位与公开资料，围绕问题形成判断，回查反证并限定实体范围 | 公司岗位正文、公开文档、既有研究、业务问题 | 公司研究、跨公司专题、证据与未知，可用于后续招聘讨论 |

研究本身可以是独立工作，不强制先绑定我方岗位。人才线索可以先存在，再由用户决定是否进入正式候选人管理。岗位标准尚未确认时仍可做草拟分析，但应明确采用的临时基准及不确定性。

### 2.1 场景需求的展开方式

承接来源文档 §21.1：每类工作明确目标、对象、依据、需思考的问题、交付和是否足以支持下一步。这些是设计与业务评审要回答的问题，不是模型每次必须填写的六个字段。下面的完成边界按用户实际请求适用；简单咨询、局部问题和材料不足时的澄清不强制产出整套报告。

| 场景 | 常见开始方式与需思考的问题 | 满足当前请求时应留下什么 | 不能作为业务完成证明 |
| --- | --- | --- | --- |
| 岗位校准 | 新需求、长期空缺、条件过多、业务变化；岗位使命与结果是什么，职责和要求如何对应，哪些是必须/加分/可培养 | 有证据的岗位理解、要求分层、可接受相邻经历、关键未知；需要长期复用时形成可部分确认的建议 | 改写 JD 措辞；保存一份草稿就称标准已确认 |
| 搜寻与吸引 | 找不到人、来源过窄、需要跨行业搜寻；能力在哪里形成，如何检索与核对人才身份，岗位价值怎样真实对应个人经历 | 有依据的公司/项目/专业社区方向、可执行搜寻条件、迁移逻辑、身份未明的线索与沟通草稿 | 只列常见招聘平台或公司；保存草稿就称已经联系 |
| 候选人评估 | 用户提供一人或一组材料；采用什么基准，哪些是本人陈述、外部证据、推断或未知，能验证什么 | 与具体岗位及个人对应的证据分析、差距、相邻经历价值、待验证项；比较时明确基准是否一致 | 关键词命中、无依据总分、默认排名或录用结论 |
| 面试 | 用户要求准备面试，或提交真实记录；问题验证谁的哪段经历，怎样区分证据强弱，实际回答改变了什么 | 针对性问题、追问、验证目的、证据判据及必要技术核验；记录关联实际材料，可回到采用的方案 | 通用题库拼接；把方案当作已发生面试；没有方案就拒绝整理真实记录 |
| 复盘 | 一批反馈不理想或面试官意见不同；搜索、要求、材料、评估分歧分别有什么证据，下一批应改变什么 | 共性观察、下一批动作、尚待统一的问题；适合长期复用的结论另成待确认建议 | 把逐人评价堆成岗位报告；没有真实过程与反馈就编招聘漏斗或归因 |
| 公司/专题研究 | 用户从公司、技术问题或招聘疑问出发；哪些岗位正文支持判断，范围、时间、反证与替代解释是什么 | 能回答研究问题的分析、准确实体归属、承重证据、不可答部分；跨公司结论限定可比范围 | hash 校验通过、样本数大、统计图多或专题标题存在 |

JD 在此指职责与工作边界，JR 指任职/甄选要求；二者不自动扩展为编制审批。岗位成功条件、候选人证据与面试判据之间要能相互追溯，不能靠字段同名建立关系。

## 3. 用一次连续工作检验需求

用户提出：“我们要招机器人数据负责人，帮我先看看这个需求有没有问题。”

Hannah 阅读用户材料，发现“数据交付管理”和“判断训练数据是否值得继续投入”是不同职责。她根据证据缺口自主查阅岗位情境或要求校准方法，并读取相关公司研究。材料属于觅蜂子公司时就限定在该实体，不把结论外推为整个智元集团的组织事实。

用人经理补充实际目标后，Hannah 更新岗位理解并列出需要确认的要求。用户确认具体内容，才成为后续工作的正式基准。

用户随后说“按这个方向找人”，Hannah 自主发现可用情报和公开资料，提出搜寻路径。公开线索先作为线索保存；同名未核实时不拼成一个候选人。

用户上传一份简历并说“这个人怎么样”，Hannah 读取当前基准与正文，交付证据分析。用户接着要求面试方案，Hannah 能找到刚才的分析继续工作，不需要用户复制全文或手工找技术引用编号。

实际面试后，用户提供记录并问“我们是不是把要求设错了”。Hannah 使用真实记录、原分析和要求变化来复盘，区分候选人证据、面试中的分歧与岗位要求问题。提出的新标准仍待用户确认；一份候选人分析不会自动成为所有候选人的评价标准。

这一串工作不靠预先写好的六步流程驱动。每一段都能单独开始、跳过、回头讨论或补充材料。

另保留来源文档 §22 的 DQE 连续体验作为独立验收样例：选择“DQE工程师（数采设备）” → 读实际 JD 与标准，澄清设备阶段和质量责任 → 形成能力画像并部分确认 → 搜寻、阅读简历、分析经历迁移 → 从个人分析继续设计问题 → 根据实际记录复盘。此处是目标体验，不断言该岗位真实职责，也不要求机器人数据负责人样例中出现的判断必须复现。

## 4. 产品中需要存在的对象

| 对象 | 存在的业务理由 | 边界 |
| --- | --- | --- |
| 招聘需求/岗位 | 让不同时间的讨论和成果围绕同一目标积累 | 草案、用户确认的要求、官网原文分别表达，不互相覆盖 |
| 人才线索/候选人 | 逐步积累个人相关的事实与证据 | 线索不强制先正式入库；人和岗位之间可以有多项关系，评估针对具体岗位 |
| 公司/专题 | 让情报可独立阅读、发现与调用 | 保留子公司/业务部范围；专题按真实研究内容建立，不强制拼公司全集 |
| 材料 | 简历、JD、公开岗位、项目、面试记录是判断依据 | 原文、提取文本和分析分开；保留来源与访问范围 |
| 工作成果 | 用户需要复用、修改、讨论和交付 | 正文自然可读；只为归属、证据与后续使用增加必要结构 |
| 已确认要求与决策 | 后续协作需要共同基准 | 记录确认者与具体内容；Agent 草案不等于组织决定 |
| 方法与思维模型 | 提供专业推理视角，支持跨场景使用 | 方法是参考知识，不是强制工作流、评分规则或自动授权 |

这些是概念对象，不预定对应七张表或七个服务。可以沿用已有业务数据，也可以重新组织读取与存储；旧 schema 名称不能反过来限制用户要完成的工作。

### 4.1 成果、标准与来源的关系

成果至少要让用户知道：是什么、属于哪个工作对象、基于哪些材料或前序成果、是否保存、从哪里产生、怎样继续使用。技术上应能稳定定位，但不要求沿用旧 resultRef/schema 格式，也不向用户暴露这些编号。

同一份成果在对话、岗位、候选人入口查看的是同一内容，不由各页面重新生成副本。分析 → 面试方案 → 实际记录保留关联；新分析、修改或用户确认不会悄悄重写此前材料与结论。候选人分析始终保留个人归属，岗位复盘只沉淀必要的去标识化共性。

岗位分析、搜寻策略、候选人分析、面试方案、实际记录、沟通草稿、公司/专题研究可以有不同结构。结构服务于复用与交互：面试问题需要能对应记录和验证目标，标准建议需要能逐项确认；普通解释不必填满所有字段。原文的六种成果 schema 与八个标准模块作为需求样例，不是新系统类型数量上限。

### 4.2 官网事实与内部共识

官网 JD、用户内部确认的要求和 Agent 建议分别表达。读取官网事实要展示可用时间及核验状态；来源陈旧、同步失败、疑似下线与确认下线不能混为一谈。允许使用最后有效材料时说明其局限，不伪装为刚核验的事实。

官网变化可能影响内部要求时，应能查看差异、定位受影响的判断，并由用户决定哪些需重新确认。这是待细化交互，不继承旧同步周期或本地校验路径，也不自动把官网变化写入内部标准。

### 4.3 标准确认与协作范围

用户看到具体建议正文，选择认可的部分并明确确认，才形成新的标准；未选择部分不被覆盖。内容或基准在确认前改变时，展示差异并重新确认。系统记录真实确认者，不以 Agent 声明、沉默或一般点赞代替。

从候选人反馈提炼的共性仍需用户审阅，不能因自动标记“无个人信息”就跳过真实确认。团队共享、共同编辑、哪些角色能确认、是否需要多人审批属于待定产品范围；“服务团队”不证明这些能力已有。新设计也不把旧 owner 分区或同一会话限制直接作为组织协作模型。

## 5. Agent 必须具备的能力

**发现与读取。** 查看任务范围内有哪些材料、方法、研究和历史成果，按对象定位并读取原文。搜索和连续遍历同时可用；搜索结果少不能阻止继续通读。多格式材料保留可追溯正文，图片内容按任务需要读取。

**专业思考。** 结合用户目标、证据缺口，自主选用一个或多个方法，也可不用。方法目录描述能帮助思考的问题和适用边界，正文提供关系、推理方式、反例与局限。禁止把场景到方法实现为硬编码映射。

**研究与核验。** 能查公开信息、沿来源读取、比较不同岗位与公司、回查反证，明确哪些推断尚未证实。统计和计算用于检验判断；不能用统计填充替代分析。

**成果工作。** 能查找、读取、创建和修改成果，解释使用了哪个基准以及修改原因，按需生成可下载文件。已有成果被新材料推翻时，应明确更正而不是静默覆盖原事实。

**人与 Agent 协作。** 能提出会改变当前工作的问题，等待补充后继续；能发现可能相关的旧成果供使用。对象或权限范围不明确时先澄清，不让用户每次重新描述整个项目，也不把历史对话自动当成当前有效要求。

**持续工作。** 长研究能展示进度、保留阶段成果、被取消或恢复。用户补充目标时能调整后续工作，并明确哪些已有结论需要重看。

工具如何命名、要几个接口、采用哪个 SDK，在这些能力定义之后决定。方法的存储结构服务于发现、读取与展示，不承担业务流程执行。

### 5.1 简历、附件和文件交付

用户可批量上传简历，每份独立显示处理状态、失败原因及重试入口；某份失败不影响其他已成功材料。解析结果供人工查看、更正、判断新建或合并，交互用可读字段与原文对照，不要求用户编辑 JSON。身份有歧义时提示确认，不仅凭姓名自动合并。

上传、解析、人工确认档案、分析保存各有含义：文件在系统中不等于正文已读，解析事实草稿不等于事实已核实，候选人确认不等于录用或认可某份分析。新设计允许无正式标准时的材料讨论；正式档案与岗位关系应在业务需要时建立，不机械复制旧“必须先有标准版本”的阻塞条件。

输入包括简历、JD、项目、公开材料、实际面试记录等，Agent 能访问获准的实际正文与必要图像。文件输出包括适合分享的 JD、人才清单、分析和面试文件；保存成功、可下载、实际内容正确需要分别验证。具体格式按场景选定，不承诺现阶段每种成果都有一键导出。

附件删除、权限撤销或来源失效后，不得用聊天副本、摘要或旧链接绕过。受影响成果应说明缺失原因与可继续范围；经过人工脱敏的独立长期成果能否脱离原材料存续，需要单独定义，既不自动放宽，也不把旧递归失效策略直接照搬。

## 6. 三种产品结构及选择

| 方案 | 适用之处 | 对当前 HR 目标的影响 |
| --- | --- | --- |
| 场景表单与固定工作流 | 输入稳定、步骤明确的重复事务 | 难容纳模糊需求、交叉研究和临时追问，不作为核心形态 |
| 单一聊天框加知识检索 | 独立咨询容易启动 | 岗位、人才、成果与确认难以持续积累，仅有聊天记录不够 |
| 对话驱动的 HR 工作空间 | 对话探索与业务对象、材料、成果相互连接 | 采用这一方向，支持独立咨询和长期工作，不要求先建完整项目 |

入口保持统一对话，页面可以提供岗位、人才、公司/专题和成果的直接入口。用户在页面选择对象、打开研究或要求继续工作时，这些成为显式上下文；Agent 也能在授权范围内自主发现相关内容。

### 6.1 工作台应展示什么

- **主对话**：显示当前目标、岗位/人才范围、用户指定材料与方法、回答、进展和成果。快捷动作只能辅助填写用户可见、可编辑的意图；用户发送后应真实调用所需能力，不能把“有按钮”当成场景已经做完。
- **岗位工作视图**：组织官网 JD、内部标准、待确认建议、搜寻策略与线索、候选人分析、面试方案与记录、反馈和复盘。能回到来源对话，也能从已有成果继续；空白处如实说明暂无成果，不自动生成占位分析。
- **人才与候选人视图**：查看身份、原材料、与各岗位的关系，以及对应分析和面试记录。当前请求讨论 A 时，不默默混入 B 的个人材料。
- **公司/专题情报**：默认显示最新可用内容及观察时间、实际覆盖和限制；读研究问题与判断，按需展开依据，从相关内容带入对话并补充意图。浏览和筛选不自动重跑分析；显式研究任务可由新 Agent 执行。
- **方法库**：阅读资源用途、内容、案例与局限，支持“带着这个视角讨论”，显示用户选择与实际引用的区别。

以上是信息职责，不预定五个顶层页签或沿用现有 URL。一个岗位的阶段成果索引也不是强制用户依次走完的招聘流程。详细来源放在可展开的依据区或就近引用处，正文先呈现有用判断，避免来源和内部字段淹没内容。

### 6.2 四种完成状态

| 用户可见含义 | 能证明什么 | 不能自动推出什么 |
| --- | --- | --- |
| 本次回答/执行结束 | 已交付当前回答或说明限制 | 岗位要求已经充分、工作业务目标达成 |
| 成果已保存 | 可在相应对象下找回和继续使用 | 用户认可了判断、文件内容必然正确 |
| 要求已确认 | 真实用户认可具体内容并形成后续基准 | 官网被修改、候选人获录用、多人均签字 |
| 当前业务问题得到解决 | 交付足以支持约定的下一步，并明确剩余问题 | 从前三种技术状态自动推导 |

“发现关键缺口并提出澄清”可以是有用的本次交付。工作台应说明已做什么、缺什么、接下来怎样继续，不能用一个完成勾选掩盖业务边界。

## 7. 由需求推导的最小运行结构

运行在云端的一个 Hannah Loop，直接调用模型 API。每次模型判断可以继续读资料、使用工具、问用户、整理成果或结束。没有固定的 planner → 分类 → 编译方法 → 检查步骤链。

第一版围绕四个职责组织：

1. **Agent 上下文与循环**：管理当前目标、可用能力、用户补充和模型交互。
2. **材料与专业工具**：提供授权阅读、检索、方法和研究能力，保存成果并落实真实确认。
3. **工作记录**：保存用户输入、实际调用结果、阶段成果与继续工作的必要信息。
4. **工作台呈现**：展示回答、业务对象、成果和进展，支持用户查看依据、修改和继续。

这些是职责边界，不等于四个微服务。不预设旧 Turn/Attempt/Loop/Step 表结构，不强行复用旧授权签名、冻结命令、读取收据协议或 FAE 的会话对象。

可靠性从真实需要出发：API 不承担长时间模型执行；云端 Worker 可独立重启；已经成功的保存动作不能因重试重复发生；任务中断后能恢复最近已记录进度；页面断开不丢任务；取消后不继续发起新动作。具体数据结构和并发控制设计在运行时实施规格中推导，不因某机制曾存在就要求继承。

只冻结需要复现的任务输入与实际使用的材料身份。用户改变目标应作为明确的新输入进入工作记录，不能为迁就旧“整条命令冻结”模型而失去持续协作能力。

## 8. 上下文和知识怎样进入思考

初始上下文提供简洁角色、当前目标、明确对象、用户指定材料以及可用方法/资料的目录。正文由 Agent 按需读取，不把整个情报库、岗位库或统计表固定塞进去。

工作记忆保留当前问题、已知事实与来源、主要判断、反证、未答问题和用户修正。材料太长时，原文仍可重新读取，阶段笔记带来源位置；不能用截取前几条或丢弃旧消息代替语义整理。

长期专业知识、已确认岗位要求、个人材料和临时工作笔记分别处理。一次候选人分析不能自动进入公共方法库，某次对话中的假设也不能自动升级为长期事实。

方法使用对用户可见：用户可浏览方法、指定讨论视角，也能查看 Agent 引用的资源。记录读取只证明内容曾返回，业务质量仍看判断、证据和适用边界。

### 8.1 连续工作与上下文范围

同一对话可以切换岗位；当前选择和用户明确目标决定本次处理范围，不能改写过去的归属。跨岗位或多人比较时要明确比较对象和材料权限，不继承旧“单轮最多一个岗位”的实现限制，也不因在同一聊天里出现过就自动授权。

上下文、历史成果、附件与工具读取采用一致的业务边界。尤其同一岗位从候选人 A 切到 B，A 的原文历史不能因“岗位相同”就自动进入 B 的个人分析。合法复盘需要多人的材料时，明确参与对象与用途后再使用。

用户显式选择的成果/方法/情报保持实际选择的内容；Agent 自主发现的补充资料说明来源。用户不需要手工提交 hash，但页面上的引用文本也不能被当作已核验来源。材料过期、无权读取或不可得时明确提示，不默默换另一份。

“最近的分析”可自主发现；存在多份互相冲突或对象不同的结果时澄清。用户口述需求可以作为明确标注的对话依据，后续是否保存为正式基准由用户决定，不能为满足旧 schema 虚构已确认版本。

### 8.2 可承接的专业资源

来源文档 §6.3 列出七份已有内容：岗位与业务情境、要求校准与 AMO、胜任力与人才画像、人才来源与能力迁移、循证判断、甄选与工作样本、候选人比较与反馈。它们是可继承的专业内容资产，不限制未来资源数量。

新设计维护简洁目录及正文，按用途与局限帮助 Agent 选择。目录进上下文、正文按需读，用户与 Agent 使用可核对的同一内容来源。场景中出现某个词不触发固定方法；记录使用资源不等于专业质量已通过。

## 9. 如何判断设计有效

先用第 3 节的连续工作与六类独立任务检验，而不是看实现了多少端点。应当验证：

- 不先填写完整岗位表也能开始有价值的需求讨论。
- 公司/专题研究能独立进行，相关结论随后可用于岗位讨论。
- 公开线索能够存在，不因旧候选人 ID 要求而丢失。
- 用户说“接着刚才的分析准备面试”，Agent 能找到对象与成果；有歧义才澄清。
- 新反馈到来后能修改判断，保留此前基准与变化原因。
- 大量岗位正文可以持续阅读，形成有反证和作用域的判断，不用计数替代。
- 草拟、保存、用户确认、实际对外行动在体验与状态上含义清楚。
- 工具失败或进程中断能解释已完成和未完成的部分，并支持继续工作。

工程验证检验授权、真实输入输出、保存与恢复；专业质量以实际材料和人工审读判断。固定步骤命中率、方法调用次数、相似度规则不作为智能化验收。

### 9.1 从来源缺口形成的具体验收任务

| 验收任务 | 预期可见行为 |
| --- | --- |
| 点击“梳理 JD/JR”并补充真实问题 | 发送正文可见，Agent 处理真实职责与要求；入口存在不代替业务质量验收 |
| 在对话保存分析，再打开岗位和候选人 | 找到同一成果、来源与继续动作，不重复生成，也不在某个历史列表里消失 |
| 从分析继续面试，再提交真实记录 | 正确承接人、岗位、基准及采用的方案；无原方案也能整理真实记录 |
| 同岗位先评 A 后评 B，再明确请求比较 | 独立评估时不混入另一人的材料；比较时说明获准对象及一致/不同基准 |
| 多份简历中一份失败，用户更正另一份 | 成功项可继续、失败项可重试，原文和更正可核对，无 JSON 编辑前置 |
| 查看官网变化并部分确认内部建议 | 展示来源差异，保留未改内容；并发变更要重新核对，不静默覆盖 |
| 从限定范围的专题继续提问 | 保留观察时间、实体和限制，能读选中的真实内容，不以 current 偷换资料 |
| 刷新/关闭页面、任务中断、重复提交 | 任务与成果可找回；恢复不重复副作用；显式重试与后台继续含义清楚 |
| 删除原始材料后尝试引用旧成果 | 明确受影响范围，不能借旧正文或链接绕过权限；独立脱敏成果按另定生命周期处理 |

质量审读检查目标相关、事实准确、证据可追溯、方法适用、未知诚实、行动可执行、对象归属正确、长期沉淀恰当、连续工作可用和用户成本。它们是评审维度，不是在线规则评分器。

接口与数据验证优先，必要时做真实进程故障，页面最后验收。模型替身、真实模型、内容审阅和生产发布分别报告；健康检查通过不等于招聘质量通过。耗时、重复读取、等待和费用需按实际场景测量，不继承原文任何未实测的性能承诺。

## 10. 历史资产与后续设计

旧系统里的用户资料、已确认要求和已保存成果是资产，需要有清晰的数据承接方案。旧执行层、兼容协议、临时补丁和通用框架不是必须保留的资产。数据承接单列为最后的交付问题，不能主导新 Agent 的结构。

FAE 和平台代码在目标能力确定后逐项检查：可直接满足需要且依赖轻的采用；专业绑定重或接口相悖的重做。暂不决定抽公共框架，也不为复用而要求 FAE 一起改造。

接下来的具体设计应依次回答：六类工作与连续协作的交互；对象与成果如何组织；工具如何让 Agent 自主发现和操作；上下文与工作记忆；云端执行与恢复；最后是历史数据承接与切换。所有场景共用同一 Hannah，实施可以分批交付能力，不以某一场景绑定一个永久执行器。

本稿未选定模型、具体 API、数据库表、数值预算或复用模块。云端自有 Loop 与退出 MetaBot/Claude Code 的决定继续有效。本文替代此前以迁移为中心的设计，作为后续讨论基础。
