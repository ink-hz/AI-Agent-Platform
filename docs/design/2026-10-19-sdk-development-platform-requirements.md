# SDK 开发管理平台需求草案

## 目标与产品边界

SDK 开发管理能力从现有 AI-Agent-Platform 延伸。它把需求、开发、版本基线、打包、测试和发布组织成一条可追溯的链路，让负责人能回答：为什么做、改了什么、用哪份源码构建、在哪些环境验证、最终发布了哪个产物。

本阶段先确定业务需求和验收口径，并验证现成开源产品，再决定页面、接口和自动化的实现顺序。AI-Agent-Platform 提供 SDK 能力的统一入口与 AI 辅助；通用研发流程优先复用成熟产品。正式选型前，需明确业务记录的唯一权威来源、身份衔接、权限和审计边界，不预设所有记录都由现有平台自行实现。

首期不接入 GitLab 的开发流程：平台不调用 GitLab Issue、Merge Request、Webhook 或流水线接口，也不依赖 GitLab 状态推进需求。现有 GitLab 仓库及本地检出的源码仅用于理解 SDK 结构、版本关系、构建脚本和测试入口。将来若接入 GitLab，应单独设计同步方向、授权和冲突处理。

## 开源选型先行

先用真实 SDK 场景试运行成熟开源产品，验证需求、任务、构建版本、测试单、缺陷和发布能否形成闭环，再决定是否开发平台专属模块。选型记录见 [开源产品评估](2026-10-19-sdk-development-platform-open-source-evaluation.md)。

试运行必须核对三类差距：① 是否能记录打包仓库及嵌套子模块的完整提交基线；② 能否按操作系统、架构、设备、固件和产物摘要保存测试证据；③ 能否按这些证据实施发布审批与阻断。若产品只能保存普通版本号或附件，须明确补充能力由谁提供、数据存在哪里，不能把演示流程等同于生产可用。

## 当前事实与设计依据

- AI-Agent-Platform 已有企业身份、平台角色、受保护 API、审计和独立业务模块。现有“AI 工程全景”用于阅读与展示，不承载 SDK 研发流程记录。
- OpenOrbbecSDKGroup 是统一打包入口。当前 `master` 提交为 `c7669cc67ff303a9d6fc45585d640a546a682dcc`，固定七个一级子模块；Viewer 还引用一份主 SDK 子模块。其脚本按 SDK、扩展模块、SDK 安装包和 Viewer 安装包的顺序构建。
- 打包仓库固定的主 SDK 提交为 `ad7518704a7ab630719a691748c4f36473a416bb`，版本为 `2.6.2`。独立主 SDK 仓库 `develop` 当前提交为 `7d2763f75e3641fbbbaad10e919f42b8f7bb6389`，版本为 `2.10.6`。开发分支版本不能代表某次打包使用的源码。
- 当前主 SDK 有 `unit`、`hw`、`scenario`、`perf` 和 `destructive` 测试分类；测试脚本可输出 JUnit XML 和完整日志。打包仓库的现有 `build_all_*` 脚本没有直接调用该测试脚本，因此平台需要分别记录构建结果与测试证据。

上述提交是需求分析时的观察值，不是平台默认发布基线。平台每次生成候选版本都应保存当次实际使用的提交和构建配置。

## 使用者与职责

| 业务职责 | 需要完成的工作 |
| --- | --- |
| 需求提出人 | 描述客户或内部场景、期望结果、适用设备和约束，补充澄清。 |
| 需求负责人 | 评估价值、范围和优先级，确认验收标准，决定纳入哪个候选版本。 |
| SDK 研发人员 | 拆解工作、记录实现与评审结论，提交可供构建的源码版本。 |
| 构建负责人 | 确认源码基线、目标平台和参数，执行或登记构建，核对产物。 |
| 测试负责人 | 制定测试范围，记录设备、固件、环境、结果和缺陷，确认复测。 |
| 发布负责人 | 核对候选版本、产物和测试证据，审批并登记实际发布与回退信息。 |
| 审计或只读使用者 | 查看授权范围内的历史记录和证据，不修改业务结论。 |

这些是业务职责，不直接等同于现有 `platform_admin` 或 `platform_owner`。实施时需要确定 SDK 专属授权与职责分离规则，避免为使用 SDK 模块扩大平台全局管理权限。

## 核心业务记录

### 需求

每条需求至少保存唯一编号、标题、背景与来源、目标用户或客户场景、适用设备和平台、期望行为、边界条件、优先级、负责人、验收标准、提出及决策时间。范围、验收标准和决策发生变化时保留历史版本与操作者。缺陷、兼容性修复、性能改进和新能力可使用共同的需求主记录，但应有明确类型。

需求可拆为开发工作项；一个工作项可支撑多条需求，一条需求也可跨多个候选版本交付。平台应展示这种关系，不以单个“完成”标签掩盖部分交付。

### 开发工作项与源码版本

工作项保存负责人、计划、技术方案、评审结论、实现状态和关联需求。首期可人工附上代码版本或评审链接作为参考证据；链接可缺省，不触发 GitLab 同步，也不把外部状态当成平台状态。

源码版本基线应记录打包仓库提交、全部一级与嵌套子模块提交、主 SDK 版本、构建脚本版本，以及记录生成时间。候选版本冻结后，修改任一提交或配置都生成新基线和新候选，不覆盖旧记录。平台明确区分当前开发分支、候选基线和实际发布基线。

### 构建与产物

构建记录包括候选基线、SDK 产品或 OEM 变体、操作系统、架构、构建配置、脚本与参数、执行环境、开始和结束时间、操作者或执行器、退出状态、日志位置。每个产物保存名称、类型、文件大小、SHA-256、存储位置及其对应的构建运行。失败、取消和超时分别呈现，不生成可发布结论。

构建矩阵至少能够表达 Windows、Linux、macOS 及架构差异；具体首批目标由业务负责人确定。平台以现有脚本为可核对的构建入口，在需求确认后再决定何时引入自动执行。

### 测试与质量结论

测试计划关联需求验收标准、候选基线和目标平台。一次测试运行记录测试套件、执行命令、产物摘要、设备型号、设备与固件版本、操作系统、环境、开始和结束时间、通过、失败、跳过数量、报告与日志。硬件相关测试必须能标明测试设备是否具备；未执行或环境阻塞不能显示为通过。

缺陷关联受影响需求、候选版本、测试运行和复测记录。测试结论只适用于已核对的产物与环境；源码或构建配置变化后，原结果继续保留，但新候选需要重新判断哪些验证必须执行。

### 发布

发布候选汇总需求、冻结基线、构建产物、测试证据、已知问题和审批。发布记录保存实际发布的产物摘要、版本、目标渠道或交付对象、发布时间、批准人、发布结果与回退路径。候选批准、实际发布和业务验收是不同事件，不相互自动代替。

若必要证据缺失、产物摘要不匹配或测试失败，平台给出明确阻断原因；例外放行须由有权人员留下范围、理由和时间，且不改写原测试结果。

## 状态与追溯规则

需求使用“草稿 → 待评审 → 已确认 → 开发中 → 待验收 → 已验收”的主路径；撤回和暂缓作为有理由的终止或暂停决定记录。需求完成以已确认的验收标准和证据为准，不以工作项关闭自动判定。

发布候选使用“基线准备 → 基线冻结 → 构建中 → 待测试 → 待发布审批 → 已发布”的主路径。构建失败、测试未通过和审批退回均保留原候选及事件，并从新的运行或候选继续。任何页面都应能从发布记录反查产物、测试、源码基线和需求，也能从需求查看已交付的候选与发布。

重要状态转换记录操作者、时间、前后值和理由。系统根据证据计算可进入的下一步；人工审批记录决策，不伪造构建或测试通过。

## AI 辅助能力

AI 可在以下位置给出附带来源的建议：整理和去重需求、分析源码影响范围、建议测试范围、解释构建或测试失败、整理发布说明。建议需明确依据的需求版本、源码基线、日志或测试报告，以及无法判断的部分。用户可以修改、采纳或驳回建议；AI 输出本身不改变验收、审批或发布状态。

源码检索和分析需要遵循平台已有的受保护内容边界。源码及私有构建日志不进入公开前端资源；对模型提供资料时按业务授权和最小范围选择，并记录所用版本。

## 首批能力与后续扩展

首批可用闭环应让团队通过 SDK 业务入口创建与评审需求，登记开发工作和准确源码基线，登记构建产物与测试报告，完成发布审批和实际发布记录，并从任一环节查看完整追溯链。通用流程可由独立部署的开源产品承载；AI-Agent-Platform 负责入口、专属分析和必要的集成。执行和证据录入可以先由人完成，但状态、授权、审计和版本关系必须是真实可用的。

后续再逐步接入构建执行、测试报告自动导入、硬件实验室、产物仓库和 GitLab 开发事件。每项自动化都应使用同一业务记录和证据规则，避免另建一套平行状态。

## 非功能要求

- SDK 入口遵守现有平台的会话、CSRF、可信身份和权限边界；独立部署的产品须另行验证身份衔接与自身授权，不能仅靠导航隐藏实现隔离。SDK 业务写入由记录的权威系统校验，身份过期或只读状态下禁止变更。
- SDK 业务数据与现有只读镜像、HR、FAE 和反馈修复数据隔离。审计事件可追加和查询，历史结论变更通过新事件表达。
- 外部服务、执行器或模型不可用时明确显示阻塞与上一次成功数据的时间，不把旧结果当作本次成功。
- 操作具有稳定身份和幂等边界，重复提交、回调或页面刷新不得重复创建发布、审批或产物记录。
- 验收优先通过真实身份和授权路径的接口测试；页面交互由用户按仓库现行测试策略最终验收。

## 可验收的业务场景

1. 提出一条带设备范围和验收标准的需求，评审修改后可查到每次决定、操作者和生效内容。
2. 从该需求创建工作项，并登记不同源码提交；页面明确显示工作进展与实际冻结的打包基线。
3. 为同一候选分别记录两种目标平台的构建。一个产物失败不改变另一个产物的真实状态。
4. 为具体产物录入单元测试和硬件测试证据。硬件缺席、跳过和失败均保持原意，不能满足“通过”的门槛。
5. 发布负责人可核对需求、全量子模块 SHA、产物摘要、测试环境和例外决定，再登记实际发布；从发布记录可以反查完整链路。
6. 不配置 GitLab API 凭据、Webhook 或开发事件接口，上述首批流程仍能完成；平台不会自行改变 GitLab Issue、MR、分支或流水线。
7. AI 建议展示依据并经过人员确认；驳回建议后，业务状态和证据不被改写。

## 实施前需要确定的业务决策

需求记录由选定的权威系统维护，避免在开源产品和 AI-Agent-Platform 中各建一套主记录。实施前需要确认谁能提出和批准需求，哪些角色能够批准例外与发布，首批覆盖的设备、操作系统和架构，以及产物的正式存储与发布渠道。这些决定将收敛权限矩阵、构建矩阵和发布门槛；不影响本草案确定的追溯关系与 GitLab 暂不接入边界。
