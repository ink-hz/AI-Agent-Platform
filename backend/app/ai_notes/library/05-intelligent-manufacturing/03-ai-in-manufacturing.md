> 面向现有 Agent 平台的选题与边界参考，不表示平台已经连接企业 ERP/MRP/MES 或具备任何已验证的工业控制能力。资料核验日：2026-10-27。

## 1. 三类能力的责任不同

“用 AI 帮制造企业”至少有三种不同工作。第一类是知识与分析辅助：查受控文件、解释指标、整理异常证据。第二类是事务自动化：查询订单、提交工单、修改计划或触发审批。第三类是现场闭环控制：依据传感信号直接调整工艺、设备或产线行为。它们的数据新鲜度、可验证性、时延、可恢复性和失误影响不同，不能用一个聊天准确率统管。

| 类别 | 可考虑的任务 | 上线前必须建立的边界 |
| --- | --- | --- |
| 知识助手 | 带引用的制度/工艺问答，术语解释，交接材料 | 文档权限、版本、生效性、无证据时明确未知 |
| 分析辅助 | 缺料原因归纳、质量问题材料整理、报表解释 | 来源截点、计算工具、样本范围、事实与推断分开 |
| 事务 Agent | 创建待审申请、按授权更新业务记录 | 身份、权限、参数校验、确认、幂等、回执与审计 |
| 工业 AI 与闭环 | 视觉检测、预测维护、工艺优化等专用应用 | 专业验证、测量与控制要求、失效策略和现场责任 |

最后一类并不等于通用大模型。机器视觉分类器、统计模型、优化器和控制器各有验证方法；不能把“能解释设备报警”推导成“能安全决定设备动作”。NIST OT 安全指南特别强调现场系统的性能、可靠性及安全约束，适用于判断连接边界；它并不为某个 AI 产品提供工业安全认证。[S12：NIST OT 安全指南](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-82r3.pdf)

## 2. 先选能交付证据、能衡量价值的场景

适合初期研究的场景包括：把工艺与质量制度整理为受控知识库；对某一订单生成包含证据链接的缺料解释；把异常记录、检验结果和处理历史汇成供工程师审阅的材料；解释 OTD、WIP、冻结库存等口径；协助准备实施访谈、需求和验收脚本。它们也需要评价，不能因为只生成文本就默认无风险。

不宜从“自动替换 BOM、自动放行不合格品、自动改采购承诺、自动调设备参数”开始证明平台价值。先确定哪些决定必须由有资格的业务角色作出，再研究 AI 能减少哪些信息查找和材料整理负担。场景优先级由问题频率、数据可得性、错误代价和可验证收益共同决定。

NIST 的生成式 AI 风险资料讨论自信地生成错误内容，并建议核验来源、评估能力及持续监测。本文的制造场景分层是据此结合业务边界形成的建议，不是 NIST 对制造流程的逐项规定。[S19：NIST AI 600-1，2.2 与测量建议](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

## 3. 检索到一段文字，不等于获得有效指令

知识记录至少需要文件编号、标题、版本、批准人、适用工厂/产品、有效期、作废状态与权限。回答“这批订单按哪个工艺做”时，需要订单执行时适用版本，不能只找检索库中最近更新的一份文件。历史问答应区分当时有效规则与现在规则；未拿到受控文件时应明确证据缺口。

库存、订单和交期属于动态业务事实。回答应标注来源系统、查询条件、组织范围和截点；过期缓存只能作为历史信息。检索索引的权限必须跟随源权限，不能先把无权文档塞入上下文再靠模型不说出来。来自文件、工单或网页的文字是待核验材料，不能自动授权 Agent 调工具、导出数据或改变规则。

## 4. 业务动作需要可复核的执行链

可把事务链定义为：理解意图 → 读取获准数据 → 形成具体变更草案 → 校验业务前置条件 → 按影响取得适当确认 → 调用业务接口 → 查询最终状态 → 交付业务回执。权限检查和关键参数校验由执行边界承担；模型判断不能替代服务端授权。

确认强度应与影响匹配：只读查询可在既有授权内执行；可逆草稿可以自动生成；会影响采购、库存、财务、质量放行或跨组织数据的动作，应依企业已批准权限与审批流程处理。展示确认时列出对象、数量、单位、旧值/新值、适用范围和后果，避免只问一句“是否继续”。持续授权也应有范围和有效期，不应把每一步小操作都变成无意义确认。

超时不能自动等于失败，更不能直接再次报工。事务 Agent 应复用业务操作标识，核对服务端处理结果，保存原始回执、失败和更正；最终回答准确区分“草案已生成”“申请已提交”“审批通过”“业务已过账”。幂等原理可参考 Microsoft 的消费者模式，具体实现仍取决于实际业务 API。[S11：幂等与外部副作用](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer)

## 5. 确定性计算与 AI 解释各司其职

MRP 需要基于明确输入和规则计算需求净额、时间与补充建议；APS 要表达约束和优化目标。AI 可以帮助收集条件、调用获准计算服务、解释结果和归纳异常，但不能用自然语言“猜一个缺料数量”代替正式计算。对一份计划结果，应保留需求、BOM、库存/在途、参数、日历和计算版本，才能复现。Microsoft 文档所示的 BOM 及供应处理说明了计划依赖的结构化输入，不能据此推断本企业软件已经具备同样接口。[S06：生产计划输入与实现示例](https://learn.microsoft.com/en-us/dynamics365/supply-chain/master-planning/planning-optimization/production-planning)

## 6. 用完整任务评价现有 Agent 平台

建立有答案或判定规则的场景集，覆盖正常查询、版本冲突、缺证据、无权限、过期数据、单位错误、重复请求、接口超时和更正。评价至少分为：证据引用正确、业务事实正确、权限边界正确、动作和回执正确、任务完整、耗时和成本。人工审核也要记录审核耗时及遗漏，不能只统计模型回答速度。

知识助手先验证引用与版本；事务 Agent 再验证真实接口契约、授权、幂等与恢复；涉及现场控制则另立专业工程项目。平台现有能力要以代码、接口、真实任务记录和业务验收确认，不能从通用模型或供应商演示外推。只有当使用者能看见证据、核对结果、理解未完成部分并承担对应决策，AI 才能成为可管理的制造信息化能力。
