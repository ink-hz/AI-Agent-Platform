# Q10 拓竹：不能判定公司缺能力，可以校准跨岗位的交接条件

**“拓竹缺哪种能力”目前不可直接回答；“哪些交接责任需要进一步核实”可以回答。** 全量正文已经出现数据生产、算法评测、物理仿真、系统可观测性、发布回滚以及安全运营。把 AI 招聘只看成建模和 Agent，然后说它缺数据、仿真或安全，是漏读正文后的假缺口。真正仍需补材料的地方，是这些职责如何连接成一次可验证的实物质量改进，以及外部供应商和内部岗位之间如何验收。

**先排除一个最容易误判的缺口：数据与评测并非没有被安排。** 数据算法岗覆盖采集、清洗、标注和场景测试集，视觉数据岗还要求按测试反馈迭代数据策略；AI 中台产品岗负责评价标准、人工评审、Candidate 验证、发布准入与回滚。由此可以确认招聘在要求数据和评价责任，不能确认既有数据质量或评测覆盖已足够。它们有职责，不等于链路已经有效运行；没有给出测试集与故障回放记录，也不等于不存在这些资产。

招聘上因此不应先发起笼统的“补数据团队”寻访，而应先拿一个打印失败案例核对：谁确定标签与根因、谁定义保留测试集、模型变化后谁判断改善成立。若任务已有承担者而缺少统一验收，是接口问题；若实际无人承担才可能成为招聘需求。只有岗位文本，尚不能完成后一步判断。

**最值得核实的是 Agent 改参数与实物质量验证之间的授权和验收，而不是再补一个 Agent 名称。** 复杂排障岗要接入传感、控制 API 和切片软件，最终自动调整参数；打印工艺岗要通过机型、材料实验，把经验转为配置与默认策略。AI 中台又把“明确平台与业务责任边界”写成职责。这使得一个具体交接问题浮现出来：一次诊断提出的参数修改，依据哪个材料/机型范围被允许执行，执行后由什么实验或观测认定有效，失败时谁决定停止自动尝试并转人工。

这里“通常需要”的依据来自岗位自己要求的交付逻辑：识别缺陷、改动控制参数和改善实际打印是三个不同结果，工具调用成功并不自动证明打印改善；软件版本回滚也不能撤回已经发生的材料加工。因此需要跨这些结果的验收条件。这个推论不依赖外部能力清单，也没有声称岗位没有安全控制。相反，中台岗明写发布准入与回滚，运动控制岗明写包括防火在内的环境控制。真正缺少的证据是它们适用于自动调参时的具体接口、限制和验证记录。

下一步校准可以直接围绕“堵头或翘曲被误诊后，参数修改是否仍会执行”开展：运行时候选人解释权限与状态恢复，领域候选人解释何种现象不足以定因，工艺候选人解释机型材料适用范围，产品负责人解释谁作发布或停止决定。这是验证交接能力的分工建议，不是从岗位邻接关系推导内部组织树。当前不能指定某个已存在团队承担最终责任，也不能宣称该责任无人负责。

**正文还有一个相反的例子：有的边界写得很清楚，不应被误读成职责遗漏。** 系统运维岗负责安全工具的可用性、性能、可观测性，明确排除策略调整和安全运营；高级安全运营岗允许一线监测与初判借助外包，却保留内部策略、升级、重大事件指挥和质量管控。合读后，前一个岗位不处理安全策略有合理的职责解释，外包参与也不是把最终处置责任全部外置。

这会改变安全岗位的面试分工：不能因为运维候选人未主导 SOC 规则就认为不符合工具运维岗；安全运营候选人则要展示如何审核外包初判、设计升级条件并在事件中作决定，不能只展示平台部署。材料没有外包合同、现行 SLA 或演练结果，所以只能说这种责任分配被招聘明确要求，不能说已按此运行。

对于上述尚未确认的交接机制，应分别保留三种可能，不能选一个作公司事实。

- **外部提供。** 某些能力可能来自供应商服务或工具，但需要合同范围、交付物和内部验收职责确认。UV 材料岗已明确存在供应商联合开发与代工厂技术转移，证明“外部参与”在拓竹有具体文本依据；它不能证明自动调参验收也外采。
- **尚未进入对应阶段。** 多模态研究岗要从零构建原型，某些产品化交接可能尚未进入当前交付范围。但不同岗位未绑定同一产品版本，不能据此断定全部 Agent 都停在研究期。
- **不通过这批公开岗位招。** 能力也可能由现有人、内部流转或未采集到的岗位承担。完整读取本包社招与校招，不等于拿到了内部任务归属和现有人员履历；本包无法进一步确认这一解释。
