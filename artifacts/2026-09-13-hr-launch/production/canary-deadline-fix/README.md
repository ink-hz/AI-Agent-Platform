# Correction: whole-response HTTP deadline supervision

This supersedes the timeout descriptions in the original3815207/961bac7 canary READMEs. Their httpx timeout was an inactivity/phase timeout, **not an aggregate response wall-clock cap**. Their old sources, passing engineering logs and README bytes are preserved as historical evidence; they do not establish that cap. Independent review reproduced a0.1-second budget taking1.082284seconds under a slowly streamed response. `red-1` here independently reproduces the defect for both canaries using actual HTTPX against an owned loopback socket:0.04-second chunks keep the inactivity timeout alive.

Both scripts now call the same small POSIX main-thread `bounded_request`. Immediately before entering HTTPX, it arms ITIMER_REAL for min(20seconds, remaining original mutation/observation deadline). A dedicated BaseException interrupts transport retry handlers, unwinds the request, then the caller records transport_unknown and the already-durable mutation as outcome_unknown. The timer is cancelled and the prior SIGALRM handler restored in finally. Non-main-thread use and an existing interval/active timer are rejected; the script never silently falls back to the weaker timeout. HTTPX's own timeout remains an additional bound.

The tests measure two real slow socket requests cut off near their0.15-second allowance, and assert elapsed<0.8seconds, restored handler/no armed timer, unknown persisted upload, and exactly one request across resume. This is evidence for blocking HTTP response interruption, not a claim that process scheduling, filesystem fsync, shutdown or uninterruptible OS work completes at an exact nanosecond. The script remains a single-process operator tool, not a host watchdog. A SIGKILL/host loss can leave the durable sending marker; resume treats it as uncertain and does not resend non-idempotent upload/DELETE operations.

The original900-second HR and300-second attachment mutation deadlines are still not renewed. Attachment observe retains its own20-second read-only window and cannot grant new DELETE authority. Three-stage attachment execution requires one operator, serial invocations of a ledger; this change adds no cross-process lock. Do not run concurrent prepare/erase/observe against the same ledger.

The previous local attachment tests ran the current root migrations, including100 and102–105, with no HR namespace. They **did not** prove physical erasure on an unmodified001–095 database. Public attachment routes and owner/CSRF behavior were real local HTTP; successful job completion relied on the reviewed erasure source and current permissions. Production S3/old-baseline acceptance remains a separate operator task.

`green-final-1` contains exact source/dependency/test snapshots, SHA fingerprints, measured slow socket timings, and the focused combined regression (existing8 HR +4attachment +3deadline). No production, model provider, browser or actual Worker restart was invoked.
