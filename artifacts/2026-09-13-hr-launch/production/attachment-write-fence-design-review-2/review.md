# Bounded follow-up: unconditional erasure fences and claim-time logical deletion

**Accepted as the smaller design within the service's legitimate-writer scope, pending implementation and real concurrency tests.** CAS is not necessary when the entire exact key is already authorized for erasure. The earlier review's “existing object must use CAS” was unnecessarily strong; that frozen report is preserved, and this report explicitly supersedes that prescription. No source changes, tests, production or model calls were performed here. Source fingerprints bind this inspection, not a future implementation.

## Multiple erasers without CAS

All business PUTs use IfNoneMatch='*'. An authorized cleanup writes Body=b'' with the exact metadata dictionary {'platform-erasure-fence':'v1'} unconditionally to its exact key. A business PUT ordered before this write leaves a payload version to purge; one ordered after an existing ordinary fence cannot create a new payload. Concurrent erasers can add further harmless fence versions. None removes any verified fence version, so they cannot remove each other's protection. No counterexample requiring CAS exists under these stated constraints. Avoiding HEAD/IfMatch acquisition removes a retry branch.

AWS's conditional-write contract checks the current version, permits writes over current delete markers, and rejects writes over an existing ordinary object. These are the premises of the ordering argument, not proof of a particular S3-compatible deployment's implementation. [AWS conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

The purge must inspect each ordinary version using HEAD with **that VersionId**, no Range, requiring ContentLength exactly zero and the exact dedicated metadata dictionary before retaining it. A latest HEAD cannot classify an older listed version. List size zero alone is insufficient; zero-byte business data without the exact marker must still be removed. DeleteMarkers are removed by explicit VersionId, never retained as fences. Do not delete all versions except this caller's fence. After bounded full pagination/re-listing, require an ordinary current fence, zero payload versions and no delete markers. Multiple harmless fences are valid. An already removed payload version can be tolerated only as an accurately established version-not-found condition; permission or ambiguous errors remain incomplete. [AWS HeadObject version/metadata semantics](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html).

A timed-out unconditional fence PUT may later add another fence, which is harmless. Retry/observation can establish protection; a timeout alone cannot establish it. No refs are erased until verification succeeds. Existing helper exception cleanup, upload cleanup and derivative cleanup must all use fence-preserving deletion; no bare DELETE, no deletion of a recognized fence, including unversioned/null-version paths. In unversioned or suspended mode, establish the zero-byte fence before any historical inspection, and never delete the current null fence. Bucket-mode drift is outside a fixed-mode proof and must be rejected/detected. Scope assumes no legitimate lifecycle/cleanup removes fences and no old unconditional payload writer remains; it does not broaden into defense against hostile external writers.

## Minimal DB closure: root's claim-time proposal is sound

Merely enumerating derive jobs is insufficient in existing 064: cancellation expires upload/abandons a lease but leaves attachment scanning/validating; record_attachment_processing_result_v64 can then create a fresh random derive job after enumeration. The concrete counterexample is scan running → eraser sees no derive job → scan completes and creates derive job → worker writes its undiscovered key.

The smaller fix is to replace only claim_attachment_erasure_job_v64 in appended migration 106. Preserve exact caller/database checks and job claiming conditions. In the same transaction, lock its exact attachment and set state='deleted', deleted_at=now(), state_reason='erasure_pending', **without destroying refs**. Do not lock/update processing jobs in this claim. Commit before repository enumerates jobs.

Verified against 064:

- attachments CHECK allows deleted with retained refs; it requires non-null deleted_at. Retained ready_at is allowed.
- Processing-result recording locks its job then attachment and checks deleted before transitioning/creating a next job. A result holding the attachment first commits any next job before claim can acquire it; a later result observes deleted and rejects. The job set is closed after claim commit.
- Derivative recording requires attachment ready; upload finalization requires uploading and no erasure job. Claim-write already checks no erasure job. Artifact finalization delegates to upload finalization. These do not resurrect the deleted attachment.
- The erasure claimer selects queued/partial jobs independently of attachment state, so already logically deleted partial work remains claimable with intact refs. Final recording requires the running erasure job and existing attachment, not a pre-deletion attachment state.
- Claim does not acquire job locks after the attachment lock; final recording retains its existing processing-job-before-attachment order. This avoids introducing that particular reverse-order deadlock. This is not a blanket claim that every unrelated database lock path was audited.

After claim commits, select **all** derive jobs for that attachment, including terminal rows with no derivative record, and compute the existing key from processing_job_id + derivative_kind using a shared exact function. Already in-flight or newly claimed existing derive jobs have known keys. Keep union with recorded derivative and all upload-attempt refs. No new random retry key is needed.

106 permission addition can be exactly SELECT (attachment_id, processing_job_id, job_kind, derivative_kind) on platform_attachments.processing_jobs to the selected maintenance role, preserving production/preview owner mapping. No full-table SELECT, mutation grant or credential substitution is needed. Existing root100 does not grant these columns. Append 106; do not edit immutable 064/100. No rewrite of the long processing-result function is needed for this closure.

## User-visible and recovery boundaries

Downloads already reject any attachment with an erasure job and require ready. The deleted state also hides the attachment in current metadata/list queries and rejects grants; this is logical deletion for an already authorized erasure. It does **not** claim physical erasure. Partial cleanup retains encrypted refs and the erasure job's partial state even though attachment state is deleted. Upload/artifact rows may retain prior states until final completion; do not imply all status representations now mean physical completion.

Claimed-running jobs after worker/process crash are a distinct recovery problem: queued/partial selection does not itself recover running. Preserve/review the actual existing ownership/recovery mechanism and never call this automatically crash-recoverable merely because partial retries work. Unknown remote writes do not justify completing the DB record.

## Minimum code and release envelope

Code: two payload PUT adapters gain IfNoneMatch; shared exact derivative key helper is reused by worker and erasure repository; S3 erasure helper writes/recognizes fences and purges only payload versions/delete markers; all cleanup paths follow that helper or narrowly remove a proved own nonfence version; duplicate derivative writes distinguish matching immutable data from fences; observer/canary recognizes zero payload plus one-or-more verified fences. DB: 106 short claim replacement and four-column maintenance read grant. Host migration helper must explicitly recognize and checksum 106 for this release, while immutable earlier ledgers stay unchanged.

Release sequence: freeze and test code/106; stop and exclude every old attachment payload writer/cleanup and account for outstanding remote requests; apply 106 with the existing supervised migration boundaries; install the same conditional/fence-aware generation for API and attachment worker before resuming traffic; run exact authorized public synthetic canary and version-aware observation; only then claim acceptance. If old in-flight unconditional requests cannot be accounted for, leave acceptance incomplete. A fixed root100-only deployment cannot claim the new online guarantee. This is limited to attachment writers, not a reason to stop unrelated Feishu or redesign HR execution.

Required small tests include two simultaneous erasers retaining each other's fences; delayed conditional original/derivative PUT; unrecorded derivative crash; scan transition vs erasure-claim lock ordering in both orders; partial retry with deleted attachment and retained refs; unknown fence PUT/restart; zero-byte unmarked payload vs marker; all-version pagination plus version-specific HEAD; cleanup cannot remove fence; root100 missing-grant failure and 106 grant success with real maintenance identity. Real MinIO/S3-compatible conditional semantics must be measured, not assumed from SDK mocks.
