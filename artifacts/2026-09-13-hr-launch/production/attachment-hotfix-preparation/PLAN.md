## Failure and ownership

INT/TERM/HUP/QUIT are trapped. A command gets a new owned process group. Timeout/signal sends TERM to that group, waits a finite grace period, then KILL/reaps if needed. Further handled signals are ignored only during this finite cleanup. Docker client termination is **not** daemon/container/DB completion evidence. Ordinary commands use10seconds (compose60, image probe20, stop15); migration supervisor uses1000seconds plus at most120seconds graceful cleanup and5seconds final reap.

On failure only the known new attachment ID and the exact old ID are stopped with restart=no, each checked by image and inspect. A failed no-start recreate with no durable new ID is recorded as uncertain; no unknown container is guessed and stopped. The image probe is cleaned only with its unique name+run label+image. Migration cleanup reads only this run's unique child receipt, verifies helper/image/root/production and container name/ID/command, then stops/removes that owned migration container. Independently, a proven grant_pending event causes a revoke attempt even if Docker cleanup failed. Both owner membership and migrator-session counts must converge to zero before cleanup is called verified; no broad peer-session termination is issued.

Failure retains whatever locks were actually acquired/attempted and any marker actually created, recorded as separate flags. It never restarts the old image, guesses another owner's containers, removes a foreign lock, drops schemas, restores the database, or automatically clears fail-closed state. SIGKILL, host loss, uninterruptible OS/daemon failure or receipt-disk failure still require external reconciliation; an exit code or dead client cannot certify cleanup.
