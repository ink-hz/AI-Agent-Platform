## Important: mutable null-version cleanup can remove a concurrent fence

`backend/app/attachments/object_writer.py:127–142` treats every nonempty returned VersionId as an immutable owned payload version and issues DELETE with that VersionId after a post-PUT local receipt/stream validation error. The string **"null" is not an immutable historical identity** in a Suspended bucket.

Concrete ordering: conditional payload PUT succeeds and returns VersionId="null"; an eraser then replaces that null slot with its zero-byte ordinary fence and verifies it; the original writer's local receipt validation fails; `_best_effort_delete` deletes VersionId="null", now addressing the new fence. This reopens future IfNoneMatch writes after the eraser may already have completed its database receipt. Unique non-null VersionIds in the currently Enabled production bucket do not have this aliasing issue, but Suspended/null behavior is explicitly supported and tested by this candidate.

Recommended minimal repair: route VersionId="null" through the same fence-preserving cleanup as a response with no immutable version ID (or explicitly remove Suspended support). Never use an earlier HEAD classification to justify deleting a mutable null slot. Add a focused negative where the successful PUT response precedes an eraser's null fence and a subsequent local receipt error; the fence must survive. Root was notified immediately. No live or simulated storage experiment was needed to establish this direct control-flow counterexample.
