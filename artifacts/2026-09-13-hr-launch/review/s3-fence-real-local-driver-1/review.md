## Important findings sent to root

1. **ThreadPoolExecutor context exit can bypass the bounded cleanup intent** (snapshot lines 135 and 161). A main-thread alarm or one of the four handled signals raises out of the body, but `with` calls shutdown(wait=True) before the outer main finally can stop the owned MinIO process. Future.result(timeout=30) does not bound executor shutdown. The half-body case puts connection.close() outside that executor context, so an eraser blocked behind the incomplete request could wait before that socket gets closed. Make task/executor lifecycle explicit; on abnormal exit close owned raw sockets first, reach owned-MinIO termination, then boundedly reap/join owned tasks and persist any unresolved-thread failure. Never mark passed on a join failure. Do not substitute an unbounded shutdown or interpreter-exit thread join for a deadline.

2. **Signed half-body PUT lacks X-Amz-Content-SHA256** (snapshot lines 147–149). The generic botocore SigV4Auth calculates a canonical hash for the nonempty raw body but does not automatically add this header. The built official MinIO source's `cmd/signature-v4-utils.go:115–127` instead defaults a signed request without that header to the empty-body hash. This makes a 403 signature failure likely before the intended 200/409/412 conditional-write exercise. Include the SHA256 of the complete raw body in the header before signing, or use S3SigV4Auth. This finding was checked against local source, not by making a network request.

## Correct evidence and scope boundaries

The driver uses a real `http.client.HTTPConnection`, declares the complete Content-Length, sends raw[:-1], submits the real eraser, then sends raw[-1:] and reads the HTTP response. This is actual client-side partial-body network transmission, not a mocked SDK PUT. However, send completion and the client fence_started Event do **not** prove the MinIO handler has received/read the partial body. Record prefix byte count, total Content-Length and this lack of a server-side receipt; do not rename the event as server acceptance. The bounded 0.25-second eraser wait only explores possible ordering. Allowing 200 before erasure wins or 409/412 when the fence wins is consistent with the requested property, provided final version-specific checks prove only verified fences and zero payload, then a further conditional PUT must return actual HTTP 412.

The 1001-version fixture requires a real multipage list; cleanup must preserve the prefix sibling; every old payload VersionId is HEADed. assert_fenced checks every ordinary version's exact metadata/zero length and the current HEAD's membership in the verified set, rejecting markers. Multiple erasers use a barrier to release both real client operations concurrently, but this does not prove identical server-side scheduling. The property tested is final fence retention and prior-payload absence under this exercised scheduling. Original PUT collision and derivative identical retry preserve the canonical version set and block future writes; their adapters expose sanitized errors, so adapter-level failures alone should not be labeled actual 412 unless a separate raw status check proves it. The raw post-fence PUT checks do require actual 412.

Suspended/null and unversioned fixtures test retained fences rather than empty buckets. A real unversioned post-fence conditional PUT must return 412. No observer mock result is used to certify these properties in this driver. The previously executed red driver at `production/s3-fence-real-local-red-1` records failed / 'erasure removed write fence' / owned_process_reaped true against the b425 core. It fails at the first fence property and therefore does not demonstrate that the later concurrency cases ran or failed.

The reused main supervision remains appropriately scoped to an owned child process group and a 0700 temporary directory, fixed loopback endpoints, generated local credentials, minimal child environment and disabled client proxies. It handles ALRM/INT/TERM/HUP/QUIT, refuses an existing timer, restores handlers, and bounds owned child TERM/KILL waits. The 300-second work alarm is not a strict total wall-clock bound because cleanup follows; the new task-thread lifecycle must be corrected as above before this claim is meaningful. No shared-service stop or production credential input appears.
