# Encrypted off-host backup restore rehearsal

Actual second attempt restored the encrypted production snapshot in an owned local PostgreSQL 17.10 cluster over a private Unix socket, with no TCP listener and no production database writes. All four decrypted files matched the original production snapshot SHA-256. Full pg_restore completed with ownership and ACL (no --no-owner/--no-acl); globals restored with all ALTER/GRANT statements retained. The 95 migration entries matched exactly; restored inventory contains 140 platform tables and 26 conversations. The local postmaster was stopped and its owned data directory removed.

The first attempt failed at globals restore because it used a different bootstrap role. Its source and failed receipt remain in ../backup-restore. Attempt 2 initializes the same platform_owner bootstrap identity and removes exactly the now-redundant CREATE ROLE platform_owner statement from a private derived globals file. Original backup bytes are unchanged. PostgreSQL documents the bootstrap-role duplicate during globals restore: https://www.postgresql.org/docs/17/app-pg-dumpall.html .

The source snapshot was taken while application writers were running. This proves this point-in-time backup can restore the control database; it is not a post-fence rollback instruction, a MinIO payload backup, zero-RPO recovery, or proof that a future snapshot restores. The release executor must take another snapshot after stopping both attachment writers and retain a forward-repair-only policy after 106/107. The encrypted copy and its private recovery key are on this workstation; raw and encrypted host backups remain private on the source host. This is an off-host copy, not an independently administered archival service.
