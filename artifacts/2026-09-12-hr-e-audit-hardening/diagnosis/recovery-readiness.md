## 1. Recovery does renew execution authority even though it does not launch

`backend/app/execution_relay/recovery_v5.py:85–138` selects only live reconciling attempts with an already-offered durable binding. `V5RecoveryAdapter.poll_once` at 200–252 calls `runtime.metabot.recover_v5_run`, not start_v5_run. `metabot_client.py:416–430` calls `/api/core-chat/v5/recovery`; the corresponding start path at 397–413 calls `/api/core-chat/runs`. `parse_observation` at 60–62 rejects replayUsed=true. These facts support nondispatch observation/stop semantics, but do not prove an external deployed executor never resumes business actions.

Crucially `recovery_v5.py:111–120` issues a fresh business tool grant when a noncancelled v6/v7 attempt has a new lease epoch, updates encrypted transport credentials, and returns that grant inside the command. `hr/tool_service.py:45–51` calls the real issue function. Exact 094 SQL at 849–868 allows live running/reconciling attempts, and authorize at 872–900 accepts the current lease while enforcing original worker/turn/owner provenance. Thus recovery refresh restores usable business-tool authority. There is no cutover lock or phase test in recovery_work today. This is sufficient platform-local evidence for a gate; do not describe it as merely reading status.

The requested checked-in Team checkout was searched for these protocol identifiers without finding executor endpoint implementation. The available metabot-dev checkout also lacked that endpoint. No external executor behavior or production identity is claimed. Platform-local grant evidence is sufficient to recommend repair without guessing the remote implementation.

### Minimal repair

In each candidate transaction, call `lock_state(connection)` before `_current` (which takes domain locks). Once `_current` verifies the existing binding and returns cancellation state, require legacy lane with continuing=True only when cancel_requested_at is absent. A denied noncancelled candidate returns no work (the handoff convention is skip and ultimately HTTP 204), with no fresh grants, encrypted wrapper update or poll timestamp update. Hold the same shared lock through the authorized grant issuance and response preparation. Do not gate only the grant-refresh branch: an existing same-epoch command may already contain a usable grant.

Preserve cancellation recovery work with stop=true, no refreshed grant, and unchanged original command/callback identity in every phase. Preserve `/runs/{run_id}/recovery` recording and event/acceptance callbacks with their existing worker/lease/hash/sequence validation; do not blanket-gate the router or record_recovery. Already accepted work must still deliver stop/results. Do not synthesize a new cancellation flag, launch or retry as part of this patch.

`hr_agent/cutover.py:28–57` deliberately treats genuinely absent gate table/singleton as legacy compatibility, while cloud requires initialization. Reuse that exact contract; do not conflate missing table/singleton with a SQL exception. Permission, connection and malformed schema errors must propagate as unavailable, not legacy permission. This patch should block cloud/draining_cloud recovery authority while allowing legacy/draining_legacy original-owner recovery and pre-102 legacy compatibility. The v5 route is HR-only already (`routes_v5.py:28` and recovery `_current` worker allowlist), so no new non-HR endpoint or policy is required; do not add a general Relay gate affecting other Bots.

Use real signed recovery HTTP and disposable PG, retain original worker/nonce/lease/binding authority. Exercise noncancelled v6/v7 renewed lease in legacy/draining_legacy (grant refresh permitted) and cloud/draining_cloud (204 and byte-identical payload, grant-count and poll timestamps). In cloud/draining_cloud preserve cancelled work response stop=true and signed original recovery/stop-proof/result recording, with stale lease and wrong worker still rejected. Include missing-table and missing-singleton legacy compatibility, plus a true database failure producing 503. A real two-connection transition/shared-lock ordering test should show grant issuance cannot slip past phase activation; reuse existing handoff race patterns. Existing recovery tests cover cancelled lost-ACK authority but not this noncancelled v6 grant path (`test_execution_recovery_v5.py:53–81,111–148`).

## 2. Platform liveness is not HR readiness

`main.py:1571–1591` checks schema once and builds an unavailable HR service with repository=None when false; API startup still succeeds. `HrAgentService._owner` at 34–40 returns retryable 503 to authorized users. `health/platform.py:14–16` is expressly public liveness and always reports ok. Owner-only detailed health at 87–93 lists review/operations/attachments but no HR state. Compose base at 138–139 probes public /api/health; the HR overlay changes environment/mounts but does not change that probe. A healthy API container therefore does not establish HR readiness.

Smallest safe improvement: add an owner-only HR service readiness field (enabled, ready/service-assembled) to detailed health, without exposing secrets, schema internals or personal data on public liveness. Mark it as startup/service assembly status, not continuously refreshed database readiness. Keep the public liveness contract stable and avoid forcing shared API restarts/failure due to one optional product lane.

Explicitly defer automatic compose readiness enforcement until a distinct probe contract and its shared API deployment implications are designed. For this release, make authenticated/preflight HR checks a required deployment acceptance step and state health/up is insufficient. This is a justified bounded deferral, not a closed orchestration readiness claim. If implementing an HR-specific readiness endpoint now, it must be separately scoped/authorized and used by the HR deployment check, with enabled-false, enabled-unready and enabled-ready tests; never silently repurpose /api/health.

A minimal owner-health regression should demonstrate HR enabled+unready remains public-live but detailed-unready, ready becomes visible, and non-owner access remains denied. A separate HTTP HR request must still return 503 on missing exact schema readiness. Do not claim this proves runtime continuous readiness after a database change.

## 3. CandidateUnavailable hides gate rejection and database fault identity

`candidate_repository.py:212–224` maps NoDataFound to not-found, selected SQL conflicts to conflict, and everything else to generic CandidateUnavailable from None. Callers catch KeyError/TypeError/ValueError/psycopg.Error (for example 249–252, 426–429). CutoverRejected subclasses ValueError, so expected phase rejection is flattened together with missing schema, permission/connection errors and decoding/programming problems. `candidate_routes.py:265–276` returns a generic safe 503; preserving that public redaction is correct. There is currently no diagnostic event in this repository mapper.

Minimal repair: retain the generic external error, but distinguish expected CutoverRejected before generic database/error mapping, using a safe internal reason/category (or dedicated CandidateUnavailable subtype) and sanitized structured diagnostics for unexpected failures. Log only an allowlisted exception class/SQLSTATE and stable repository operation/category, never str(error), raw SQL, detail/context, DSN, body, candidate name or exception traceback. Prefer one central mapper over broad exception refactoring. Preserve rollback, conflict/not-found mappings and existing caller compatibility.

Focused tests should assert expected gate rejection has the specific internal reason and no SQL fault diagnostic; a deliberately missing function/table returns generic HTTP503 but records only safe schema-error identity; a connection error is distinguished safely; injected malicious secret text in an exception does not occur in response/log output. This prevents a broken database from satisfying a weak `raises(CandidateUnavailable)` gate regression. Keep true database role/transaction coverage where feasible, and label exception-boundary injections as such.

Changing all repository decoding exceptions or SQL conflict semantics is wider than this audit and can be deferred explicitly. Merely stating that unavailable is fail-closed does not resolve operator diagnosis or weak gate-test evidence; safe categorization plus narrow diagnostic tests is a concrete minimal fix.
